## 静态审计：已确认的状态隔离缺陷

核对本地 Minecraft 1.20.1 Forge 映射 jar 和实例内实际 DH/Oculus jar 字节码后确认：

1. `RVP_DhGlStateScope.close()` 使用原生 GL 恢复纹理、活动纹理单元、VAO、深度/混合等状态，未同步 Minecraft 相应缓存；恢复 `RenderSystem` shader 指针并不等于恢复全部缓存。
2. Minecraft `BufferUploader.bindImmediateBuffer(VertexBuffer)` 只在目标不等于 `lastImmediateBuffer` 时真正绑定 VAO。RVP 原生恢复 VAO 后未调用 `BufferUploader.invalidate()`，缓存所指对象与真实绑定可能不同。
3. `ShaderInstance.apply()` 通过 `RenderSystem` / `GlStateManager` 绑定采样纹理，`clear()` 通过缓存包装层解绑。原生恢复旧纹理而不更新缓存，会留下不一致状态；后续是否错绑取决于实际调用序列和缓存命中。
4. DH 的 `MinecraftGLWrapper` 对深度函数、纹理单元、纹理绑定等同时执行原生 GL 调用和 `GlStateManager` 调用，不能把 RVP 仅恢复原生状态视为等价操作。
5. 本实例 Oculus 的 framebuffer/program 缓存 Mixin 已加载，即使光影关闭也不能只按裸 OpenGL 状态审计。

这是确定存在的实现缺陷，但**尚未证明它在用户观察到的消失帧中被触发，也未证明它能独立解释全部症状**。本轮仅审计、记录，没有据此修改渲染实现或替换测试 jar。

### 代码因果链

RVP 故障位置：`RVP_DhFramebufferSet.attachBorrowedTextures()` 第 29～30 行：

```java
if (attachedColorTexture == colorTexture && attachedDepthTexture == depthTexture) {
    return;
}
```

该判断把“纹理数值名称相等”错误等同于“仍是上一次的纹理对象”。实际流程为：

1. `protectTrackedVehicles=true` 时，近距真实载具就能触发借用附件初始化，小窗口下 RVP 的两个 FBO 持有 DH 旧颜色/深度纹理对象。
2. DH 3.2.0 的 `GlDhMetaRenderer.createAndBindTextures()` 在窗口改变后先删除旧深度纹理，再新建深度纹理；颜色纹理也先删除再创建。驱动允许立即复用同一数值名称，本次日志明确仍是 54/53。
3. 删除名称不等于立即销毁其它未绑定 FBO 仍引用的旧纹理对象。DH 自身 FBO 重新挂接到新对象，RVP 的两个 FBO 仍保留旧对象。
4. RVP 每帧查询名称对应的新纹理尺寸，得到 2560×1351，并扩容自己的离屏/深度复制目标；但由于名称没变，上述提前返回跳过了真正的 `glFramebufferTexture2D`，借用附件还是旧的 854×480。
5. 模型成功画入新尺寸 RVP 离屏目标，合成却受旧附件范围限制，并写进 DH 已不消费的对象。旧深度复制只覆盖旧区域，新副本其余区域为 0；以 Forward-Z 重建时会被解释为近处遮挡，进一步丢弃有效载具片元。
6. 现有返回值仍把该调用记为 `DH_COMPOSITED`，因此不会触发 `SILHOUETTE` 回退；样本查询大于零也只能证明旧附件范围内有片元通过，不能证明写到了 DH 当前目标。

这能解释 `RVP_FIRST` 绕开问题：它输出至世界最终目标，不走这组 DH 借用附件。关闭 tracked 后，如果 remote 首次出现晚于窗口放大，借用附件首次建立时已是新对象，也可避免本次触发条件；这一时间关系是代码推导，未把早期用户 A/B 当作严格同场景时序验证。**保护开关不是 OpenGL 错误的必要条件：只要先建立借用附件、再让 DH 同名重建纹理，remote-only 也存在同样风险。**

### 修正诊断数据的解释

旧尺寸范围外的 `glReadPixels` 可能不写入目标内存且不报 GL 错误。原像素探针使用 `memAlloc` 未填充哨兵，因此 frame=5 之后出现的 `rgba=1,1,1,1 / depth=2.3694278E-38`、或“DH 颜色恰好等于上次源深度的四字节表示”，是**越界回读留下的旧内存内容，不能当作真实 GPU 附件颜色/深度**。独立实验预填 `0x5a` 和 -7，越界读后哨兵原样保留且 GL 无错误，已验证这一点。

修复验证时应先消除此处诊断歧义：回读前填哨兵，并记录/验证实际附件覆盖范围；“无 glError”不能视为回读有效。frame=40 的旧范围内样本与独立 GPU 对照不受这项限制影响。

### 最小修复方向与边界

本轮按“先定位根因”要求，**未改正式渲染行为、未替换新的测试 jar**。最小修复应在 RVP 内让两个借用 FBO 每次接收 DH 纹理时重新挂接当前对象，删除仅凭数值 ID 提前返回的缓存；不能只比较 ID，也不能只比较尺寸，因为同尺寸资源重建仍可能复用名称。无需新增 Mixin、无需改本体、无需改 DH。

### 根因：保护副本与正常实体渲染取光入口不一致

旧 `RVP_DhTrackedVehicleCollector.packedLight()` 使用 `LevelRenderer.getLightColor(level, vehicle.blockPosition())`，以实体物理原点所在方块取光。载具接地后原点可能略低于地表；对坐标向下取整后，会读到草方块/基岩内部，天空光为 0，导致整个保护模型使用极暗的统一 packed light。

正常实体渲染则通过 `EntityRenderDispatcher.getPackedLightCoords(vehicle, partialTick)` → `EntityRenderer.getPackedLightCoords` → `vehicle.getLightProbePosition(partialTick)`。本体 `AbstractVehicle` 已覆写最后这个方法，返回 **`mainCubeOBB.obb().center()`**，无主碰撞盒时才返回实体原点。本轮只读反汇编实例内 `ywzj_vehicle-1.20.1-0.5.9-all.jar`，确认实际安装版本也具有此行为。原版入口同时保留渲染器覆写和着火补光规则，直接调用它比在 RVP 硬编码取光高度更准确。

| LAV-AD | `(397.2431, -60.02775, 318.9450)` | `(397,-61,318)`，草方块 | 0 | 15（空气） |
| M142 | `(370.0464, -60.02775, 318.6215)` | `(370,-61,318)`，草方块 | 0 | 15（空气） |

这证明原点陷入实心地块的条件在该实机存档实际存在，且高度约 `-60.02775` 向下取整会落入 `-61`。表中“一格上方”用于展示地表光照断层，**不是修复时采用固定 +1 高度**。存档是退出后的保存状态，不能冒充 05:23:50 当帧的 OBB/光照查询；新日志会在复测时补齐运行时 `origin/probe/nativeLight/selectedLight` 对照。
