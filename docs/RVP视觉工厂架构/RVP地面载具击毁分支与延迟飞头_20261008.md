# RVP 地面载具击毁分支与延迟飞头

2026-10-08。用户批准实施，并明确“直接飞头不殉燃、飞头沿用本体全部可脱落部件行为”；批准新增 `VehiclePartSpawner.spawnDestroyedParts` 的最小 HEAD Mixin。

## 行为

| 概率 | 击毁当时 | 后续 |
| --- | --- | --- |
| 30% | 立即调用本体飞头 | 不生成 RVP 殉燃；保留普通近烟、长程烟和本体残件表现 |
| 30% | 开始殉燃，保留部件 | 始终不调用飞头生成器 |
| 40% | 开始殉燃，保留部件 | 在总殉燃时间的 40%～80% 随机 tick 调用本体飞头一次 |

服务端用一次 `nextInt(100)` 分支，延迟分支再抽一次整数 tick。总时长 `T = round(wreckLifetimeSeconds × 20 × 40%)`，增长/收缩包含在 T 内；延迟闭区间为 `[ceil(T×40%), floor(T×80%)]`。默认残骸配置 60 秒：T=480 tick（24 秒），飞头为击毁后 192～384 tick（9.6～19.2 秒）。短样本不保证观测比例恰好等于 30/30/40。

`wreckLifetimeSeconds=0` 时保持本体立即飞头且无殉燃。仍只处理 `TrackedVehicle` / `WheeledVehicle`，不以 `onGround` 筛选；飞机、舰船及 `VehiclePart` 不接管。无可脱落部件的车也不伪造炮塔，抽中飞头时本体按原有 `detachable` / 结构 / 渲染骨门控执行。

延迟飞头后，已脱落部件的舱盖/炮口/接缝出口按现有解析器停止；其余有效出口沿原时间表运行至 T，不重置殉燃时长。不会增加第二次伤害爆炸、弹药消耗或方块着火。

## 实现边界

- `vehicle/wreck/RVP_WreckDestructionState`：公共时间表、概率分段、40%～80% 整数边界和当前 NBT schema。唯一比例字段在此类的 `WRECK_LIFETIME_PERCENT`。
- `server/wreck/RVP_DestroyedPartLaunchManager`：服务端抽签、保存及延迟任务；`LevelTickEvent.END` 仅遍历等待表。调用前先保存已消费标记，再凭一次性许可重入本体方法，防重入和重复飞头。
- `mixin/VehiclePartSpawnerMixin`：仅 HEAD 转发/取消，不存业务状态。目标为双端安全工具类，不改 `AbstractVehicle` 字节码，不新增 Accessor。现有 JSON、继承、伤害前事件和网络包均无法单独阻止该静态脱落调用，故需要这个最小入口。
- `network/S2CWreckDestructionState` + 客户端安全桥：仅 S2C，下发 UUID、维度和时间表。网络协议由 26 升至 27，客户端与服务端必须一起更新。
- `client/visual/cookoff/RVP_ClientWreckDestructionState`：允许快照先于实体生成包抵达；缺少结果时不喷燃，避免立即飞头分支闪出火焰。
- `RVP_WreckCookoffController`：真实残骸按服务端击毁时刻计时；不再按本客户端首次观察时刻计时。无伤害 `/rvpcookoff` 预览仍只在客户端运行；真实击毁状态优先于预览。

本体源码、所有模型/贴图/音效和载具包 JSON 均不改。资源目录中的唯一代码配置改动是注册已获批准的 Mixin。

## 同步、保存与生命周期

状态保存在实体 ForgeData 的 `ywzj_rvp:WreckDestruction` 下，由正常存档流程保存。新击毁立即向追踪者广播；`StartTracking` 向重连/重新进入范围的玩家补发同一时间表。配置中途变化不会改写已经抽出的计划，客户端 common 值不同也不会改变真实殉燃时长。

服务端区块卸载时释放实体引用；重新加载读取原时间表，若已超过飞头时刻且残骸仍存在则执行一次。服务端不运行时游戏时钟不推进；卸载但世界继续运行时会跨过原定时刻，不强制加载区块。残骸提前被移除则取消任务。已消费的记录读档后不再生成部件。

客户端离开世界/维度或实体离开时清理快照；F3+T 仅清视觉绑定，权威快照保留，因此不会重新点燃。既存无本功能记录的残骸不补抽签，开始追踪时收到零时长快照，只显示普通烟。

长程烟门控与服务端时间表同源：立即飞头直接放行；两个殉燃分支在 T 结束后再等待一次服务端确定的 30～60 tick。近处普通烟保持原有逻辑。未追踪的远距代理残骸不在本功能新增支持范围内。

现有残骸清理仍有效：本体有约 60 秒自动清理上限，RVP 的提前清理还使用原有生命周期规则。本次不延长残骸寿命；若残骸先被清理，尚未到期的延迟飞头不会产生幽灵残件。

## 验证

自动测试覆盖：均匀 0～99 全域得到 30/30/40 分段；默认 480/192～384 tick；短时长的整数上下界；立即飞头零殉燃；只殉燃永不飞头；延迟到时、读档与执行标记去重；缺失/矛盾 NBT 拒绝；S2C 的 UUID、维度、绝对时间及已执行状态往返。

验证结果（2026-10-08）：根目录按指定 Java 17 环境执行 `./gradlew build` 成功，787 项测试全部通过（本次新增 10 项）。`./gradlew runServer --console=plain` 冒烟按 10 秒日志轮询，日志 `logs/server_smoke_wreck_20261008_0201.log` 第 1383 行出现 `Done (3.266s)!`。新旧日志核对：8 项本体缺模型、abramsx 副本路径、`rvp_bomber:ac130u` 配方和 `rvp_bomber:tu160` 载具加载错误在启动前日志已存在，本次未新增错误。冒烟后已关闭本次服务端、wrapper 和其专属 Gradle daemon，jps 复核无本次残留，25565 无监听。

客户端仍需实机确认三分支外观、多人同时观察、近远往返/F3+T、飞头后旧出口消失、无炮塔车和非地面载具对照。普通启动冒烟没有实际击毁车辆，不能替代飞头实体生成与多人视觉验收。
