# RVP 烟雾受光与不遮光实现

日期：2026-10-30。当前爆炸、载具成功开火和火箭发动机共用烟雾受光通道。烟雾可以接受这些光，烟雾贴图自身不会再成为屏幕光的遮挡物。方块、实体和 DH 地形的遮挡继续保留，P5 真实方块光仍关闭。

同日追加：RVP 载具 `muzzle_flash` 炮口特殊贴图也接入同一受光通道，详见第 8 节。原炮口贴图、模型、动画和材质不变；这里增加的是贴图自身的受光，不增加第二个炮口光源。

## 1. 原因与两份不同的信息

原来的全屏程序根据场景深度找到受光表面。没有写深度的烟没有独立受光位置；写深度的 MCHR 爆炸烟、白磷烟又可能被当成实体挡住后面的光。仅改变烟雾是否写深度不能同时解决这两个问题。

现在分别使用：

- **不含粒子烟的场景深度**：决定方块、实体、DH 地形和光影手持物的遮挡。
- **烟雾自身的真实面片、贴图 UV、颜色及 Alpha**：决定烟在哪里、哪部分透明、应受到多少光。Alpha 即透明度，UV 即贴图上当前帧的位置。

因此烟在天空前也可以受光，不再把后面的墙当成烟的位置。烟雾正常绘制、原贴图和原透明度保持原样；新增通道只补上受光颜色，不让烟雾参与遮挡深度。

## 2. 深度采集与远端投影

统一深度采集从 `AFTER_WEATHER` 改到 **`AFTER_TRIPWIRE_BLOCKS` 的 HIGHEST 优先级**：透明方块/绊线层已经完成，粒子引擎尚未开始。源码与当前 Forge 1.20.1 字节码已核对，普通与 Fabulous 两条路径均先画绊线层、后画粒子。

当前 Oculus 1.8.0 在进入世界透明阶段时绘制不透明手持物；新的采集位置仍能保留其压缩深度遮罩。世界颜色继续在 `AFTER_LEVEL` 读取光影最终结果，随后在 CRT/TV/HUD 之前合成。

远端弹药原有粒子远平面作用域也改在 `AFTER_TRIPWIRE_BLOCKS` 的 NORMAL 优先级开启，于 `AFTER_PARTICLES` 关闭：先保存世界矩阵和深度，随后才为远程尾迹粒子临时扩大远平面。远端弹体本身仍使用原来独立的远平面作用域。

近景与 DH 各自的投影、观察矩阵和空深度方向继续独立处理，先还原位置再选择最近表面，不比较两张深度图的原始数值。烟后来即使写入主深度，也不会改变已经复制的光照遮挡快照。

## 3. 覆盖的烟雾

粒子引擎中的烟从本体已经存在的 public `getParticles()` 入口只读收集；该入口也是现有热成像通道使用的入口。没有新增 Mixin、访问器、粒子替身或队列改写。

| 来源 | 当前覆盖 |
| --- | --- |
| 原版 | 普通/大烟、灰烬烟、营火烟、爆散烟 |
| 本体 | SmokeCloud、导弹尾烟、DustSmoke、履带扬尘粒子 |
| RVP 粒子 | MCHR 爆炸/炮口/受损烟、近处和长程击毁烟、热诱弹拖尾、白磷烟、火箭尾迹/地面烟浪 |
| RVP 自绘 | 击毁炮口烟、默认爆炸云、核爆云、温压云和凝结云壳 |

粒子调用原来的绘制函数只获取当前面片，保留图集动画、UV、旋转、抖动叠层、颜色和透明度。自绘烟在正常顶点出口增加转发记录器，原顶点继续正常绘制。只记录烟雾几何，不给火花、雨滴或方块碎片统一加烟雾受光。

其它模组完全私有的自绘烟需要通过同一 `capture` 入口接入；当前实现不根据任意类名猜测材质。

## 4. 所有屏幕光共用计算

烟雾使用 `RVP_ScreenLightPass` 已选出的同一批光源，不按爆炸、炮口或发动机类型排除。位置、半径、颜色、亮度、年龄衰减、二脉冲和全局强度都与普通表面光一致。

烟是参与散射的薄面片，不要求像固体一样朝向光源。距离衰减仍为 `(1-(距离/半径)^2)^2`。烟面片到光源之间继续用不含烟的近景/DH 深度做八步遮挡检查，真实墙体仍能挡住光。

输出保留烟贴图的明暗和 RGB 色相，并乘以 `贴图 Alpha × 粒子 Alpha`。全透明像素贡献为零；烟越透明，其受光贡献越弱。显示叠加只增加 RGB，保留原场景 Alpha，避免亮方框、改写烟的透明度或把整张背景当成烟。

新层不写深度，也不读取烟后来写入的深度。程序喷焰、普通表面光及可选空气散射均共享同一份干净深度，所以不会被这些粒子烟裁掉。

这仍是屏幕空间视觉近似，不是烟尘密度模拟或完整三维阴影。Bloom 仍只执行既有光晕通道，没有把整个烟雾画面重新提取一次光晕。

## 5. 性能与生命周期

最多记录 32768 个四边形，按实际贴图分组并复用数组。面片包围球不与任何活动光球相交时，不提交额外绘制。灯光仍使用现有八灯预算、照明半径和客户端距离设置，不按烟粒子数量生成光源。

每显示帧清空有效长度；换世界和资源重载清除旧贴图编号，释放自有显卡顶点缓冲。材质探测不提交到画面；原粒子引擎及烟雾队列不改动。外部贴图、采样器、FBO、裁剪、深度/剔除缓存、RGB/Alpha 混合方程和透明度都恢复。

## 8. 炮口特殊贴图同样受光、不挡光

### 8.1 接入点与原有深度规则

载具 display 的 `special_bone_effects[].type = "muzzle_flash"` 指定炮口特殊骨。特殊骨就是模型中单独绘制某种材质的那部分几何，尺寸和显隐仍由原模型、原动画控制。

本体 `ModRenderTypes.muzzleFlash` 本来就使用 `COLOR_WRITE`：保留深度测试，只写颜色，不写深度。因此本次没有更换材质，也没有把炮口从深度图中擦掉。直接沿用此规则，原炮口贴图和新增受光层都不能变成遮挡物；车体、方块和 DH 地形仍然参与原来的光路遮挡。

缺少的是独立受光位置。`RVP_VehicleBedrockModel.renderSpecialBones` 现在通过继承覆盖，给本体原绘制流程提供一个转发式 `MultiBufferSource`（按材质取得顶点出口的对象）：

1. 只识别本体真实 `muzzleFlash(texture)` 材质实例，不根据武器 ID、骨名称或贴图文件名推断。
2. 正常顶点继续写入原出口；同时记录已绘出的最终位置、当前贴图 UV、RGBA。UV 表示图集的取样区域，Alpha 表示当前动画透明度。
3. 后处理使用同一批已筛选的八盏光，为这些顶点增加受光颜色。没有添加新光源，也没有重新画一遍模型或另算动画。

当前权威包的九份炮口特殊材质 display 均使用 `bedrock_backend: rvp`，通过这一路径接入；RVP 自定义挂架经同一模型工厂创建的 `muzzle_flash` 也走相同入口。普通车体、玻璃和座舱屏材质不被记录。没有改本体、载具包、贴图资源或 Mixin。

### 8.2 为什么需要区分两种坐标

粒子提供“世界位置减相机位置”后的坐标，程序还要乘观察矩阵，也就是把世界朝向转到玩家眼前的那一步。模型顶点在进入出口前已经乘过骨骼、载具和观察变换，处于观察空间。

因此缓存按“实际贴图编号 + 坐标空间”分组，即使同一张贴图同时用于模型和粒子，也不能混成一个批次。炮口批次使用单位观察矩阵，表示不再重复旋转；光球剔除使用与显卡上传完全相同的观察空间光位置。这样转动视角或移动到远离世界原点的位置时，炮口不会受光错位，也不会被错误剔除。

两个类型共用原来的 **32768 个四边形总上限**、贴图缓存和显存缓冲，没有再开一套同等预算。采集窗口从世界 `AFTER_SKY` 到 `AFTER_TRIPWIRE_BLOCKS`，并排除光影太阳阴影绘制，界面预览不混入当帧世界光照。关闭屏幕光或进入热成像时仍沿用原炮口显示。

### 8.3 透明边缘、墙体与亮度边界

受光层继续采样炮口实际图集，并乘“贴图 Alpha × 顶点 Alpha”。透明区域没有光贡献，原动画缩放和淡出不变。只叠加 RGB，不改场景 Alpha，不写深度；从贴图面片到光源仍检查粒子前保存的实体、方块及 DH 深度。

这表示炮口贴图可以接受爆炸、其它炮口和发动机的屏幕光，同时不会挡住这些光或程序尾焰。已经达到显示白色上限的原贴图核心没有额外增亮空间；边缘和较暗区域仍可显示新增受光。此次没有为炮口另做高动态亮度或新增光晕提取，已有炮口环境光及其光晕规则继续生效。
