# RVP 屏幕特效通用性能日志

2026-11-06。为当前RVP屏幕空间渲染接入统一性能记录，目录共 **35个统计阶段**，包含效果、输入准备、复制、合成与整帧对照；并非35种独立特效。

默认关闭。未开启时不创建性能文件或文件线程，不申请显卡查询，不读取计时时钟。开启状态只属于当前客户端会话，F8“保存本地”只保存统计间隔，不会让下次启动自动开始录制。

## 开关与文件

客户端指令，不需要服务器管理员权限，也不向服务器发包：

```text
/rvprenderperf on
/rvprenderperf off
/rvprenderperf status
/rvprenderperf interval 2
/rvprenderperf mark 近处爆炸_40步
```

- `on`开始记录，重复执行保持当前会话；`off`停止新增采样，最后几帧显卡结果在后续渲染帧里异步收尾。
- `interval`设置汇总间隔，范围1～30秒，默认2秒；仍逐帧采样，并不是每两秒只抽一帧。
- `mark`把场景说明、当前帧号和会话内时间写进同一文件，用于区分远近、不同F8参数及基线。
- F8入口：**屏幕特效性能 → 右键“性能日志开关与统计频率”标题 → 开始性能记录 / 停止性能记录 / 查看记录状态与文件路径**。

文件位于当前游戏目录：

```text
logs/rvp-screen-performance.log
```

UTF-8，每行一个完整JSON对象，便于搜索和后续脚本统计。性能记录器不使用SLF4J/Log4j、不打印控制台，性能数据和文件错误都不会由它转发到`latest.log`。指令只回显开关、状态和路径；普通游戏自身对聊天/指令的记录不由本系统接管。

文件达32MiB后轮转为同目录`rvp-screen-performance.log.1`，保留一个备份。后台队列最多64份记录，磁盘跟不上时丢弃计数可见，不阻塞渲染；文件不可写的原因从`status`或F8状态操作查看。

## 每条记录是什么

| `type` | 含义 |
| --- | --- |
| `session_start` | 会话号、显卡/驱动接口、Java版本、GPU时间戳能力、完整阶段目录及统计口径 |
| `window` | 一个汇总时间窗口，包含CPU/GPU统计、工作量及环境快照 |
| `mark` | 用户标记的场景、帧号和会话内时间 |
| `session_end` | 正常停止/收尾完成，记录总帧数及写入器状态 |
| `process_exit` | 客户端退出时尽力刷新已完成记录；上下文销毁后不能再读取未完成GPU结果 |

会话统计行带`session`区分会话，后台写入时间为明确标注的UTC。窗口另带首尾帧号、距会话开始的时间，显卡结果晚到不会改变它所属的窗口。快速停止再开启时，旧会话尚未完成的查询明确计为缺失，不移到新会话。

主要窗口字段：

| 字段 | 含义 |
| --- | --- |
| `frames`、`first_frame`、`last_frame` | 本窗口记录了多少显示帧及首尾编号 |
| `start_ms_since_session`、`end_ms_since_session` | 窗口在会话内的时间范围，单位毫秒 |
| `frame_interval_ms`、`fps_estimate` | 相邻显示帧开始时间间隔和推算帧率，包含整个游戏的CPU/GPU等待等因素 |
| `context_first`、`context_last` | 窗口首尾分辨率、世界、暂停、光影状态，以及每秒刷新的Java堆与累计GC读数 |
| `context_changes` | 环境快照变化次数，包括进程内存/GC采样变化；比较分辨率仍应直接看首尾字段 |
| `query_budget_drops` | 查询池已满而没有测GPU的范围数，CPU记录仍保留 |
| `unbalanced_scopes` | 未按正常嵌套关闭的范围数，应为0 |
| `writer_dropped_records` | 有界写盘队列丢弃的累计条数 |

每阶段字段：

- `cpu_submit_ms`：主线程进入到离开该范围所经过的时间，包含驱动调用和等待；不是CPU使用率。
- `gpu_ms`：显卡开始/结束命令时间戳之间的跨度，包含流水线等待；不是显卡利用率、温度、显存占用或纯算术忙碌时间。
- 两者均给出单次调用的`avg`、`max`、`p95`、`samples`。P95表示95%的样本不超过此值；多次模糊调用的P95是单次调用分位数，不是整帧分位数。
- 每阶段每窗口最多保留最近2048份分位数样本，`p95_samples`显示实际分位数样本数；平均和最大值覆盖全部有效样本。
- `cpu_ms_per_frame`、`gpu_ms_per_frame`是本窗口该阶段总耗时除以窗口总帧数，方便看平均帧预算；GPU样本不完整时后者为空，避免把少测数据误当性能提升。
- `gpu_missing_samples`记录GPU不支持、预算不足、超时或快速重启导致的缺失，绝不把CPU耗时替代GPU时间。

`gpu_status`区分`not_executed`（窗口内未进入）、`cpu_only`（明确只测CPU）、`unavailable`（未测到GPU）、`partial`（部分缺失）、`available`（有效样本完整）。范围进入后可能因没有可见对象而早退，因此调用次数不等于实际draw次数。

**所有范围都是包含子级的时间；父子两行不能重复相加。CPU与GPU又是并行执行的，也不能把两列直接相加。** `frame.render`包含Minecraft和其它模组，是整帧渲染阶段对照，不称为RVP总耗时。

## 工作量指标

`metrics`只输出确实接通的已知项；没有字段表示未知，不代表0。

| 键 | 统计口径 |
| --- | --- |
| `draw_calls` | 已挂钩的实际独立屏幕效果draw调用；不推测被包含模型内部的draw次数 |
| `post_passes` | 原版PostChain实际登记的后处理步骤数，不拆链也不重排 |
| `gui_quads` | GUI逻辑矩形/面片数量，区别于引擎合批后的实际draw次数 |
| `submitted_pixels_upper_bound` | 提交矩形的像素上界，按实际渲染分辨率换算；包含重叠和后来被丢弃的像素 |
| `ray_samples_upper_bound` | 上述像素数乘本次程序最大体积步数；不是实际执行步数 |
| `copies` | 场景颜色或深度复制调用数 |
| `copy_destination_bytes_estimate` | 按复制目标尺寸/格式估算字节，不是显存总线的实际带宽读数 |
| `submitted_items` | 对应调用点的光源、喷流、烟段、波层或光斑条目数；具体筛选阶段由调用点决定 |
| `upload_bytes_estimate` | 动态视频噪点等纹理上传目标字节数 |
| `texture_allocation_bytes_estimate` | 已接通自有二维纹理的新分配量，不是当前显存存量 |

体积计数与当前程序一致：大爆炸读取F8的16～64步；尾烟读取当次实际步数；喷流主积分最多20步；喷流的一像素可见度最多7×3条视线、每条20步；普通冲击波为8步正面积分。广域喷流光晕只读已算好的一像素结果，不误记成整片20步体积。

## 测量方式与自身开销

显卡使用成对`GL_TIMESTAMP`查询：让显卡排队写下开始/结束时刻，正常隔至少两帧再检查可用性，只有完成后才读取结果。不使用`glFinish`、阻塞等待、逐像素回读，也不占用其它模组可能正在用的`GL_TIME_ELAPSED`目标，因此支持嵌套和共存。依据见[Khronos ARB_timer_query规范](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_timer_query.txt)。

查询对最多256个，未完成的结果在后续渲染帧中最多等待两秒，超时记缺失并释放。后台写盘队列有界，窗口和P95样本也有界；连续记录不会无限积累查询或历史帧。

录制有自身开销：时间戳、CPU计时、计数、汇总和首次查询分配都不是免费操作。GUI为准确包住延迟批处理，**仅在录制时**会在被测效果前后flush（提交尚未真正画出的GUI批次），这会改变合批成本。应在同一录制方式下比较参数，并关闭F8窗口观察场景；首次查询池分配可能形成额外尖峰。停止后恢复原来的GUI提交方式。

建议记录：先开日志保留几秒无效果基线，再用`mark`分别标注远景、近景、镜头进入烟火、多效果叠加和不同采样步数；停止后以`gpu_ms_per_frame`和`cpu_ms_per_frame`比较完整窗口，结合复制量/像素上界解释变化。
