# RVP炮火支援终端使用与配置指南

> 适用版本：Minecraft 1.20.1 Forge / 炮火 profile schema v3（2026-09-09）
> 正式配置client_1：`run/client_1/limitless_vehicle/rvp/data/rvp/fire_support_profiles/default.json`
> 正式配置server：`run/server/limitless_vehicle/rvp/data/rvp/fire_support_profiles/default.json`
> Schema：[fire_support_profile.schema.json](../../schemas/fire_support/fire_support_profile.schema.json)
> 作者示例：[default.json](../../examples/fire_support_profiles/default.json)
> 当前实现与完整调参说明：[RVP 炮火支援技术文档与调参指南](./RVP炮火支援技术文档与调参指南_20260906.md)

## 1. 玩家操作

1. 从 `ywzj_vehicle:tab_rvp` 创造栏取得 profile 自动生成的炮火支援终端变体；每个 profile 对应一个带 profile 标识的 ItemStack。
2. 主手或副手持有终端，右键或按 K 打开战术地图炮火工具。
3. 终端已锁定对应 profile，地图中的“配置”行只读；依次选择弹药方案、打击模式与落区。弹药方案可以是一种武器，也可以是配置好的多武器混合打击。各选择行既可用两侧箭头轮换，也可点击中部展开下拉框；在地图左键设置锚点。
4. 条状/徐进弹幕可拖动方向手柄；侧栏可调整半径、长度、宽度与步长。
5. 检查非权威弹数/呼叫时间预估，点击“确认呼叫”。服务端会重新校验全部选择。
6. 呼叫阶段可换手、换快捷栏或把绑定终端移入背包；死亡、断线或终端离开物品栏会取消。
7. 进入打击阶段后任务与玩家生存、连接和 `/reload` 解耦。只有任务所有者再次主手或副手持有同一终端实例时才能请求停火；停火默认 80 Tick 后生效，已生成弹体不会删除。

profile 可在 `call_stage.consume_terminal_on_completion` 中开启终端消耗。开启后，支援全部完成或停火实际生效时，系统只删除本次任务绑定的同一 `terminal_instance`；如果终端期间被丢出，任务结束后的掉落实体加载、拾取和重新登录都会继续删除该实例。取消、失败和呼叫阶段中止不会消耗终端。

终端会在当前客户端会话中记住 profile、弹药方案、打击模式、落区、动态参数、目标点和方位。关闭地图再打开不会丢失；点击“重置参数”或服务端成功 `/reload` 发布新 revision 时才恢复默认。任务 UUID、呼叫截止时间、进度和绑定终端也来自服务端权威更新，因此重新打开界面仍能看到最近的活动任务或终态，并可继续请求停火。

不持终端按 K 时仍保持普通战术图/载具炮兵图分流。终端上下文不会借用载具 `ARTILLERY` 射击链。

## 2. 正式 profile

首个正式 profile 为 `rvp:default`。它保留 `rvp:f14d_mk84` 单武器方案，并新增由 MK-84 与非制导重型火箭 `rvp:f14a_iriaf_yasser` 组成的混合方案。两种真实 RVP 弹体均保留碰撞、引信、爆炸、模型、声音与归属；Java 中没有按武器 ID 分支。

| 选项 | 正式值 |
| --- | --- |
| MK-84 一基数 | 4 发 |
| MK-84/Yasser 混合一基数 | 6 发，阶段内按 MK-84、MK-84、Yasser 循环 |
| 急促打击 | 6 发，40 秒呼叫，60 Tick 主射，散布 ×1.5 |
| 效力打击 | 2～3 发试射 + 8 发主射，60 秒呼叫，180 Tick 主射 |
| 监视打击 | 2～3 发试射 + 8 发主射，60 秒呼叫，600 Tick 主射 |
| 混合急促打击 | 9 发：6 枚 MK-84、3 枚 Yasser |
| 混合效力/监视打击 | 2～3 发试射 + 12 发主射，共 14～15 发 |
| 点状弹幕 | 半径 4～32 米 |
| 条状弹幕 | 长 24～96 米、宽 4～32 米 |
| 徐进弹幕 | 长 32～112 米、宽 4～32 米、步长 4～32 米 |

正式配置已放宽为单玩家 4 个、全服 32 个活动任务，单任务最多 128 发、最多 64 个唯一落点 Chunk，目标距离 0～8192 格，请求冷却 20 Tick。落点实际跨越超过 64 个唯一 Chunk 时任务仍会以 `CHUNK_LIMIT` 失败，保留最终保险边界。

## 3. 配置作者流程

复制[作者示例](../../examples/fire_support_profiles/default.json)，放到：

```text
limitless_vehicle/<包名>/data/<namespace>/fire_support_profiles/<path>.json
```

资源 ID 为 `<namespace>:<path>`。配置只接受 `schema_version: 3`，不兼容旧键、不迁移旧版 JSON。顶层必须提供 `item.translation_key`；`holder_policy` 只配置允许的手。v1 的 munition 顶层 `weapon` / `delivery` 必须手工改成 `weapons[]`，即使只有一种武器也不能保留旧写法。先用 Draft 2020-12 Schema 做编辑器校验，再以服务端 reload 日志为最终结论；运行时解析器还会检查跨字段约束、武器索引、权重、有限数、步长、任务持续时间与性能预算。

新增 profile 不需要修改 Java 物品注册表。服务端发布 profile 后，客户端会自动生成一个带 `rvp_fire_support.profile_id` 的终端 ItemStack，并重建创造栏内容；只需同时在载具包语言资源中提供 `item.translation_key` 对应的翻译键。旧的无 profile 标识终端按 `rvp:default` 兼容处理。

新增弹药方案时：

- `weapons` 必须有 1～64 项，每项 `weapon` 都必须解析为真实且互不重复的 `RVP_WeaponData`；
- 每项 `weight` 为 1～512 的整数，总和不超过 512。按声明顺序轮转，例如 `2:1` 为 `A、A、B`；每个 phase 独立从 A 开始，权重不会增加总弹数；
- `registration_phase_enabled` 控制该方案是否执行试射；打击模式内的试射阶段使用 `registration_phase: true` 显式标记，调度器不按阶段 ID 猜测；
- 每个成员独立配置 `delivery`。`vertical_projectile` 只拒绝不能创建实体弹体的 `LASER`、`TARGETING_POD` 等类型；HITL 或依赖操作手的武器允许作为失去持续制导的垂直入场弹体使用；
- 只选择已通过无载具探针的武器；
- 不把 `fire_data.fire_mode`、`burst_count` 或 `canister_count` 当成任务弹数；
- 新几何或新投送方式应注册类型化工厂，不在任务管理器里按 ID 分支。

## 4. 资源与本地化

物品模型使用 `minecraft:item/generated`，贴图位于 `assets/ywzj_rvp/textures/item/fire_support_terminal.png`。贴图为 32×32 RGBA 像素风资源，不涉及任何 Bedrock 载具结构模型。

终端名称、tooltip、三种打击模式、三个阶段、三类落区、动态参数、任务状态以及所有服务端拒绝原因均有 `zh_cn` / `en_us` 对应键。配置中的 `translation_key` 只负责显示，不参与权限判断。

## 5. 性能与安全预算

系统同时应用 profile 限制和不可配置硬上限：

| 预算 | 硬上限 / 正式 profile |
| --- | --- |
| 顶层炮火弹体生成 | 8 发/服务器 Tick |
| 新增预加载 Ticket | 24 个/服务器 Tick |
| Chunk 等待 | 1200 Tick |
| 全局活动任务 | 硬上限 64；正式 profile 32 |
| 单任务顶层弹 | 硬上限 512；正式 profile 128 |
| 武器生命期 | 72000 Tick |
| 单发直接子实体 | 4096 |
| 单任务顶层+直接子实体 | Integer.MAX_VALUE |
| 主爆炸半径 | 512 格 |
| 主爆炸伤害 | 1000000000 |

预算解析使用饱和整数运算，避免恶意 `release_events × payload.count` 溢出。混合方案的每个武器成员都按任务最大弹数做保守最坏审计。现在允许多级子母弹链，不再仅因 `allow_submunition=true` 拒绝整个 profile；当前武器可见的直接展开量仍受宽松绝对上限约束。垂直投送在高地上方不足固定生成高度时会钳制到世界顶端内侧，并将偶发生成失败重试 20 次。

正式 MK-84 的审计结果为：`life=1200` Tick、直接子实体 0、主爆炸伤害 1200、半径 18。正式 profile 中混合效力/监视打击最坏为 15 发；权重只决定这 15 发使用哪种武器，不会再乘以成员数。低 TPS 只延后游戏 Tick，调度器不会用墙钟补发，且每个实际 Tick 仍受 8 发全局预算约束。

## 6. 验证与排障

构建：

```powershell
$env:JAVA_HOME='对应本地java路径'
$env:JAVA_TOOL_OPTIONS='-Djdk.net.unixdomain.tmpdir=自设定临时目录'
./gradlew build
```

专服冒烟运行 `./gradlew runServer`，每 10 秒检查 `run/server/logs/latest.log`，出现 `Done (Xs)!` 才通过。日志检索必须按[调试与修复规范](../../调试与修复规范.md) §5.1 只判断新增错误。

载具包不会由 Gradle 自动复制到 `run/*`。测试正式 profile 前需把仓库 `limitless_vehicle/rvp` 全量同步到对应运行目录；不要只复制单个 JSON 后误把版本差异当成炮火故障。

客户端最终人工回归至少覆盖：主/副手入口、K 键原分流、三类预览和拖柄、小分辨率裁剪、旧 revision、生命周期、停火、重连、`/reload`、宽落区 Chunk 上限，以及原 GPS/雷达/载具 `ARTILLERY` 与类型化弹体渲染。
