## 1. 当前结论

炮火支援终端已完全实现在 `limitless-vehicle-rvp-addon` 内，没有修改 `ywzj_vehicle`，没有新增 Mixin，也没有修改载具结构模型。

2026-09-08 起，`RVP_FireSupportDeliveryTypes` 同时提供三种投送：保留
`rvp:vertical_projectile`，新增默认固定虚拟炮位、单发不可达时可近距回退的
`rvp:ground_launched_projectile` 和生成真实飞机的
`rvp:air_launched_projectile`。普通非 GPS 地射仍只接受无推进、无恒速、无制导的 `MACHINEGUN`/`ROCKET`；含 GPS
链路的可生成实体弹体另行放宽推进与恒速限制；空中投送接受
`BOMB`、空对地 `MISSILE` 和 `ROCKET`，由指定飞机按预计算航线从本地 `rack_offset` 挂架位置投放。
空中方案必须选择 `air_strike`，不得混合空中与地面投送；飞机被击落时以 `AIRCRAFT_DESTROYED` 结束任务。

GPS 定点扩展仅作用于空射和地射：主制导或末段制导链路包含 GPS 的可生成实体弹体均可使用每发 pattern 落点作为固定目标。目标 Y 取该落点地表高度；GPS 空射不执行无制导弹道反解，而是从 profile 指定的固定前置距离释放并继承实时载机速度。普通非 GPS 地射仍保持无推进、无恒速、无制导的 `MACHINEGUN`/`ROCKET` 约束。GPS 弹保留本体推进、恒速、末段制导和既有虚拟中段规则，不复用玩家 GPS 队列。

任务在 `scheduledTick - preload_ticks` 开始执行确定性解算和生成点 Chunk 租约，计划 Tick 仍是实体实际生成时间。
C2S 协议号为 10，请求和任务冻结同时携带“落区方位”与独立“入场方位”；地图以金色落区手柄和固定 48 像素半径的青色入场手柄分别编辑，两行均以 5° 步进。首次指定目标时，入场方位取玩家当前位置指向目标，之后不再随玩家移动。

正式 `rvp:default` 中，MK-84 和耄耋重磅炸弹改为空投，Yasser、M30、M30-WP、M-31 使用固定地射；M30、M30-WP、M-31 的 `rounds_per_unit` 均为 6，趣味重磅炸弹为 4。运行包维护源为
`run/client_1/limitless_vehicle/rvp`，相关 profile 同步镜像到 `run/server`。探针语法为
`rvpdebug firesupportprobe <vertical|ground|air> <weapon> [target]`。

当前实现如下：

1. 注册表中只保留通用物品 `ywzj_rvp:fire_support_terminal`；每个已发布 profile 自动生成一个带 profile 标识的 ItemStack 变体。主手或副手右键、或持有时按 K，都会打开现有战术地图上的炮火支援工具。
2. `RVP_TacticalMapScreen.MapMode` 仍只有 `TACTICAL` 与 `ARTILLERY`。终端通过 `RVP_TacticalMapTool` / `RVP_TacticalMapHost` 组合进 `TACTICAL` 地图，没有复制 Screen，也没有冒充载具炮兵模式。
3. `RVP_FireSupportMissionManager` 在服务端权威验证、创建并逐 Tick 推进任务；客户端只提交选择和目标，不决定最终弹数、时间表、散布、权限或投送结果。
4. profile 独立放在 `data/<namespace>/fire_support_profiles/*.json`，引用真实 RVP 武器资源 ID，并通过 `item.translation_key` 驱动终端变体名称；Java 不按武器路径分支，也没有把炮火字段写入 `RVP_WeaponData`。
5. 被引用武器仍负责弹体类型、弹道、引信、碰撞、毁伤、子母弹、声音和渲染；profile 负责呼叫、任务弹数、阶段、落区和投送参数。
6. `RVP_ProjectileSpawner` 已增加 `RVP_ProjectileSpawnContext` 入口，并由 `RVP_ProjectileEntityFactory` 统一创建类型化 RVP 弹体；空中任务使用真实指定飞机作为 `sourceVehicle`，不伪造武器站。
7. `RVP_FireSupportPatternTypes` 已注册点状、条状和徐进三种几何；`RVP_FireSupportDeliveryTypes` 当前注册垂直、固定地射和空中释放三种投送。
8. 呼叫阶段与打击阶段采用不同生命周期。呼叫阶段可由所有者主动立即取消，也会按冻结的 profile 在死亡、断线或绑定终端丢失时取消；进入打击阶段后不再受这些玩法事件或 `/reload` 影响，停火请求默认延迟 80 Tick 生效。
9. 一个 `munition` 现在是一份弹药方案，可包含 1～64 种真实 RVP 武器；每发由服务端按声明顺序和整数权重确定。空中方案内所有成员必须共享同一飞机与航线配置，且不得混入其他投送类型。

空中任务由 `RVP_FireSupportAirstrikeController` 按任务级连续固定翼航线运行：先按每发弹道解算参考投放点，再用向心 Catmull-Rom 曲线连接入场点和投放参考点，最后一个投放点至出场点使用直线延长段。插件读取 `FixedWingVehicle` 的 `turnRateBySpeed`、`xTurnRate`、`yTurnRate`、`zTurnRate` 做偏航、俯仰、滚转渐进跟随；其他载具使用插件回退参数并记录一次诊断日志。飞机沿实际前向速度推进，转弯能力不足时允许偏离参考曲线，不会在投放点平移或倒飞；最后一发成功生成后立即切换到既定出场方向，并从该 Tick 起继续飞行 `exit_distance_m` 对应的参考时长，随后移除完整飞机。

原始释放点只作为参考触发点，同一 `weaponId` 的待投送弹体组成池，飞机经过对应参考点后按顺序取弹；每个参考点最多尝试一次，失败弹体可在后续参考点或出场延长段重试。每发仍不得早于原始计划 Tick，实时挂架世界坐标、飞机当前切线速度和完整姿态会重新解算离散弹道，并补偿转弯产生的法向偏差。被击落则保留残骸并停止剩余计划；路径或实体短暂不可用时等待同 UUID 飞机恢复，200 Tick 超时返回 `AIRCRAFT_LOST`。只有载具毁伤状态或 `KILLED` 移除才返回 `AIRCRAFT_DESTROYED`。空中任务最多运行至 `acceptedTick + max_mission_duration_ticks + 1200`，超时停止未投送计划并返回 `CHUNK_TIMEOUT`。

## 3. 当前玩家体验

### 3.1 打开、取消与停火

| 操作/状态 | 当前行为 |
| --- | --- |
| 主手或副手持终端并右键 | 打开普通战术地图画布及炮火侧栏 |
| 主手或副手持终端并按 K | 优先打开炮火工具；未持有时保持原 K 键分流 |
| 终端只在背包中 | 不能打开工具，也不能提交新呼叫或请求取消/停火 |
| 呼叫阶段换手、换快捷栏或移入背包 | 任务继续；守卫会在玩家物品栏内按绑定 UUID 查找终端 |
| 呼叫阶段手持绑定终端并按“取消呼叫” | 服务端立即将任务置为 `CANCELLED/USER_CANCELLED` |
| 呼叫阶段死亡、断线或绑定终端离开物品栏 | 按冻结的 `cancel_on_*` 策略取消；正式 profile 三项均为 `true` |
| 打击阶段死亡、断线、换手、丢弃终端或 `/reload` | 已接受任务继续执行 |
| 打击阶段手持绑定终端并按“停火” | 进入 `CEASE_FIRE_PENDING`；正式 profile 默认 80 Tick 后停止未生成弹 |
| 停火已被接受后再失去终端 | 不撤销停火倒计时 |
| 玩家在打击阶段离线或死亡 | 使用同 UUID、已清理名称的 Forge 假玩家继续提供弹体 owner；不伪造载具 |

终端实例 UUID 保存在 ItemStack NBT 的 `rvp_fire_support.terminal_instance`。新请求所报 hand 必须与服务端实际手中终端一致；呼叫守卫按实例 UUID 搜索所有物品栏槽位；取消/停火则重新扫描 profile 允许的主副手。重复 UUID 会被视为身份不唯一并拒绝新呼叫。

`call_stage.consume_terminal_on_completion` 默认值为 `false`。开启后，仅当任务进入 `COMPLETED` 或停火实际生效进入 `CEASED` 时，按冻结的 `terminal_instance` 与 `profile_id` 精确删除绑定终端；`CANCELLED`、`FAILED`、死亡、断线取消和终端丢失不消耗。在线库存和已加载掉落实体会立即扫描，之后的掉落实体加载、拾取和玩家登录也会继续拦截同一实例；该保护仅保留到当前服务器停止。

### 3.2 地图操作

1. 当前持有的终端 ItemStack 已锁定 profile；配置行只读。选择弹药方案、打击模式和落区预设。弹药方案可为单一武器，也可为配置好的混合打击。
2. 在地图左键设置锚点；条状与徐进预设可以拖动方向手柄。
3. 侧栏参数行按 profile 的 `min/max/step` 调整，方位按 5° 步进，也可由地图手柄更新。
4. 工具显示预计弹数范围、呼叫时间和任务持续时间，并绘制点、条、徐进落区预览。
5. 点击“呼叫支援”发送带独立 nonce 的请求。
6. 服务端接受后回传任务 UUID、权威 seed、规范化参数、呼叫截止 Tick、首发与末发计划 Tick。
7. 状态面板显示 `CALLING`、`STRIKING`、`CEASE_FIRE_PENDING` 及完成、取消、停火、失败终态；呼叫阶段按钮为“取消呼叫”，打击阶段按钮为“停火”。

客户端会话内会保留选择、动态参数、目标点和方位；关闭后重新打开不会丢失。成功发布新 revision 或点击“重置参数”会恢复相应默认值。当前只接受地面 X/Z 锚点，不跟踪实体目标。

## 4. 数据模型与扩展边界

### 4.1 数据驱动阶段

打击模式没有 `RAPID/EFFECT/MONITOR` Java enum 分支。每个模式由若干通用 phase 组成：

- `start_delay_ticks`：首阶段相对打击开始，后续阶段相对上一已包含阶段的末弹；
- `rounds`：`fixed`、`random_min/random_max`、`base_multiplier + rounding: ceil` 三选一；
- `interval_ticks` 或 `duration_ticks`：二选一；
- `registration_phase`：标记该 phase 是否属于试射。

弹药方案的 `registration_phase_enabled` 默认为 `true`；设为 `false` 时，调度器跳过所有 `registration_phase: true` 的 phase，而不是根据 phase ID 猜测“registration”。

若一个阶段有 `N > 1` 发且配置 `duration_ticks = D`，第 `i` 发偏移为：

```text
round(D × i / (N - 1)), i ∈ [0, N-1]
```

`N = 1` 时偏移为 0。多个弹可以因四舍五入落在同一计划 Tick，但运行时仍受全局每 Tick 8 发以及每任务每 Tick一次投送尝试的限制。

### 4.2 弹数与武器模板

```text
基数阶段弹数 = ceil(rounds_per_unit × base_multiplier)
任务总弹数 = 所有未被跳过 phase 的弹数之和
```

武器的 `fire_data.fire_mode`、`burst_count`、`burst_delay`、`canister_count`、载具弹仓容量和射击间隔都不参与任务弹数或节奏。一发计划弹只生成一个顶层 RVP 弹体；子弹药由武器自身 `submunition_data` 处理。

`weapons[].weight` 只决定这些计划弹使用哪种武器，不增加总弹数。每个 phase 用 `roundInPhase` 从第一个成员重新轮转；权重 `2:1` 的声明顺序固定产生 `A、A、B` 循环，因此随机试射数量不会改变主射首发武器。每个计划弹冻结成员下标，同一发等待 Chunk 或生成失败重试时不会换武器。

当前没有实体炮兵库存，也不扣玩家背包中的武器弹药。终端是否在任务成功完成或停火生效后消耗，由每个 profile 的 `call_stage.consume_terminal_on_completion` 控制，且只删除任务绑定的终端实例。

### 4.3 类型注册表

当前几何类型：

- `rvp:point`：半径圆内按面积均匀采样；
- `rvp:line`：沿方位长轴的矩形内均匀采样；
- `rvp:creeping`：从锚点沿方位按 `step_m` 向前推进并横向散布。

当前投送类型包括 `rvp:vertical_projectile`、`rvp:ground_launched_projectile` 和 `rvp:air_launched_projectile`。两个注册表在静态初始化后冻结，重复 ID 直接失败；JSON 不能引用 Java 类名、反射、命令或脚本。

## 5. 当前 JSON schema

### 5.1 位置、加载与 revision

运行时文件位于：

```text
limitless_vehicle/<包名>/data/<namespace>/fire_support_profiles/<path>.json
```

资源 ID 为 `<namespace>:<path>`。正式维护文件 `run/client_1/limitless_vehicle/rvp/data/rvp/fire_support_profiles/default.json` 发布为 `rvp:default`。

解析器仅接受 `schema_version: 3`，严格拒绝未知字段、旧键别名、重复 ID/武器、非法权重、非法资源 ID、非有限数、越界参数、缺失武器和未知类型。v3 用 `item.translation_key` 描述自动生成的终端 ItemStack，`holder_policy` 不再包含 `required_item`。旧 JSON 不迁移，v1 的 munition 顶层 `weapon` / `delivery` 必须手工改为 `weapons[]`。reload 使用候选快照：整批校验通过才原子发布并增加 revision；失败时保留旧快照。登录和数据包同步事件会把规范化 profile 快照发送给客户端，新请求 revision 过期时返回 `STALE_REVISION`。

完整字段以以下两个文件为准：

- `docs/schemas/fire_support/fire_support_profile.schema.json`
- `docs/examples/fire_support_profiles/default.json`

### 5.2 顶层与生命周期字段

| 字段 | 默认/约束 | 当前语义 |
| --- | --- | --- |
| `schema_version` | 必填，仅 `3` | 当前且唯一 schema 版本 |
| `display.translation_key` | 必填 | 只影响显示 |
| `item.translation_key` | 必填 | 自动生成的终端 ItemStack 名称翻译键 |
| `holder_policy` | 必填 | 新呼叫、取消和停火时验证允许的手 |
| `holder_policy.allowed_hands` | `main` / `off` 集合 | 新请求验证声明 hand；取消/停火扫描允许的手 |
| `call_stage.base_duration_ticks` | 默认 `800` | 乘模式倍率后向上取整，至少 1 Tick |
| `cancel_on_player_death` | 默认且首版固定 `true` | 仅 `CALLING` 生效 |
| `cancel_on_terminal_lost` | 默认且首版固定 `true` | 仅 `CALLING` 生效 |
| `consume_terminal_on_completion` | 默认 `false` | 为 `true` 时，`COMPLETED`/`CEASED` 精确删除任务绑定终端；按实例 UUID 处理，不替代为同 profile 终端 |
| `cancel_on_disconnect` | 默认 `true` | 仅 `CALLING` 生效，可配置关闭 |
| `strike_stage.cease_fire_delay_ticks` | 默认 `80` | `STRIKING` 停火请求接受后的延迟 |

### 5.3 limits 与硬上限

| 字段 | 解析默认 | 不可配置硬边界 |
| --- | ---: | ---: |
| `min_target_distance_m` | `0` | 不得小于 0 |
| `max_target_distance_m` | `2048` | 不得超过 16384 |
| `max_rounds_per_mission` | `96` | 512 |
| `max_active_missions_per_player` | `1` | 不得超过全局配置上限 |
| `max_active_missions_global` | `16` | 64 |
| `request_cooldown_ticks` | `100` | 非负整数 |
| `max_mission_duration_ticks` | `2400` | 正整数 |
| `max_loaded_chunks_per_mission` | `8` | 正整数 |
| `max_parameter_count` | `16` | 32 |

`vertical_projectile` 参数：

### 5.5 空中投送与 `air_strike`

空中投送数据必须配置 `aircraft_id` 和飞机本地挂架坐标：

```json
{
  "aircraft_id": "ywzj_vehicle:rafale",
  "rack_offset": { "x": 0.0, "y": -2.0, "z": 0.0 },
  "entry_distance_m": 1280.0,
  "exit_distance_m": 768.0,
  "release_altitude_above_impact_m": 256.0,
  "min_release_altitude_above_impact_m": 96.0,
  "gps_release_distance_m": 768.0,
  "carrier_speed_m_per_tick": 2.5,
  "preload_ticks": 80,
  "heading_jitter_deg": 0.0
}
```

`rack_offset` 会按飞机当前偏航、俯仰和滚转姿态转换到世界坐标；弹体在飞机实际挂架附近生成。`entry_distance_m` 默认 1280 格，`exit_distance_m` 与 GPS 专用的 `gps_release_distance_m` 均默认 768 格。飞机不再停留或折返到每个释放点，而是连续跟随全局平滑曲线；最后一发成功后，末段改为沿参考出场点方向的直线离场，并按 `exit_distance_m / carrier_speed_m_per_tick` 的参考时长清理飞机。实际挂架偏离参考点时，非 GPS 炸弹、空对地导弹和火箭弹重新解算离散弹道；GPS 弹不做弹道拟合，直接继承实时载机速度并由原生制导飞向固定目标。`air_strike` 模式的阶段使用 `base_multiplier: 1.0`。服务端和客户端均禁止空中方案选择其他模式，且禁止空中/地面混合方案。

## 7. 服务端任务生命周期

### 7.1 状态机

```text
请求拒绝（不创建任务）

CALLING
  ├─ 玩家主动取消 / 死亡 / 断线 / 绑定终端丢失 → CANCELLED
  └─ callDeadlineTick 到达 → STRIKING

STRIKING
  ├─ 全部计划弹成功加入世界 → COMPLETED
  ├─ 有效停火请求 → CEASE_FIRE_PENDING → 生效 Tick → CEASED
  └─ Chunk 上限/超时、世界边界、投送不支持或连续失败 → FAILED
```

`CALLING → STRIKING` 在截止 Tick 原子发生。此后任务不再检查玩家在线、生存、终端持有状态或当前 profile revision。`/reload` 只影响新请求；任务持有创建时冻结的 profile、munition、全部成员 delivery/武器数据、规范化参数和带成员索引的完整计划。

任务不缓存可变 `ItemStack` 或 `Player` 引用。所有者仍在线且存活时使用真实 `ServerPlayer` 作为 owner；否则在任务维度取得同 UUID 的 Forge 假玩家。服务器重启不会恢复内存任务或在飞弹体。

终态任务会在服务端保留 1200 Tick，用于所有者重连后补发最终状态；请求 nonce 和停火 nonce 同样按玩家隔离、最多保留 64 项并在 1200 Tick 后清理。

### 7.2 Tick 调度和失败

- 任务列表采用轮转起点，避免固定顺序长期偏向同一任务。
- 全服每 Tick 最多成功生成 8 个顶层炮火弹体。
- 单个任务在一次服务端 Tick 中至多尝试当前一发；逾期计划弹顺延，不按墙钟补齐。
- `WAITING_FOR_CHUNK` 不计普通投送失败次数。
- 同一计划弹连续 20 次普通生成失败后，任务以 `DELIVERY_FAILED` 结束。
- 每发成功后广播进度；阶段、停火与终态变化也广播。详细状态只发给任务所有者。

## 8. 取消、停火与幂等

`C2SRequestFireSupportCeaseFire` 同时承载两种语义：

- 对 `CALLING`：验证所有者及允许手中的绑定终端后立即取消；
- 对 `STRIKING`：记录 `now + cease_fire_delay_ticks` 并进入 `CEASE_FIRE_PENDING`；
- 对 `CEASE_FIRE_PENDING`：重复请求成功但不改变最早生效 Tick。

请求包只发送任务 UUID 和独立 nonce，不发送可信 hand 或终端实例。服务端直接读取玩家两只手。生效 Tick 的调度顺序是先判断停火截断，再尝试同 Tick 投送，因此生效 Tick 及之后尚未加入世界的计划弹都不会生成；已经加入世界的弹体不删除。

新呼叫和取消/停火分别维护 nonce 缓存。同 nonce、同内容重发返回首次结果；同 nonce 改内容返回 `NONCE_CONFLICT`，不会创建第二个任务或改变原停火时间。

## 10. Chunk、性能与武器预算

### 10.1 生成前租约

`RVP_FireSupportSpawnChunkLeaseManager` 为任务/维度/Chunk 去重申请 `TicketType.POST_TELEPORT` 临时票：

- 每服务器 Tick 最多首次申请 24 个 Ticket；
- 同一任务的唯一 Chunk 数受 profile 限制；
- 不同步强制生成 Chunk，也不使用永久 force chunk；
- 只有 Chunk 达到 entity-ticking 才允许生成弹体；
- 普通投送从该 Chunk 当前已知的最后计划生成 Tick 起等待超过 1200 Tick 返回 `CHUNK_TIMEOUT`；空中任务的入场/目标租约使用任务安全截止 Tick，即 `acceptedTick + max_mission_duration_ticks + 1200`。
- 任务进入任一终态后释放内存租约，已添加的临时 Ticket 自然过期。

弹体成功加入世界后继续调用 `primeDynamicChunkPath()`，沿用既有飞行路径加载系统。

### 10.2 武器发布预算

profile 发布时会对弹药方案的每个真实武器成员分别审计：

| 项目 | 当前硬上限 |
| --- | ---: |
| 顶层弹体生命期 | 72000 Tick |
| 单顶层弹体直接子实体数 | 4096 |
| 主爆炸半径 | 512 |
| 主爆炸伤害 | 1,000,000,000 |
| 单任务顶层与直接子实体展开数 | `Integer.MAX_VALUE`，使用饱和运算防溢出 |

每个成员都按 `max_rounds_per_mission` 做保守最坏审计，而不是按权重折算。当前允许多级子母弹链，不再因为 `allow_submunition=true` 直接拒绝 profile。预算审计针对当前武器可见的直接展开量；配置高展开武器时仍必须做专服压力测试。

### 10.3 归属与友伤

弹体 owner 是真实玩家或同 UUID 假玩家，`sourceVehicle` 为 `null`。当前没有额外友军过滤，伤害归属和友伤行为沿用 RVP/本体机制。

服务端冒烟使用 `./gradlew runServer` 后台启动，每 10 秒检查一次新增日志；出现 `Done (Xs)!` 才算通过。日志检索需加 `-a`，并只判断相对 `docs/调试与修复规范.md` §5.1 基线新增的错误。用户手动关服不等于启动失败，结论以日志为准。

载具包不会由 Gradle 自动同步到 `run/*`。验证正式 profile 前，应把 `limitless_vehicle/rvp` 完整同步到目标运行目录。

## 15. 后续扩展边界

当前 schema v3 已形成数据驱动终端变体、单武器与混合武器闭环，后续能力应在既有扩展点上增加：

- 新落区几何：新增 `RVP_FireSupportPatternFactory` 并注册；
- 新投送方式：新增 `RVP_FireSupportDeliveryFactory` / `RVP_FireSupportDelivery` 并注册；
- 队伍共享：在当前只发所有者的状态同步之外增加明确 audience 策略；
- 后勤库存：增加独立资源提供者，不把扣料塞进任务调度器；
- 实体跟踪、激光校射或观察员修正：作为新的权威目标/授权协议设计；
- 跨重启恢复：任务与在飞弹体必须一起设计持久化，不能只恢复其中一半；
- 通用配置化 Item：未来只需让能力处理器引用现有 `fire_support_profile`，不重写任务、网络、几何或投送层。

任何扩展仍须遵守：不修改 `ywzj_vehicle` 本体、不硬编码武器 ID、弹体使用 RVP 类型化 renderer、只接受当前 JSON schema、默认不新增 Mixin、不修改载具结构模型。
