## 1. 结论先行

本功能可以在 `limitless-vehicle-rvp-addon` 内完整落地，不需要修改 `ywzj_vehicle`，也没有新增 Mixin 的必要。

推荐方案是：

1. 新增固定注册物品 `ywzj_rvp:fire_support_terminal`，中文名为“RVP炮火支援终端”；玩家主手或副手持有该物品时，右键或按 K 打开现有战术地图的“炮火支援工具”上下文。
2. 不复制第二张地图，也不把终端冒充当前已有的 `ARTILLERY` 载具炮兵模式；保留 `RVP_TacticalMapScreen` 作为地图画布，通过可插拔 `RVP_TacticalMapTool` 接入终端侧栏、落区预览和任务状态。
3. 服务端通过独立的 `RVP_FireSupportMissionManager` 权威创建和逐 Tick执行任务。客户端只提交选择，不决定弹数、计时、有效范围、最终散布或是否允许发射。
4. 炮火支援配置独立放在 `data/<namespace>/fire_support_profiles/*.json`。配置引用武器资源 ID，但不把炮火支援字段塞进 `RVP_WeaponData`，也不按武器文件名写 Java 分支。
5. 被引用武器作为“弹体/战斗部模板”：继续使用现有 `RVP_WeaponData`、RVP 弹体实体、引信、伤害、子母弹、特效和类型化 `EntityRenderer`。终端的射击模式独立决定逻辑炮弹数量、呼叫时长、试射、发射间隔、任务持续时间与模式散布倍率。
6. 把现有 `RVP_ProjectileSpawner` 泛化为接受“无载具发射上下文”，不要创建假载具，也不要构造一个残缺 `RVP_ProjectileWeapon` 去绕过其载具/武器站前置条件。
7. 用两个类型注册表保持开闭原则：`RVP_FireSupportPatternTypes` 负责点状、条状、徐进弹幕；`RVP_FireSupportDeliveryTypes` 负责实际投送。新增同类预设只改 JSON；新增全新几何或投送机制只增加工厂实现并注册，不改任务调度核心。
8. “必须手持才生效”拆成两个生命周期语义：提交请求时必须主手或副手持有终端；接受后进入默认 40 秒、可由 JSON 调整的“呼叫阶段”，此时玩家死亡或绑定的那一台终端离开玩家物品栏会取消呼叫。呼叫完成后进入“打击阶段”，任务与玩家生存、终端持有、断线及配置重载解耦，除非任务所有者重新以主手或副手持有该任务绑定的同一终端实例并按下“停火”，否则剩余投送不可被玩法事件打断；停火请求默认延迟 4 秒生效，只阻止届时尚未生成的炮弹，已经生成的弹体继续自然飞行。

建议先落地“垂直入场真实弹体”投送：任务到时在服务端校验后的落区上方生成真实 RVP 弹体，使其自然飞行、碰撞和爆炸。它比直接在坐标调用爆炸更能复用既有机制，也保留可见弹道、来袭音效、拦截和地形遮挡。

### 2.2 当前“炮兵地图”不是所需终端

当前 `RVP_TacticalMapScreen.MapMode` 只有 `TACTICAL` 与 `ARTILLERY`。`ARTILLERY` 模式的目标是给玩家正在操纵的载具武器做逆 CCIP 自动瞄准：

- `RVP_ClientEvents.ywzj_rvp$resolveMapMode()` 读取 `LocalVehiclePlayer` 当前武器；
- 当前武器必须是 `RVP_WeaponBase` 且 `misc_data.artillery_map=true`；
- 地图悬停会持续调用 `RVP_ArtilleryFireControlState.designate(...)`；
- `RVP_ArtilleryFireControlState` 又要求有效载具、武器站和当前武器；
- 空格最终调用当前载具武器的客户端射击链路。

炮火支援终端需要允许步行玩家使用，且炮弹来自独立服务端任务，因此不得把它强行塞进这条载具火控链。推荐让终端仍使用普通战术地图画布，但安装一个独立的地图工具上下文。

### 2.3 战术地图必须先做无载具安全化

当前 `RVP_TacticalMapScreen` 为 4,324 行，仍有 18 处直接读取 `LocalVehiclePlayer.instance`，其中多处没有判空。步行手持终端打开地图时，这些分支可能 NPE。

实施时应把地图数据源分为：

- 通用玩家/地图数据：始终可用；
- 载具雷达、当前武器、远程载具服务器实体缓存：仅存在有效 `LocalVehiclePlayer` 时可用；
- 终端工具数据：来自炮火支援客户端快照和任务状态。

不能仅新增一个构造参数和按钮就认为地图已经支持步行终端。

### 2.4 现有弹体生成器与载具绑定

`RVP_ProjectileSpawner.spawn(...)` 当前从 `vehicle.level()` 取世界，并在生成后处理后坐力相关的载具上下文。`RVP_ProjectileWeapon.shoot()` 还包含重装、剩余弹药、武器站锁定、后坐力、热量和载具物理等条件，这些都不属于远程炮火终端。

好消息是 `RVP_BaseBullet.initFromWeapon(...)` 已经把 `shooterVehicle` 与 `vehicle` 保存为可空引用，其大量碰撞、归属、子母弹和爆炸路径已有空值保护：

- 有玩家 owner 即可通过 `checkShooterValid()`；
- `initColdLaunch(null)`、`setWireLaunchUnit(null, ...)` 可以安全跳过载具挂架逻辑；
- `VehicleExplosion` 接受空的载具实体参数；
- 子母弹会继承父弹的可空 `shooterVehicle` 与玩家 owner。

仍须通过单元/集成测试完成一次“无载具弹体”专项审计，而不是仅依据当前空值检查推断全部武器都安全。

## 3. 建议的玩家体验

### 3.1 打开与失效

| 操作/状态 | 建议行为 |
| --- | --- |
| 主手或副手持终端，右键空气 | 打开战术地图并启用炮火支援侧栏 |
| 主手或副手持终端，按 K | 优先以终端上下文打开战术地图；不持有时保留当前普通/载具炮兵图行为 |
| 呼叫阶段切换手持槽、把终端移到背包 | 不取消已接受呼叫；绑定终端仍在玩家物品栏即可继续。新呼叫仍要求主手或副手持有终端 |
| 呼叫阶段玩家死亡、丢弃/转移绑定终端或断线 | 取消尚未进入打击阶段的呼叫，不生成任何炮弹；死亡即使开启 `keepInventory` 也取消 |
| 打击阶段玩家死亡、丢弃终端、换手或断线 | 任务继续，不取消余弹；任务面板保留状态，但未手持绑定终端时“停火”按钮禁用 |
| 所有者手持绑定终端并按“停火” | 服务端复核所有者及主/副手中的终端实例，随后登记请求；默认 80 Tick（4 秒）后停止尚未生成的炮弹，已生成弹体不删除 |
| 配置正在同步或 revision 过期 | 禁用“呼叫支援”，显示“配置已更新，请重新选择” |
| `/reload` 成功 | 原子替换 profile 快照，仅影响新请求；已接受任务继续使用创建时冻结的不可变配置和计划 |

“手持”用于打开工具、提交新请求和请求停火：玩家主手或副手当前 ItemStack 的 Item 必须是 `RVP_Items.FIRE_SUPPORT_TERMINAL`。服务端接受新呼叫时还要校验它解析出的 profile 与请求一致，并为该具体 ItemStack 生成、记录服务端权威的终端实例 UUID（例如 NBT `rvp_fire_support.terminal_instance`，物品堆叠上限为 1）；呼叫阶段按实例 UUID 搜索玩家物品栏，因此换手、换快捷栏槽或移入背包不算“丢弃”，实体丢出、放入容器、交给他人或以其他方式离开玩家物品栏才取消。若因管理员命令或复制产生重复实例 UUID，应拒绝新呼叫并记录诊断信息，不能任选其中一个。打击调度本身不再查询终端，但停火请求必须重新验证任务所有者主手或副手中的实例 UUID 与任务绑定值完全一致；仅有同类型的另一台终端或把对应终端放在背包中都不满足条件。

### 3.2 操作流程

1. 玩家打开终端战术地图。
2. 侧栏选择弹种。
3. 选择射击模式：急促射、效力射或监视射。
4. 选择打击模式预设：点状弹幕、条状弹幕或徐进弹幕。
5. 在地图左键指定中心/起点；条状与徐进弹幕可拖动方向手柄设置方位和长度。
6. 使用由 JSON 参数规格动态生成的滑条/数值框调整半径、宽度、长度、步长等“期望散布”。
7. UI 显示由当前配置推导的呼叫倒计时、总弹数、试射数、预计首发到达、任务持续时间和落区预览。
8. 点击“呼叫支援”，客户端发送一次请求。
9. 服务端重新解析实际手中终端、profile revision、弹种/模式/预设和全部数值；接受后绑定终端实例，冻结完整任务计划，并返回任务 ID、权威随机种子、规范化参数与起止 Tick。
10. 地图显示任务状态：`呼叫中 → 打击中（试射/校射间隔/主射）→ 完成`。打击阶段显示“停火”按钮；只有任务所有者主手或副手持有绑定终端实例时可按，服务端接受后显示默认 4 秒的“停火命令传达中”倒计时。

首版建议只支持地面坐标，不接受“直接锁定实体”。移动实体追踪、激光校射、队伍共享和观察员修正可作为后续独立能力，避免第一版同时引入目标权限和持续跟踪问题。

## 4. 领域模型与开闭原则

### 4.1 分层

```text
物品入口 / K 键
  → RVP_ClientActionsAccess（双端安全桥）
  → RVP_TacticalMapScreen（只拥有地图画布）
       └─ RVP_FireSupportMapTool（终端侧栏、预览、提交）
              ↓ C2S 只发送选择

服务端 C2S 处理器
  → RequestValidator + revision/限流/距离/参数/武器白名单校验
  → TerminalIdentity + CallGuard（仅呼叫阶段跟踪绑定终端与玩家状态）
  → SchedulePlanner（配置 → 不可变任务计划）
  → MissionManager（ServerTick 调度）
       ├─ PatternTypes：roundIndex → 计划落点
       ├─ SpawnChunkLease：确保入场区块可 Tick
       └─ DeliveryTypes：计划落点 → 真实 RVP 弹体
              ↓
       RVP_ProjectileSpawner（无载具 SpawnContext）
              ↓
       既有 RVP_BaseBullet / 引信 / 毁伤 / 子母弹 / 特效 / 渲染
```

### 4.2 核心扩展接口

建议接口只依赖公共 Minecraft/RVP 类型，不引用 `Minecraft`、`Screen`、`LocalPlayer` 等客户端类。

```java
public interface RVP_FireSupportPattern {
    ResourceLocation typeId();

    // 调用本项目弹幕几何实现：按权威种子、轮次和已校验参数生成本发计划落点。
    RVP_FireSupportImpactPoint resolve(RVP_FireSupportPatternContext context);
}

public interface RVP_FireSupportPatternFactory<T> {
    ResourceLocation typeId();

    // 调用本项目严格配置解析器：把类型专属 JSON 转换为不可变数据并校验参数规格。
    T parseAndValidate(JsonObject data, RVP_ConfigProblemCollector problems);

    RVP_FireSupportPattern create(T data);
}

public interface RVP_FireSupportDelivery {
    ResourceLocation typeId();

    // 调用本项目弹体投送器：把一发任务计划转换为实际实体；失败时不得吞掉任务状态。
    RVP_FireSupportDeliveryResult deliver(RVP_FireSupportDeliveryContext context);
}
```

注册表冻结规则：内建工厂在公共初始化阶段注册，注册重复 type ID 直接失败，初始化完成后冻结。JSON 只能引用已注册类型，不允许 Java 类名、反射、命令字符串或脚本。

### 4.3 为什么不为三种射击模式写 Java enum 分支

急促射、效力射、监视射都是“若干计时阶段”的组合。将名称硬编码成 `switch (RAPID/EFFECT/MONITOR)` 会导致以后新增“持续压制”“照明射”“烟幕遮蔽”时修改调度核心。

推荐让 JSON 声明阶段：

- 阶段开始延迟；
- 固定弹数，或基数倍率；
- 固定间隔，或在指定持续时间内均匀分配；
- 本阶段散布倍率；
- UI 阶段名称。

`RVP_FireSupportSchedulePlanner` 只解释通用阶段数据，不认识“急促射”字符串。

### 4.4 弹药基数与弹体模板的边界

每个弹种配置 `rounds_per_unit`，定义“一基数有多少发”。射击模式阶段用 `base_multiplier` 计算主射弹数：

```text
主射弹数 = ceil(rounds_per_unit × base_multiplier)
任务总弹数 = 各阶段固定弹数 + 各阶段主射弹数
```

统一使用向上取整，确保急促射的 1.5 基数不会少于配置意图。例如一基数 5 发，急促射为 `ceil(7.5)=8` 发。

被挂接武器 JSON 的 `fire_data.fire_mode`、`burst_count`、`burst_delay` 和 `canister_count` **不参与终端任务弹数与节奏计算**。一发任务炮弹对应一个顶层 RVP 弹体；需要子弹药效果时应使用武器的 `submunition_data`。这样可避免“任务基数 × 武器点射 × canister”不可控放大。

首版“弹药基数”是任务规模定义，不代表有一个实体炮兵库存；默认不会从玩家背包扣本体炮弹。以后如需后勤库存，增加 `RVP_FireSupportResourceProvider`（例如 unlimited、玩家物品、阵营库存）即可，不应把扣料逻辑写入 `MissionManager`。

## 5. 推荐 JSON schema

### 5.1 文件位置与加载原则

正式文件：

```text
limitless_vehicle/rvp/data/rvp/fire_support_profiles/default.json
```

资源 ID由 `fire_support_profiles/` 后的相对路径派生：上述文件为 `rvp:default`。只接受当前 `schema_version`，严格拒绝未知字段、重复 ID、非法资源 ID、非有限数值、越界参数和未知工厂类型；不写 `legacy*`、`migrate*` 或旧键别名。

服务端是玩法配置权威。`RVP_FireSupportProfileManager` 发布不可变 snapshot/revision，并在 `OnDatapackSyncEvent` 将规范化 profile 同步给客户端。请求携带客户端当前 revision，服务端遇到旧 revision 直接拒绝，避免 `/reload` 后按旧 UI 发射。

| 字段 | 类型/默认 | 语义 |
| --- | --- | --- |

| `translation_key` | 必填字符串 | UI 弹种名 |
| `weapon` | 必填资源 ID | 必须解析到 `RVP_WeaponData`，且类型可被所选 delivery 支持 |

### 5.6 fire mode 与 phase 字段

| 字段 | 类型/默认 | 语义 |
| --- | --- | --- |
| `id` | 必填小写标识 | 模式选择 ID；Java 调度器不按名称分支 |
| `translation_key` | 必填 | UI 模式名 |
| `call_duration_multiplier` | 正数，默认 `1.0` | 乘到 `call_stage.base_duration_ticks`；有效时长为 `ceil(base × multiplier)`，至少 1 Tick |
| `dispersion_multiplier` | 正数，默认 `1.0` | 乘到预设几何尺寸；急促射建议大于 1，效力/监视射相同 |
| `phases` | 1～16 项 | 按顺序执行；每个阶段至少一发 |
| `phase.start_delay_ticks` | 非负整数 | 首阶段相对“进入打击阶段”、后续阶段相对“上一阶段最后一发”的延迟 |
| `phase.rounds.base_multiplier` | 正数 | 与 `rounds_per_unit` 相乘；和 random/fixed 互斥 |
| `phase.rounds.rounding` | `ceil` | 首版只允许 `ceil`，避免配置作者产生不同理解 |
| `phase.rounds.random_min/max` | 正整数 | 权威 seed 在闭区间内选固定试射数；两者必须同时出现 |
| `phase.interval_ticks` | 正整数 | 相邻炮弹间隔；和 `duration_ticks` 互斥 |
| `phase.duration_ticks` | 非负整数 | 第一发到最后一发的时间跨度；和 `interval_ticks` 互斥 |

若阶段有 `N>1` 发并使用 `duration_ticks=D`，第 `i` 发偏移建议为：

```text
round(D × i / (N - 1)), i ∈ [0, N-1]
```

这保证第一发在阶段起点、最后一发准确落在阶段终点。`N=1` 时偏移为 0。

按示例配置：

| 模式 | 弹数 | 呼叫阶段 | 散布 | 主射持续 |
| --- | --- | --- | --- | --- |
| 急促射 | `ceil(1.5 × 基数)` | `800` Tick，即默认 40 秒，最快 | 预设尺寸 ×1.5，最大 | 60 Tick，短 |
| 效力射 | 先随机 2～3 发，再发 `ceil(2 × 基数)` | `ceil(800 × 1.5)=1200` Tick，即 60 秒，中等 | 预设尺寸 ×1.0，中等 | 180 Tick，中等 |
| 监视射 | 先随机 2～3 发，再发 `ceil(2 × 基数)` | `ceil(800 × 1.5)=1200` Tick，即 60 秒，中等 | 预设尺寸 ×1.0，中等 | 600 Tick，长 |

这里的呼叫阶段从服务端接受任务开始，到打击阶段可以开始生成第一发为止。真实命中还要加 `vertical_projectile` 从生成高度飞到地面的时间；UI 应同时显示“呼叫完成/首发入场”和估算“首发命中”，不能把两者混写成绝对保证。默认基准是 40 秒，示例用数据化倍率保持“急促射最快、效力射与监视射中等”的原始要求；服主可直接调整基准或各模式倍率。

### 5.7 三种打击预设的准确语义

所有尺寸是服务端硬边界内的“计划落区尺寸”，不是额外叠加武器 `fire_data.spread`。

| 预设 | 锚点/方向 | 参数 | 采样语义 |
| --- | --- | --- | --- |
| 点状弹幕 | 中心点 | `radius_m` | 在半径内按面积均匀采样，`r = radius × sqrt(U)` |
| 条状弹幕 | 中心点 + 方位 | `length_m`、`width_m` | 在以方位为长轴的矩形内均匀采样 |
| 徐进弹幕 | 起点 + 前进方位 | `length_m`、`width_m`、`step_m` | 中心线按步长向前推进；roundIndex 单调映射到步号，同一步内横向散布 |

射击模式的 `dispersion_multiplier` 同时乘到这些尺寸，再按服务器 profile 最大值截断。急促射因此天然比另外两种更散；效力射和监视射可以保持相同中等散布。

徐进弹幕的顺序必须由 `roundIndex` 决定，不能为每发独立随机一个纵向位置，否则视觉上不会“徐进”。若总弹数少于步数，均匀跳过部分步；若总弹数多于步数，则每一步分配若干发，仍按起点到终点单调推进。

## 6. 服务端任务生命周期

### 6.1 状态机

```text
REQUESTED
  → VALIDATING
      ├─ REJECTED
      └─ CALLING（默认 40 秒；冻结任务配置与计划）
           ├─ 玩家死亡/绑定终端离开物品栏/断线 → CANCELLED
           └─ 呼叫截止 Tick 到达（原子转换） → STRIKING(phase 0..n)
                ├─ 正常投送 → COMPLETED
                ├─ 所有者手持绑定终端并按停火 → CEASE_FIRE_PENDING
                │                    ├─ 默认 4 秒内继续按原计划投送
                │                    └─ 到期 → CEASED（截断未生成炮弹）
                └─ 不可恢复的技术错误 → FAILED
```

任务内保存：任务 UUID、玩家 UUID、绑定终端实例 UUID、维度、profile ID/revision、冻结后的 profile/munition/delivery 数据、munition/mode/pattern ID、规范化参数、目标 X/Z、方位、权威 seed、接受 Tick、呼叫截止 Tick、当前阶段/弹序号、下一发 Tick、可空的停火生效 Tick和累计失败数。任务不得缓存 `ItemStack` 或 `Player` 的可变引用。

`CALLING → STRIKING` 是在呼叫截止 Tick 发生的不可逆原子状态转换，不得因 Chunk 尚未就绪而延长“可被死亡/丢弃取消”的窗口。生成前预加载应尽量在呼叫阶段末段完成；若截止时首发 Chunk 仍未达到 entity-ticking，任务仍先进入 `STRIKING`，再按受限等待/超时策略处理投送。进入后，玩家死亡、终端丢失、换手、离线及 `/reload` 都不得把任务转回呼叫阶段或取消余弹。

停火请求只允许任务所有者针对处于 `STRIKING`/`CEASE_FIRE_PENDING` 的任务发送，并且请求处理时任务所有者必须在 `holder_policy.allowed_hands` 指定的手中持有实例 UUID 与任务绑定值完全一致的终端。服务端主线程处理首次有效请求时记录 `ceaseFireEffectiveTick = serverHandledTick + cease_fire_delay_ticks`；重复请求幂等并保留最早生效 Tick，不能借重复点击推迟或提前。当 `gameTime >= ceaseFireEffectiveTick` 时，调度器必须先执行截断判断、再执行同 Tick的投送；凡尚未通过 `level.addFreshEntity(projectile)` 成功加入世界的计划弹均标记为 `CEASED`，已经加入世界的弹体不回收、不失效。终端只在停火请求这一瞬间校验：请求一经接受，随后换手、丢弃终端或死亡都不撤销已经开始的 4 秒停火倒计时。

`/reload` 仅原子发布供新请求使用的新 snapshot/revision。已经接受的 `CALLING` 和 `STRIKING` 任务持有完整不可变计划及其所需配置副本，不因旧 revision 或武器引用在新快照中变化而中断；这是保证“打击阶段不可被配置重载打断”的必要条件。

首版任务可只保存在内存中：现有 RVP 弹体注册为 `noSave()`，服务器重启本就不会保留在飞弹体；重启后取消未完成炮火比“恢复任务但丢失已发炮弹”更一致。将来需要跨重启恢复时，再把任务和弹体持久化作为同一项完整设计，不能只保存一半。

服务器停止、进程崩溃、维度卸载失败或投送器连续不可恢复异常属于技术边界，不视为玩家可触发的“打断”；首版内存任务无法承诺跨重启继续执行。应把这类结束状态记录为 `FAILED` 或随进程终止，并与玩家死亡/丢弃终端/停火的玩法语义分开统计。

### 6.2 每 Tick 执行顺序

1. `ServerTickEvent.END` 遍历任务；`CALLING` 任务先由 `RVP_FireSupportCallGuard` 检查玩家存活/在线以及绑定终端实例仍在其物品栏，否则取消。
2. 呼叫截止 Tick 到达时无条件将玩法状态原子切换为 `STRIKING`；从此打击调度不再读取玩家生命、在线状态、手中或物品栏中的终端，也不比较当前 profile revision。只有独立的停火请求处理器会即时读取任务所有者和主/副手中的绑定终端。Chunk/投送准备不足只能延迟首发或最终形成技术失败，不能继续套用呼叫阶段取消规则。
3. 对处于 `STRIKING`/`CEASE_FIRE_PENDING` 且到期的任务，先判断停火生效 Tick；若已到达则把所有未生成计划弹截断并结束任务。
4. 使用全局每 Tick 发射预算做公平轮转，由 pattern 按冻结 seed、全局 roundIndex、总弹数和权威参数生成计划 X/Z。
5. 检查世界边界；服务端加载目标 Chunk 后用 `MOTION_BLOCKING_NO_LEAVES` 或明确约定的 Heightmap 重新计算地面 Y，不信任客户端 Y。
6. 入场 Chunk 未处于 entity-ticking 时提交短期 Ticket并推迟本发，不同步生成区块中的实体；推迟期间仍持续检查停火生效 Tick。
7. 调用冻结的 delivery 配置生成一发真实弹体；只有 `level.addFreshEntity(projectile)` 成功才推进 roundIndex，并以这一成功点作为“已经生成”的唯一判据。
8. 成功后调用现有 `projectile.primeDynamicChunkPath()`，把后续飞行交回现有路径管理器。
9. 仅在状态变化、阶段变化、停火请求/生效、失败或完成时发送 S2C；倒计时由客户端根据服务器 Tick本地推进，不每 Tick 发包。

### 6.3 任务时间与 TPS

调度使用 `serverLevel.getGameTime()`，不使用 `System.currentTimeMillis()`。TPS 降低时炮火节奏随游戏 Tick变慢，可避免低 TPS 下为追赶墙钟时间同 Tick爆发大量实体。

设置不可配置的全局 `MAX_SPAWNS_PER_TICK`（建议 8～16）。多个任务同 Tick到期时轮转，每发可延后但不可丢失；S2C 状态显示“调度拥塞”。服务器恢复后也不得在一 Tick补齐全部逾期炮弹。

### 6.4 幂等与重复包

`C2SRequestFireSupport` 带客户端随机 nonce。服务端按玩家短期缓存最近 nonce：

- 同 nonce、同内容：返回原任务结果，不创建第二个任务；
- 同 nonce、不同内容：拒绝并记录警告；
- nonce 缓存有数量和过期上限。

## 7. 挂接 RVP 武器的实现

### 7.1 武器解析

服务端通过：

```java
CommonAssetsManager.vehicleWeaponManager().getIndex(weaponId)
```

解析配置引用，并要求：

1. 索引存在；
2. `index.data()` 是 `RVP_WeaponData`；
3. `weaponKind` 被 delivery 支持；
4. 武器不依赖该 delivery 无法提供的实时载具/武器站状态；
5. 估算生命期、子弹药最大展开数和毁伤配置不超过服务端绝对预算。

不允许在实体、投送器或渲染器里写 `weaponId.getPath().equals("...")`。弹种差异来自 profile 引用和既有武器 JSON 数据。

### 7.2 泛化 ProjectileSpawner

建议新增不可变上下文：

```java
public record RVP_ProjectileSpawnContext(
        ServerLevel level,
        RVP_WeaponData weaponData,
        RVP_EnumWeaponKind weaponKind,
        @Nullable AbstractVehicle sourceVehicle,
        @Nullable WeaponUnit sourceWeaponUnit,
        LivingEntity owner,
        Vec3 spawnPosition,
        RVP_BaseBullet.AimRot aim,
        Vec3 initialMotion,
        @Nullable Entity lockTarget,
        @Nullable Vec3 designatedTarget,
        boolean inheritVehicleVelocity
) {}
```

现有载具武器的所有 `spawn(...)` 重载继续保留，由它们构造 context 后调用新核心方法；炮火投送器构造 `sourceVehicle=null`、`sourceWeaponUnit=null` 的 context。这样现有调用点无须大面积改写。

同时把 `RVP_ProjectileSpawner` 私有的 kind→实体构造逻辑集中为一个公共项目内工厂，供子母弹和炮火共用，消除当前 `RVP_ProjectileSpawner` 与 `RVP_SubmunitionSpawner` 的重复映射。

### 7.3 垂直入场 delivery

`rvp:vertical_projectile` 的执行：

1. pattern 产生计划落点 X/Z；
2. 服务端加载并读取该 X/Z 的权威地表 Y；
3. 生成点为 `(x, groundY + spawn_height_above_impact_m, z)`；
4. 初始方向为向下，`entry_speed_m_per_tick` 未配置时使用武器 `resolveMuzzleSpeed(kind)`；
5. owner 为发起玩家，使既有伤害来源、击杀归属和命中提示尽量保持一致；sourceVehicle/sourceWeaponUnit 为空；
6. 不调用载具后坐力、弹仓、热量、锁定、GPS 消耗或武器站可编程引信存储；
7. 成功入世后调用 `primeDynamicChunkPath()`。

初版建议只承诺非制导弹道弹、火箭、炸弹和布撒弹。武器本身的风、阻力、重力和推进仍会改变实际命中，因此地图预览是“计划落区”，不是像载具逆 CCIP 那样的精确命中承诺。

### 7.4 为什么不直接调用爆炸/效果

直接在到期 Tick调用 `RVP_DetonateApplier` 或 `VehicleExplosion` 虽然简单，但会绕过：

- 弹体飞行与来袭表现；
- 方块/实体碰撞；
- 引信；
- 子母弹；
- 弹体拦截；
- 类型化渲染与飞行音效；
- 部分命中归属和调试链。

它可以以后作为新的 `rvp:instant_effect` delivery 明确实现，但不应成为默认炮火。

## 8. 战术地图接入

### 8.1 不增加第三个 MapMode

`MapMode.ARTILLERY` 已经代表“载具炮兵火控和输入透传”。终端不应新增 `MapMode.FIRE_SUPPORT` 后继续在 4,324 行 Screen 中堆大量 `if`。

推荐新增：

```java
public interface RVP_TacticalMapTool {
    ResourceLocation id();
    void initialize(RVP_TacticalMapHost host);
    void tick(RVP_TacticalMapHost host);
    boolean mouseClicked(RVP_TacticalMapHost host, double x, double y, int button);
    void renderOverlay(RVP_TacticalMapHost host, GuiGraphics graphics, int mouseX, int mouseY, float partialTick);
    void onClose();
}
```

接口本身属于客户端包，因为含 `GuiGraphics`；公共 Item 只通过 `RVP_ClientActionsAccess.openTacticalMap(openRequest)` 请求客户端安装某个工具 ID。服务端公共代码绝不能直接引用该接口。

首版 Screen 构造器可接收一个可空 tool；以后如果同屏需要多个能力，再演进为按优先级的工具列表。原无参和 `MapMode` 构造器继续保留，避免影响现有调用者。

### 8.2 FireSupportMapTool 职责

- 按当前服务端 profile snapshot 构建弹种、射击模式和预设选择器；
- 根据 pattern 工厂暴露的参数规格动态生成数值控件，不为 `radius_m/length_m/width_m/step_m` 分别硬编码整套 UI；
- 管理本次客户端草稿：锚点、方向、参数和选择；
- 绘制点圆、条状矩形、徐进箭头/步线；
- 计算非权威弹数和 ETA 预览；
- 发送一次 C2S 请求；
- 接收权威任务状态后显示呼叫倒计时、任务边界、阶段、余弹与停火状态；
- 请求尚未接受时，玩家不再手持终端则禁止提交；进入呼叫阶段后，即使换手或把绑定终端移入背包也保留状态面板；
- 进入打击阶段后保留任务状态和“停火”按钮；只有任务所有者当前主手或副手持有绑定终端实例时按钮可用，否则置灰并提示“需手持本任务终端”；
- 客户端点击停火后仍等待服务端复核；接受后显示“停火命令传达中”及服务端权威生效 Tick，拒绝则展示具体原因；
- 客户端不根据物品状态自行取消任务，所有生命周期转换都等待服务端状态包。

地图画布继续负责坐标变换、缩放、拖动和地图裁剪；工具不要复制这些实现。

### 8.3 输入建议

- 左键空白地图：设置锚点；
- 左键拖动方向手柄：设置条状/徐进方位与长度；
- 右键或中键拖动：平移地图，保留现有手感；
- 鼠标滚轮：缩放；
- 侧栏滑条/数值框：精确调整 JSON 允许的参数；
- “确认呼叫”必须是显式按钮，不能像当前炮兵图悬停那样持续改变并立即执行。

终端上下文不允许车辆输入透传，也不调用 `RVP_ArtilleryFireControlState`。

## 9. 网络协议

### 9.1 建议新增消息

| 消息 | 方向 | 内容 |
| --- | --- | --- |
| `S2CFireSupportProfileSnapshot` | S2C | revision、摘要、规范化 profile；登录和成功 reload 发送 |
| `C2SRequestFireSupport` | C2S | revision、hand、munition/mode/pattern ID、目标 X/Z、方位、参数 Map、nonce |
| `S2CFireSupportRequestResult` | S2C | nonce、接受/拒绝原因、任务 UUID、权威 seed、规范化参数、呼叫截止 Tick、首/末计划 Tick |
| `S2CFireSupportMissionUpdate` | S2C | `CALLING/STRIKING/CEASE_FIRE_PENDING` 等阶段、已发/总数、下一发 Tick、停火生效 Tick、完成/取消/失败原因 |
| `C2SRequestFireSupportCeaseFire` | C2S | 任务 UUID与 nonce；校验 sender 是任务所有者、任务已进入打击阶段，并且主/副手持有任务绑定的同一终端实例 |

新增消息后升级 `RVP_Network.PROTOCOL`。所有集合、字符串、压缩块和动态参数必须使用显式上限；客户端端消息通过公共 endpoint/桥转发到客户端状态，公共网络类不直接 import 客户端 Screen。

### 9.2 服务端校验顺序

1. sender 存在，包字段可解码且数值全部有限；
2. nonce、字符串长度、集合数和参数数在协议绝对上限内；
3. 请求 revision 等于当前服务端 profile revision；
4. 请求 hand 当前仍持匹配的炮火支援终端；
5. 从实际 ItemStack 解析 profile，不信任客户端传 profile ID；
6. munition/mode/pattern ID存在于该 profile；
7. 武器引用仍解析为允许的 `RVP_WeaponData`；
8. 玩家维度允许，目标 X/Z 在世界边界内，水平距离在 profile 范围内；
9. 动态参数键集合准确匹配 pattern 规格，逐项按 min/max/step 规范化；不接受多余键；
10. 重新计算弹数、阶段 Tick、总持续时间、有效散布尺寸和最坏实体预算；
11. 检查玩家/全局并行任务、请求冷却、Chunk 预算和全局发射预算；
12. 为实际手中 ItemStack 创建/读取终端实例 UUID，建立包含完整配置副本的不可变计划并进入 `CALLING`，返回权威结果。

客户端提交的 Y、总弹数、ETA、有效散布、任务 UUID或随机 seed 一律不采信。

停火包走独立的最小校验链：字段/nonce 有界 → 根据任务 UUID 查找活动任务 → sender UUID 必须等于任务所有者 → 状态必须是 `STRIKING` 或 `CEASE_FIRE_PENDING` → sender 的主手或副手必须持有终端，且其实例 UUID 等于任务绑定 UUID → 首次请求写入权威生效 Tick并广播。不能只检查 Item 类型或 profile，也不能相信客户端声称的 hand/实例 ID；必须直接读取服务器上的两只手。可复用 `RVP_FireSupportTerminalIdentity.matchesBoundTerminalInAllowedHand(...)` 这一纯校验方法，但不能复用会检查当前 revision、目标和冷却的新呼叫验证全链。

### 9.3 状态同步范围

首版只把任务详情发给任务发起玩家。将来需要队伍共享时增加 `RVP_FireSupportAudienceResolver`，根据 scoreboard team/阵营决定观察者；不要直接向全服广播详细目标坐标，以免产生信息泄漏。

## 10. 区块加载、性能与滥用防护

### 10.1 生成前与生成后的两个阶段

现有 `RVP_ChunkPathLoadManager` 接受一个已经存在的 Entity，因此无法为“尚未生成的远程炮弹”预加载入场 Chunk。

新增 `RVP_FireSupportSpawnChunkLeaseManager`：

- 只为未来 `preload_ticks` 窗口内即将发射的落点 Chunk申请短期 `TicketType.POST_TELEPORT`；
- 相同任务、相同 Chunk去重；
- 每 Tick新增 Ticket有全局预算；
- Chunk达到 entity-ticking 后才允许生成；
- 任务完成/取消后停止刷新，Ticket自然过期；
- 不使用永久 force chunk，不遍历或同步加载目标周围大范围区块。

弹体成功生成后继续使用现有 `primeDynamicChunkPath()`，不另建第二套飞行路径系统。

### 10.2 预算建议

除 profile 可调限制外，再设硬上限：

- 每 Tick新生成炮火弹体不超过 8～16；
- 每 Tick新增炮火预加载 Chunk不超过 16～32；
- 单任务最多 512 逻辑弹、8～16 个同时预加载 Chunk；
- 全局任务最多 64；
- 单玩家默认 1 个活动任务；
- 单任务连续 Chunk等待超时建议 200 Tick；
- 单发 delivery 失败最多重试 3 次，且重试不突破每 Tick预算。

武器若有子母弹，profile 验证还应估算其最大实体展开数；仅限制顶层炮弹数量不足以保护服务器。

### 10.3 归属与友伤

真实弹体 owner 设为发起玩家，因此伤害归属沿用当前 RVP/本体机制。首版不额外实现“禁止打友军”，因为不同服务器阵营语义不统一；如需要，后续在任务接受前增加可插拔 `RVP_FireSupportAuthorizationPolicy`。不要在爆炸阶段临时过滤队友，那会让不同毁伤类型产生不一致。

## 13. 验收矩阵

### 13.1 功能

- 主手与副手右键均可打开，背包中但未手持不可用；
- K 键持终端进入终端上下文，不持有时保持当前行为；
- 呼叫阶段基准 40 秒可由 JSON 调整，切换手/槽位或移入背包不取消，死亡或绑定终端离开物品栏则取消；
- 每个 JSON 弹种均显示正确基数和武器名；
- 急促射为 1.5 基数、最快/最散/最短；
- 效力射先 2～3 发试射，间隔后 2 基数，中等持续；
- 监视射先 2～3 发试射，间隔后 2 基数，长持续；
- 点、条、徐进三种模式参数可调，服务端实际落区与权威预览一致；
- 真实 RVP 弹体的模型、纹理、音效、引信、毁伤、子母弹和视觉正常；
- 进入打击阶段后死亡、丢弃终端、换手、断线和 `/reload` 都不影响剩余投送；
- “停火”只在任务所有者主手或副手持有该任务绑定的同一终端实例时可用；其他终端或仅放在背包中均不可用；
- 服务端接受“停火”后 4 秒内仍按计划投送，到期后仅尚未生成的炮弹停止投送，已发弹体继续飞行；停火接受后再丢弃终端不撤销倒计时。

### 13.2 安全

- 未持终端伪造 C2S；
- 请求 hand 与实际手不一致；
- 新呼叫时把终端移入背包后继续伪造请求；
- 呼叫阶段伪造/复制终端实例 UUID，或把绑定终端放入容器后继续呼叫；
- 非所有者停火、呼叫阶段提前停火、未手持/只在背包持有绑定终端、手持另一台终端、重复停火包与篡改任务 UUID；
- profile/mode/munition/pattern 不存在；
- `/reload` 后提交旧 revision；
- NaN、Infinity、超长字符串、超大 Map、未知参数和负数；
- 超世界边界、跨维度、超距；
- 重复 nonce、同 nonce 改内容；
- 单玩家/全局并行任务、弹数、持续时间和 Chunk 预算超限。

### 13.3 回归

- 原 K 键普通战术图/载具炮兵图分流；
- 原 GPS 单点/多点和快速标记；
- 原雷达列表、双击锁定与快捷发射；
- `RVP_ArtilleryFireControlState` 偏航优先门控；
- 所有现有 RVP 武器从载具正常发射；
- RVP 弹体使用类型化 renderer，不回退注册本体 `BulletEntityRenderer`；
- 专服启动不加载客户端 Screen、Minecraft 或渲染类型。

## 14. 明确不采用的方案

### 14.1 新建或复制一套炮火地图 Screen

会复制地图缓存、缩放、坐标换算和标记渲染，后续两套 UI 必然漂移。使用 map tool 组合即可。

### 14.2 把终端塞进现有 `ARTILLERY` 模式

现有模式与 `LocalVehiclePlayer`、武器站、逆 CCIP、载具输入透传和空格射击强绑定。终端没有这些前提，强行复用会制造大量空值分支和输入冲突。

### 14.3 伪造载具或 WeaponUnit

`RVP_ProjectileWeapon` 的重装、弹药、锁定、后坐力和热量都依赖真实载具结构。伪对象难以满足不变量，且可能把错误引用写进弹体。应该泛化弹体生成上下文。

### 14.4 直接调用爆炸作为默认投送

会绕过真实弹体的大量既有行为。只能以后作为显式新 delivery。

### 14.5 在 Java 按弹种 ID分支

违反项目规则，也阻塞数据包扩展。Java 只按类型化 profile、weapon kind、pattern type 和 delivery type 工作。

### 14.6 新增 Mixin

本功能可由 Item 覆写、现有客户端桥、Screen 组合、Forge reload/网络/Tick事件和独立服务实现。已有替代路径充分，不满足新增 Mixin 的必要性条件。

### 14.7 修改载具结构模型

终端是普通物品，炮火来自独立弹体投送，不需要修改任何 `data/rvp/models/bedrock/vehicle/*.structure.json`。本文不请求结构模型变更授权。

## 15. 最终建议

按“数据与纯逻辑 → 无载具弹体 → 权威任务 → 地图工具”的顺序实施。最先做的技术探针不是 UI，而是：

1. 选一个真实 RVP 炮弹武器 JSON；
2. 用 `sourceVehicle=null`、玩家 owner 在已加载 Chunk生成一发；
3. 验证完整飞行、碰撞、爆炸、归属和子母弹；
4. 再固化 `RVP_ProjectileSpawnContext`。

只要这个探针通过，三种射击模式和三种弹幕就主要是可测试的调度/几何问题；若探针发现某些弹体仍隐式依赖载具，应修正通用空载具契约或把该武器标为该 delivery 不支持，而不是回退到假载具或 Mixin。

近期用静态注册终端可最快闭环，领域接口又与未来“配置化 Item”平台解耦。未来平台实现后，增加一个 `rvp:fire_support` 能力处理器引用同一 `fire_support_profile`，即可把炮火支援挂到其他终端定义或组合更多能力，而任务、网络、落区和弹体投送层无需改写。
