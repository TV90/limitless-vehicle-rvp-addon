# RVP 炮火支援技术文档与调参指南

> 适用基线：Minecraft 1.20.1 Forge，`limitless-vehicle-rvp-addon` 当前实现（2026-09-10）
> 运行时配置client_1：[default.json](../../../run/client_1/limitless_vehicle/rvp/data/rvp/fire_support_profiles/default.json)
> 运行时配置server：[default.json](../../../run/server/limitless_vehicle/rvp/data/rvp/fire_support_profiles/default.json)
> JSON Schema：[fire_support_profile.schema.json](../../schemas/fire_support/fire_support_profile.schema.json)
> 完整示例：[default.json](../../examples/fire_support_profiles/default.json)

本文以当前 Java、正式载具包 JSON 和测试为准，说明 RVP 炮火支援终端的运行链、`fire_support_profiles` 全部字段、数据驱动终端 ItemStack 变体、与 `weapons` 的联动边界及调参方法。历史方案文档只用于理解设计背景；若历史描述与本文不同，以当前代码为准。

## 1. 功能边界

炮火支援终端把“真实 RVP 武器弹体”组织成远程、服务端权威的打击任务：玩家在战术地图选择弹药方案、打击模式、落区、目标 X/Z 和方向，服务端重新校验并生成确定性时间表和武器序列，随后从每个计划落点上方投送真实 RVP 弹体。一个弹药方案既可只有一种武器，也可按权重混合多种武器。

系统刻意分成两类数据：

- `data/<namespace>/fire_support_profiles/*.json` 决定谁能呼叫、呼叫多久、多少发、何时发、落区几何、投送高度、并发和区块预算。
- `data/<namespace>/weapons/*.json` 决定每枚弹体是什么、如何运动、制导、碰撞、触发引信、爆炸、播放特效以及是否释放子弹药。

炮火支援不借用载具 `ARTILLERY` 模式，不创建假武器站，也不在 Java 中按武器 ID 分支。空中投送会按 profile 的 `aircraft_id` 生成真实本体载具。内建三种落区 `rvp:point`、`rvp:line`、`rvp:creeping`，以及垂直、固定地射、实体飞机空中投送三种方式。

每个已发布 profile 还会根据 `item.translation_key` 自动生成一个终端 ItemStack 变体。所有变体共用注册表物品 `ywzj_rvp:fire_support_terminal`，profile ID 写入 `rvp_fire_support.profile_id`；因此新增 profile 不需要修改 Java 物品注册表。客户端收到新快照后会重建创造栏内容。

profile 可通过 `call_stage.consume_terminal_on_completion` 配置终端消耗。开启后，任务进入 `COMPLETED` 或停火生效后的 `CEASED` 时，服务端按任务冻结的 `terminal_instance` 和 `profile_id` 精确删除绑定终端；不会删除同 profile 的其他终端。取消、失败、死亡、断线取消和终端丢失均不消耗。删除保护覆盖在线玩家库存、已加载掉落实体，以及任务结束后重新加载、拾取或登录时出现的同一实例；保护记录仅保留当前服务器会话。

## 2. 从资源加载到落弹的技术链

### 2.1 加载与热重载

`RVP_FireSupportProfileManager` 扫描所有载具包中的：

```text
data/<namespace>/fire_support_profiles/<path>.json
```

文件资源 ID 为 `<namespace>:<path>`。例如 `data/rvp/fire_support_profiles/default.json` 发布为 `rvp:default`。

加载过程为：

1. 资源监听器先收集本轮全部候选 JSON。
2. 等本体武器索引完成后，严格解析当前 schema，并通过实际武器索引解析每个 `munitions[].weapons[].weapon`。
3. 任一候选有未知字段、非法值、重复 ID、失效武器引用或超预算，整批拒绝。
4. 整批成功后原子发布不可变快照，并把 `revision` 加一；失败时继续使用旧快照。
5. 新快照同步给客户端。旧 revision 的呼叫请求会被拒绝，客户端需使用新快照重新提交。

只接受 `schema_version: 3`，不迁移旧版 JSON，也不接受旧键别名。v1 中位于 munition 顶层的 `weapon`、`delivery` 已删除，必须手工改写为 `weapons[]`。v3 用 `item.translation_key` 描述 profile 生成的终端 ItemStack 名称，移除 `holder_policy.required_item`。

### 2.2 请求校验

客户端预览和弹数估算不具权威性。收到呼叫请求后，服务端依次复核：

- 包结构、选择 ID、有限数、参数数量和 nonce；
- profile revision；
- 请求手中是否持有通用炮火终端、ItemStack 的 profile ID 是否与请求 profile 一致，以及该手是否在 `allowed_hands`；
- 终端实例 UUID 是否唯一且确实归该玩家所有；
- profile、弹药方案、打击模式和落区是否存在；
- 目标是否位于世界边界、坐标硬边界和 profile 水平距离范围内；
- 动态参数键是否与预设完全相等，数值是否在范围内且与步长对齐；
- 权威随机种子生成的弹数、呼叫时长和每发 Tick 是否满足任务上限；
- 玩家/全服并发数和请求冷却；
- 弹药方案的全部 `weapons[].weapon` 是否仍能从本体索引解析为 `RVP_WeaponData`，各自投送工厂是否可创建。

请求内容通过后才冻结为任务。相同 nonce 会返回稳定结果；用同一 nonce 篡改内容不会创建第二个任务。

### 2.3 任务状态机

任务主要状态为：

```text
CALLING -> STRIKING -> COMPLETED
   |          |
   |          +-> CEASE_FIRE_PENDING -> CEASED
   +-> CANCELLED
任意投送硬失败 -> FAILED
```

- `CALLING`：检查玩家死亡、断线策略和绑定终端是否仍在玩家物品栏。换手、换快捷栏或移入背包不算丢失；移入容器、丢弃或唯一性破坏会取消。
- `STRIKING`：任务与玩家生存、在线状态、持有终端和 `/reload` 解耦，使用接受时冻结的数据继续执行。
- 空中支援机路径或实体短暂不可用时，界面显示恢复倒计时并冻结当前任务阶段；同 UUID 飞机在 200 Tick 内恢复后，呼叫、投放、停火及出场时间整体顺延。恢复超时以 `AIRCRAFT_LOST` 失败，不会误报为被击落，也不会生成替代飞机。
- 呼叫阶段请求中止会立即 `CANCELLED`；打击阶段请求停火会进入 `CEASE_FIRE_PENDING`，到 `cease_fire_delay_ticks` 后停止尚未生成的弹，已生成弹体不会删除。
- 停火只能由任务所有者在主手或副手持有任务绑定的同一终端实例时请求。
- 玩家离线或死亡后若任务仍在打击阶段，系统用同 UUID 的 Forge 假玩家维持伤害归属，不伪造载具。

### 2.4 公平调度、区块租约与生成

任务管理器每个服务器 Tick 轮转活动任务，最多成功生成 8 枚顶层炮火弹体；同一任务在一次 Tick 遍历中最多尝试当前一发，因此并发任务不会被单个密集任务完全饿死。低 TPS 只会延后游戏 Tick，不按墙钟追赶补发。

每发的执行顺序为：

1. 用阶段内弹序号和冻结权重选择本发武器；失败重试保持同一成员，不重新轮转。
2. 用任务 seed、全局弹序号、锚点、方向、落区参数和模式散布倍率计算权威 X/Z。
3. 为落点 Chunk 请求短期租约；每 Tick 最多新增 24 个 Ticket，同任务同 Chunk 复用。
4. Chunk 达到 entity-ticking 后读取 `MOTION_BLOCKING_NO_LEAVES` 高度图。
5. 使用该武器成员自己的投送参数，在地面上方生成真实 RVP 弹体；空间不足时钳制到世界构建顶端内侧。
6. 调用通用 `RVP_ProjectileSpawner`。三个载具/武器站来源均为空，owner 为玩家或对应假玩家。
7. 弹体生成成功后沿用既有动态飞行路径加载、实体生命周期、碰撞、引信、爆炸和子弹药链。

区块等待超过计划 Tick 后 1200 Tick 会失败。普通生成失败连续 20 次才使任务失败；等待区块不计入这 20 次。所有终态都会释放任务租约。

注意：当前任务循环只在 `now >= nextSpawnTick` 时调用投送，因此 `preload_ticks` 虽被传给租约管理器，任务管理器不会提前于该发计划 Tick 主动调用投送。它当前主要定义租约 API 的允许窗口，并未实现“提前 N Tick 主动申请 Ticket”的效果；调大它不能消除首次远程 Chunk 等待。

## 3. 与 `weapons` JSON 的联动

### 3.1 引用和准入

`munitions[].weapons[].weapon` 必须是本体权威武器索引里真实存在的 `RVP_WeaponData` 资源 ID。同一弹药方案不得重复引用同一武器，不能引用普通本体武器并靠路径名伪装，也不能省略命名空间。

`rvp:vertical_projectile` 会拒绝不产生实体弹体的 `LASER`、`TARGETING_POD`，运行时还要求 `RVP_ProjectileEntityFactory` 支持该武器 kind。HITL、操作手制导或 HITL CLOS TV 武器不会仅因制导方式被 profile 解析器拒绝，但炮火生成上下文没有武器站、锁定目标或持续客户端输入；这类武器只能按其无持续操作输入时的实际行为运行，配置作者必须实测，不能把“可加载”理解为“制导能力完整可用”。

### 3.2 profile 不会覆盖的武器行为

投送生成的是计划弹所选成员的真实弹体，因此下列 `weapons` 数据继续生效：

| `weapons` 区域 | 炮火投送中的作用 |
| --- | --- |
| 顶层 `type` / 解析后的 weapon kind | 决定具体 RVP 弹体实体类型与能力。 |
| `projectile_data`、重力、阻力、发动机、生命期 | 决定生成后的运动与存活；但初始速度见下节。 |
| `fuse_data` | 决定触地、延时、近炸、寿命终点等引信行为。 |
| `collision_data` | 决定直击伤害、穿透/碰撞等行为。 |
| `detonate_data` | 决定主爆炸、方块破坏和其他落点效果。 |
| `effects_data` | 决定轨迹、爆炸及其他视觉/声音效果。 |
| `guidance_data` | 实体仍会读取；但炮火上下文不提供载具锁定或持续操作输入。 |
| `submunition_data` | 按武器自身触发条件释放；其直接展开量参与 profile 发布预算审计。 |
| `misc_data` | 仍由真实弹体按既有语义使用。 |

### 3.3 profile 会取代或绕过的武器开火语义

炮火直接调用弹体生成核心，不经过载具武器开火、装填和弹药消耗链，因此这些字段不决定炮火任务节奏或数量：

- `shoot_interval`、`fire_data.fire_mode`、`burst_count`、`charge`、机炮预热等；
- `max_capacity`、`reload`、弹药物品；
- 后坐力、武器站俯仰/偏航限制、载具热量；
- `fire_data.spread` 或武器自身开火散布；炮火落点散布由 pattern 与 `dispersion_multiplier` 决定；
- `fire_data.canister_count` 不会扩增任务顶层弹数。若武器本身会生成额外实体，应由真实弹体/子弹药数据表达并接受预算审计。

任务顶层弹数只由 `rounds_per_unit` 和所选 `phases[].rounds` 计算；`weapons[].weight` 只分配武器类型，不增加弹数。

### 3.4 初速度、方向和载具继承

- `entry_speed_m_per_tick > 0`：直接用该值作为生成瞬间速度大小。
- `entry_speed_m_per_tick = 0`：调用武器按 kind 解析出的初速。
- 若武器解析初速非正，沿用 RVP 统一的最小初速 `0.01 格/Tick`；投送层不再引入另一套最小值。
- 初始方向默认竖直向下；`heading_jitter_deg` 在向下半球的圆锥内产生按面积均匀的随机倾斜，名字中的 `heading` 不表示围绕任务方位角固定偏转。
- 炮火明确传入绝对初始 motion 且没有来源载具，因此 `inherit_vehicle_velocity` 不会给弹体叠加载具速度。
- 生成后的速度上限、重力、阻力、推进、转向、引信和碰撞仍由武器数据控制。

空射和地射的 GPS 实体弹会把每发 pattern 解析出的落点作为固定目标；目标 Y 为该落点的地表高度，不读取玩家 GPS 队列。GPS 主制导或 `terminal_guidance` 任一阶段包含 GPS 即满足定点能力。GPS 地射仍可先尝试普通弹道解算并在无解时竖直兜底；GPS 空射则不使用无制导弹道反解，而是在目标上游固定距离建立释放点，并以实时载机速度释放。非 GPS 弹仍使用原有地表上方 0.5 格基准。实体生成后继续由 RVP 原有 GPS、推进、恒速和末段制导逻辑运行，炮火投送不模拟额外的无世界制导轨迹。

修改 `entry_speed_m_per_tick` 时必须同时复核武器的近炸半径、触地判定、穿透/碰撞步进和最大速度；过高速度可能缩短可见飞行时间，也可能暴露高速碰撞配置问题。

### 3.5 武器性能硬预算

profile 发布时，从每个武器成员的真实数据提取并校验：

| 项目 | 不可配置硬上限 |
| --- | ---: |
| 顶层弹体生命期 | 72000 Tick |
| 单枚顶层弹体直接子实体 | 4096 |
| 单任务“顶层 + 直接子实体” | `Integer.MAX_VALUE` |
| 主爆炸半径 | 512 格 |
| 主爆炸伤害 | 1,000,000,000 |

直接子实体估算为所有 `submunition_data.releases[]` 的 `resolveReleaseEvents() × Σ payload.count` 之和，并使用饱和整数运算。每个成员都按 `max_rounds_per_mission` 做保守最坏审计，而不是按权重折算；多级子母弹不会仅因存在嵌套链被拒绝，但当前预算只精确统计所引用顶层武器可见的直接子实体，配置作者仍需审计子载荷自己的展开链。

## 4. `fire_support_profiles` JSON 全字段

### 4.1 顶层

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `schema_version` | 是 | 只能为 `3`。 |
| `display.translation_key` | 是 | profile 的本地化键，只影响显示。 |
| `item.translation_key` | 是 | 自动生成终端 ItemStack 的名称翻译键；不参与服务端权限判断。 |
| `holder_policy` | 是 | 新呼叫和停火的持有规则。 |
| `call_stage` | 否 | 呼叫阶段生命周期；省略时使用字段默认值。 |
| `strike_stage` | 否 | 打击阶段停火延迟。 |
| `limits` | 是 | 服务端距离、任务、区块和参数上限。 |
| `munitions` | 是 | 1～64 个可选弹药方案。 |
| `fire_modes` | 是 | 1～32 个打击模式。 |
| `patterns` | 是 | 1～32 个落区预设。 |

解析器拒绝任何未声明字段。`id` 和参数键必须是小写简单标识；资源 ID 必须是合法的 `namespace:path`。

### 4.2 `holder_policy`、`call_stage`、`strike_stage`

| 字段 | 默认 | 范围/语义 |
| --- | ---: | --- |
| `holder_policy.allowed_hands` | `main`,`off` | 至少一项，只允许 `main` / `off`，不可重复。 |
| `call_stage.base_duration_ticks` | `800` | 1～72000 Tick；实际呼叫时长还乘模式倍率并向上取整。 |
| `call_stage.cancel_on_player_death` | `true` | 当前版本必须为 `true`。 |
| `call_stage.cancel_on_terminal_lost` | `true` | 当前版本必须为 `true`。 |
| `call_stage.cancel_on_disconnect` | `true` | 可设 `false`；仅影响 `CALLING`。 |
| `call_stage.consume_terminal_on_completion` | `false` | 为 `true` 时，仅在 `COMPLETED`/`CEASED` 精确删除任务绑定的 `terminal_instance`。 |
| `strike_stage.cease_fire_delay_ticks` | `80` | 0～72000 Tick；仅截断到期后未生成弹。 |

### 4.3 `limits`

| 字段 | 解析器默认 | 约束 | 实际含义 |
| --- | ---: | --- | --- |
| `min_target_distance_m` | `0` | `>= 0` | 玩家到目标 X/Z 的最小水平距离。 |
| `max_target_distance_m` | `2048` | `>= min` 且 `<= 16384` | 最大水平距离。 |
| `max_rounds_per_mission` | `96` | 1～512 | 权威计划顶层弹数上限。 |
| `max_active_missions_per_player` | `1` | 正数且不大于全局值 | 单玩家活动任务数。 |
| `max_active_missions_global` | `16` | 1～64 | 单服务器活动任务数。 |
| `request_cooldown_ticks` | `100` | `>= 0` | 成功接受请求后，到下次可成功请求的 Tick 间隔。 |
| `max_mission_duration_ticks` | `2400` | `>= 1` | 从接受任务到计划末弹的最大 Tick 数。 |
| `max_loaded_chunks_per_mission` | `8` | `>= 1` | 一个任务累计登记的唯一落点 Chunk 上限，不是同时加载数。 |
| `max_parameter_count` | `16` | 1～32 | 单个 pattern 的动态参数个数上限。 |

这些“解析器默认”只在字段缺失时生效；Schema 和正式配置把 `limits` 各字段列为必填，作者应全部显式填写。

### 4.4 `munitions[]`、`weapons[]` 与 `delivery`

| 字段 | 必填/默认 | 说明 |
| --- | --- | --- |
| `id` | 必填 | profile 内唯一的弹药方案选择 ID。 |
| `translation_key` | 必填 | 弹药方案 UI 文案键。 |
| `rounds_per_unit` | 必填，1～512 | 一基数顶层逻辑弹数；不读取武器容量或弹仓。 |
| `registration_phase_enabled` | 默认 `true` | 为 `false` 时跳过所有 `registration_phase: true` 阶段。 |
| `weapons` | 必填，1～64 项 | 按声明顺序排列的真实武器成员；同一方案内武器 ID 不得重复。 |
| `weapons[].weapon` | 必填 | 真实 `RVP_WeaponData` 资源 ID。 |
| `weapons[].weight` | 必填，1～512 | 该成员在阶段轮转中的连续槽位数；全体权重和不得超过 512。 |
| `weapons[].delivery.type` | 必填 | `rvp:vertical_projectile`、`rvp:ground_launched_projectile` 或 `rvp:air_launched_projectile`。 |
| `weapons[].delivery.data` | 必填对象 | 此武器成员独立的类型化投送参数；可为空对象采用该类型默认值。 |

权重按阶段内弹序号解释。设权重总和为 `W`，先计算 `slot = roundInPhase mod W`，再按声明顺序寻找包含该槽位的累计权重区间。例如权重 `2:1` 固定产生 `A、A、B、A、A、B...`。每个 phase 都从 `roundInPhase = 0` 重新开始，所以随机试射为 2 发还是 3 发都不会改变主射首发武器；落区仍使用全局弹序号，混合武器不会重复相同散布点。

飞机路线由所有计划弹的上游投放点组成，并通过向心 Catmull-Rom 曲线平滑连接；非 GPS 弹的释放点沿用具体 RVP 武器的离散弹道求解，GPS 弹使用 `gps_release_distance_m` 固定前置释放点。原始计划 Tick 只作为不得提前投送的下限，不要求飞机停留在释放点。
飞机每 Tick 通过动态路径管理器预载未来 5 Tick 的飞行区块；动态路径使用与本体 `EntityUtil.keepChunkLoaded` 一致的 `POST_TELEPORT` Region Ticket 距离参数 3，保证远处新区块进入 entity-ticking。在实际提交本 Tick 位移前，控制器按“当前姿态到下一姿态”的精确线段枚举全部穿越区块。只要其中任一区块尚未获票、未加载或未达到 entity-ticking，飞机就保持原坐标并冻结航线，绝不进入该区块。恢复等待期间，同 Tick 末尾预载和下一 Tick 重试始终指向最初受阻的同一个逻辑步骤，避免高速转弯时交替覆盖两条不同路径而永久等不到正确 Ticket。检查采用转向后的下一姿态而非上一 Tick 速度，高速转弯同样受此硬门禁保护。其新增区块预算优先级低于等待/活动弹体、高于远距视觉载具。
同一架飞机同 Tick 同时被空袭控制器和远距可视化服务申请路径时，管理器保留高优先级 `AIR_SUPPORT` 的完整路径及单 Tick 终点；低优先级零速单区块请求不得将其覆盖。
飞机由插件侧按 `FixedWingVehicle` 的公开转向参数做连续偏航、俯仰和滚转跟随；非固定翼使用安全回退参数。弹体从飞机当前完整姿态变换后的挂架附近生成，按实时挂架位置、飞机切线速度和当前姿态重算离散弹道，并对转弯侧向误差做法向补偿；导弹收到本发地面目标坐标作为指定目标。
该类型接受 `BOMB`、空对地 `MISSILE` 和 `ROCKET`，拒绝空对空制导以及 HITL/操作员持续制导。任务内所有成员必须使用同一飞机和同一空投参数，不得与地面投送混合。

同一 `weaponId` 的计划弹体在运行时组成武器池。飞机经过对应参考释放点后取该池队首弹；同一参考点只尝试一次，若当前区块或弹道暂不可用，弹体保留到后续参考点或出场延长段重试。所有武器池清空后任务立即进入 `COMPLETED`，飞机从最后一发实际成功 Tick 起沿参考出场方向直线飞行，并按 `exit_distance_m / carrier_speed_m_per_tick` 的参考时长清理；飞机被击落、任务达到安全截止或恢复窗口耗尽时分别按 `AIRCRAFT_DESTROYED`、`CHUNK_TIMEOUT` 或 `AIRCRAFT_LOST` 结束。

`fire_modes` 中的 `air_strike` 是空中方案专用选项，主阶段必须使用 `base_multiplier: 1.0`。客户端只展示与当前弹药方案兼容的模式，服务端仍独立执行同样的权威校验。指定飞机进入载具毁伤状态或以 `KILLED` 原因离开世界后，任务以 `AIRCRAFT_DESTROYED` 失败；普通区块卸载不会被当作击落。已投送弹数保留，后续计划不再执行。

### 4.5 `fire_modes[]`、`phases[]` 与时间表公式

模式字段：

| 字段 | 默认/范围 | 说明 |
| --- | --- | --- |
| `id` | 必填 | profile 内唯一。Java 不识别 `rapid` 等名称，行为完全由数据决定。 |
| `translation_key` | 必填 | UI 文案键。 |
| `call_duration_multiplier` | 默认 `1`，`(0,100]` | 呼叫时长倍率。 |
| `dispersion_multiplier` | 默认 `1`，`(0,100]` | 对 pattern 的所有几何尺寸统一乘算。 |
| `phases` | 1～16 项 | 按声明顺序执行。 |

阶段字段：

| 字段 | 默认/约束 | 说明 |
| --- | --- | --- |
| `id` | 必填且模式内唯一 | 阶段标识，只用于数据和显示。 |
| `translation_key` | 必填 | UI 文案键。 |
| `registration_phase` | 默认 `false` | 是否受弹药方案的 `registration_phase_enabled` 控制。 |
| `start_delay_ticks` | 默认 `0`，不得为负 | 首阶段相对打击开始；后续阶段相对上一个已包含阶段的末弹。 |
| `rounds` | 必填 | 三种规则必须且只能选一种。 |
| `interval_ticks` | 与 `duration_ticks` 二选一，正数 | 相邻弹固定间隔。 |
| `duration_ticks` | 与 `interval_ticks` 二选一，`>= 0` | 本阶段首弹到末弹的总跨度，弹间 Tick 取四舍五入。 |

弹数规则：

```text
base_multiplier: count = ceil(rounds_per_unit × base_multiplier)，rounding 必须为 "ceil"
fixed:           count = fixed
random:          count = 服务端 seed 在 [random_min, random_max] 闭区间取整数
```

总时间公式：

```text
callTicks = ceil(call_stage.base_duration_ticks × call_duration_multiplier)
first phase start = start_delay_ticks
later phase start = previous included phase lastTick + start_delay_ticks
mission last = callTicks + final strikeOffsetTicks
```

当阶段只有 1 发时，该发位于阶段 start Tick，`duration_ticks` 不会人为延迟它。若用 `duration_ticks` 且多于 1 发，第 `i` 发偏移为 `round(duration × i / (count - 1))`；过短 duration 可能让多发落在同一 Tick，但仍受全局每 Tick 8 发和每任务每 Tick一次尝试的运行时预算延后。

### 4.6 `patterns[]` 与动态参数

公共字段为 `id`、`translation_key`、`type` 和 `data.parameters`。每个参数规格均为：

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| `type` | 只能为 `double` | 当前唯一动态数值类型。 |
| `default` | `min <= default <= max` | UI 初始值。 |
| `min` | `> 0` | 服务端允许下界。 |
| `max` | `>= min` | 服务端允许上界。 |
| `step` | `> 0` 且不大于范围宽度 | 请求值必须从 `min` 起按此步长对齐。 |
| `unit` | 非空字符串 | 只用于显示，不参与换算；`m` 在当前实现中等同格。 |

参数键必须与类型要求恰好相等：

| `type` | 必需参数 | 实际几何 |
| --- | --- | --- |
| `rvp:point` | `radius_m` | 圆内按面积均匀随机；实际半径为 `radius_m × dispersion_multiplier`。 |
| `rvp:line` | `length_m`, `width_m` | 以锚点为中心的有向矩形内均匀随机；长、宽都乘散布倍率。 |
| `rvp:creeping` | `length_m`, `width_m`, `step_m` | 从锚点沿正方向逐步推进；三个尺寸都乘散布倍率。 |

方向角 `0°` 指向 `+Z`，`90°` 指向 `+X`。条状弹幕沿方向前后各占一半长度；徐进弹幕从锚点开始，只向方向正向推进到 `length_m`。徐进步数为 `floor(scaledLength / scaledStep) + 1`；由于长度和步长同时乘同一散布倍率，步数通常不随模式倍率变化。总弹数少于步数时会跳过部分台阶，多于步数时多发会共享台阶。

#### 5.1 投放点与具体航线的规划流程

空中支援实际维护两套概念：**参考航线**用于决定飞机何时经过哪些释放参考点，**实际航迹**由固定翼飞机当前姿态和转向能力推进，允许与参考航线产生偏差。相关入口和职责如下：

1. **先生成每发的地面影响点。** `RVP_FireSupportMissionManager.createDeliveryContext()` 为每个 `PlannedRound` 调用 `RVP_FireSupportPattern.resolve()`。几何实现位于 `RVP_FireSupportPatternTypes`：`point` 在目标锚点周围按半径散布，`line` 按长轴和横向宽度采样，`creeping` 按长轴步进和横向宽度生成徐进点。几何输入包含目标 X/Z、落区方位、全局轮次、总弹数、服务端 seed、规范化参数和模式散布倍率，因此同一任务的落点可重复；混合武器只改变该轮使用的弹药，不改变轮次落点。

2. **按制导能力选择单发航点策略。** `RVP_FireSupportAirstrikeController.buildRoute()` 遍历冻结的完整弹序计划，调用 `RVP_AirLaunchedProjectileDelivery.resolvePlan()`；投送器再通过内部 `RVP_AirstrikeRoutePlanningStrategy` 接口，按每发武器的主/末段制导能力选择普通离散弹道实现或 GPS 固定前置实现。该接口只负责本发释放计划，不承载任务入场点、出场点或 JSON 类型注册。建立任务级参考航线时飞机尚未生成，各实现读取目标地表高度，将 `release_altitude_above_impact_m` 限制在世界顶端以内；随后由 `inbound_heading_degrees` 和确定性 `heading_jitter_deg` 得到入场单位向量 `d = (sin(heading), 0, cos(heading))`。

   非 GPS 弹逐格降低候选高度到 `min_release_altitude_above_impact_m`，并调用 `RVP_FireSupportBallisticSolver.solveAirRelease()`，按具体武器的离散炸弹/投射物步进模拟，直到弹体穿过目标高度，得到水平释放距离 `L`。GPS 主制导或末段制导弹不执行该无制导反解，直接令 `L = gps_release_distance_m`，且高度钳制后低于最小释放高度即失败。释放点统一位于目标来向的上游：

   ```text
   release = (impactX - d.x * L, groundY + releaseAltitude, impactZ - d.z * L)
   ```

   因此不同非 GPS 武器即使攻击同一个地面影响点，也可能因弹道、重力、寿命和载机速度得到不同的 `L`；GPS 弹的 `L` 完全由 profile 决定。固定 GPS 释放点若超出世界边界则明确失败，不静默缩短或改为目标正上方投放。

3. **把弹体释放点换算为飞机中心航点。** `RVP_FireSupportAirstrikeRoutePlanner.plan()` 使用本地挂架偏移反推机体中心，而不是把挂架释放点直接当成飞机位置：

   ```text
   aircraftCenter = release - rotateRack(rack_offset, inboundDirection)
   ```

   `rotateRack()` 按任务入场方向把飞机本地 X/Z 偏移旋转到世界水平坐标，Y 偏移参与高度换算。这样飞机经过参考中心时，挂架才位于预计算释放点附近。

4. **由公共实现生成入场点、投放点和出场点。** GPS 与普通弹体策略产生的释放点先按原始轮次合并，再统一交给 `RVP_FireSupportAirstrikeRoutePlanner`；混合弹种不会拆成多架飞机或多条航线。设释放点（参考挂架航点）为 `R[0..n-1]`、对应参考飞机中心为 `C[0..n-1]`。普通原顺序路线的首尾点仍为：

   ```text
   entry = C[0]   - inboundDirection * entry_distance_m
   exit  = C[n-1] + inboundDirection * exit_distance_m
   ```

   若任务全部武器的主制导为 `NONE`，且末段制导缺失或为 `NONE`，规划器会先按上述原首发公式计算并冻结 `entry`，然后仅在水平 X/Z 平面重排 `R` 及其对应 `C`。令 `axis = normalizeXZ(taskAnchor - entry)`，退化时回退既有入场方向；主排序键是 `R` 投影到 `axis` 后的投影点至 `entry` 距离，升序表示靠近出发点者优先。次排序键取右法向量 `right = (axis.z, 0, -axis.x)` 上的有符号垂距并按数值升序，因此顺序为负侧远到近、轴上、正侧近到远；完全同位时保持原列表顺序。高度不参与排序。重排后的首点不会反向修改已冻结的 `entry`，出场点改由重排后的末点计算。

   每个重排点继续携带原 `roundIndex`、武器、落点与 `plannedTick`，时间槽不重新分配；`plannedTick` 仍只作为不得提前下限，实际经过时间可按新航程等待或顺延。`RoundRef`、同武器待投送池与参考点使用同一空间顺序，失败弹仍只在后续同武器参考点或出场延长段重试。飞机延迟生成而重排起始 Tick 时，已冻结的 `entry` 与空间顺序保持不变。

   只要任一成员的主制导或末段制导不是 `NONE`，整次任务就保持原轮次顺序。每个首发之后的 GPS 航点会在中心上游添加对准起点 `A[i] = C[i] - d × turnLeadDistance`，控制点变为 `... → previousCenter → A[i] → C[i]`；`A[i] → C[i]` 是沿该发 GPS 期望入场方向 `d` 的直线段，GPS 中心位置及 `gps_release_distance_m` 不变。首发从已有沿 `d` 的入场段进入，因此不额外插入对准段。转向段继续用向心 Catmull-Rom 平滑连接；出场段仍为直线。

   对准距离从前一参考中心到当前 GPS 中心的水平航向估算转角 `angle`；前序向量为零时沿用最近有效航向，若仍不可用则使用 `d`。规划复用飞机航速和 `advance()` 的偏航限速：

   ```text
   maxYawPerTick = min(yawTurnRate,
                       max(0, carrierSpeed × turnRateBySpeed) × yawTurnRate)
   turnTicks = ceil(angle / maxYawPerTick)
   turnLeadDistance = carrierSpeed × turnTicks × 1.5
   ```

   `FixedWingVehicleData` 的基础转向参数在建线前读取；非固定翼使用控制器已有回退参数。参考曲线恰好经过 GPS 中心时采用该发的期望入场切线，随后才转入后续航段。

5. **为参考点计算航线 Tick。** 规划器先按采样曲线弧长确定控制点距离，再用 `carrier_speed_m_per_tick` 换算行程时间。每发的原始计划时间和参考经过时间为：

   ```text
   plannedTick = callDeadlineTick + strikeOffsetTicks
   actualTick  = max(plannedTick,
                     previousActualTick + ceil(segmentDistance / carrierSpeed))
   ```

   所以飞机不会为了赶时间倒飞或瞬移到投放点；若两个投放点间隔过短，后一个参考点会局部顺延，GPS 对准段增加的弧长也会计入顺延。`RoutePlan.ScheduledRelease` 保存轮次、原始 Tick、实际参考 Tick、弹体释放点、飞机中心、曲线弧长位置和可选的 GPS 入场方向；时间重排会保留该方向标记。

6. **呼叫结束后生成飞机并推进实际航迹。** 呼叫阶段只准备目标区块并冻结航线，不会生成飞机；只有呼叫截止 Tick 已到且任务先从 `CALLING` 切换为 `STRIKING` 后，控制器才在 `entry` 出发点生成真实本体飞机，初始朝向取参考曲线切线。之后每 Tick 使用 `route.distanceAt(logicalTick)` 和 `route.tangentAtDistance()` 得到期望方向，再由 `RVP_FireSupportAirstrikeRoutePlanner.advance()` 读取 `FixedWingVehicle` 的 `turnRateBySpeed`、`xTurnRate`、`yTurnRate`、`zTurnRate`，限制偏航、俯仰和滚转的单 Tick 变化。飞机沿当前实际前向以配置速度移动，不被强行拉回参考曲线；因此 Catmull-Rom 是参考方向场，不是实体位置传送轨迹。飞行中的实际转向参数仍按现有控制器从飞机实体捕获，基础载具参数只用于预先估算 GPS 对准段。

7. **经过参考点后触发投放，并使用实时挂架位置复算。** `nextCandidateRound()` 会在飞机逻辑 Tick 经过参考释放点且达到该发原始计划 Tick 后，从对应 `weaponId` 的池中取队首轮次。每个参考点只尝试一次；若区块、弹道或实体生成暂时失败，剩余弹体可在后续参考点或出场延长段重试。

   真正 `prepare/deliver` 时，控制器通过 `snapshot()` 取得飞机当前完整姿态、挂架世界坐标和插件维护的当前速度。非 GPS 弹再由 `RVP_FireSupportBallisticSolver.solveActualAirRelease()` 进行三维离散弹道修正；GPS 弹不做拟合，直接以实时载机三维速度作为初速度，速度缺失、非有限或近零时才回退到入场方向的 `carrier_speed_m_per_tick`。两条路径都已把载机速度包含在初始化速度中，不会由生成器重复叠加。

8. **末发完成后的离场。** 最后一发真实生成时，控制器记录该世界 Tick，并将期望方向切换为 `route.direction()`；飞机仍按固定翼转向限制渐进修正，不立即消失。完整飞机的清理截止为：

   ```text
   exitEndTick = lastActualDeliveryTick
                 + ceil(exit_distance_m / carrier_speed_m_per_tick)
   ```

   到达该参考时长后才移除飞机。这个计时从最后一发实际成功 Tick 开始，因此末发因 Chunk、弹道或实体生成失败而延迟时，不会缩短完成后的离场段。

## 6. 调参方法

### 6.1 推荐顺序

每次只调整一层，便于定位偏差：

1. 先单独实测 `weapons` 弹体：坠落、碰撞、引信、爆炸、子弹药和视觉必须正常。
2. 固定 `rounds_per_unit`，只调打击模式弹数与节奏。
3. 固定弹数与节奏，只调三类落区的 default/min/max/step。
4. 调投送高度、初速和扰动，并重新验证引信与高速碰撞。
5. 最后根据多人压测收紧并发、任务弹数、目标距离和唯一 Chunk 上限。

不要同时改 profile 的弹数、武器爆炸半径和子母弹数量；三者会乘法放大毁伤与实体负载。

### 6.2 弹数与节奏

- 总弹数先按模式最坏值计算。带随机试射时用 `random_max` 做预算。
- 权重只决定总弹数中各武器的顺序与近似比例；希望整轮精确配比时，让阶段弹数成为权重总和的整数倍。
- `duration_ticks` 表示首末弹跨度，不是“每发间隔”；固定间隔使用 `interval_ticks`。
- 后续阶段的 `start_delay_ticks` 从上一阶段末弹算起。若期望“试射结束 4 秒后效力打击”，填 80 Tick，而不是从打击开始算绝对 Tick。
- `max_mission_duration_ticks` 从任务接受开始计入呼叫阶段，必须满足 `callTicks + 最后一发 strikeOffset`。
- 密集计划可能受 8 发/Tick全局预算和公平轮转延后。需要稳定齐射视觉时，不要依赖大量同 Tick 弹体。

### 6.3 落区与爆炸半径

调落区时同时比较武器主爆炸半径 `R`：

- 点状半径接近或小于 `R` 时，中心区域爆炸高度重叠；远大于 `R` 时覆盖更广但空隙增加。
- 条状实际长宽为 JSON 值乘 `dispersion_multiplier`。正式急促打击的 `64 × 16` 会变为 `96 × 24`。
- 徐进弹幕的锚点是起点，不是中心。把锚点放在友军前沿时，要给首个落点和爆炸半径留安全余量。
- `heading_jitter_deg` 改变飞行入射方向，不改变 pattern 预先算出的目标 X/Z；但斜入射、弹体气动和碰撞会让实际爆点偏离计划点。

### 6.4 高度与入场速度

- 更高的 `spawn_height_above_impact_m` 提供更长可见飞行时间，也延长弹体占用和对沿途 Chunk 的需求；世界顶端钳制会使山地实际高度差变小。
- 更高的 `entry_speed_m_per_tick` 缩短到达时间并减弱横向运动影响，但会增加高速穿透、碰撞漏判或瞬时加载压力的风险。
- 设为 `0` 才会回退到武器初速。对初速很低或为特殊发射语义的武器，必须显式设正值并实测。
- 对近炸弹，生成高度必须高于有效引信建立条件；对延时/定时弹，还需核对武器寿命是否覆盖完整下落。

### 6.5 Chunk 与并发预算

`max_loaded_chunks_per_mission` 统计任务实际遇到的唯一落点 Chunk。随机落区跨 Chunk 数与锚点相对 Chunk 边界、尺寸、方向和弹数共同相关，不能只用面积除以 256。

保守调法：

- 小型点状：先给 8～16；靠近 Chunk 角时圆形会同时覆盖多个 Chunk。
- 中等条状/徐进：先按包围盒可能穿过的 Chunk 数再留 25%～50% 裕量。
- 宽落区、高并发或远距离任务：先降低 `max_active_missions_global`，再逐步增加每任务 Chunk 上限。
- 若频繁 `CHUNK_LIMIT`，先缩小 pattern 最大尺寸或减少弹数；不要第一反应把上限推到极大。
- 若频繁 `CHUNK_TIMEOUT`，检查服务器区块生成/加载能力。空中任务会从原始最早入场 Tick 开始预加载，并允许局部顺延至 `acceptedTick + max_mission_duration_ticks + 1200`；调大 `preload_ticks` 仍不会绕过任务 Chunk 上限。

实体压力的最低估算为：

```text
顶层实体 = 同时活动任务 × 每任务最坏顶层弹数
直接展开实体 = 顶层实体 × (1 + 每枚直接子实体数)
```

这只是直接层估算；嵌套子弹药、爆炸方块更新、粒子和声音还会增加负载。

### 6.6 安全型起步模板

为新武器建 profile 时，建议先采用：单玩家 1 个、全局 4～8 个任务；单任务 8～24 发；8～16 个唯一 Chunk；点状半径不超过武器可靠测试范围；`heading_jitter_deg: 0`；固定正入场速度。通过专服和多人实测后再逐项放宽。

## 7. 配置作者流程

1. 复制[完整作者示例](../../examples/fire_support_profiles/default.json)到载具包相应目录。
2. 修改资源 ID、翻译键和 `munitions[].weapons[]`；单武器也必须使用一项数组，不要保留 v1 的 munition 顶层 `weapon` / `delivery`。
3. 用 [JSON Schema](../../schemas/fire_support/fire_support_profile.schema.json)做编辑器静态校验。
4. 运行 `/reload`，确认日志出现“已发布 N 个炮火支援 profile，revision=X”。若整批失败，按日志字段路径修复。
5. 用管理员探针先验证真实弹体：

```mcfunction
/rvpdebug firesupportprobe <vertical|ground|air> <weapon> [target]
```

例如：

```mcfunction
/rvpdebug firesupportprobe air rvp:f14d_mk84 ~ ~ ~
```

6. 再用终端覆盖点、条、徐进、主副手、旧 revision、死亡/断线、终端丢失、取消呼叫、延迟停火和 `/reload`。

当前开发维护源为 `run/client_1/limitless_vehicle/rvp`；服务端验证所需 profile 与武器数据镜像到 `run/server`。

## 8. 玩家操作摘要

1. 主手或副手持有 `ywzj_rvp:fire_support_terminal` 的 profile 变体，右键或按 K 打开炮火地图工具。
2. 当前物品已经锁定 profile；配置行只读。选择弹药方案、打击模式和落区，在地图左键设置锚点；混合方案的逐发武器由服务端配置决定。
3. 条状/徐进落区可调整方向；按侧栏范围与步长调整几何参数。
4. 客户端显示的弹数和时间只是预估，点击确认后以服务端响应为准。
5. 呼叫阶段可取消；打击阶段可请求延迟停火。两者都要求手持任务绑定的同一终端实例。

若 profile 开启完成后消耗，服务端不会按 profile 或翻译键寻找替代物，而是删除任务创建时冻结的 `terminal_instance`。终端在任务期间被丢出时，任务结束后的掉落实体加入、玩家拾取和玩家登录流程仍会拦截该实例；同 UUID 的复制品也会被删除。

不持终端按 K 时仍走普通战术图/载具炮兵图分流。客户端会记住本会话草稿；成功发布新 revision 或点击重置参数后恢复默认。

## 9. 排障索引

| 现象/原因 | 优先检查 |
| --- | --- |
| profile 整批不发布 | 未知字段、schema 版本、重复 ID/武器、非法权重或权重总和、武器索引、类型兼容和硬预算。 |
| `STALE_REVISION` | 客户端尚未使用服务端最新 profile 快照。 |
| `INVALID_PARAMETERS` | 参数键不完全一致、NaN/Infinity、越界或未从 min 按 step 对齐。 |
| `INVALID_SCHEDULE` | 最坏弹数或“呼叫 + 末弹”超过 limits。 |
| `WEAPON_UNAVAILABLE` / `DELIVERY_UNSUPPORTED` | 武器不是 RVP 数据、reload 后索引失效、kind 无实体工厂或投送类型不支持。 |
| `CHUNK_LIMIT` | 实际唯一落点 Chunk 超过任务上限。 |
| `CHUNK_TIMEOUT` | 普通投送目标 Chunk 在计划 Tick 后 1200 Tick 内未达到 entity-ticking；空中任务超过 `acceptedTick + max_mission_duration_ticks + 1200` 安全截止。 |
| `DELIVERY_FAILED` | 当前一发连续 20 次生成失败；查服务端异常和弹体工厂。 |
| `TRAJECTORY_UNREACHABLE` | 弹道本身无法形成有效投放点或路线数据无效；正常的投放间隔不足会由空中路线局部顺延，不再直接触发此原因。 |
| 爆点与预览有偏差 | 入场扰动、弹体重力/气动/制导、碰撞和引信；预览显示的是计划 X/Z，不是保证爆点。 |
| 弹数与载具弹仓不一致 | 正常；炮火弹数不读取 `max_capacity`、reload 或 `fire_data`。 |
