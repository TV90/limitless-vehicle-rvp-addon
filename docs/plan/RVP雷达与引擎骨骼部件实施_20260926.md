# RVP 雷达与引擎骨骼部件实施记录（2026-09-26）

> 需求（用户定版）：新增两种骨骼模块类型——①RADAR 雷达部件：被打坏后对应雷达强制关闭，
> 多雷达载具按雷达分粒度、外置雷达中继车雷达被打坏母车失去外置雷达；②ENGINE 引擎部件：
> 窗口内累计直击伤害超一档功率减半（受损）、超二档功率清零（瘫痪，不关发动机、
> 方向机/高低机照常），两档均可被快修修复。写法与现有骨骼化部件框架一致。

## 一、调研结论（三路并行子代理）

1. **多雷达分粒度无需大改**：CSSA5/PS1SM 的跟踪/搜索雷达本就是两个独立 PartUnit
   （`lock_radar`/`scan_radar`，骨名=部件 id、独立 OBB/血量），`bone_modules` 写两条即成；
   全载具包不存在"同一 PartUnit 双雷达"。
2. **外置中继链自动断开**：`RVP_ExternalRadarSyncService.hasAnyRadarOn` 逐雷达查 `isOn()`，
   中继车雷达强制关闭后母车探测/扇区/锁自动清空——要求 2 零改动满足。
3. **三个"复活点"必须堵**（否则打坏的雷达被重新开机）：
   ① `RVP_GunnerRadarActions.prepareLockRadar`（gunner 锁定前自动开机）；
   ② `GunnerExternalRadarController.turnOnRelayRadars`（中继车 gunner 每 tick 保活开机）；
   ③ `C2SRadarPowerToggle`（玩家手动开机同步包——本体 toggle 是纯客户端本地操作，
   RVP 已有同步包补齐服务端）。
4. **关闭语义**：`RadarUnit.toggle(false)`（自带清锁定目标；RadarUnit 不是 SwitchableUnit，
   自持 on 字段，不进 NBT/不 syncData）；HUD/RWR/扫描/开关动画全链路自带 `isOn()` 门
   （`RVP_RadarScanService:85/:175`、`RVP_ClientRadarTickHandler:119`、`RadarUnit.tick:73`），
   强制关闭后自然停摆。
5. **引擎零 Mixin 挂点**：履带/轮式/船驱动字段是 public 逐实例字段（`initData→inject` 写入
   一次后本体不再重算），照 `RVP_WingSweepState` 先例经本体 `VehicleMoveEvent`（每载具每 tick）
   覆写 base×系数。**硬约束**：不碰 `ENGINE_ON`、不把 POWER 压 ≤20——本体炮塔/武器/雷达的
   `hasPower()`（POWER>20）门保持原样（发动机关闭约 80t 后 POWER≤20 即炮塔停转，此即
   "关发动机会卡方向机"的代码依据，削动力绝不能走这条路）。
6. **`bone_modules` 键=命中候选骨**：`resolve()` 的候选集 = hitbox_damage_factor ∪
   vehicle_explosion ∪ bone_modules 键——新骨只写 bone_modules 即纳入命中判定；
   **其 `damage_factor` 会覆盖 hitbox_damage_factor 同骨倍率**（manager :979-981），
   故新条目 damage_factor 必须照抄各车现有值。

## 二、实现内容

### RADAR
- `BoneModuleType.RADAR`（不参与爆炸百分比破坏，雷达只能直击打坏）。
- 服务端强制关闭三层：
  - **即时**：`tryDestroyBoneModules` 销毁 RADAR 后 `RVP_RadarModuleEnforcer.forceRadarOff`
    （toggle(false) 清锁）；
  - **巡检兜底**：`RVP_RadarModuleEnforcer`（ServerTickEvent 每 20t 遍历全部载具，
    失效骨雷达仍 isOn → 压回 off），任何遗漏的开机路径 1 秒内被纠正；
  - **三处 gate**：①②③（见调研 3）在 `toggle(true)` 前查
    `isModuleActive(vehicleId, radar.getId(), RADAR)`，失效即拒绝。
- 维修恢复：dev 队列自动（`repairableTypes` 缺省白名单排除 TRACK，新类型自动可修）；
  恢复后 `restoreRadar` 自动开机（用户定版"修好自动开机"）。

### ENGINE
- `BoneModuleType.ENGINE` + `BoneEngineConfig`（`bone_modules` 条目 `engine` 子对象：
  `threshold_light` / `threshold_heavy` / `power_multiplier_damaged` / `damage_window_ticks`，
  缺省 Java 默认 60/150/×0.5/600t；**2026-09-27 起 9 台引擎载具已按车种显式配置**：
  履带式坦克 600/900（t90m/t84bm/m1a2sep/ztz100/vt4/abramsx）、
  步战/防空 450/700（bmpt72/bukm3/ps1sm），详见载具配置清单）。
- **单发直毁路径跳过 ENGINE**（`tryDestroyBoneModules` 循环 `continue`）：失效完全由
  窗口累计驱动，否则一发过 min_damage 的炮弹会跳过受损档直接瘫痪。
- 累计：`tryDestroyBoneModules` 开头（无模块/低伤早退**之前**）`accumulateEngineDamage`
  ——hitBoneName+triggerDamage 累入 `RVP_EngineDamageTable`（UUID+骨→累计值+衰减速率，
  累计时捕获 `thresholdHeavy/window`，每 tick 线性衰减，**中间量不持久化**）；
  跨过重损阈值即 `destroyModule(ENGINE)` + `syncBoneModuleState`（瘫痪档随状态表持久化）。
  一处埋点覆盖三个调用方（RVP_BaseBullet 直击 / RVP_LaserWeapon 激光 /
  RVP_VehicleHurtScalingHandler 本体武器重放）。**爆炸波及暂不累计**（已知边界）。
- 消费端 `RVP_EnginePowerHandler`（VehicleMoveEvent，服务端）：逐骨档位
  （失效=2 瘫痪 / 累计≥阈1=1 受损 / 否则 0），取最差档 → 字段覆写 base×倍率：
  履带 `TrackedVehicle` 7 字段（brake/forward/backwardAcceleration、maxSpeedF/B、
  turnAcceleration、maxTurn）；轮式 `WheeledVehicle` 与船 `VesselVehicle`
  （brake/forward/backwardForce、maxSpeedF/B、turnStep、maxTurn）同法支持；
  直升机/固定翼动力走 POWER 比例路径不适用字段覆写（已知边界，未削）。
  未配置引擎部件的载具 `restoreAndCleanup` 幂等还原（零开销路径）。
- 客户端可见：新 `S2CEngineDamageState`（entityId+骨→档位 0/1/2，差分推送）→
  `RVP_ClientEngineDamageState` 侧表 → 面板 ENGINE 栏目（正常/受损黄注记/瘫痪红框）。
- 维修：`tryStart` 成功即 `clearVehicle` 清累计（受损档随快修回落）；瘫痪档走 dev 队列
  掷骰恢复，`restoreBoneModules` 恢复 ENGINE 时清该骨累计（防恢复后残存累计立即再跨阈值）。

## 四、已知边界

1. 爆炸波及不累计引擎伤害（只累计直击）；如需"炸到引擎骨也累计"，在
   `destroyModulesByExplosionRadius` 加同款累计即可。
2. 直升机/固定翼配 ENGINE 不生效（POWER 比例路径不适用字段覆写，未做）。
3. 引擎累计中间量不持久化（停服清零受损档进度；瘫痪档随失效表持久化，不受影响）。
4. TRACK 履带模块仍为占位（用户确认暂不做）；其"动力损失"未来实现可与
   RVP_EnginePowerHandler 共用消费端。
5. 雷达强制关闭不写 NBT：本体 RadarUnit.on 本就不持久化，重启后雷达默认开机 →
   若模块仍失效，巡检 1 秒内压回 off。

## 八、实机事故：引擎覆写 NaN 污染 + 修复（2026-09-27）

**现象（用户实机）**：打瘫引擎后进入载具 → 载具消失、地形消失、无法操作；重进世界
载具加载失败。

**根因（日志 latest.log 00:50:11 Cupboard 拦截 NBT 实证）**：t90m 存档
`Pos:[1287.3, NaN, 6454.9]`、`Rotation:[NaN, 0]`、`turret.xRot/yRot:NaN`——整车
位置/朝向/炮塔被 NaN 污染后写档，重新加载即 `Entity has invalid position`
（EntityType 加载异常 → 实体丢弃 → 所在区块渲染异常）。

**污染链路（复盘）**：`RVP_EnginePowerHandler` 每覆写 `setDeltaMovement` 路径的驱动力
字段无 NaN 防护——`damagedMultiplier` 跨骨共享变量存在被非法配置污染的理论通路，
且基准捕获（captureXxx）在 inject 时序竞态下可能捕获到未初始化值；任一 NaN 进入
`setDeltaMovement` → 本体物理 tick 逐链扩散到位置/旋转/炮塔 → 存档固化。

**修复（三处防御，防火墙式）**：
1. 载具位置 NaN 时直接跳过本 tick 覆写并还原清理（不火上浇油）；
2. 倍率合法性钳制：damagedMultiplier/multiplier 任何 NaN/负数/＞1 一律钳回 0.5，
   最终值仍非法则整 tick 跳过覆写；
3. 基准校验 `capturedValid`：捕获的 14 个动力字段任一非有限或 ≤0 时跳过覆写
   （防 inject 竞态捕获到未初始化值）。

**善后提示**：已污染的存档里那辆 t90m 的 NBT 已含 NaN，需删除该实体（或用
NBT 编辑器修 Pos/Rotation）后重新放车；新 jar 不会再产生新的污染。

## 九、部件受击分轨判定（2026-09-27 用户定版）

**需求**：除 ERA 外的部件，受击判定按**实际到骨伤害**（乘命中倍率、过装甲层后的
最终入账值），不按武器裸伤——"防弹衣逻辑"：大倍率装甲骨上的雷达被小倍率弹蹭一下
不该打坏。

**实现**：`tryDestroyBoneModules` 增加 `useFinalDamageForModules` + `finalBoneDamage`
参数（分轨）：
- **ERA**：仍按模块前伤害（`preHitboxDamage` / `hitDamageBeforeHitbox` / `predicted`，
  旧平衡——装甲车 ERA 门槛按裸弹伤设计）；
- **其余模块（雷达/引擎累计/APS/干扰机等）**：按实际到骨伤害（`finalDamage` /
  激光 `hitDamage` 过装甲后 / 重放 `adjustedAmount`）重判 min_damage 门槛。
三个调用方（RVP_BaseBullet / RVP_LaserWeapon / RVP_VehicleHurtScalingHandler）已同步
传最终伤害；旧 4 参重载保留（等价分轨关闭）。

**实机清单补充**：9. 打瘫引擎进车不再出现载具/地形消失（修复验证；已污染存档先删车）；
10. 大倍率装甲骨（如炮塔 0.4 倍率）上的雷达骨，小伤害弹不再一击打坏（到骨伤害
不足 min_damage）。

**需求**：命中展板（`RVP_HitIndicatorOverlay`，右上角"命中XX -x%"）下方显示 60 tick
（3 秒）战果文案——摧毁敌方部件显示"摧毁光电干扰机/引擎/APS 探测器"等；
把敌方引擎打进受损档时显示"重创发动机"。

**实现**：

  `shooter` 参数（三调用方传入：弹体 owner / 激光 shooter / 本体武器重放 source 攻击者）；
  每销毁一个模块即 `notifyModuleHit` 推送（gunner 等非玩家射手不发；

## 十、"瘫痪后还能开"根因修复 + 战果通知 UI 三改 + HUD 速度行（2026-09-27 第二轮）

### 10.1 引擎瘫痪失效根因与重构（基准重锚）

**现象**：引擎打瘫后（含上下车后）载具仍可驾驶。

**根因**：首版 `RVP_EnginePowerHandler` 用"一次性内存捕获"（首次接管时把本体动力字段
抄进 EngineRuntime 作基准，之后覆写=基准×倍率）。本体在**玩家上下车/跨区块卸载重载/
display 变更**等时机会 `initData → VehicleData.inject` **把动力字段重置回 JSON 配置满值**，
而 captured 标记还在——覆写继续用旧基准、或 capturedValid 拒绝后字段停留 inject 满值
→ 瘫痪车复活。

**修复（重构）**：删除捕获态全套（captured/baseXxx/capturedValid/restoreAndCleanup），
`applyPower` 改为**每 tick 从 `CommonAssetsManager.vehicleDataManager().getVehicleData()`
直读该载具 JSON 权威配置**（与 inject 写入同源；RVP 战术地图已有同款调用先例），
覆写 = 配置值 × 倍率——本体无论何时重置字段，下一 tick 即被纠正回"配置值×0"。
覆写只在"该载具配置了引擎部件"时发生，未配置载具字段从不被触碰。NaN 防火墙保留
（位置非有限/配置值非有限时跳过本 tick）。EngineRuntime 只剩档位差分记忆。

## 十四、NaN 真正根因实锤（存档 NBT 抓现行）+ 修复（2026-09-27 深夜第三轮）

### 14.1 推翻"旧档遗留"结论——新会话存档内抓到 NaN 现行

对新世界(24)（03:01 会话，修复 jar）存档 entities/*.mca 全量解压扫描：**1 辆 t90m 的
Pos[Y] = 0x7FF8000000000000（标准 quiet NaN）、Rotation[0] = NaN**——NaN 在修复 jar
下依然产生，前一轮"旧档遗留"结论错误（02:33 会话零警告是因为那辆 NaN 车属于更早会话，
而本次新产生的 NaN 车只在退出存档后、下次加载时才暴露）。

### 14.2 真正根因（除零，实锤）

瘫痪档旧实现把 `maxSpeedForward` 一并 ×0；本体 `TrackedVehicle.tickMove:165` 转向公式：

```java
this.setYRot(this.getYRot() + vt + Math.abs(vf) / maxSpeedForward * vt / 5);
```

**除以被清零的 maxSpeedForward → 0/0 = NaN**（一转向即触发）→ NaN 进 YRot →
getLookAngle 返回 NaN → setDeltaMovement(NaN) → 下一 tick 物理引擎
setPos(y−NaN) → Pos 全 NaN → turret 旋转同污染 → 退出存档固化 → 下次加载
`Entity has invalid position` 载具消失。"受损档 ×0.5"除数非零无恙，**只有打瘫才炸**
——与两次实机复现完全吻合。前两轮修复（捕获模式、NaN 防火墙）都没抓到它，因为
NaN 不经过 RVP 覆写的值本身（乘 0 合法），而是本体拿清零字段当除数。

### 14.3 修复（除零保护）

`applyPower` 重写倍率作用面：**速度上限字段（maxSpeedForward/Backward）与转向上限
（maxTurn）永不参与倍率**（保持配置原值——maxSpeed>0 但加速度/转向力为 0 时 vf/vt
恒 0，车依然寸步不动，且本体任何除以该字段的公式都安全）；只倍率化"力/加速度"类字段
（brake/forward/backwardAcceleration（Force）、turnAcceleration/turnStep）。
轮式/船的 turnStep 同理为积分速率也倍率化，maxTurn 保留原值。

### 14.4 平衡配置同轮确认（上一批，随本 jar 生效）

雷达骨 min_damage 统一 20；履带车 max_speed_forward=50KPH，倒车 ztz100=50 /
bmpt72+t90m=4 / 其余=25。引擎累计口径复核为实际到骨伤害（3BM59 近距 1 发受损
2 发瘫；带衰减 3 发瘫、掉血约 1100——与用户实测自洽）。

`能量==0 → POWER=0` → `hasPower()` 假 → tickMove 直接 return（转向同样会停）。

## 二十一、重创档"只能转向不能开"根因 + 极速/加速度分路（2026-09-28 凌晨）

**用户实机**：重创档（×0.5）下转向正常、前进/后退完全无法起步。且"没油+发动机未损坏
时能正常开"（本体 getEnergy 在 infiniteFuel 下返回 Float.MIN_VALUE，POWER 照常到 100）。

**根因**：履带车前进速度 = 每 tick `vf += forwardAcceleration` 积分，同时 PhysicsEngine
对接地车辆每 tick 施加**地面摩擦减速**——加速度砍半后净加速 ≤ 摩擦，车辆永远起不了步；
转向是直接积分朝向速率不经摩擦，故转向正常。此前把"功率减半"实现为全字段 ×0.5，
把起步能力也砍没了。

**修复（极速/加速度分路）**：`applyPower` 拆双倍率——`speedMult` 作用于极速/转向上限
（maxSpeedForward/Backward、maxTurn），`accelMult` 作用于加速度/推力/转向速率
（forwardAcceleration 等）。重创档 speedMult=0.5（极速 25 KPH）、accelMult 钳 ≥0.2
（保留起步能力）；瘫痪档 1e-4 全字段（趴窝）。诊断日志同步记录两路倍率与实际字段值。

**实机清单（第九轮）**：重创 → 能正常起步、极速 25 KPH（速度行可见）；瘫痪 → 趴窝；
快修恢复后极速 50。


## 二十二、双雷达主控开关语义 + 修好自动开机同步（2026-09-28 凌晨第二波）

## 二十三、主控开关方向判定修复（2026-09-28，用户实机"一好一坏关不掉"）

**根因（审自身代码发现）**：主控开关的方向判定用了 `workingOnNow.equals(snapshot)`——
但 `workingOnNow` 是 tick 末读取的实时状态，而本体 InputHandler 的逐台翻转在**本 tick
更早**的按键事件里已执行完：按下时原来开着的雷达刚被翻成关 → workingOnNow 永远 ≠
快照 → 永远判为"有未开"→ 纠正逻辑把刚关掉的完好雷达**又强行开回**。这就是"一好一坏
关不掉雷达"（反辐射无法反制）的完整链路，与"只开不关"旧版无关（那版已删）。

**修复**：方向判定只比较**快照 vs 工作雷达 id 集合**（`snapshot.containsAll(工作雷达id)`
且数量一致 = 按键前全开）。判定语义不变：按键前全开 → 本次全关（反辐射反制）；
有未开的 → 本次全开（回到双雷达）。

**实机**：一好一坏 → 按 3 → 完好雷达关闭（可反制 ARM）；再按 3 → 重新开启。


## 二十四、重创档动力倍率 0.75（2026-09-28，用户定版）

**背景**：§21"重创档 accelMult=max(0.5, 0.2)=0.5 能起步"的结论被用户实机推翻——

### 29.1 现象与根因（两个叠加，均非本轮炮管功能引入，0925 骨模块系统时代遗留）

   真炮管报"炮塔"，0.6/0.4 倍率跟着错。

渲染（`VehicleRender.renderHitbox` 红框）与命中 part_unit 源同对象故渲染正确；普通

mixin（仅 VectorUtil 过滤）、initData 快照、插值旧值均无嫌疑。

### 31.2.4.9 面板行全空真根因实锤：StyleScope 挂起重算缺失（2026-09-28，用户实机日志+反编译）

反编译 AUI（1.2.4 mapped）渲染管线闭合链条：

- **渲染读 `Document.getPaintList()`**（RenderNode 列表）；
- `drawFlatDocumentInContext` 每帧调 **`commitPendingStyleRecalcForRender()`** →
  `style.flushPendingUpdates()`——刷 StyleScope **挂起的样式重算**并更新 PaintList；
- **挂起入口 = `Document.requestStyleRecalc(element)`**（StyleScope.requestRecalc，
  **SUBTREE 模式**整个子树重算）；

**此前所有轮次从未调过 requestStyleRecalc**——运行中 append 的行永远不进 PaintList（不渲染）；
markDirty 走 RenderQueue（视觉重绘脏，另一条队列），与样式重算是两套独立机制。

**修复**：`refreshDynamic` 末尾 `document.requestStyleRecalc(categoryScroll)`（SUBTREE 子树
重算挂起）+ 保留 markDirty(RELAYOUT|REPAINT) 视觉标脏——渲染帧自动 commit 重建 PaintList。

**教训入册**：AUI 的 DOM 变更生效链 = `requestStyleRecalc（挂起）→ 渲染帧
commitPendingStyleRecalcForRender → flushPendingUpdates → PaintList → 绘制`；`refresh()/
refreshStyles()` 是**模板热重载**（重新解析 HTML 模板，非轻量刷新，滥用即闪烁根源）；
`markDirty` 只管视觉重绘不重布局。

### 31.2.4.11 面板刷新最终架构：首建一次 + 运行中原地更新（2026-09-28 第四版，用户实机确认）

**决定性对照**：本体改装屏在 init 时一次建全列表、运行中零调用即实时上屏——**AUI 每帧
渲染直接读 DOM 当前态，但 init 之后 append 的新子树不进入渲染**（原因同前两轮推断）。

**最终架构**：

3. 行结构固定化：`buildRow` **恒建 extra 槽**（空文本占位，原地更新按固定子序写）；
4. init 不再清缓存（Document 同实例，元素引用跨 init 有效）。

## 三十二、俯视图 TOP VIEW 闪烁根治：取景冻结（2026-09-29，交接遗留项）

### 32.1 排查过程（三轮排除，全部有实据）

面板第四版确认"成功了大半"后的交接遗留——俯视图走 `renderSkeletonNative` 每帧原生
scissor 绘制（不走 DOM/AUI），本轮反编译 AUI（1.2.4 mapped，decomp 缓存在
`_tmp_aui_decomp/`）+ 对照本体观瞄实现逐链排查：

1. **DOM 画布矩形排除**：`Element.getBoundingClientRect` → `Rect.of` → `RectFrameCache`
   （帧内缓存/帧外回退 `getCommittedRectIfValid`，按 viewportVersion+styleVersion+scroll
   依赖哈希校验）——`#skeleton-canvas` 是 `position:absolute; 100%×100%` 锚点，父级
   `flex: 0 0 45%` 定高；`markDirty(RELAYOUT)` 的目标（hpText/hpFill/categoryScroll）
   均不在其祖先链上，提交矩形跨帧稳定；
2. **数据链路排除**：`VehicleCubeOBB.update` 的 `positionO/rotationO` 快照时机、
   `AbstractVehicle.tick` 末尾 `updateOBBs`、本体 `VehicleScopeOverlay` 同款插值数学
   （xo→getX / positionO→position / slerp rotationO→rotation / lerpZRotDiff）——静止时
   全部输入对 partialTick 不变，本体观瞄图无闪烁报告佐证数据源干净；
3. **上屏链路排除**：`ApricityScreen.render` 内 AUI 画完即 `endBatch`，原生绘制在其后
   （z=400 深度已实证）；`drawRectByCorner` 纯 hLine/vLine 无 GL 状态副作用；
   `resolveFlatDocumentBaseZ` 分层（1+layer×251.25）不影响已验证的 z=400。

### 32.2 根因

**俯视图是全项目唯一每帧重算"取景框"的绘制**：旧版 `render()` 每帧用插值实时数据重算
fit cube 的**旋转敏感 AABB 包络**（`hw·|cos|+hd·|sin|`）→ `scale = min(画布/包络)` 与
`translate(−包络中点)` 逐帧变化——炮塔回转（车体本地系里炮管组 cube 中心绕塔轴公转）、
悬架微振、行驶俯仰侧倾时，**整个俯视图逐帧缩放+平移跳动**，即交接文档假设的
"帧间布局跳动"。本体观瞄图同数据不闪，正因它固定 10px/格、锚定载具中心、无自适应包络。

### 32.3 修复（`RVP_EquipSkeletonRenderer.render` + 面板屏调用点）

- **包络改角度无关半径**：`max(√(cx²+cy²)+√(hw²+hd²))`（fit cube 中心到载具原点距离
  + 角点半径，三角不等上界）——画布空间中整车随炮塔**刚性旋转**（180−炮塔偏航全局旋转），
  角点到原点距离恒定，任意炮塔角/车体朝向都不裁切；
- **取景冻结缓存 `Framing`**（面板屏实例持有、开屏自然重置）：key = 载具 entityId+画布
  像素尺寸；半径**只增不减**——实测变大（炮塔扫到更远）立即跟随一档后再次冻结，变小
  不收缩——静止时帧间像素级全等，无任何连续缩放呼吸；
- **居中锚定载具原点**（删除包络质心居中，本体观瞄同款锚点选择）；fit 排除炮管的既有
  设计不变（炮管超出包络的裁切行为与旧版一致）。

## 三十三、回血闪烁真根因 + t90m 烟雾弹链路（2026-09-29 第二轮，用户实机反馈）

### 33.1 回血闪烁真根因（AUI 反编译证据链闭环）

**触发开关**：`buildDynamicSignature` 含 `(int) vehicle.getHealth()`——焊枪回血 +1%/2t、
快修每 tick 回血 → 回血期间每个 10 帧节流点签名几乎必变 → `refreshDynamic` 全路径高频跑；
平时（静止不打架）签名不变早退，永远走 committed 快路径——这就是"只有回血时闪"。

**失效链**（反编译 AUI 1.2.4 mapped，缓存于 `_tmp_aui_decomp/`）：
1. `hpText.setTextContent` 当场 `invalidateLayoutSubtree` + `forEachRoute` 沿祖先链清
   html/body/main 的 layoutVersion/size/box（Element.java:1781-1793）；
2. `markDirty(RELAYOUT)` 在 commit 时 `Drawer.flushUpdates` 对每个标脏元素 `forEachRoute`
   清到根 + `position.clear()` **递归清整树 committedRect**（Drawer.java:38-44、
   RenderElement.java:86-91）→ `skeletonCanvas` 的已提交矩形每轮必失效；
3. `renderSkeletonNative` 在 refreshDynamic **之后的同帧**裸读 `getBoundingClientRect` →
   committed 失效 → `Rect.of` 走实时重建 → 命中"擦了一半"的缓存态：`#skeleton-canvas` 是
   `100%×100%` 空锚点 div，containing block 尺寸缓存中间态不可直接给出时**百分比尺寸塌陷
   为 0**（Size.java:520/556/833-858）→ `rect.width<=8` → 整帧跳过 → 俯视图与底色帧交替
   = 疯狂闪烁。AUI 自身重绘无空白帧（每帧全量 paintList），问题全在 RVP 读点时机。

### 33.2 修复（三点，纯客户端）

1. **画布矩形帧首预读 + 两帧稳定才采用**（`RVP_EquipPanelScreen`）：`getBoundingClientRect`
   挪到 `super.render` **之前**（上一帧 commit 完成后的自洽态，committed 必有效）；原始读数
   连续两帧一致（±1px）才更新采用值，无效（≤8px）沿用最近有效矩形——瞬时塌陷/位移读数
   全部过滤，跳帧空白与 scissor 跳动同根消灭；
2. **Framing key 收敛为 vehicleId**（`RVP_EquipSkeletonRenderer`）：包络半径是视空间量与
   画布尺寸无关；§32 版把画布尺寸放进 key，画布 ±1px 抖动即重置取景（放大器之二）——
   收敛后画布变化只影响当帧 scale 换算、不重置只增不减半径；
3. **回血期 DOM 无效化减量**：`updateDynamicRows` 行内容签名门控（不变零写入零 markDirty）、
   `rebuildQueues` 的 `fillQueueList` replaceChildren 按队列签名门控（prune 校验照跑）、
   `updateHp`/`updateForecast` 等值守卫（AUI `setTextContent` 无条件 markDirty(15)，等值
   不写）、`refreshDynamic` 只对**真正变化**的容器 markDirty。

## 三十五、调查：爆炸伤害对 ERA 的破坏机制（2026-09-29，只调查未改动）

### 35.1 两条破坏链

**机制一（直击·累计）**——AP 弹与爆炸半径 ≤5 的弹药直击载具：`tryDestroyBoneModules`：

- 埋点：命中 bone_modules 配置骨（含 ERA；引擎/炮管走专属累计段不入通用表）→ 伤害累入
  `RVP_BoneCumulativeDamageTable`（键=载具UUID+骨名）；
- 失效判定：该骨累计 ≥ `min_damage`（=累计失效阈值；ERA 数据全部 100/块，t90m 16 块）
  → `destroyModule(ERA)` 整骨失效 + 命中点 MCHR 爆炸特效（scale=骨配置 explosion=2）+
  战果通知；
- 修复联动：快修整骨恢复（line 331）与焊枪部件修复（WrenchRepairHandler line 143）都
  **清该骨累计**——不存在"修好后残留旧累计、一蹭就爆"；快修 ERA 配额
  ceil(坏块×25%) 至少 1；载具离开世界清累计表（跨维度/退出不残留）。

**机制二（爆炸·百分比，不走累计表）**——爆炸半径 >5：

- **二A（HE 直击）**：HE 直击（radius>5）走 `destroyModulesByExplosionRadius` 直击分支
  ——**不进累计表**（"HE 炸多块不走累计"，§31.2.4 定版），纯按半径百分比破坏；
- **二B（波及）**：爆炸中心 radius 盒内、非直击的其它载具同比例破坏；
- 阈值表：radius ≤5=0% / ≤8=10% / ≤12=25% / ≤18=50% / >18=**100% 全毁**；
- 数量 = floor(存活 ERA 骨数 × 百分比)；直击**保底 1 块**、按 ERA 骨 OBB 中心到命中点
  距离近者优先爆；波及**无保底、无距离衰减**（爆炸边缘的车与贴脸的车同百分比）、随机
  选块；叠加骨（ERA+干扰机同骨）只毁 ERA 保留设备（`participatesInBlastDestruction`
  仅 ERA 参与）；
- 已失效 ERA 骨不进候选（按活性过滤），不会重复破坏。

### 35.2 调查发现（⚠️ 需要定版/留意，本轮未改）

1. **ERA 累计入账口径与定版文档分叉**：2026-09-27 定版 javadoc 与调用注释写"ERA 按
   模块前伤害（裸弹伤，装甲车 ERA 门槛按裸弹伤设计）"，但 09-28 全模块累计化的通用
   累计（HitboxFactorManager tryDestroyBoneModules 内 `accumulate(vehicleId, boneName,
   moduleTriggerDamage)`，含 ERA）在实弹路径（useFinalDamageForModules=true）入账的是
   **finalBoneDamage=过命中倍率+装甲后的实际到骨伤害**——即现行代码 ERA 累计按装甲后
   伤害计，装甲越厚 ERA 越难攒满，"裸弹伤门槛"已不成立。二选一：改代码回裸弹伤轨，或
   改 javadoc/定版为现行口径；
2. **机制二B 无距离衰减**：大半径爆炸波及范围内所有载具（含很远边缘）同百分比掉 ERA
   ——仅陈述现状（原定版即如此），若要"贴脸多炸、边缘少炸"需把百分比乘距离系数；
3. 机制一与机制二的入口互斥：HE 直击（radius>5）只走百分比不累计；AP/小爆炸只走累计
   不百分比——同一发不会双重破坏。

## 三十六、ERA 爆炸破坏加"爆心视距"判定（2026-09-29 第八轮，用户定版）

**背景**：§35.1 机制二按纯半径百分比破坏——>18 半径直接全毁，"正面挨导弹、侧后 ERA
却掉了"不合理（用户实机反馈）。

### 36.1 规则（`destroyModulesByExplosionRadius`）

爆心（直击=命中点，波及=爆炸中心）到候选 ERA 骨 **OBB 中心**的连线，被本车**其它
骨骼**的实时 OBB 阻挡 → 该 ERA 剔除出候选（**半径再大也不炸**）；百分比基数改为
**可见块数**（保底/最近优先/随机逻辑不变）。流程：半径阈值前置（≤5 直接 return，
零开销）→ 活性候选 → **视距过滤** → 百分比破坏。

- **遮挡物来源**：结构模型**全骨**逐骨 `resolveBoneObbs`（§29 实时 OBB 同源）——车体/
  装甲骨无模块但才是主要遮挡物（moduleByBoneName 不含它们）；每次爆炸建一次
  `骨名→OBB列表`（爆炸是离散事件，千次量级线段-OBB 测试远低于 0.1ms）；
- **射线测试**：复用本体 `OBB.clip(from,to)`（slab 算法）；
- **防误挡三则**：①候选**自身骨**的 OBB 不算遮挡；②爆心位于某遮挡 OBB **内部**时该
  遮挡不计（贴板/入车爆炸不应全挡）；③遮挡入射点双 ε——距爆心 >0.2 格且 >线段 5%
  才算真遮挡（防贴板 grazing 误挡 ERA 安装面）；
- **防御**：hitPos==null / 模型解析失败 → 不过滤保持原行为；候选 OBB 解析为空 → 视为
  可见（保守，不因解析问题静默清零）；
- 纯逻辑抽 `filterBonesByLineOfSight` + 5 个 JUnit（正面板挡后侧/侧向可见/爆心在遮挡内
  不遮挡/贴板 grazing ε/旋转 OBB 遮挡）全过。

### 36.2 冒烟流程修正（用户要求）

runServer 冒烟轮询到 `Done (Xs)!` 后**立即按 java 进程 taskkill 关服**，tasklist 复验
为 0——不再等 stdin EOF 自退（曾因上一实例未退净导致下一次冒烟日志文件被占用起服失败）。

### 36.3 实机清单（第二十四轮，待用户实测）

1. 正面挨大口径 HE/导弹：只掉爆心可见侧的 ERA，侧后 ERA 不再跟着掉；
2. 侧面贴脸爆炸：该侧 ERA 按百分比掉，对面侧不掉；
3. 贴装甲面爆炸：安装面上的 ERA 正常炸（ε 容差生效，不出现"贴板全不炸"）；
4. 超大半径（>18）爆炸：视野开阔侧全毁、被车体挡住侧保留。

## 三十七、RVP 武器自毁距离（2026-09-29 第九轮，用户需求）

**需求**：到达自毁距离的弹药消失或爆炸；机枪/机炮默认自毁距离 1024 米；其它 RVP 武器
默认不自毁、可配置。口径：米=格，**沿弹道累计飞行路程**（与可编程空爆同源）。

### 37.1 数据（`RVP_ProjectileData`，weapon JSON `projectile` 子对象）

- `"self_destruct_distance"`：float，米。缺省 -1=未配置 → 类别默认：
  `MACHINEGUN`（机枪/机炮，含普通弹/霰弹/鸭弹）**1024**，其它类别 0（不自毁）；
  显式配置优先——显式 `0` 关闭（含显式关闭机枪默认）；
- `"self_destruct_explode"`：bool 缺省 false=消失（discard）；true=爆炸——
  `detonateFuseAt(pos, NORMAL)` 完整引信语义（继承 ON_FUSE 子母弹等配置；弹药无爆炸
  配置退化为消失）；
- 访问器 `resolveSelfDestructDistance(RVP_EnumWeaponKind)` / `isSelfDestructExplode()`
  ——类别默认按武器 KIND 判定（非武器 ID，合规）；
- 字段说明已补 `RVP武器数据模型文档.md` RVP_ProjectileData 表。

### 37.2 运行时（`RVP_BaseBullet`，机枪/通用两条 tick 链共用）

- `tickSelfDestruct()`：每 Tick 累加命中扫掠运动段长（`programmableAirburstSegment*`，
  两链的 `tickHit` 都会赋值）到 `selfDestructTravelled`；越界即**沿线插值到精确越界点**
  （高速弹体单 Tick 段长可达数十米，端点会超程）——爆炸模式 `detonateFuseAt`，消失模式
  `discard`；`selfDestructTriggered` 置位防重复；仅服务端执行；
- 调用点两处：通用链 `tick()` 在 `tickMotion` 之后；机枪链
  `RVP_BulletEntity.tickBulletServerPostMotion()` 在 bounce 引信之后（空爆/近炸优先级
  更高，先到先触发）。

### 37.3 实机清单（第二十五轮，待用户实测）

1. 机枪/机炮对空/对地扫射：弹道飞满 1024 米即消失（观察曳光终止点，约 20+ Tick）；
2. 任一武器 `projectile` 配 `"self_destruct_explode": true`：到距时在弹道上爆炸
   （有爆炸配置的走自身爆炸伤害/特效）；
3. 导弹/火箭/炸弹未配置：行为与之前完全一致；
4. 机枪 JSON 显式 `"self_destruct_distance": 0`：恢复为不收敛（不再 1024 自毁）。

### 37.4 数据应用：TKB-1055 近炸提升 + 400 米自爆（2026-09-29，用户需求）

`weapons/ps1_tkb1055.json`（ps1sm 的 TKB-1055 SACLOS-SAM，载具包不进 git）：

- `fuse_data.proximity_radius`：**3.0 → 6.0**（近炸触发范围翻倍；爆炸波及半径
  `detonate_data.explosion_data.proximity_radius=8.0` 未动）；
- `projectile_data` 新增 `"self_destruct_distance": 400` + `"self_destruct_explode": true`
  ——400 米自爆（走该弹自身爆炸 damage 100 / radius 6；§37.2 通用链覆盖导弹，
  `performAmmoEntityTickHit` 运动段对导弹同样有效）。

## 三十八、辅助设备吃爆炸伤害（2026-09-29 第十轮，用户定版方案）

**需求（用户原案）**：部件受损原先只吃直击伤害；改为——**爆心与辅助设备连线没有被
其它 OBB 阻挡的辅助设备，扣除和载具受到伤害同等的虚拟血量**。

### 38.1 规则（按用户原案字面实现）

爆炸对载具实收伤害 X → 该车全部设备骨（bone_modules 中非 ERA/引擎/炮管/维修、
min_damage>0 且模块仍激活）中**视距内**（爆心→骨 OBB 中心连线无本车其它骨骼 OBB 阻挡，
复用 §36 LOS 过滤与三防误挡）的每根骨的通用累计表**各等额扣 X**；累计 ≥ min_damage →
`destroyModule`（逐模块失效 + 战果通知）。ERA 不变（机制二百分比，本规则排除 ERA 不
双计）；引擎/炮管不变（自有专属累计段）。面板虚拟血量/失效三态经既有同步自动更新。

⚠️ **全额口径**：每根可见骨各扣全额 X（非均摊）——一发 100 伤 HE 打掉爆心视野内所有
min_damage≤100 的设备（雷达 20/ECM 20/APS 30/DIRCM 30 全没，干扰机 100 剩皮）；被车体
挡住的设备安全。实机过狠可再改均摊/距离衰减（另立一轮）。

### 38.2 实现（`RVP_VehicleHitboxFactorManager.accumulateExplosionEquipmentDamage` + handler 两入账点，零 Mixin）

## 四十一、双雷达"概率性交替开关"根治 + 炮管受损扩散改固定+5（2026-09-29 第十五轮，用户实测）

### 41.1 交替开关真根因（全链路写点清查，非 enforce 误压）

用户实测：双雷达载具有概率交替开关。全量清查 `RadarUnit.on` 写点（服务端 S1-S7 / 客户端
C1-C6，见调查报告），enforce 强压判定键核实无误压；真凶 = **同一个"按 3"有两个门控不同
的写者**：

| | 本体 InputHandler（C1） | RVP 主控纠正（C2 旧版） |
|---|---|---|
| 触发 | `InputEvent.Key` 回调（**帧末 pollEvents** 执行） | `isDown` 每 tick 轮询上升沿（ClientTickEvent.END） |
| 门控 | 仅 `action==PRESS` + `mc.screen!=null` 跳过 | 无 screen 门、isDown 上升沿 |
| 范围 | 当前武器站的雷达 | 全车完好雷达 |

三个"只有一方执行"的错位窗口 → 快照基线被污染 → 下次方向判定反转 → 交替：

1. **快按**：down/up 两事件落同一帧间隙（fps>20 时多数帧无 tick）→ base 翻了、RVP 的
   isDown 轮询**永远没检出边沿** → 本次语义退化为逐台翻转 + 快照记录半途状态 → 下次慢按
   主控方向与预期相反；
2. **按住 3 开/关界面**：`setScreen → releaseAll()` 清 isDown；关界面后**键重复（REPEAT）**
   事件把 isDown 重新置 true → RVP 检出**假上升沿**执行主控翻转，而 base 只收到 REPEAT
   （非 PRESS）跳过 → 没有新物理按键却多翻一次——每开关一次界面翻一次 = 正是"交替开关"；
3. 上车/下车/载具重绑瞬间按着 3：假边沿。

放大器：base InputHandler **无损坏 gate**——每次按 3 坏雷达被 `toggle(null)` 翻开、1 tick
后才被 enforce 压回（视觉"雷达闪开"）。

### 41.2 修复（`RVP_ClientEvents` 重写，§22.2 主控语义不变）

1. **边沿判定改与本体同源**：新 `InputEvent.Key` 监听（`EventPriority.LOWEST` 保证在本体
   同事件 handler 之后）——仅 `action==PRESS`（天然排除 REPEAT 假边沿）、`mc.screen==null`
   （与本体 handleVehicleAction 同门）时置 **pending 校平标记**（含雷达键绑鼠标键的
   `MouseButton.Pre` 同路由监听，与 base onKey(MouseButton) 对齐）；
2. **本 tick 不再立即纠正**：ClientTickEvent.END 只做**下一 tick 校平**——本体翻转无论
   落在哪个 tick（键事件时序错位被吸收），校平都把全车完好雷达幂等收敛到同一期望方向
   （方向判定仍用快照：校平后立即重写快照为稳定态，不再被翻转过程污染）；
3. **坏雷达同帧即时压回**：事件监听里发现本体把坏雷达翻开的（isOn）立即 `toggle(false)`
   ——不进渲染帧、无闪烁（旧版靠 enforce 下一 tick 压回会闪）；
4. 校平是幂等 toggle：本体同帧多翻的一次被吸收，双写者不再叠加出多余翻转。

### 41.3 炮管受损档精度惩罚改固定扩散+5（用户定版）

`RVP_WeaponBase` 三选一"正常射击但散布 ×10"（`extraSpread = inaccuracy×9`）改为
**固定扩散 +5**（`extraSpread = 5`，消费点本就是加法 `spread = inaccuracy + extraSpread`）
——×10 对小散布武器惩罚过轻、大散布武器过重，固定增量全武器一致。哑火/炸膛两支不变。

### 41.4 实机清单（第三十轮，待用户实测）

### 41.5 近炸直伤排除出爆炸设备损伤口径（2026-09-29 第十六轮，用户实测）

**用户实测**：近炸引信一发把（视距内）所有辅助设备炸坏，"不像正常的爆炸判定毁伤"。

**根因**：近炸引爆（`detonateFuseAt(PROXIMITY)`）对本体的**定向全额直伤**
（`resolvedProximityTarget.hurt`，本体设计为"强制全额、不依赖 VehicleExplosion 距离
衰减、模拟直接命中"）挂着爆炸 msgId——被 §38 爆炸设备损伤钩子当成"爆炸对载具的实收"
入账。导弹级近炸直伤 800~2400 **全额且不过装甲**（HE 直击对设备走直击口径=过装甲后
实收，通常几十到几百）→ 视距内设备（阈值 20/30/100）一发全清。口径错配：近炸直伤是
"定向直伤"（点对点），不是"面积爆炸对载具的实收"。

**修复**（`RVP_VehicleHurtScalingHandler` 三处钩子统一加门）：爆炸设备入账排除
**RVP 结算窗口**（`RVP_HitVehicleListener.inRvpDamage()`，深度计数）——近炸直伤、
APS 拦截引爆等窗口内的定向伤害不入爆炸设备口径；窗口外的正常爆炸波及（如近炸弹的
`triggerExplosion` 波及其它载具、本体武器爆炸）判定不变。

**口径说明**：修复后近炸触发目标车设备吃 0（其车体已吃全额直伤，设备毁伤不由这发
定向伤害额外承担）；该弹爆炸对**其它**载具的波及仍按 §38 正常判定（视距内+衰减实收）。
若实机觉得"近炸贴脸应顺带毁设备"，可再定一个波及当量口径（另立一轮）。

### 41.6 外源爆炸双段入账去重（2026-09-29 第十七轮，用户实测 SBW 火箭筒一发拆 800 引擎）

**用户实测**：SBW 火箭筒炸坦克车体 -576 血（正常），但一发摧毁 800 累计阈的引擎——
部件虚拟血量入账超过车体实收 = 重复计算。本体/永无止境系列武器正常。

**根因（SBW 源码链路全查实）**：SBW 火箭对目标造成**两段独立 hurt**——直击段
`performDamage`（`gunfire`/`gunfire_absolute` 源）+ 爆炸段 `CustomExplosion` →
`onExplosionDetonate` 事件（原版 explosion 源，距离+可见性衰减）。**两段都非本体
`ywzj_vehicle.explosion` msgId** → handler 两段都走直击骨解析分支 → `tryDestroyBoneModules`
对同一根引擎骨**各入账一次**（直击段 ~300 + 爆炸段 ~576 ≈ 876 ≥ 800）。车体实收 =
两段合计 576（正常）；本体/永无止境武器单段单源（RVP 弹走 skip 自结算）所以正常。

**修复**：通用累计表 `accumulate` 新增带 `gameTime` 的重载——**同一游戏 tick 内同一
载具同一骨只接受首次入账**（键 `vehicleId|bone` → gameTime，重复调用返回当前累计不变），
六处累计调用点（设备/引擎/炮管/爆炸路径）全部切换。第二段同 tick 再碰同骨即被忽略——
一发 SBW 火箭对引擎只入账一次（~300 或 ~576，两发才能拆 800）。

**已知副作用（量级可接受）**：高射速武器同一 tick 多发命中同一部件骨只计第一发（该表
只服务炮管/引擎/设备三类累计部件，普通机枪/机炮弹不走此表）。跨 tick 不受影响。

### 41.7 入账口径根本修订：按"本段 hurt 实际血量损失"（2026-09-29 第十八轮，用户实测"bug 依旧、直击段就有问题"）

**同 tick 去重后用户复测仍异常**——深挖发现去重只挡"同 tick 重复"，挡不住 SBW 的
**三段跨 tick 结构**：performDamage 的穿甲/普通两次 forceHurt（同 tick，被去重并成 1 笔）
+ **CustomExplosion 延迟冲击波**（`shockwaveDelay` 按距离最长 100 tick，跨 gameTime，去重
拦不住）→ 延迟段再入账一次；且每段入账的 desiredFinal 含命中箱倍率（Engine 骨 1.3）与
本体重放数学，多段相加必然超载。

**根治（入账口径根本修订）**：`onVehicleAttack` 事件时点在扣血**之前**——捕获重放前
血量，重放完成后取差值 `actualLoss = healthBefore − self.getHealth()`；引擎/炮管/设备的
累计入账与 §38 爆炸设备钩子全部改用 **actualLoss（本段 hurt 实际血量损失）**：

- 语义即 §38 用户原案"扣除和载具受到伤害同等的虚拟血量"的严格化——多段武器每段各计
  各的实际损失，**总和恒等于载具总掉血**（SBW 火箭三段合计 576 → 引擎共入账 576 <
  800，存活且面板可见渐进中间态）；
- RVP 自家弹：重放 desiredFinal 本就等于该段实际损失，数值不变（零行为漂移）；
- ERA 分轨保留（predicted 模块前伤害，不受影响）；
- actualLoss = 0（伤害被阈值吞掉）时不入账不重放模块判定；
- §41.6 同 tick 去重保留（跨 tick 的合法多次爆炸各自入账，语义正确）。

### 41.8 SBW 武器直击段丢失——调查结论：SBW 上游行为，接受现状（2026-09-29，用户定版）

**现象**：SBW 武器打 ywzj 载具"有时候只有爆炸伤害没有直击伤害"（静止载具也偶发）。

**排查**：本体 SBW 兼容层（`EntityUtil.getHitResult` 的 `SuperbWarfareCompat.getHitResult` +
TACZ mixin）只覆盖**本体/TACZ 弹 → SBW 载具**方向；SBW 武器打 ywzj 载具走 SBW 自家
`IAdvancedHitDetection` 扫描（`ProjectileEntity.getHitResult` AABB 分支，静止载具包围盒
clip 正常必触发直击），不经过本体兼容层——**兼容层无可修点**。

**根因（SBW 上游 `ProjectileEntity.kt`，两处）**：
1. onHitEntity 开头 `this.damageValue *= (deltaMovement.length() / velocityValue)
   .coerceIn(0.0, 1.0)`——直击伤害随"当前速度/出膛速度"比例衰减（火箭阻力减速），爆炸
   伤害 `explosionDamageValue` 固定——远距离直击趋向 0、爆炸照常满额；
2. `tick()` 方块命中优先截断 `endVec` 后才做实体扫描——低瞄准角时火箭先触地/触墙，
   实体扫描段缩短，直击丢失、爆炸照常。

**用户定版**：接受现状，不再追修。相关联动（部件虚拟血量入账口径）已由 §41.7 根治
（按本段 hurt 实际血量损失入账，与 SBW 是否有直击段无关，均不会超额）。

### 41.9 辅助设备虚拟血量爆炸伤害距离衰减（2026-09-29 第十九轮，用户需求"最远处衰减到 5%"）

**公式**：部件虚拟血量入账 = 载具实收伤害 × `mult`，
`mult = clamp(1 − 0.95 × (骨最近OBB中心距爆心 / 爆炸半径), 0.05, 1)`——爆心贴脸全额、
爆炸半径处 5%、更远维持 5% 保底。设备/炮管/引擎三类统一；ERA 百分比与大导弹直伤口径
不受影响；`DEVICE_FALLOFF_MIN = 0.05` 可调。

**半径来源两路**：

1. **RVP 弹（精确）**：`RVP_BaseBullet.triggerExplosion` 触发前
   `pushExplosionRadius(radius)`、finally `pop`（manager ThreadLocal，同 tick 同线程）——
   空爆/近炸/直击各自的 resolvedRadius；
2. **外源 mod 爆炸（半径未知）**：回退固定参考半径 `FALLOFF_DEFAULT_RADIUS = 24` 格
   （常量可调；改 ≤0 = 外源爆炸不衰减维持全额）。

**实现**：`accumulateExplosionEquipmentDamage` 加 `explosionRadius` 参数；遮挡映射构建
从 `filterExplosionCandidates` **内联进本方法**（视距过滤与逐骨距离共用一次映射，废弃该
辅助方法）；handler 三钩子传 `peekExplosionRadius()`。

点 / push 载具互撞 / makeBoundingBox / tickPower 流体），缩结构 cube 会连碰撞一起缩。方案与
审计记录：`docs/plan/RVP船转向depth倍率_方案与提示词_20261001.md`。

**审计修正（实施前抓出，规格原稿两处错误）**：
1. **`depth` 是 `public double` 不是 float**（`VehicleCubeOBB.java:31`，旁证 AbstractVehicle:627
   显式窄化）——原稿 `depth:F` 会匹配失败直接 InjectionError；修正为 `depth:D` + handler double；
2. `parseVehicle`"全空即 EMPTY"早退必须纳入新字段——否则只配此字段的载具（052D）配置静默失效；
3. `@Mixin`/`@ModifyExpressionValue`/`@At` 三处 `remap = false`（mod 类非混淆）；
4. `tickMove()` 实测仅服务端执行（`AbstractVehicle.tick:545` 服务端分支）→ 配置只需服务端可用，
   无客户端同步要求。

**实现（3 文件 + 1 配置，零碰撞路径触碰）**：
- `RVP_VehicleExtendedConfigManager`：`VehicleExtendedConfig` 加第 7 组件
  `float turnDepthScale`（EMPTY=1.0f，isEnabled 纳入 ±1e-6 判定）；新增
  `parseTurnDepthScale`（`physics_info.turn_depth_scale`，非有限值/≤0 → 1.0）；
  静态入口 `getTurnDepthScale(AbstractVehicle)`；
- 新增 `mixin/RVP_VesselTurnDepthMixin.java`（公共数组）：`@ModifyExpressionValue`
  单点缩放 `tickMove` 内 `VehicleCubeOBB.depth`（D）的两处 GETFIELD（`depth > 0` 判定 +
  atan2 分母，均为预期缩放点）；handler 只做乘法+配置查询，零客户端类型引用；
- `ywzj_rvp.mixins.json` 公共数组登记。

**生效路径**：载具 JSON `physics_info.turn_depth_scale` → 数据包 reload
（`RVP_VehicleExtendedConfigManager.apply/parseVehicle`）→ `VehicleExtendedConfig.turnDepthScale`
→ `RVP_VesselTurnDepthMixin.rvp$scaleTurnDepth`（tickMove 两处 depth 读取 ×scale）→ 转向
角速度 atan2 分母缩小 → 掉头加速。碰撞路径（collectContacts/push/makeBoundingBox/tickPower）
不经过 tickMove，逐字节未动。

## 四十八、"大碰撞箱过穿"真正根因：原版 getEntities 单分节注册盲区（2026-10-01 深夜，字节码实锤+修复）

**排查历程**：§47 的近炸引信假设被用户实测否定（AGM-179 无近炸配置）。用户以
`/rvpobb watch`（含消失检测）复现并观测到决定性现象——**"没命中的导弹根本没有
watch 信息"**：watch 与真实命中链（`findEntityOnPathForSegment`）共用同一
`level().getEntities(...)` 候选收集，**watch 看不见 = 真实命中链也看不见**。

**根因（原版 1.20.1 字节码实锤，javap 反编译）**：
1. **单分节注册**：`PersistentEntitySectionManager.addEntityWithoutEvent` 只用
   `entity.blockPosition()` 派生一个 SectionPos——120 格的 052D 也只注册在其位置所在的
   **一个 16³ 分节**（无包围盒分节展开）；
2. **查询分节粗筛**：`EntitySectionStorage.forEachAccessibleNonEmptySection` 只遍历
   查询盒 X/Z ±2 分节、Y **下方扩 4 上方扩 0** 范围内的分节，`EntitySection.getEntities`
   的逐实体 AABB intersects 只对**已访问分节内的注册实体**执行；
3. **结论**：弹的段盒（查询盒）落在离载具注册分节超过 ±2 分节的船体区域（052D 艉部
   远端 5 分节、艏部 2.3 分节、俯冲高处的 Y 上方）时，`getEntities` **确定性返回空** →
   命中链无候选 → 完整过穿。probe 用 256 格长查询盒（跨几十个分节含注册分节）所以总能
   看到船（解释 probe 与实弹的矛盾）；卸 RVP 仍复现（本体固有语义）✓；小目标整体贴近
   注册分节 ✓；"碰撞箱越大盲区越大" ✓；§46 瞄准点（最大 OBB 中心）恰在 ±2 分节扩展
   边界上放大了暴露 ✓。

**修复（RVP 侧 2 文件 + 工具，不碰本体）**：
1. 新增 `util/RVP_ServerVehicleIndex`：`EntityJoinLevelEvent/EntityLeaveLevelEvent`
   维护每维度服务端 AbstractVehicle 注册表；`mergeWithVehicleIndex(level, queryBox,
   baseResults, extraFilter)`——注册表逐载具按 makeBoundingBox 包络（与原版粗筛同标准）
   与查询盒相交补筛，合并进原版 getEntities 结果；
   **⚠️ 2026-10-02 开关状态：本体修复覆盖其 AmmoEntity 链但 RVP 弹未受益
   （走自己的 findEntityOnPathForSegment，加 RVP 又过穿）——补丁已重新开启
   （`PATCH_ENABLED=true`）；待本体修复源码上传后核实再评估关闭；
2. `RVP_BaseBullet` 三处命中候选查询接补筛：`findEntityOnPathForSegment`（直击主链）、
   `findProximityTargetOnSegment`（近炸扫掠）、`tickTopAttackFuse`（攻顶探测）——
   原版查得到的照旧、盲区里的巨型载具由注册表兜底，谓词原样复用零语义变化；
3. `/rvpobb` 工具同步：probe/watch/VANISHED 重扫接注册表，新增 `/rvpobb querytest`
   （对最近载具的 OBB 中心/包络角放 2 格小查询盒跑**原版**查询，逐点报告"找到/★盲区"——
   盲区可视化，注册表补筛后命中链不再依赖原版查询）。
