# RVP 雷达与引擎骨骼部件实施记录（2026-09-26）

> 需求（用户定版）：新增两种骨骼模块类型——①RADAR 雷达部件：被打坏后对应雷达强制关闭，
> 多雷达载具按雷达分粒度、外置雷达中继车雷达被打坏母车失去外置雷达；②ENGINE 引擎部件：
> 窗口内累计直击伤害超一档功率减半（受损）、超二档功率清零（瘫痪，不关发动机、
> 方向机/高低机照常），两档均可被快修修复。写法与现有骨骼化部件框架一致。

## 一、调研结论（三路并行子代理）

1. **多雷达分粒度无需大改**：CSSA5/PS1SM 的跟踪/搜索雷达本就是两个独立 PartUnit
   （`lock_radar`/`scan_radar`，骨名=部件 id、独立 OBB/血量），`bone_modules` 写两条即成；
   全载具包不存在"同一 PartUnit 双雷达"。
2. **外置中继链自动断开**：`RVP_ExternalRadarSyncService.hasAnyRadarOn` 逐雷达查 `isOn()`，
   中继车雷达强制关闭后母车探测/扇区/锁自动清空——要求 2 零改动满足。
3. **三个"复活点"必须堵**（否则打坏的雷达被重新开机）：
   ① `RVP_GunnerRadarActions.prepareLockRadar`（gunner 锁定前自动开机）；
   ② `GunnerExternalRadarController.turnOnRelayRadars`（中继车 gunner 每 tick 保活开机）；
   ③ `C2SRadarPowerToggle`（玩家手动开机同步包——本体 toggle 是纯客户端本地操作，
   RVP 已有同步包补齐服务端）。
4. **关闭语义**：`RadarUnit.toggle(false)`（自带清锁定目标；RadarUnit 不是 SwitchableUnit，
   自持 on 字段，不进 NBT/不 syncData）；HUD/RWR/扫描/开关动画全链路自带 `isOn()` 门
   （`RVP_RadarScanService:85/:175`、`RVP_ClientRadarTickHandler:119`、`RadarUnit.tick:73`），
   强制关闭后自然停摆。
5. **引擎零 Mixin 挂点**：履带/轮式/船驱动字段是 public 逐实例字段（`initData→inject` 写入
   一次后本体不再重算），照 `RVP_WingSweepState` 先例经本体 `VehicleMoveEvent`（每载具每 tick）
   覆写 base×系数。**硬约束**：不碰 `ENGINE_ON`、不把 POWER 压 ≤20——本体炮塔/武器/雷达的
   `hasPower()`（POWER>20）门保持原样（发动机关闭约 80t 后 POWER≤20 即炮塔停转，此即
   "关发动机会卡方向机"的代码依据，削动力绝不能走这条路）。
6. **`bone_modules` 键=命中候选骨**：`resolve()` 的候选集 = hitbox_damage_factor ∪
   vehicle_explosion ∪ bone_modules 键——新骨只写 bone_modules 即纳入命中判定；
   **其 `damage_factor` 会覆盖 hitbox_damage_factor 同骨倍率**（manager :979-981），
   故新条目 damage_factor 必须照抄各车现有值。

## 二、实现内容

### RADAR
- `BoneModuleType.RADAR`（不参与爆炸百分比破坏，雷达只能直击打坏）。
- 服务端强制关闭三层：
  - **即时**：`tryDestroyBoneModules` 销毁 RADAR 后 `RVP_RadarModuleEnforcer.forceRadarOff`
    （toggle(false) 清锁）；
  - **巡检兜底**：`RVP_RadarModuleEnforcer`（ServerTickEvent 每 20t 遍历全部载具，
    失效骨雷达仍 isOn → 压回 off），任何遗漏的开机路径 1 秒内被纠正；
  - **三处 gate**：①②③（见调研 3）在 `toggle(true)` 前查
    `isModuleActive(vehicleId, radar.getId(), RADAR)`，失效即拒绝。
- 维修恢复：dev 队列自动（`repairableTypes` 缺省白名单排除 TRACK，新类型自动可修）；
  恢复后 `restoreRadar` 自动开机（用户定版"修好自动开机"）。

### ENGINE
- `BoneModuleType.ENGINE` + `BoneEngineConfig`（`bone_modules` 条目 `engine` 子对象：
  `threshold_light` / `threshold_heavy` / `power_multiplier_damaged` / `damage_window_ticks`，
  缺省 Java 默认 60/150/×0.5/600t；**2026-09-27 起 9 台引擎载具已按车种显式配置**：
  履带式坦克 600/900（t90m/t84bm/m1a2sep/ztz100/vt4/abramsx）、
  步战/防空 450/700（bmpt72/bukm3/ps1sm），详见载具配置清单）。
- **单发直毁路径跳过 ENGINE**（`tryDestroyBoneModules` 循环 `continue`）：失效完全由
  窗口累计驱动，否则一发过 min_damage 的炮弹会跳过受损档直接瘫痪。
- 累计：`tryDestroyBoneModules` 开头（无模块/低伤早退**之前**）`accumulateEngineDamage`
  ——hitBoneName+triggerDamage 累入 `RVP_EngineDamageTable`（UUID+骨→累计值+衰减速率，
  累计时捕获 `thresholdHeavy/window`，每 tick 线性衰减，**中间量不持久化**）；
  跨过重损阈值即 `destroyModule(ENGINE)` + `syncBoneModuleState`（瘫痪档随状态表持久化）。
  一处埋点覆盖三个调用方（RVP_BaseBullet 直击 / RVP_LaserWeapon 激光 /
  RVP_VehicleHurtScalingHandler 本体武器重放）。**爆炸波及暂不累计**（已知边界）。
- 消费端 `RVP_EnginePowerHandler`（VehicleMoveEvent，服务端）：逐骨档位
  （失效=2 瘫痪 / 累计≥阈1=1 受损 / 否则 0），取最差档 → 字段覆写 base×倍率：
  履带 `TrackedVehicle` 7 字段（brake/forward/backwardAcceleration、maxSpeedF/B、
  turnAcceleration、maxTurn）；轮式 `WheeledVehicle` 与船 `VesselVehicle`
  （brake/forward/backwardForce、maxSpeedF/B、turnStep、maxTurn）同法支持；
  直升机/固定翼动力走 POWER 比例路径不适用字段覆写（已知边界，未削）。
  未配置引擎部件的载具 `restoreAndCleanup` 幂等还原（零开销路径）。
- 客户端可见：新 `S2CEngineDamageState`（entityId+骨→档位 0/1/2，差分推送）→
  `RVP_ClientEngineDamageState` 侧表 → 面板 ENGINE 栏目（正常/受损黄注记/瘫痪红框）。
- 维修：`tryStart` 成功即 `clearVehicle` 清累计（受损档随快修回落）；瘫痪档走 dev 队列
  掷骰恢复，`restoreBoneModules` 恢复 ENGINE 时清该骨累计（防恢复后残存累计立即再跨阈值）。

## 四、已知边界

1. 爆炸波及不累计引擎伤害（只累计直击）；如需"炸到引擎骨也累计"，在
   `destroyModulesByExplosionRadius` 加同款累计即可。
2. 直升机/固定翼配 ENGINE 不生效（POWER 比例路径不适用字段覆写，未做）。
3. 引擎累计中间量不持久化（停服清零受损档进度；瘫痪档随失效表持久化，不受影响）。
4. TRACK 履带模块仍为占位（用户确认暂不做）；其"动力损失"未来实现可与
   RVP_EnginePowerHandler 共用消费端。
5. 雷达强制关闭不写 NBT：本体 RadarUnit.on 本就不持久化，重启后雷达默认开机 →
   若模块仍失效，巡检 1 秒内压回 off。

## 八、实机事故：引擎覆写 NaN 污染 + 修复（2026-09-27）

**现象（用户实机）**：打瘫引擎后进入载具 → 载具消失、地形消失、无法操作；重进世界
载具加载失败。

**根因（日志 latest.log 00:50:11 Cupboard 拦截 NBT 实证）**：t90m 存档
`Pos:[1287.3, NaN, 6454.9]`、`Rotation:[NaN, 0]`、`turret.xRot/yRot:NaN`——整车
位置/朝向/炮塔被 NaN 污染后写档，重新加载即 `Entity has invalid position`
（EntityType 加载异常 → 实体丢弃 → 所在区块渲染异常）。

**污染链路（复盘）**：`RVP_EnginePowerHandler` 每覆写 `setDeltaMovement` 路径的驱动力
字段无 NaN 防护——`damagedMultiplier` 跨骨共享变量存在被非法配置污染的理论通路，
且基准捕获（captureXxx）在 inject 时序竞态下可能捕获到未初始化值；任一 NaN 进入
`setDeltaMovement` → 本体物理 tick 逐链扩散到位置/旋转/炮塔 → 存档固化。

**修复（三处防御，防火墙式）**：
1. 载具位置 NaN 时直接跳过本 tick 覆写并还原清理（不火上浇油）；
2. 倍率合法性钳制：damagedMultiplier/multiplier 任何 NaN/负数/＞1 一律钳回 0.5，
   最终值仍非法则整 tick 跳过覆写；
3. 基准校验 `capturedValid`：捕获的 14 个动力字段任一非有限或 ≤0 时跳过覆写
   （防 inject 竞态捕获到未初始化值）。

**善后提示**：已污染的存档里那辆 t90m 的 NBT 已含 NaN，需删除该实体（或用
NBT 编辑器修 Pos/Rotation）后重新放车；新 jar 不会再产生新的污染。

## 九、部件受击分轨判定（2026-09-27 用户定版）

**需求**：除 ERA 外的部件，受击判定按**实际到骨伤害**（乘命中倍率、过装甲层后的
最终入账值），不按武器裸伤——"防弹衣逻辑"：大倍率装甲骨上的雷达被小倍率弹蹭一下
不该打坏。

**实现**：`tryDestroyBoneModules` 增加 `useFinalDamageForModules` + `finalBoneDamage`
参数（分轨）：
- **ERA**：仍按模块前伤害（`preHitboxDamage` / `hitDamageBeforeHitbox` / `predicted`，
  旧平衡——装甲车 ERA 门槛按裸弹伤设计）；
- **其余模块（雷达/引擎累计/APS/干扰机等）**：按实际到骨伤害（`finalDamage` /
  激光 `hitDamage` 过装甲后 / 重放 `adjustedAmount`）重判 min_damage 门槛。
三个调用方（RVP_BaseBullet / RVP_LaserWeapon / RVP_VehicleHurtScalingHandler）已同步
传最终伤害；旧 4 参重载保留（等价分轨关闭）。

**实机清单补充**：9. 打瘫引擎进车不再出现载具/地形消失（修复验证；已污染存档先删车）；
10. 大倍率装甲骨（如炮塔 0.4 倍率）上的雷达骨，小伤害弹不再一击打坏（到骨伤害
不足 min_damage）。

**需求**：命中展板（`RVP_HitIndicatorOverlay`，右上角"命中XX -x%"）下方显示 60 tick
（3 秒）战果文案——摧毁敌方部件显示"摧毁光电干扰机/引擎/APS 探测器"等；
把敌方引擎打进受损档时显示"重创发动机"。

**实现**：

  `shooter` 参数（三调用方传入：弹体 owner / 激光 shooter / 本体武器重放 source 攻击者）；
  每销毁一个模块即 `notifyModuleHit` 推送（gunner 等非玩家射手不发；

## 十、"瘫痪后还能开"根因修复 + 战果通知 UI 三改 + HUD 速度行（2026-09-27 第二轮）

### 10.1 引擎瘫痪失效根因与重构（基准重锚）

**现象**：引擎打瘫后（含上下车后）载具仍可驾驶。

**根因**：首版 `RVP_EnginePowerHandler` 用"一次性内存捕获"（首次接管时把本体动力字段
抄进 EngineRuntime 作基准，之后覆写=基准×倍率）。本体在**玩家上下车/跨区块卸载重载/
display 变更**等时机会 `initData → VehicleData.inject` **把动力字段重置回 JSON 配置满值**，
而 captured 标记还在——覆写继续用旧基准、或 capturedValid 拒绝后字段停留 inject 满值
→ 瘫痪车复活。

**修复（重构）**：删除捕获态全套（captured/baseXxx/capturedValid/restoreAndCleanup），
`applyPower` 改为**每 tick 从 `CommonAssetsManager.vehicleDataManager().getVehicleData()`
直读该载具 JSON 权威配置**（与 inject 写入同源；RVP 战术地图已有同款调用先例），
覆写 = 配置值 × 倍率——本体无论何时重置字段，下一 tick 即被纠正回"配置值×0"。
覆写只在"该载具配置了引擎部件"时发生，未配置载具字段从不被触碰。NaN 防火墙保留
（位置非有限/配置值非有限时跳过本 tick）。EngineRuntime 只剩档位差分记忆。

## 十四、NaN 真正根因实锤（存档 NBT 抓现行）+ 修复（2026-09-27 深夜第三轮）

### 14.1 推翻"旧档遗留"结论——新会话存档内抓到 NaN 现行

对新世界(24)（03:01 会话，修复 jar）存档 entities/*.mca 全量解压扫描：**1 辆 t90m 的
Pos[Y] = 0x7FF8000000000000（标准 quiet NaN）、Rotation[0] = NaN**——NaN 在修复 jar
下依然产生，前一轮"旧档遗留"结论错误（02:33 会话零警告是因为那辆 NaN 车属于更早会话，
而本次新产生的 NaN 车只在退出存档后、下次加载时才暴露）。

### 14.2 真正根因（除零，实锤）

瘫痪档旧实现把 `maxSpeedForward` 一并 ×0；本体 `TrackedVehicle.tickMove:165` 转向公式：

```java
this.setYRot(this.getYRot() + vt + Math.abs(vf) / maxSpeedForward * vt / 5);
```

**除以被清零的 maxSpeedForward → 0/0 = NaN**（一转向即触发）→ NaN 进 YRot →
getLookAngle 返回 NaN → setDeltaMovement(NaN) → 下一 tick 物理引擎
setPos(y−NaN) → Pos 全 NaN → turret 旋转同污染 → 退出存档固化 → 下次加载
`Entity has invalid position` 载具消失。"受损档 ×0.5"除数非零无恙，**只有打瘫才炸**
——与两次实机复现完全吻合。前两轮修复（捕获模式、NaN 防火墙）都没抓到它，因为
NaN 不经过 RVP 覆写的值本身（乘 0 合法），而是本体拿清零字段当除数。

### 14.3 修复（除零保护）

`applyPower` 重写倍率作用面：**速度上限字段（maxSpeedForward/Backward）与转向上限
（maxTurn）永不参与倍率**（保持配置原值——maxSpeed>0 但加速度/转向力为 0 时 vf/vt
恒 0，车依然寸步不动，且本体任何除以该字段的公式都安全）；只倍率化"力/加速度"类字段
（brake/forward/backwardAcceleration（Force）、turnAcceleration/turnStep）。
轮式/船的 turnStep 同理为积分速率也倍率化，maxTurn 保留原值。

### 14.4 平衡配置同轮确认（上一批，随本 jar 生效）

雷达骨 min_damage 统一 20；履带车 max_speed_forward=50KPH，倒车 ztz100=50 /
bmpt72+t90m=4 / 其余=25。引擎累计口径复核为实际到骨伤害（3BM59 近距 1 发受损
2 发瘫；带衰减 3 发瘫、掉血约 1100——与用户实测自洽）。

`能量==0 → POWER=0` → `hasPower()` 假 → tickMove 直接 return（转向同样会停）。

## 二十一、重创档"只能转向不能开"根因 + 极速/加速度分路（2026-09-28 凌晨）

**用户实机**：重创档（×0.5）下转向正常、前进/后退完全无法起步。且"没油+发动机未损坏
时能正常开"（本体 getEnergy 在 infiniteFuel 下返回 Float.MIN_VALUE，POWER 照常到 100）。

**根因**：履带车前进速度 = 每 tick `vf += forwardAcceleration` 积分，同时 PhysicsEngine
对接地车辆每 tick 施加**地面摩擦减速**——加速度砍半后净加速 ≤ 摩擦，车辆永远起不了步；
转向是直接积分朝向速率不经摩擦，故转向正常。此前把"功率减半"实现为全字段 ×0.5，
把起步能力也砍没了。

**修复（极速/加速度分路）**：`applyPower` 拆双倍率——`speedMult` 作用于极速/转向上限
（maxSpeedForward/Backward、maxTurn），`accelMult` 作用于加速度/推力/转向速率
（forwardAcceleration 等）。重创档 speedMult=0.5（极速 25 KPH）、accelMult 钳 ≥0.2
（保留起步能力）；瘫痪档 1e-4 全字段（趴窝）。诊断日志同步记录两路倍率与实际字段值。

**实机清单（第九轮）**：重创 → 能正常起步、极速 25 KPH（速度行可见）；瘫痪 → 趴窝；
快修恢复后极速 50。


## 二十二、双雷达主控开关语义 + 修好自动开机同步（2026-09-28 凌晨第二波）

## 二十三、主控开关方向判定修复（2026-09-28，用户实机"一好一坏关不掉"）

**根因（审自身代码发现）**：主控开关的方向判定用了 `workingOnNow.equals(snapshot)`——
但 `workingOnNow` 是 tick 末读取的实时状态，而本体 InputHandler 的逐台翻转在**本 tick
更早**的按键事件里已执行完：按下时原来开着的雷达刚被翻成关 → workingOnNow 永远 ≠
快照 → 永远判为"有未开"→ 纠正逻辑把刚关掉的完好雷达**又强行开回**。这就是"一好一坏
关不掉雷达"（反辐射无法反制）的完整链路，与"只开不关"旧版无关（那版已删）。

**修复**：方向判定只比较**快照 vs 工作雷达 id 集合**（`snapshot.containsAll(工作雷达id)`
且数量一致 = 按键前全开）。判定语义不变：按键前全开 → 本次全关（反辐射反制）；
有未开的 → 本次全开（回到双雷达）。

**实机**：一好一坏 → 按 3 → 完好雷达关闭（可反制 ARM）；再按 3 → 重新开启。


## 二十四、重创档动力倍率 0.75（2026-09-28，用户定版）

**背景**：§21"重创档 accelMult=max(0.5, 0.2)=0.5 能起步"的结论被用户实机推翻——

### 29.1 现象与根因（两个叠加，均非本轮炮管功能引入，0925 骨模块系统时代遗留）

   真炮管报"炮塔"，0.6/0.4 倍率跟着错。

渲染（`VehicleRender.renderHitbox` 红框）与命中 part_unit 源同对象故渲染正确；普通

mixin（仅 VectorUtil 过滤）、initData 快照、插值旧值均无嫌疑。

### 31.2.4.9 面板行全空真根因实锤：StyleScope 挂起重算缺失（2026-09-28，用户实机日志+反编译）

反编译 AUI（1.2.4 mapped）渲染管线闭合链条：

- **渲染读 `Document.getPaintList()`**（RenderNode 列表）；
- `drawFlatDocumentInContext` 每帧调 **`commitPendingStyleRecalcForRender()`** →
  `style.flushPendingUpdates()`——刷 StyleScope **挂起的样式重算**并更新 PaintList；
- **挂起入口 = `Document.requestStyleRecalc(element)`**（StyleScope.requestRecalc，
  **SUBTREE 模式**整个子树重算）；

**此前所有轮次从未调过 requestStyleRecalc**——运行中 append 的行永远不进 PaintList（不渲染）；
markDirty 走 RenderQueue（视觉重绘脏，另一条队列），与样式重算是两套独立机制。

**修复**：`refreshDynamic` 末尾 `document.requestStyleRecalc(categoryScroll)`（SUBTREE 子树
重算挂起）+ 保留 markDirty(RELAYOUT|REPAINT) 视觉标脏——渲染帧自动 commit 重建 PaintList。

**教训入册**：AUI 的 DOM 变更生效链 = `requestStyleRecalc（挂起）→ 渲染帧
commitPendingStyleRecalcForRender → flushPendingUpdates → PaintList → 绘制`；`refresh()/
refreshStyles()` 是**模板热重载**（重新解析 HTML 模板，非轻量刷新，滥用即闪烁根源）；
`markDirty` 只管视觉重绘不重布局。

### 31.2.4.11 面板刷新最终架构：首建一次 + 运行中原地更新（2026-09-28 第四版，用户实机确认）

**决定性对照**：本体改装屏在 init 时一次建全列表、运行中零调用即实时上屏——**AUI 每帧
渲染直接读 DOM 当前态，但 init 之后 append 的新子树不进入渲染**（原因同前两轮推断）。

**最终架构**：

3. 行结构固定化：`buildRow` **恒建 extra 槽**（空文本占位，原地更新按固定子序写）；
4. init 不再清缓存（Document 同实例，元素引用跨 init 有效）。

## 三十二、俯视图 TOP VIEW 闪烁根治：取景冻结（2026-09-29，交接遗留项）

### 32.1 排查过程（三轮排除，全部有实据）

面板第四版确认"成功了大半"后的交接遗留——俯视图走 `renderSkeletonNative` 每帧原生
scissor 绘制（不走 DOM/AUI），本轮反编译 AUI（1.2.4 mapped，decomp 缓存在
`_tmp_aui_decomp/`）+ 对照本体观瞄实现逐链排查：

1. **DOM 画布矩形排除**：`Element.getBoundingClientRect` → `Rect.of` → `RectFrameCache`
   （帧内缓存/帧外回退 `getCommittedRectIfValid`，按 viewportVersion+styleVersion+scroll
   依赖哈希校验）——`#skeleton-canvas` 是 `position:absolute; 100%×100%` 锚点，父级
   `flex: 0 0 45%` 定高；`markDirty(RELAYOUT)` 的目标（hpText/hpFill/categoryScroll）
   均不在其祖先链上，提交矩形跨帧稳定；
2. **数据链路排除**：`VehicleCubeOBB.update` 的 `positionO/rotationO` 快照时机、
   `AbstractVehicle.tick` 末尾 `updateOBBs`、本体 `VehicleScopeOverlay` 同款插值数学
   （xo→getX / positionO→position / slerp rotationO→rotation / lerpZRotDiff）——静止时
   全部输入对 partialTick 不变，本体观瞄图无闪烁报告佐证数据源干净；
3. **上屏链路排除**：`ApricityScreen.render` 内 AUI 画完即 `endBatch`，原生绘制在其后
   （z=400 深度已实证）；`drawRectByCorner` 纯 hLine/vLine 无 GL 状态副作用；
   `resolveFlatDocumentBaseZ` 分层（1+layer×251.25）不影响已验证的 z=400。

### 32.2 根因

**俯视图是全项目唯一每帧重算"取景框"的绘制**：旧版 `render()` 每帧用插值实时数据重算
fit cube 的**旋转敏感 AABB 包络**（`hw·|cos|+hd·|sin|`）→ `scale = min(画布/包络)` 与
`translate(−包络中点)` 逐帧变化——炮塔回转（车体本地系里炮管组 cube 中心绕塔轴公转）、
悬架微振、行驶俯仰侧倾时，**整个俯视图逐帧缩放+平移跳动**，即交接文档假设的
"帧间布局跳动"。本体观瞄图同数据不闪，正因它固定 10px/格、锚定载具中心、无自适应包络。

### 32.3 修复（`RVP_EquipSkeletonRenderer.render` + 面板屏调用点）

- **包络改角度无关半径**：`max(√(cx²+cy²)+√(hw²+hd²))`（fit cube 中心到载具原点距离
  + 角点半径，三角不等上界）——画布空间中整车随炮塔**刚性旋转**（180−炮塔偏航全局旋转），
  角点到原点距离恒定，任意炮塔角/车体朝向都不裁切；
- **取景冻结缓存 `Framing`**（面板屏实例持有、开屏自然重置）：key = 载具 entityId+画布
  像素尺寸；半径**只增不减**——实测变大（炮塔扫到更远）立即跟随一档后再次冻结，变小
  不收缩——静止时帧间像素级全等，无任何连续缩放呼吸；
- **居中锚定载具原点**（删除包络质心居中，本体观瞄同款锚点选择）；fit 排除炮管的既有
  设计不变（炮管超出包络的裁切行为与旧版一致）。

## 三十三、回血闪烁真根因 + t90m 烟雾弹链路（2026-09-29 第二轮，用户实机反馈）

### 33.1 回血闪烁真根因（AUI 反编译证据链闭环）

**触发开关**：`buildDynamicSignature` 含 `(int) vehicle.getHealth()`——焊枪回血 +1%/2t、
快修每 tick 回血 → 回血期间每个 10 帧节流点签名几乎必变 → `refreshDynamic` 全路径高频跑；
平时（静止不打架）签名不变早退，永远走 committed 快路径——这就是"只有回血时闪"。

**失效链**（反编译 AUI 1.2.4 mapped，缓存于 `_tmp_aui_decomp/`）：
1. `hpText.setTextContent` 当场 `invalidateLayoutSubtree` + `forEachRoute` 沿祖先链清
   html/body/main 的 layoutVersion/size/box（Element.java:1781-1793）；
2. `markDirty(RELAYOUT)` 在 commit 时 `Drawer.flushUpdates` 对每个标脏元素 `forEachRoute`
   清到根 + `position.clear()` **递归清整树 committedRect**（Drawer.java:38-44、
   RenderElement.java:86-91）→ `skeletonCanvas` 的已提交矩形每轮必失效；
3. `renderSkeletonNative` 在 refreshDynamic **之后的同帧**裸读 `getBoundingClientRect` →
   committed 失效 → `Rect.of` 走实时重建 → 命中"擦了一半"的缓存态：`#skeleton-canvas` 是
   `100%×100%` 空锚点 div，containing block 尺寸缓存中间态不可直接给出时**百分比尺寸塌陷
   为 0**（Size.java:520/556/833-858）→ `rect.width<=8` → 整帧跳过 → 俯视图与底色帧交替
   = 疯狂闪烁。AUI 自身重绘无空白帧（每帧全量 paintList），问题全在 RVP 读点时机。

### 33.2 修复（三点，纯客户端）

1. **画布矩形帧首预读 + 两帧稳定才采用**（`RVP_EquipPanelScreen`）：`getBoundingClientRect`
   挪到 `super.render` **之前**（上一帧 commit 完成后的自洽态，committed 必有效）；原始读数
   连续两帧一致（±1px）才更新采用值，无效（≤8px）沿用最近有效矩形——瞬时塌陷/位移读数
   全部过滤，跳帧空白与 scissor 跳动同根消灭；
2. **Framing key 收敛为 vehicleId**（`RVP_EquipSkeletonRenderer`）：包络半径是视空间量与
   画布尺寸无关；§32 版把画布尺寸放进 key，画布 ±1px 抖动即重置取景（放大器之二）——
   收敛后画布变化只影响当帧 scale 换算、不重置只增不减半径；
3. **回血期 DOM 无效化减量**：`updateDynamicRows` 行内容签名门控（不变零写入零 markDirty）、
   `rebuildQueues` 的 `fillQueueList` replaceChildren 按队列签名门控（prune 校验照跑）、
   `updateHp`/`updateForecast` 等值守卫（AUI `setTextContent` 无条件 markDirty(15)，等值
   不写）、`refreshDynamic` 只对**真正变化**的容器 markDirty。
