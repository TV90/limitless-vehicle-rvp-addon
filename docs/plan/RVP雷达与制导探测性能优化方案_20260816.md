# RVP 雷达与制导探测性能优化技术方案

> 阶段：方案稿。目的：解决纯 Forge 服务端严重掉 TPS 问题——把"超大箱子扫描实体"改为
> "遍历已加载实体（O(实体)）"，并按 **显示 vs 决策** 分流：雷达显示走服务端快照广播（参考 MCHR），
> 导弹导引头/干扰判定保持服务端权威、仅优化扫描方式。
> 日期：2026-08-16

## 1. 背景与现状（TPS 热点）

| 系统 | 现状 | 成本 |
| --- | --- | --- |
| 玩家雷达显示 | 客户端 `RVP_ClientRadarTickHandler.scanPhaseRadar` → `Radar.scanTargets` | `getEntities(±maxScanDistance 立方体)`：1024 范围 → 2048³ ≈ **200 万区块截面**/次 |
| 炮手雷达表（AI 载具） | 服务端 `RVP_RadarScanService`（每 4 tick）→ `Radar.scanTargets` + `appendRadarVisibleChaffDecoys` | 同上，每 4 tick 数百万截面 |
| ARH/AIR 导引头探测 | 服务端制导 `RVP_RuntimeSeekerSupport.scanRadarTarget/scanInfraredTarget` | `Radar.scanTargets` / `getEntities(±range 立方体)`（range 可达上千格） |
| 干扰/脱锁判定 | 服务端制导 `RVP_CountermeasureState.query` → `hasJamInSeekerCone/findDecoyInSeekerCone` | 走廊/目标中心箱子 `getEntities`（已封顶 256，仍每导弹每 tick） |

**根因**：`Radar.scanTargets` 用 `maxScanDistance` 建 `AABB ±R` 立方体做 `getEntities`，遍历的是**箱子内所有区块截面**（O(R³)），而不是实体数。长程雷达（F16 1024、SAM 更高）单次就是数百万次截面查找。

**参考 MCHR（`MCH_EntityInfoManager` + `MCH_EntityInfoClientTracker`）**：
- 服务端每 tick 遍历 `world.loadedEntityList`（O(实体)）→ 过滤 → 全量快照 `PacketEntityInfoSync` 广播给所有客户端。
- 客户端本地跟踪 + 过期清理，**只渲染不扫描**。

## 2. 核心原则：显示 vs 决策 分流

| 类别 | 系统 | 数据流 | 结论 |
| --- | --- | --- | --- |
| **显示（客户端 UI）** | 玩家雷达 overlay / 超视距锁定盒 | 服务端广播接触快照 → 客户端过滤渲染 | ✅ 走快照广播（参考 MCHR） |
| **决策（服务端权威）** | ARH/IR 导引头目标选择、干扰/脱锁判定 | 服务端制导自行 O(实体) 扫描 | ✅ 只改扫描方式，**不广播** |

**为什么导引头/干扰判定不广播**：
- 它们是导弹的**实时制导决策**（追踪谁、是否脱锁、转锁哪个诱饵），必须服务端权威。
- 广播过去的"接触清单"最终还要导引头自己再做 FOV/角度/距离/脱锁计算——服务端仍要算，广播只增加网络与客户端负担，无收益。
- 所以对它们只做"扫描方式 O(实体) 化"，保留现有 FOV/角度/记忆/脱锁逻辑。

## 3. 雷达显示：服务端快照广播（客户端过滤）

### 3.1 服务端
```java
// 每 2~4 tick 节流
for (ServerLevel level : server.getAllLevels()) {
    for (Entity e : level.getEntities().getAll()) {        // O(已加载实体)
        if (isRadarVisible(e))                             // 载具/弹体/箔条（含类别）
            snapshot.put(e.getId(), RadarContact.of(e));   // id + 位置 + 类别
    }
}
sendToClients(new S2CRadarSnapshot(snapshot, seq));        // 节流广播
```

- 只广播**轻量信息**：entityId + 位置（可量化）+ 类别枚举（VEHICLE / AMMO / CHAFF / DECOY）。
- 节流：每 2~4 tick；可选按玩家载具周围半径裁剪，控制包体。
- 乱序保护 + 客户端本地过期清理（对齐 MCHR `snapshotSeq` / 超时清理）。

### 3.2 客户端
```java
void applySnapshot(S2CRadarSnapshot pkt) {
    for (RadarUnit radar : 本地载具的雷达) {
        List<Entity> contacts = 现有扫描面积过滤(pkt 实体清单);
        // 距离 ≤ maxScanDistance / 扇区角 / 扫描高度 / 弹体信号缩放 / 箔条可见性与上限
        for (Entity c : contacts) radar.detect(c);          // 写回本体雷达表
    }
}
```

- **扫描面积判定逻辑完全复用现有代码**（`RVP_RadarScanHelper` 的距离/扇区/高度/弹体信号/箔条过滤），只是数据源从"箱子扫"换成"广播清单"。
- 命中结果仍写回本体 `radar.detect(entity)` → 现有雷达 overlay / 超视距 / SARH/ARH 武器锁定读的仍是这张表，**行为不变**。

### 3.3 保留的现有功能
| 功能 | 保留方式 |
| --- | --- |
| 雷达 overlay / 锁定盒 | 客户端从广播清单过滤 → 写回 `radar.detect()` → 现有渲染/锁定读取 |
| 扫描面积（距离/扇区/高度） | 过滤逻辑复用 |
| 弹体信号缩放（RVP 弹体入表） | 客户端按类别+位置套用 `appendRvpAmmoTargets` 的缩放 |
| 箔条可见性（热焰弹不入表、箔条入表、上限 8 均匀分布） | 复用 `filterRadarInvisibleDecoys` / `appendRadarVisibleChaffDecoys` |
| 炮手（AI）雷达表 | 服务端单独保留：改 O(实体) 遍历，喂本体雷达表（导弹制导依赖） |

## 4. 导弹导引头探测（ARH / AIR / IR）：服务端 O(实体) 扫描

- 现状：`scanRadarTarget` / `scanInfraredTarget` 用 `Radar.scanTargets` / `getEntities(±range)` 大箱子扫。
- 改：服务端遍历导弹周围已加载实体（或按类别预筛），套用现有 `passesAcquireLimits`（距离/角度）+ 信号缩放 + chaff 抗性罚分。
- **不广播**：导引头需要的是实时目标清单做制导，服务端自算。
- 保留：`scanIntervalTick` 节流、`maxLockAngle` FOV、`scanRadius` 封顶（256）、IR 可锁热焰弹、ARH/AIR 可锁箔条（chaff 抗性罚分）。

## 5. 干扰/脱锁判定：服务端 O(实体) 扫描

- 现状：`RVP_CountermeasureState.query` → `hasJamInSeekerCone` / `findDecoyInSeekerCone` 用走廊箱子 `getEntities`（每导弹每 tick）。
- 改：服务端遍历导弹检测区域内已加载干扰物实体（`RVP_Decoy`），套用现有锥体角度/距离/40 tick 记忆/`seekerJamLimit` 判定。
- **不广播**：脱锁/转锁是导弹决策，服务端权威。
- 保留：锥形∪目标 40 格圆并集、40 tick 视场记忆、追"记忆最久"诱饵转锁、干扰期关近炸、烟雾 OBB 遮蔽。

## 6. 落地步骤

1. **服务端扫描 O(实体) 化**（先去最大热点，功能不变）：
   - `RVP_RadarScanService`（炮手雷达表）：把 `Radar.scanTargets` 换成遍历已加载实体 + 现有过滤。
   - `RVP_RadarScanHelper.appendRadarVisibleChaffDecoys`：箱子扫换成小范围已加载实体过滤。
   - `scanRadarTarget / scanInfraredTarget`（导引头）：换 O(实体) 过滤。
   - `hasJamInSeekerCone / findDecoyInSeekerCone`（干扰）：换小范围 O(实体) 过滤。
2. **新增 S2C 雷达快照**：`S2CRadarSnapshot`（entityId+位置+类别+seq）+ 服务端快照构建（节流）+ 客户端接收/过滤/写回本体雷达表。
3. **客户端雷达 overlay/BVR 复用**：不改造渲染，只换数据来源。
4. **验证**：`runServer` 冒烟 + 实测 TPS（对比优化前后）。

## 7. 快照包设计（参考 MCHR）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `entityId` | int | 接触实体 id |
| `x/y/z` | int 或 float（量化） | 位置（客户端还需实体本体渲染，仅需位置做面积判定） |
| `category` | enum | VEHICLE / AMMO / CHAFF / DECOY |
| `snapshotSeq` | long | 递增序号，乱序保护 |
| 节流 | 2~4 tick | 或按玩家载具半径裁剪 |

- 客户端本地过期清理（超时 + 缺席序号），服务端不发 REMOVE（对齐 MCHR）。

## 8. 风险与权衡

| 项 | 说明 |
| --- | --- |
| 快照包体 | 实体多时包大 → 节流 + 半径裁剪；信息极简（id+位置+类别） |
| 显示延迟 | 节流 2~4 tick → 雷达接触最多滞后 0.1~0.2s，可接受 |
| 服务端权威性 | 导引头/干扰判定**不**改广播，保持服务端计算 → 无公平性/权威问题 |
| 改动面 | 新增快照包 + 服务端构建 + 客户端过滤接入；雷达 overlay/锁定零改造 |
