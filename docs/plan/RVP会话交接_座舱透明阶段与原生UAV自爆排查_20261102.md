## 直接放置 UAV 自爆不回传：排查结论

### 已确认的逻辑缺口

1. `RVP_VehicleSelfDestructService.java:29` 只用 `isDeployableUavInstance(carrier)` 区分是否需要回传。直接放置的本体 `uav: true` 载具没有这个母车部署标记，因而被当作普通有人载具。
2. 同文件第 36、44 行：返回点安全校验和 `returnPassengersForTermination` 仅对部署实例执行；普通原生 UAV 的返回函数直接短路成功。第 56–62 行实际执行 `stopRiding → setDestroyed → detonateAtCarrier → discard`，没有显式的 ServerPlayer 传送同步或回传结果校验。
3. 本体 `AbstractVehicle.java:878–887` 登机时记录 `fakeOperatorPosition` 并生成假玩家。第 1099–1110 行能提供原生 UAV 的返回点；说明此场景本来有返回点，并不是普通有人载具那种无返回点的情况。
4. 下车链 `LivingEntity.stopRiding → dismountVehicle → ServerPlayer.dismountTo` 最终是 `removeVehicle + setPos`；与 `ServerPlayer.teleportTo` 不同，它不发送明确的客户端传送包，也不建立 teleport acknowledgement 状态。
5. 本体 `AbstractVehicle.removePassenger:856–874 → onLeaveVehicle:931–943` 已清空驾驶员。之后 `onRemovedFromWorld:397` 要求 `getDriver() instanceof ServerPlayer && fakeOperator != null` 的显式回传兜底无法再触发。
6. `RVP_LinkedUavEventHandler.handleDismount:397` 同样只接管部署实例，直接放置 UAV 不会被 RVP 的返回队列补救。

### 对实测现象的解释与证据边界

- 服务端下车坐标可能短暂被设回假玩家位置，但客户端没有收到强制传送同步，后续旧位置的移动包仍可能覆盖服务端坐标；这条链路可以解释“爆炸后留在无人机位置”。创造模式/单机有更宽松的移动校验，不能靠反作弊纠正来保证回传。
- 这不是单纯“爆炸太快”：原生 UAV 这一分支根本没有可靠的回传事务。应先补分支与同步，再考虑爆炸执行点；只加延时不能形成保证。
- 本次证据为用户实测 + 本地源码调用链；已用当前构建依赖 0.6.2-all 的字节码核对本体关键方法。没有完成带客户端的日志复现，因此没有声称观测到了某一个移动包实际回写。
- `uav_c4` 配置的 `uav: true`、`self_destruct_vehicle: true` 正确，不应为修复此问题改炸弹伤害或半径。
- 现有 `RVP_SelfDestructSequenceTest` 仅验证传入回调的执行顺序；调用者把原生 UAV 的回传回调短路为成功，测试没有覆盖这一分类缺口。

## 补充排查：SUAV 与三种旋翼无人机的部署模式

- 用户追问为何三种旋翼无人机没有采用 SUAV 相同部署模式；本轮只解释与对照，不改配置/源码。
- 母车部署入口实际共用 `RVP_DeployableUavService.deploy`、`configureLink`、M 键切换和 RVP 母车返回队列；并非三种旋翼机另建了一套母车部署器。
- 差异来自原模板：`suav.json` 没有本体 `uav` 字段，默认 false，且 `hide_passenger: true`；`uav_c4/uav_recon/uav_rpg.json:35` 均保留 `uav: true`。新增母车候选时只引用既有模板，没有统一这个开关。
- 因此 SUAV 登机由 RVP handleMount 的 !vehicle.uav 分支记录原位置并传送，不生成假玩家；三种旋翼机跳过该分支，由本体 onEnterVehicle 生成 FakePlayer。母车部署的三机仍有 RVP 部署标记和返回锚点，直接放置则没有；不要混淆原生 UAV 标志与 RVP 部署身份。
- 当前 ZBL08A 的 SUAV 偏移 [0,100,0]、水平初速 1 block/tick；三旋翼机偏移 [4,4,0]、初速 0，切回母车悬停且禁止盘旋。这部分是固定翼与旋翼飞控/起飞差异，不要求操作者管理也采用不同模式。
