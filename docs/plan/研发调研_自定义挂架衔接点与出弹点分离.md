## 一、需求描述

现状：自定义挂架（`rvp_custom_mounts`）的模型衔接点与弹药出弹点是同一处——
都由部件结构模型中 `structure_bone + "_barrel"` 骨骼（下称"锚定骨"，如 `pylon1_barrel`）的
Cube 推算而来。当挂架模型与挂载弹药在结构模型上相距较远时，弹丸会从挂架衔接处而不是
弹位打出。

目标：允许为部件额外指定一根**出弹骨骼**（如 `pylon1_shoot_barrel`）：

- 渲染衔接位置仍按锚定骨（`pylon1_barrel`）的 Cube 推算；
- 实际发射时弹药从出弹骨的 Cube 位置打出；
- 未配置出弹骨时，回退到现有行为（从锚定骨出弹），完全向后兼容。

## 二、现状机制（调研确认）

### 2.1 出弹点（Bolt）的产生与流转

```
载具包加载（datapack reload，双端各自执行）
  └─ VehicleDataManager 解析 vehicles/*.json → BaseVehicleData 模板（每载具类型一份）
       └─ BaseVehicleData:119  partData.initStructureModel(model, vehiclePartGroups)
            └─ WeaponUnitData.initStructureModel（本体，WeaponUnitData.java:147）
                 ├─ bolts 已在 JSON 手工配置（WeaponUnitPojo.bolts）→ 直接用
                 ├─ 否则从 structure_bone+"_barrel" 骨的 Cube 递归推算（buildBolts:191）
                 │    每个 Cube = 一根炮管：offset=Cube 前端面中心，barrelLength=Cube.depth
                 └─ [RVP] WeaponUnitDataMixin @Inject(TAIL)：rvp_structure_bolt_bones 追加额外挂点 Bolt
  └─ 载具实体生成时（每实例）
       └─ WeaponUnit 构造器（WeaponUnit.java:141）：this.bolts.addAll(data.getBolts())
            （data 未配置时兜底 Bolt(Vec3.ZERO,0,0,0)）
```

### 2.2 出弹点的全部消费方（改造必须同时覆盖）

| 消费方 | 位置 | 说明 |
|--------|------|------|
| **弹丸出生点** | `VehicleMissile.shoot:93` 等 `weapon.shoot(aimContexts…)` | 出生位置 = `aimContext.from`（= Bolt 炮口 + 方向×barrelLength）。**注意：aimContexts 由客户端计算后经 `ClientVehicleAction` 上传，服务端信任该坐标生成弹丸**（ClientVehicleAction.java:88） |
| 客户端开火请求 | `WeaponUnit.aimContexts():905` / `aimContext():754` | 遍历 `bolts` 生成；RIPPLE 用 `getCurrentBolt()`，SALVO 用全部 bolts |
| 瞄准射线起点 | `LocalVehiclePlayer.java:414` | `weaponUnit.worldCurrentBoltPosition()` |
| CCIP 连续命中计算 | `WeaponUnit.toAimPosition:877` / CCIP 释放点 | bolts 全量平均 |
| 枪口烟特效 | `AbstractVehicleWeapon.shoot:258` | `aimContext.from` |
| 本体默认武器模型渲染 | `WeaponUnit.render:411-425` | 按 remainAmmo 从 bolts **末尾**往前取 N 根渲染（这正是 RVP `replace_weapon_display` 抑制的逻辑） |
| **RVP 挂架渲染锚点** | `RVP_CustomMountRenderLogic.resolveAttachmentTransform:363` | `xTurnGroup.pivotOffset + bolts.get(0).offset + barrelLength/2`（第一根 Bolt 炮口中点） |

**关键结论**：前 6 项全部经由 `WeaponUnit.bolts` 这一个列表派生，只要在数据模板层替换
`bolts`，开火/瞄准/CCIP/特效自动全部跟随，无需逐点改造。唯独第 7 项（RVP 渲染锚点）
不能跟着换——它必须留在锚定骨上，这正是本需求要解耦的点。

### 2.3 Cube → Bolt 几何（本体 buildBolts:191-211）

- `bolt.offset` = Cube **前端面中心**（`x+w/2, y+h/2, z`），经骨骼自身旋转 + 子骨层级平移（像素/16）；
- `bolt.barrelLength` = Cube 的 depth（Z 向长度），Z+ 为炮管轴线；
- 子骨骼的 Bolt 带骨骼欧拉角（`bolt.xRot/yRot`，支持斜置发射）。

### 2.4 挂架渲染锚点的替代数据源（已确认可用）

`VehicleCubeGroup`（挂架锚定的 xTurnGroup）本身持有：
- `pivotOffset`（:23）
- `cubeOBBs: List<VehicleCubeOBB>`（:24），每个 `VehicleCubeOBB` 有 `.position`（**Cube 中心**
  在组空间的全局变换位置，VehicleCubeOBB.java:58）与 `.depth`（:31）

即：`pivotOffset + cubeOBBs.get(0).position` ≡ 现在的 `pivotOffset + bolts.get(0).offset + (0,0,barrelLength/2)`
（Bolt 前端面 + 半管长 = Cube 中心）。**锚点可以从组自身 Cube 推算，不经过 Bolt 列表**，
两者在未配置出弹骨时逐点等价，配置后锚点保持不动。

## 三、实现方案（推荐）

### 3.1 新参数：部件级 `rvp_shoot_bolt_bones`

加在载具 JSON 的 `parts` 条目上，与现有 `rvp_structure_bolt_bones` 完全对称：

```jsonc
// data/rvp/vehicles/xxx.json → parts[]
{
  "id": "pylon1",
  "type": "ywzj_vehicle:weapon",
  "structure_bone": "pylon1",                    // 锚定：本体会找 pylon1_barrel 建组与默认 Bolt
  "rvp_structure_bolt_bones": ["pylon1_barrel"], // （可选，现状参数）多挂点发射位置补充
  "rvp_shoot_bolt_bones": [                      // ★ 新增：出弹骨，配置后全量替换出弹 Bolt 集
    "pylon1_shoot_barrel"
  ]
}
```

自定义挂架条目 `rvp_custom_mounts` **不需要任何改动**：`attach_part_unit_id` 锚定语义不变，
只是锚点推算改为不再读取 Bolt 列表（见 3.3）。

**为什么放部件级而不是 `rvp_custom_mounts` 条目里**：
1. 出弹点是**服务端玩法属性**（Bolt 模板在双端数据层构建，出弹坐标虽由客户端上传，
   但计算源 `bolts` 必须双端一致），而 `rvp_custom_mounts` 是客户端视觉配置，语义不符；
2. 出弹点与具体挂架条目无关（同一武器站的多个挂架条目共享一份 Bolt，阵风
   mount_1/mount_2 若按条目配置还得定义合并规则）；
3. 与现有 `rvp_structure_bolt_bones` 参数位置、解析、注入机制完全对称，实现成本最低。

> ⚠️ **本节论点已被方案修订推翻**：`rvp_custom_mounts` 实际在服务端同样有完整数据
> （`VehicleDataManagerMixin` 在 datapack 加载时双端解析），出弹点写进条目没有双端
> 障碍；条目级配置反而带来"开火顺序 = 消失顺序"的构造性对齐与每武器独立出弹骨，
> 见顶部【方案修订】与 §6。

### 3.2 出弹 Bolt 重建（服务端+客户端数据层）

全部落在现有 [WeaponUnitDataMixin](../../src/main/java/org/ywzj/rvp/mixin/WeaponUnitDataMixin.java)：

1. **解析**：`WeaponUnitPojoMixin` 加 `@SerializedName("rvp_shoot_bolt_bones")`
   （照抄 `rvp_structure_bolt_bones`，WeaponUnitPojoMixin.java:30）；
   `WeaponUnitDataMixin.<init> TAIL`（:44）拷贝到 `@Unique` 字段。
2. **重建**：在现有 `ywzj_rvp$initExtraBoltBones`（:66，`initStructureModel` TAIL）内，
   当 `rvp_shoot_bolt_bones` 非空时：
   - 用与本体 `buildBolts` / 现有 `ywzj_rvp$appendBoltsFromBone`（:120）相同的
     "逐 Cube 一根炮管"算法，对出弹骨生成 Bolt；
   - **全量替换** `this.bolts`（`@Shadow` 已存在，:31），不再追加；
   - 偏移换算到 xTurnGroup 空间：出弹骨若属于其他 `VehicleCubeGroup`，沿用现有
     `groupDelta = group.globalTransform().offset().subtract(pivot)`（:86）；若不属于任何组，
     沿骨骼 parent 链向锚定骨最近公共祖先累计平移（bind pose 静态值，BedrockBone.parent 可用），
     自身旋转写入 `bolt.xRot/yRot`（与现有算法一致）。
3. **优先级语义**（写入参数文档）：

   | 优先级 | 来源 | 说明 |
   |---|---|---|
   | 1（最高） | `rvp_shoot_bolt_bones` | 非空时**全量替换**最终出弹集，`rvp_structure_bolt_bones` 与手工 `bolts` 均不再参与出弹 |
   | 2 | 手工 `bolts` JSON（本体参数） | 本体现状 |
   | 3 | `_barrel` Cube 推算 + `rvp_structure_bolt_bones` 追加 | 本体现状（回退路径，即现有行为） |

   双挂架场景：把两个挂架的出弹骨都列进 `rvp_shoot_bolt_bones`（如
   `["pylon1_shoot_barrel", "pylon2_shoot_barrel"]`），RIPPLE/SALVO 轮转与原行为一致。

### 3.3 挂架渲染锚点与 Bolt 解耦（客户端渲染）

[RVP_CustomMountRenderLogic.resolveAttachmentTransform](../../src/main/java/org/ywzj/rvp/client/render/RVP_CustomMountRenderLogic.java#L345)
`attach_part_unit_id` 分支改为：

```java
// 现状：translate = xTurnGroup.pivotOffset + bolts.get(0).offset + (0,0,barrelLength/2)
// 改为：translate = xTurnGroup.pivotOffset + cubeOBBs.get(0).position（首 Cube 中心，等价点）
```

- `VehicleCubeGroup.cubeOBBs.get(0).position` 即锚定骨首个 Cube 的中心（VehicleCubeOBB.java:58），
  与旧锚点逐点等价 → **未配置出弹骨时渲染零变化**；配置后锚点自动留在锚定骨，不被出弹骨带跑。
- `attach_bone` 模式（直接锚到载具模型骨骼）不受影响，无需改动。
- 需要注意 cubeOBBs 为空时回退 `pivotOffset` 并打调试日志（与现状 xTurnGroup==null 回退同级）。

### 3.4 各消费方在改造后的自动行为（无需额外改动）

| 消费方 | 改造后行为 |
|--------|-----------|
| 弹丸出生（服务端信任客户端 aimContext） | ✅ 从出弹骨 Cube 打出 |
| 瞄准射线 / 准星（LocalVehiclePlayer:414） | ✅ 跟随出弹位（符合直觉：从弹位瞄） |
| CCIP / 释放点平均 | ✅ 跟随出弹集 |
| 枪口烟特效 | ✅ 跟随出弹位 |
| RIPPLE/SALVO 轮转、countFire | ✅ 不变（索引轮转语义不变） |
| 冷发射（cold launch） | ✅ 同样走 aimContext.from |
| 本体默认武器模型渲染（未被 RVP 抑制时） | ⚠️ 会渲染在出弹位（可接受；配置了自定义挂架+replace_weapon_display=true 时本就被抑制，无感） |

### 3.5 与本体 0.5.10 及既有 RVP 功能的兼容

- **不改本体任何代码**，全部为 RVP mixin/渲染逻辑修改；
- `WeaponUnit.xTurnGroup`、`WeaponUnitData.bolts/xTurnGroup`（均已 `@Shadow`）、
  `BedrockBone.parent` 均存在且本次本体更新未触碰；
- `rvp_structure_bolt_bones` 老配置在未配置新参数时行为完全不变（rafale/j15/f22a/j10c 零回归）；
- RVP 弹道劫持（RocketEntityMixin 只改速度积分）、激光武器包装、弹舱（WeaponBayUnit）
  均不触碰出弹点链路，无冲突。

## 四、已知约束与风险

| # | 约束/风险 | 等级 | 说明与对策 |
|---|-----------|------|-----------|
| 1 | **跨动画组的出弹骨为"绑定位姿烘焙"** | ⚠️ 中 | Bolt 偏移烘焙进锚定组空间，出弹骨若挂在**另一个独立动画的部件组**下（且该组会独立转动），发射位置不跟随其动画。对策：规范要求出弹骨挂在锚定骨同一刚体链下（pylon1 → pylon1_barrel 与 pylon1_shoot_barrel 同为子骨，或后者是前者子骨），此时烘焙是精确的；文档给反例。 |
| 2 | 出弹骨带自身欧拉角时方向 = 锚定组旋转 + 骨骼自转 | 低 | 与现有 rvp_structure_bolt_bones 行为一致；斜置导弹场景实测确认方向即可。 |
| 3 | 锚定骨无 Cube 而依赖子骨递归的边界 | 低 | buildBolts 递归子骨，而 cubeOBBs 由组构建时聚合子骨（BaseVehicleData:289），两者覆盖范围一致；个别模型结构差异需实机确认锚点不偏移。 |
| 4 | `/reload` 热重载 | 低 | 模板重建与本体现行为一致（已生成实体不刷新），无需额外处理。 |
| 5 | 手工 `bolts` 与新参数同时配置 | 低 | 按优先级表：新参数胜出。需在参数文档与排查文档中写明，避免误配。 |
| 6 | **结构模型铁律（agents.md L20）** | ⚠️ 高 | `shoot_structure_bones` 指向的骨骼必须**真实存在于结构模型**
   （`data/rvp/models/bedrock/vehicle/*.structure.json`）。接入分两条路：
   **(a) 优先复用既有骨骼**（现有 `_barrel` / 挂架相关骨中 Cube 位置合适者，零结构改动）；
   **(b) 确需新增骨骼**（如 `*_shoot_barrel` 占位名对应的新骨）→ 属结构模型修改，
   **必须先向用户请示获确认，动手前备份原文件（`*.structure.json.bak`）**，
   禁止擅自重构骨层级/移动枢轴/批量改写 cube。本功能实现本身（Java/配置层）
   不触碰任何结构模型文件。 |

## 五、实施步骤与测试清单（v2 修订：条目级 `shoot_structure_bones`）

> v1（部件级 `rvp_shoot_bolt_bones`）步骤已废弃，被本节取代；v1 思路仅保留在 §3 作为
> 部件级兜底参数的参考。

### 5.1 实施步骤

1. **配置解析**：`RVP_CustomMountConfig` record 新增 `shootStructureBones`
   组件与 `GsonHelper` 解析（手动解析，无 `@SerializedName`，非 `RVP_*Data` 链路）；
   每个字段补中文注释（agents.md 注释纪律）。
2. **出弹队列构建（公共代码，双端可用）**：新建
   `org.ywzj.rvp.mount.RVP_ShootBoltQueueResolver`（非 mixin 包）：
   - 输入：vehicleId 的 `RVP_CustomMountConfigCache` 条目 + 结构模型
     （`CommonAssetsManager.structureModelManager()`）；
   - 规则：命中当前武器的条目按 `(ammo_slot, configOrder)` 排序 → 逐条目把
     `shoot_structure_bones` 的 Cube 按"逐 Cube 一根炮管"展开为 Bolt（算法复用
     `WeaponUnitDataMixin.ywzj_rvp$appendBoltsFromBone` 的等价实现，抽到公共辅助类）；
   - 偏移换算：出弹骨相对锚定骨的 bind-pose 骨链行走（`BedrockBone.parent` 累计平移 +
     自身旋转写 `bolt.xRot/yRot`），不读取 `vehiclePartGroups`（避免新增 @Accessor）；
   - **禁止引用任何 `@OnlyIn(CLIENT)` 类型**（agents.md Mixin 纪律 L38）。
3. **应用到载具实例（零 Mixin：Forge 事件 + 公共 API）**：
   - **公共写入模式**：`WeaponUnit.getBolts()` 返回**活引用**（WeaponUnit.java:1044），
     本体 `Ztz99a`/`Z10` 构造器内即以 `getBolts().clear(); getBolts().add(...)` 改发射点
     （Ztz99a.java:82-84）——RVP 采用同一公共模式，不碰私有字段、不加 setter；
   - **挂起**：`EntityJoinLevelEvent`（FORGE 总线，双端）把加入的 `AbstractVehicle`
     放入挂起集合（`WeakHashMap` 防泄漏）；
   - **排空**：LevelTick 事件（服务端与客户端各自的现有/新增 tick 处理器）每 tick
     尝试对挂起车辆应用：`partUnits` 就绪（`initData()` 已跑完，AbstractVehicle.java:436）
     且结构模型与配置缓存可用 → 按武器站解析出弹队列 → `getBolts().clear(); addAll(队列)`
     → 移出挂起集合；
   - **时序注意**：服务端首次生成路径 `initData()` 在 `onAddedToWorld()`（:368）触发，
     晚于 `EntityJoinLevelEvent`，故必须"挂起 + 排空"而非事件内直接应用；
   - **双端必须成对**：客户端开火 `aimContexts` 从客户端单位 Bolt 计算，客户端单位

     不触碰 `WeaponUnitData` 模板——未配置 shoot 骨的武器站与全部数据模板零影响；
   - **重复进入维度**：跨维度重生为新实例，join 事件重新触发，天然重放。
4. **渲染侧改造（纯 Java，无 Mixin）**：`RVP_CustomMountRenderLogic`：
   - `resolveAttachmentTransform` 锚点改用 `xTurnGroup.cubeOBBs.get(0).position`

### 5.2 Mixin 纪律合规（agents.md L24-39，v2 零 Mixin 结论）

| 触点 | v2 方案 | 合规性 |
|------|---------|--------|
| 出弹队列应用 | `EntityJoinLevelEvent` + LevelTick 排空 + 公共 `getBolts()` 活引用改写 | Forge 事件（L26-3 优先级）+ 公共 API 模式（本体 Ztz99a/Z10 同款），**零 Mixin** |

| 渲染锚点/消失顺序修正 | 纯 `RVP_CustomMountRenderLogic` Java 改动 | 无 Mixin |

替代方案排除记录（按 L26 逐级）：
1. JSON 数据字段 ❌ —— `rvp_custom_mounts` 字段本身即数据层，但"应用为 Bolt 集"需触达
   本体运行时对象，数据层无法表达；
2. 继承/组合 ❌ —— `WeaponUnit` 由 `BaseVehicleData.createPartUnits`（本体）工厂构造，
   载具包 parts 无法指定 RVP 子类；本体自家扩展（Ztz99a）也是用活引用改 Bolts 而非子类；
3. Forge 事件 ✅ —— **采用**：`EntityJoinLevelEvent` + LevelTick 排空，公共 API 完成全部写入；
4. 网络包 —— 不需要（S2C 配置同步已存在，队列构建是本地计算）；
5. `@Accessor` —— 不需要（不读私有字段；`getBolts()` 公共活引用足够）。

**结论：本功能零新增 Mixin 类、零新增/修改注入点，agents.md L24-39 全部满足，
无需 L36 前置确认的 Mixin 事项。** 唯一需要用户确认的非 Mixin 事项：接入载具时
出弹骨是"复用结构模型既有骨骼"还是"新增骨骼"（后者触发 L20 请示 + 备份）。

## 六、条目级方案（已升级为推荐，见顶部【方案修订】）

**条目级参数**（`rvp_custom_mounts[].shoot_structure_bones`）：把出弹骨写在自定义挂架条目里。
- 优点：与 `missile_bones`（消失渲染骨骼）写在同一处，出弹队列 = 条目按
  `(ammo_slot, 配置顺序)` 拼接，开火轮转与弹药消失**构造性对齐**；同一 mount 在
  不同 `weapon_id` 条目下可指向不同出弹骨（每武器独立弹位）。
- 需一并处理：同武器站多条目的合并规则（按 slot 排序拼接）、未配置条目的回退
  （整站无配置 → 现状行为）、消失顺序公式修正为与开火同序（现状为高 slot 先隐，
  属现存错位）。
- 原"缺点"中"双端属性不符"不成立：`rvp_custom_mounts` 服务端同样有完整数据
  （见 §3.1 修订注）。"无挂架条目的武器站无法使用"保留为已知边界，此类需求
  （默认显示武器的自定义出弹骨）再用部件级 `rvp_shoot_bolt_bones` 兜底。

## 八、2026-09-14 追记：放置/重进不应用复发与修复

**提交 `80770e2d`**（拉取式 `ensureApplied` 重写 + 队列表同步加固）修复了"F14D 放置后从挂点出弹、
退出重进才正常"，但实机仍有两个残留症状：

- **症状 A**：ea18g 的 `ea18g_aim120d` 放置后**有概率**不应用自定义出弹点；
- **症状 B**：同栏的 `ea18g_aim260a` 放置后正常，**存档退出重进后出弹点退回挂点**（与旧 bug 方向相反）。

### 根因

1. **预热门控绑错数据源 + 200 tick 永久放弃**：`tryPrewarmVehicle` 就绪门控等的是
   `RVP_CustomMountConfigCache`（登录期 `S2CVehicleRvpConfig` 填充）——配置缓存就绪晚于
   载具生成时，200 tick 后载具被移出 PENDING **永久不再重试**，客户端出弹点永久粘在挂点模板
   （`VariableProjectileSpawner`/挂架模板 bolts）。客户端是导弹出生坐标的权威端（服务端信任
   客户端 aimContexts），客户端粘住即实锤；
2. **多弹种槽客户端开火绕过兜底**：`ea18g_aim120d`/`ea18g_aim260a` 同栏（`variable_aam` 站
   weapons 数组），本体 `VehicleMultiWeapons.doClientShoot` 自行计算 aimContexts，
   **不经过** `RVP_WeaponBase.doClientShoot:114` 的 `ensureApplied` 兜底——错过预热后客户端
   没有任何补拉时机。放置时 aim120 为默认位（预热正常覆盖），切到 aim260 后两型弹的
   `shoot_structure_bones` 相同故"看起来正常"；重进后预热竞态失败的一侧就表现为挂点出弹。

### 修复（零新增 Mixin，全部复用现有链路）

1. **就绪门控改用队列表本身**：`RVP_ShootBoltQueueResolver` 新增
   `hasStationQueue(vehicleId, station)`（沿母站链查 `QUEUES`，锁内）；`tryPrewarmVehicle`
   改为按站查 `hasStationQueue` 命中即 `ensureApplied`——队列表在登录同步/数据重载即重建
   （80770e2d 已加固其同步可靠性），比配置缓存更早可用且与实际应用数据源完全一致；
2. **删除 200 tick 永久放弃**（`CONFIG_WAIT`/`CONFIG_WAIT_LIMIT_TICKS`/`hasShootStructureBones`
   移除）：队列表未就绪/无配置的载具留在 PENDING 每 tick 低成本幂等重试（`ensureApplied`
   口径×表版本未变时零开销），就绪或 `/reload` 热加配置后自动补应用；载具卸载由既有
   `onEntityLeaveLevel` 清理，无泄漏。无出弹骨配置的载具行为零影响；
3. **多弹种槽客户端开火兜底**：`VehicleMultiWeaponsChargeGateMixin`（既有 client 数组 Mixin）
   的 `doClientShoot` HEAD 注入开头追加
   `RVP_ShootBoltQueueApplier.ensureApplied(rvp.getVehicle(), rvp.getWeaponUnit())`——
   多弹种槽开火瞬间客户端 bolts 必为当前口径队列（本就绕过 RVP_WeaponBase.doClientShoot，
   该处是唯一兜底缺口）。

### 遗留观察项

- `lookupQueueById` 的"该站任一队列"回退在多弹种槽下会拿其他口径的队列（aim120/aim260 出弹骨
  相同时无观感差异；若日后各口径出弹骨不同，需改为"未命中即不应用"或按口径严格隔离）；
- 实机回归：ea18g 反复放置 aim120/aim260、存档退出重进、F14D 回归、出弹骨配错的弹开火自动纠正。

### 诊断开关与排查指引（2026-09-14 深夜追加）

新增诊断开关 `RVP_DebugFlags.SHOOT_BOLT`（`/rvpdebug flags shootbolt on`，双端）：
`ensureApplied` 的四类分支全量打日志——vehicleId 未就绪跳过 / 幂等跳过 / 查表未命中 / 应用。
**排查口径**：

- 日志出现"查表未命中"→ 客户端队列表内容异常（S2C 同步与本地重建不一致）；
- 完全无 `[RVP][出弹]` 日志 → 客户端 tick 拉取未触发（LocalVehiclePlayer.vehicle 为空
  / 事件未注册），需查载具引用；
- 出现"幂等跳过"但弹仍从挂点出 → bolts 被其它路径覆写回模板（需查本体侧对 bolts 的写入）。
