# RVP 动态光源与屏幕空间体积合成实现计划

> 日期：2026-10-29  
> 状态：按 2026-10-30 用户补充要求，代码控制光源、固定关闭 P5，并实现 DH / Iris/Oculus 光影兼容
> 目标环境：Minecraft 1.20.1 / Forge / `limitless-vehicle-rvp-addon`  
> 基本原则：只改 RVP Addon，不改 `ywzj_vehicle` 本体；先做屏幕空间视觉光，再按需要增加真正的 Minecraft 动态光。

**当前执行范围以文末第十一至十三节为准。** 下文 P4/P5 和早期关闭 DH/光影的策略保留为方案与历史，不表示当前读取武器光源 JSON、允许开启真实方块光，或仍在 DH/光影环境整层禁用屏幕光。

## 一、先说结论

RVP 内建议采用“两层光源”方案：

1. **屏幕空间光**：在世界已经渲染完成后，利用颜色缓冲和深度缓冲，给当前画面中能看见的地形、载具和实体表面加上有颜色的光照。它适合炮口闪光、爆炸闪光和火箭发动机尾焰，响应快、颜色自由、不会修改世界方块。
2. **真正的动态光**：只给爆炸和少量大口径开火临时放置不可见的 `LightBlock`。这是 Minecraft 的方块光系统，能够改变地形的实际亮度和实体的光照值，但会产生服务端方块更新，不能让每一个机枪口和每一台火箭发动机每 Tick 都使用。

这里的几个术语用人话解释如下：

- **屏幕空间**：先把世界画成一张图，再对图上的像素加工。因此它能照亮屏幕上看得见的墙、地面和实体，但不会真的改变世界里的光照数据，也不会穿过挡住它的墙。
- **深度缓冲**：显卡保存的“这个像素离相机有多远”。利用它可以判断光应该落在哪个可见表面上。
- **体积合成**：把光看成一个有半径的球、锥或椭球，在像素位置计算衰减，而不是只画一张平面贴图。本计划第一阶段实现的是“带体积衰减的屏幕空间光”，不是完整的烟雾参与介质光。
- **Bloom**：把过亮区域模糊后叠回画面，形成光晕。它是视觉效果，不等于 Minecraft 的真实光照。

第一版不新增 Mixin、不改本体、不改结构模型、不改贴图音效和载具包 JSON。这样可以先把效果、性能和兼容性验证清楚。

当前 `RVP_ShockwaveRenderer` 已经在 `AFTER_WEATHER` 捕获深度、在 `AFTER_LEVEL` 绘制。计划不会再随意增加一套每个光源一个帧缓冲的实现，而是先设计共享的场景帧资源，避免重复复制颜色和深度。

## 三、总体数据流

```text
服务端爆炸 / 客户端开火 / 导弹发动机燃烧
                    │
                    ▼
          RVP_ScreenLightManager
       （短闪光 + 持续光 + 合并/限额）
                    │
                    ▼
   一次场景颜色/深度捕获 + 世界坐标重建
                    │
                    ▼
      screen_light.fsh：半径衰减、遮挡、表面受光
                    │
                    ▼
        画面合成 → 可选 Bloom → UI/CRT 后处理

  爆炸/大口径开火（可选） ──► 服务端临时 LightBlock
                              └─► 真正改变 Minecraft 方块光
```

## 四、分阶段实施

### P0：基线和渲染时序确认

这一阶段只做只读检查、日志和小范围诊断，不先动资源。

1. 确认 `RVP_ShockwaveRenderer`、Distant Horizons（远景地形）和 CRT/TV 后处理各自使用的颜色/深度目标。
2. 确认普通世界、实体、载具、半透明烟尘在 `AFTER_LEVEL` 时是否都已经写入深度。
3. 确认启用 Iris/Shader Pack 时 RVP 是否还能安全取得场景颜色；拿不到时必须自动关闭屏幕空间光，而不能让渲染线程崩溃。
4. 确定最终顺序：
   - 世界实体完成后复制场景颜色和深度；
   - 屏幕空间光叠加；
   - 可选 Bloom；
   - 最后才进入 CRT/TV 等全屏后处理；
   - 不把 HUD、准星和菜单当作被照亮的世界表面。
5. 如果现有压力波流程已经持有可复用的场景目标，则抽取公共 `RVP_ScreenFrameResources`；否则第一版使用独立目标，但仍保持每帧最多一次颜色/深度复制。

**P0 通过条件**：在无 Shader Pack、Iris、Distant Horizons、CRT/TV 四种组合下，确认每种环境可用或明确降级，不出现额外的 OpenGL 错误。

### P1：建立 RVP 屏幕空间光源管理器

新增客户端代码，建议放在 `org.ywzj.rvp.client.light`：

- `RVP_ScreenLight`：一个光源的只读状态，字段包括世界坐标、RGB 颜色、半径、强度、剩余 Tick、来源类型、持续光键和表面受光权重。
- `RVP_ScreenLightManager`：统一管理短时光和持续光，提供 `addTransient`、`upsertPersistent`、`removePersistent`、`tick`、`clear`、`collectVisible` 等方法。
- `RVP_LightSourceType`：例如 `MUZZLE`、`EXPLOSION`、`ROCKET_ENGINE`，只用于预算、调试和参数默认值，不用于识别具体武器。
- `RVP_ScreenLightBudget`：负责距离裁剪、半径裁剪、重复光合并和最大光源数限制。

管理规则：

1. 第一版最多提交 8 个屏幕空间光源；近距离光优先，远距离光按亮度和屏幕覆盖面积排序。实际数值通过性能测试调整。
2. 相近的同类短光合并，避免机枪连射导致每一发都增加一个 Shader 循环。
3. 火箭发动机使用 `PersistentKey=实体 UUID`，每 Tick 更新位置，不创建新光源。
4. 世界切换、退出服务器、实体移除、燃烧结束时统一清理，避免“换维度后画面仍有一盏灯”。
5. 没有活动光源时不复制场景、不执行全屏 Shader。
6. 所有方法使用清晰中文注释；调用本项目或 `ywzj_vehicle` 方法时说明调用目的，和现有代码注释规范保持一致。

**P1 不新增网络包、不新增 JSON 字段**，先用已有爆炸事件参数和代码默认值验证管理器。

### P2：实现屏幕空间灯光合成

建议新增以下客户端资源和代码；这些是计划文件，实施时要先按项目规则检查两个资源命名空间是否已有同名文件，并在创建前取得确认：

- `src/main/java/org/ywzj/rvp/client/light/RVP_ScreenLightPass.java`
- `src/main/resources/assets/ywzj_rvp/shaders/core/screen_light.json`
- `src/main/resources/assets/ywzj_rvp/shaders/core/screen_light.vsh`
- `src/main/resources/assets/ywzj_rvp/shaders/core/screen_light.fsh`

Shader 的基本步骤：

1. 复制当前场景颜色和深度。
2. 通过深度和观察矩阵/投影矩阵，把屏幕像素还原成世界坐标。
3. 对每个有效光源计算距离衰减：光源中心最亮，超过半径后为零。
4. 用深度判断光源是否被当前可见表面挡住，避免“隔墙照亮”。
5. 根据表面方向近似计算受光强度；没有 G-buffer 法线时，用深度邻域估算表面朝向。
6. 将 RGB 光加到场景颜色，但不修改透明度和 HUD。
7. 处理无深度目标、Shader Pack 接管渲染目标或矩阵无效的情况：跳过本帧并记录限频诊断日志。

这里的效果边界必须明确：

- 能照亮当前画面中可见的地形、方块、载具和实体表面。
- 不能改变 Minecraft 的方块光等级，不能照亮当前没有被渲染到屏幕上的实体。
- 不能透过墙照亮墙后；墙后目标需要真正的 Minecraft 动态光或另一个可见角度。
- 实体是否“变亮”取决于它是否写入场景深度，以及其材质是否允许最终颜色被后处理叠加；这需要实机验证半透明模型和特殊 Shader。

### P3：接入三类光源

#### 3.1 爆炸光

在 `RVP_DefaultExplosionEffectFactory` 创建默认爆炸视觉时登记短时光，在 `RVP_DefaultExplosionEffectInstance` 里维护其生命周期。

- 继续使用现有 `RVP_VisualEffectEvent` 的位置、半径、种子、持续时间和 `flash` 标志。
- 光源强度随年龄衰减：第一帧白热核心，随后过渡到橙红，再快速减弱。
- 爆炸半径只作为初始视觉半径，必须设置单独的屏幕光上限，避免核爆半径直接变成整张地图的白屏。
- 不新建一个只负责闪光的视觉事件类型，避免触发 `publishedCount` 后抑制现有默认烟尘或声音。
- 现有 MCHR 火花、烟尘、声音和镜头震动保持不变；屏幕空间光是附加层。

#### 3.2 开火光

在现有 `VehicleFireEvent.Post` 路径接入，优先抽出一个共用的 `RVP_FiringMuzzleResolver`，供炮口烟和灯光共同使用。

- 复用 `RVP_WeaponResolveHelper.unwrap`、`WeaponUnit`、`RVP_AimContexts.muzzle` 和已有口径解析。
- 根据类型化的 `fire_data`、口径、齐射/连射状态和炮口位置计算光源，不使用 `weaponId.getPath().equals(...)`。
- 大口径火炮使用短、强、偏白的光；机枪使用弱、短、可合并的光；火箭/导弹发射闪光由同一管理器处理。
- 高射速武器采用“同源合并 + 冷却窗”，避免每一发都触发一次完整屏幕合成。
- 如果当前客户端事件只覆盖本地开火，需要检查远端开火是否已有同步链路；若没有，再增加一个最小的 RVP S2C 开火视觉包，只传位置、方向、光源参数和开始 Tick，不传武器 ID。

#### 3.3 火箭发动机光

不要在 `RVP_RocketFlameParticle` 的每一粒粒子上创建灯，否则粒子数量会直接变成光源数量。建议：

1. 从现有本地弹体渲染器和 `RVP_RemoteMissileTrailEmitter` 抽取共用的“发动机是否正在燃烧、喷口在哪里”查询。
2. 以弹体 UUID 作为持续光键，在发动机燃烧期间调用 `upsertPersistent`。
3. 光源位置跟随喷口，颜色和半径由推进阶段调整；一级燃烧期最亮，燃尽后立即删除。
4. 弹体被移除、区块卸载、客户端换维度或远端尾迹超时都必须删除持续光。
5. `RVP_RocketFlameParticle` 继续负责全亮火焰和尾迹本身；新的屏幕光只负责把附近可见表面染亮，避免把火焰亮度误当成环境光。

### P4：可配置化，但不提前污染载具包

P1-P3 先使用安全的代码默认值。效果稳定后，再决定是否开放 JSON 配置。推荐使用类型化数据类，不把逻辑塞进字符串或旧版兼容键：

| 配置位置 | 建议内容 | 生效范围 |
|---|---|---|
| `fire_data` 的新增 `muzzle_light` 对象 | `enabled`、颜色、半径、强度、持续 Tick、连射合并窗口 | 开火闪光 |
| `effects_data` 的新增 `rocket_engine_light` 对象 | `enabled`、颜色、半径、强度、燃烧期门控 | `has_rocket_engine=true` 的弹体 |
| `visual_effect_data` 的新增屏幕光对象 | `enabled`、颜色、半径、强度、衰减、Bloom 开关 | 爆炸视觉 |

具体字段名需在实现前确认当前 schema 的严格程度。所有新增 `@SerializedName` 字段必须补齐单位、默认值和生效条件的 JavaDoc，并补充 schema/解析测试；缺失字段必须保持旧行为。开发源仍以项目根 `limitless_vehicle/` 为唯一权威副本，任何包文件修改前都要先列变更清单、备份并取得确认。

### P5：可选的真正 Minecraft 动态光

如果屏幕空间光已经满足“看起来被照亮”的要求，就不必开启这一阶段。若需要 F3 光照值、方块亮度变化和实体实际受光，再增加服务端方案：

新增建议类：

- `src/main/java/org/ywzj/rvp/server/light/RVP_DynamicBlockLightManager.java`
- `src/main/java/org/ywzj/rvp/server/light/RVP_DynamicBlockLightEntry.java`

实现规则：

1. 服务端在爆炸和少量大口径开火时寻找附近空气方块，临时放置 `Blocks.LIGHT`，光等级从配置或默认值计算。
2. 保存被替换前的 `BlockState`；到期时只有在当前位置仍是本系统放置的光源时才恢复，玩家后来放置的方块不能被覆盖。
3. 合并附近相同光源，限制同时存在的条目数量和持续时间；区块未加载时跳过。
4. 使用服务端已有的爆炸/开火事实，不信任客户端自行请求，避免客户端伪造动态光包。
5. 发动机持续光默认不走 `LightBlock`，因为每 Tick 改方块会造成大量光照更新；发动机采用屏幕空间光，爆炸/重炮才可选用真实动态光。
6. 服务端冒烟时重点检查：方块更新、区块边界、玩家放置方块、维度切换、服务器关闭和异常中断后的清理。

这一阶段仍然不需要 Mixin。若将来要求不放置 `LightBlock`、而是像 `sable-light-overhaul` 一样直接接管光照引擎，则必须另立变更申请：明确目标类/方法、先证明 JSON、继承/接口、Forge 事件、网络管理器和访问器都不可行，并在用户确认后才允许新增 Mixin。本计划不包含该 Mixin。

### P6：可选 Bloom 和真正体积雾光

屏幕空间光稳定后再加 Bloom：

1. 从过亮的爆炸/发动机光提取高亮区域。
2. 使用半分辨率或四分之一分辨率做两次模糊。
3. 把模糊结果叠回屏幕空间光之后、CRT/TV 之前。
4. 无法取得目标或 Shader Pack 冲突时关闭 Bloom，不影响基础光。

如果以后需要烟雾内部的光柱、尘埃被照亮等“真正体积光”，再把光源输入接到现有压力波/体积效果管线。不要把 `warp_world` 的折射逻辑直接改成灯光逻辑，否则会把冲击波和光照耦合，难以调试。

## 六、性能和兼容性边界

- 每帧最多一次场景颜色/深度复制；不为每个灯创建帧缓冲。
- 基础屏幕光初始上限 8 个，持续光按距离和屏幕覆盖面积裁剪。
- 发动机光按实体合并，机枪闪光按时间窗合并。
- 无活动光时完全跳过 Shader。
