# TWS 首次发射后全部航迹框消失的清表时序修复

日期：2026-11-05。

## 现象与已确认根因

以歼-10C 对 TWS 目标首次发射 PL-12 时，游戏短暂卡顿，全部目标框消失，稍后恢复；多机型均可复现。TWS 是“边扫描边跟踪”，航迹是雷达已经发现并持续记录的目标。

已确认导致**卡顿后全部框消失**的是公共雷达接触表的清理顺序，不是 PL-12 的武器 ID 分支或歼-10C 独有数据。

1. 根目录权威配置 `limitless_vehicle/rvp/data/rvp/vehicles/j10c.json` 的雷达为 `scan_animation_mode: phase`、`y_rot_speed: 0`、`scan_period_tick: 30`。相控阵以电子方式改变探测方向，不需要机械转动；这里的零转速本身是正常配置。J-15、J-16、J-16D、F-22A 等也使用零机械转速。
2. 本体 `RadarUnit.tickTargets()` 按 `max((long)(range / yRotSpeed / 20 * 1000) * 2, 100)` 计算接触寿命。正范围除以零得到正无穷，转成 `long` 后再乘二溢出，最终寿命变成 **100ms**。记录时间来自现实时间 `System.currentTimeMillis()`，游戏没推进时也会变老。
3. 本体 `RadarUnit.tick()` 先执行 `tickTargets()` 清表，再执行 `tickLock()` 检查硬锁，最后才探测。原 RVP 客户端每刻只在 END（本刻结束）为有效接触续期；已有 START（本刻开始）处理只负责同 ID 实体交接。
4. 两次游戏更新之间一旦出现超过 100ms 的停顿，下一刻本体先删光旧接触。之后 RVP 的 END 续期只遍历剩余记录，无法挽救空表；下一次完整扫描才重新发现目标。歼-10C 的 30 刻扫描周期在 20 TPS（每秒 20 刻）时约为 1.5 秒，与“片刻后恢复”一致。
5. 服务端原接触续期在 END 每两刻执行，名义间隔就已达到 100ms，也存在相同的抢先清表窗口。

本轮读取实机目录 `logs/latest.log`、`logs/debug.log`，没有得到能直接量出首次发射各阶段耗时的记录。代码中存在弹体显示、喷焰与屏幕光首次使用路径，但不能仅凭“首次卡顿”就判定具体哪条路径耗时。本轮不把资源首次初始化认定为已证实的卡顿根因，也未声称消除了首次发射本身的停顿。

## 修复

- `RVP_ClientRadarTickHandler` 复用现有客户端 START 事件，在本体更新载具前先统一目标引用，再对玩家拥有的工作中相控阵雷达执行完整接触检查和续期。该 START 监听使用最低优先级，即在同一事件的大多数监听器之后执行，避免它们的首次加载耗时提前消耗这次续期。
- 续期沿用现有的存活、原生实体/广播样本有效性、可探测类型、扫描高度、距离及角度检查，并执行已有隐身距离过滤。失效模块、断电、已击毁载机和关闭的雷达不提前续期。机械雷达仍沿用本体客户端寿命。
- 客户端 END 保留移动后的复查和原扫描节流；START 只检查已知接触，不扫描新目标、不推进扫描计数、不把 TWS 升级成硬锁，也不重新建立用户已经解除的锁定。
- `RVP_RadarScanService` 将已有服务端接触检查改为每刻 START 执行；新目标扫描仍保持原 END 调度与原间隔。

仅修改 RVP Java 事件处理；未修改本体、结构模型、权威载具/武器 JSON，也未新增 Mixin、注入点或网络字段。正常更新时间戳的措施覆盖两次游戏更新之间的长帧；同一刻内部任意位置的长耗时仍需实机采样核对。

## 自动验证

新增 `RVP_RadarContactHoldOrderTest`，使用生产 START 入口、本体真实探测表、`tickTargets()` 与 `tickLock()`，只替代无窗口世界、操作手和网络写锁这些外部边界。通过修改时间戳模拟 5 秒停顿，不依赖真实等待。

六项回归覆盖：

- 原本体零转速路径确实会删光老接触。
- START 续期后两条有效接触及已有硬锁保持；尚未扫描的第三个目标仍不入表。
- 死亡、出距离目标仍被移除；普通 TWS 接触不会变为硬锁。
- 机械雷达保持本体过期行为。
- 载机断电不能续期。
- END 事件不能替代本体清理前的 START 处理。

在项目根目录按 `AGENTS.md` 的 Java 17 环境运行 `./gradlew build`，结果 **BUILD SUCCESSFUL**，281 个测试类、1650 项测试、0 失败、0 错误。构建日志：`build/tws-first-shot-build.log`。

## 实机验收

1. 重启客户端，进入测试世界，歼-10C 开雷达，保留多个 TWS 航迹，对其中一个目标首次发射 PL-12；检查其余目标框是否连续，记录首次发射本身是否仍有停顿。
2. 分别检查近距原生实体和原生跟踪范围外的广播目标；已有硬锁在首发停顿后应保持，用户主动解除后不应自动变回硬锁。
3. 让目标死亡、出角度/高度/距离包络，关闭雷达、断电和损毁雷达模块；目标应按原条件退出，不能因为提前续期形成残留框。
4. 以 J-15/J-16/F-22A 等相控阵机型交叉验证；联机客户端、服务端同时更新 RVP jar。
5. 若首发仍卡顿，围绕第一次弹体生成/显示、尾烟/喷焰、屏幕光首次使用抓取 CPU 与帧耗时，单独确认具体阻塞点。

本轮未启动图形客户端，以上实机画面与首次耗时采样尚未完成。
