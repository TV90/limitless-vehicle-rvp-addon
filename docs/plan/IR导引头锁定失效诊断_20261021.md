# IR 导引头锁定失效诊断（2026-10-21 夜间）

> 现象：改用「连续跟踪 dwell」后，IR 弹基本锁不上；HUD 无锁定，发射被拒。
> 结论：**不是语义问题，是 4 个接线缺口 + 2 个路由/计数缺陷**，其中 2 个是「必死」级，任何一台车都过不去。
> 证据均给出 file:line，可直接复核。

---

## 一、必死级缺陷（任意一条都足以让全部 IR 弹失效）

### D1. `sendArmedUpdate()` 是空实现 ⇒ 服务端永远收不到 armed

`client/state/RVP_IrSeekerTracker.java:286-289`

```java
private static void sendArmedUpdate(WeaponUnit unit, ResourceLocation weaponId,
                                    int entityId, boolean armed) {
    // 步骤 9 接线点。
}
```

- 网络包 `network/C2SIrSeekerArmed.java` 已写好、也已在 `network/RVP_Network.java:114-117` 注册，但**客户端从不构造它**（全仓只有该包自身引用）。
- 结果：`RVP_ServerIrSeekerArmedTable` 只有 AI 炮手会写；玩家侧永远为空。
- 消费方 `weapon/core/RVP_ProjectileWeapon.java:184-193`：IR 弹只认服务端 armed 表，空即拒射并提示 `ui.rvp.ir_seeker_not_armed`。
- **表现**：即使客户端显示已锁，按左键也打不出去。

### D2. armed 写进去的键，和读取用的键不是同一个 ⇒ 锁定一秒内被自己清掉

- `arm()`（`RVP_IrSeekerTracker.java:179-196`）把状态存在 **mixin 传入的 unit**（`tickFor(self, ...)`，`mixin/WeaponUnitTickFireControlMixin.java:118`）。
- `maintainArmed()`（`:231-258`）由 `tick(Minecraft)` 用 `LocalVehiclePlayer.getWeaponUnit()`（= 根站/操作站）遍历状态，命中后调 `resolveRvpWeapon()`（`:260-268`）：

```java
return unit.getIndexedWeapons().stream()
        .filter(w -> w instanceof RVP_WeaponBase)   // ← 多弹种/agent 包装是 VehicleMultiWeapons / VehicleWeaponAgent
        ...
```

- 本包 13/17 个 IR 武器站的武器写成了 `["rvp:a","rvp:b",...]` 多弹种列表 ⇒ 站上实际对象是 `VehicleMultiWeapons`/`VehicleWeaponAgent`，**不是** `RVP_WeaponBase` ⇒ 解析返回 null ⇒ 下一 tick 直接 `unarm(unit, st, "weapon-gone")`。
- **表现**：dwell 满的瞬间闪一下 lock，下一 tick 就被清掉，永远停不住。

## 二、路由缺陷：大部分站根本喂不到 tracker

mixin 只在两种情况下调 `tickFor`（`:118`）：

```java
if (sensorType == IR || RVP_IrLockHelper.usesIrAcquireOnEo(sensorType, data)) { tickFor(...) }
```

`usesIrAcquireOnEo` = `EO && IR发射武器 && !enable_ir_hmd`；而 `sensorType == RF` 的分支在 `:81` 就直接 `return`（原意是保 ARH/SARH 手感）。

17 个 IR 武器站的实际情况：

## 三、计数缺陷：HMD 的 dwell 按「扫描次」而不是「tick」累加

`client/state/RVP_ClientHmdState.java:859` 先 `if (++irScanCounter < IR_HMD_SCAN_INTERVAL) return;`（`IR_HMD_SCAN_INTERVAL = 2`，`:45`），之后才在 `:919` 调 `feedHmdCandidate` 一次。

- 每 2 tick 才 +1 ⇒ **实际锁定延迟 = 配置值 × 2**（0.5s→1s、2s→4s）。
- 命中判据 `IR_HMD_OUTLINE_TOLERANCE_DEG = 0.0`（`:47`）+ 锥半角 `max_lock_angle/2 = 2°`，HUD 平滑有滞后，扫一次丢一帧就会走 grace，进度反复清零。

## 四、显示缺陷：非 HMD 弹即使 armed 也不显示锁定

`client/state/RVP_ClientHmdState.java:201-210`

```java
public Entity getIrArmedEntity() {
    ...
    if (unit == null || irLaunchWeapon == null) return null;   // ← irLaunchWeapon 只在 HMD 通道赋值
    return RVP_IrSeekerStateTable.getArmedEntity(unit, irLaunchWeapon.getWeaponId());
}
```

- `irLaunchWeapon` 仅在 `checkIrHmd()` 里对 `enable_ir_hmd` 弹赋值 ⇒ **非 HMD 弹（ah1z_fim92 / lavad_fim92 / z10_ty90 等）恒返回 null** ⇒ 红圈、锁定音（`RVP_ClientSeekerTone.java:99`）、对地锁定框全都不出现，看起来就是"锁不上"。
- 另外这里用的是 `LocalVehiclePlayer` 的操作站，和 D2 的键空间问题同源。

## 五、行为偏差：HMD 追踪期没有"套上并跟踪"，反而可能被伺服甩掉

- `feedHmdCandidate`（`:135-175`）刻意**不**调用 `unit.aim()`（注释说怕炮塔拖拽钳制锥）；
- `maintainArmed`（`:245`）却在 armed 后对所有弹（含 HMD）`unit.aim(目标中心)`。
- 用户期望的是"改前那样：头瞄一压上就套住并跟着目标、可以在离轴圈里离轴，只是晚一点才算锁定"。当前实现：**追踪期没有任何视觉/伺服反馈，armed 后突然开始转塔**，观感与期望相反。

## 九、追踪期准星抖动（2026-10-21 深夜修复）

### 现象

能锁上，但「已套上目标、尚未锁定」的 TRACKING 期间武器站准星疯狂抖动；锁定（ARMED）后不抖。

### 根因：伺服与鼠标**每 tick 交替写** `xAimRot`

| 写入方 | 频率 | 位置 |
|---|---|---|
| 伺服（旧） | **每 2 tick 一次**（只在 HMD 扫描 tick 上） | `RVP_IrSeekerTracker.feedHmdCandidate` 的 `aimAt`；HMD 扫描间隔 `IR_HMD_SCAN_INTERVAL = 2`（`RVP_ClientHmdState:867`） |
| 本体鼠标瞄准 | **每 tick** | `LocalVehiclePlayer.tickAim → weaponUnit.aim(freeAimPos())`（`:229`） |
| 本体站级锁定瞄准（仅 ARMED） | 每 tick | `WeaponUnit.tickFireControl` 的 `aim(center)`（AABB 中心，与伺服的 OBB 中心不同点） |

`WeaponUnit.aim()` 只要目标角与当前 `xAimRot` 不等就写字段并发 `ClientVehicleAction`（`WeaponUnit:807-820`），服务端收到即覆盖 `setXAimRot`（`PartUnit:494`）。于是每一 tick 的 `xAimRot` 在「目标角」和「鼠标角」之间来回翻转（HMD 弹 10 Hz），`tickRot` 的伺服目标跟着翻转 ⇒ 准星抖。

ARMED 不抖，是因为 `maintainArmed` 每 tick 伺服一次，与鼠标同频（谁后写谁生效，服务端最终稳定在伺服点）—— 正好反证「频率不齐」是抖的主因。

### 修法（3 个文件）

| 文件 | 改动 |
|---|---|
| `client/state/RVP_IrSeekerTracker.java` | 新增 `servoTracking(root)`：**每 tick**（`tick(Minecraft)`，ClientTickEvent.END）对 TRACKING 状态伺服；`tickFor`/`feedHmdCandidate` 里删掉 `aimAt`（只做候选与 dwell）；超过 dwell 宽限仍未被喂入 ⇒ 就地回 SEARCH（防切武器后幽灵伺服）；新增 `isServoActive(WeaponUnit)`（按根站归一、带新鲜度判定） |
| `mixin/LocalVehiclePlayerMachinegunLeadTurnMixin.java` | 新增 `@Redirect tickAim` 的 `WeaponUnit.aim` 调用：伺服期间跳过鼠标瞄准；`ywzj_rvp$shouldSuppressMouseAim` 增加 IR 伺服判断（SCOPE 的鼠标增量同样不写） |
| `mixin/WeaponUnitSoftRfMixin.java` | `tickFireControl` 的站级锁定瞄准：伺服期间跳过（避免与伺服的 OBB 中心瞄准点同 tick 交替） |

结果：TRACKING/ARMED 期间瞄准只有**一个写者**（tracker，END 阶段、晚于本体 `tickAim`），`xAimRot` 单调跟随目标 ⇒ 不抖。

### 行为变化（有意）

- 伺服期间炮塔由导引头接管，鼠标不再能抢方向（这与改前「锁定后炮塔锁死目标」一致，只是提前到 TRACKING）。
- 想中断：关导引头 / 切武器 / 目标消失；状态清空后鼠标立即恢复。
- 若以后想改回「只有锁定后才伺服」，把 `servoTracking` 里的 TRACKING 分支删掉即可（一处）。

验证：`compileJava --offline` BUILD SUCCESSFUL；改前备份 `_bak/ir_servo_jitter_20261021_222427`。

## 十、最终定案：炮塔不强制转向，只做「头瞄框跟随」（2026-10-21 22:45）

§九 的做法是「保留伺服、让伺服独占瞄准」，能消抖但代价是追踪/锁定期间炮塔锁死、鼠标抢不回方向。用户决定改用更简单的语义：

> **IR 通道完全不写 `xAimRot/yAimRot`。炮塔始终由玩家鼠标控制；只有头瞄框（视觉层）跟随目标。**

### 改动（相对 §九）

| 文件 | 最终状态 |
|---|---|
| `client/state/RVP_IrSeekerTracker.java` | 删除 `servoTracking`、`maintainArmed` 的 `aimAt`、`aimAt` 方法本体、`Vec3`/`RVP_AimPointResolver` 导入 ⇒ **全文 0 处 `aim(`**。只保留候选扫描、dwell 累积、arm/unarm、上报、hold 保活 |
| `mixin/LocalVehiclePlayerMachinegunLeadTurnMixin.java` | **完全还原**（不再屏蔽鼠标 `tickAim`/SCOPE 增量） |
| `mixin/WeaponUnitSoftRfMixin.java` | 保留一个守卫：`isIrLockActive(self)` ⇒ 跳过 `tickFireControl` 的「站级锁定自动瞄准」 |
| `RVP_IrSeekerTracker#isIrLockActive` | 由 `isServoActive` 改名：IR 通道占用（TRACKING 有活候选 / ARMED 有活目标）时，本体火控不得把炮塔拽向锁定目标 |

### 为什么锁定后还要屏蔽 tickFireControl

`arm()` 会写站级 `lockedEntity`（HUD 锁定框、`RVP_ClientSeekerTone`、部分外部雷达链路还要读它）。本体会在 `tickFireControl` 里对 `lockedEntity` 做 `aim(AABB 中心)`——不屏蔽的话，锁定后炮塔仍会被强行转向。屏蔽只作用于这一个 `aim` 调用，方法内其余逻辑（锁定有效性检查、雷达实体切换等）照常执行。

### 结果

- 追踪期：炮塔跟你鼠标走，头瞄框自己套目标，dwell 到点出红圈/锁定音。
- 锁定后：炮塔仍跟你鼠标走；**转开就会让目标离开 hold 包线，超过 `seeker_lock_hold_grace_tick`（默认 6t）自动掉锁** —— 炮塔指向本身就是「保持照射」的操作要求。
- 发射门（`passesShootLockGates`）与离轴终检仍按 armed 表 + 离轴基准方向判定，与炮塔无关（HMD 默认以中立安装轴为基准）。
- 非 HMD（固定导引头）弹：包线本来就以炮塔轴为准，所以必须把准星压住目标才累积 dwell —— 正是「视场内有目标」的语义。

验证：`compileJava --offline` BUILD SUCCESSFUL（422→427 行，CRLF 保持）。改前备份 `_bak/ir_servo_jitter_20261021_222427`。

## 十一、追踪期「截获中」文案（2026-10-21 22:55）

### 实现

## 十三、命中面板爆炸伤害与真实掉血不符（2026-10-22 01:15，已修）

### 现象

ZTZ99B 用 `DTB-10-125 高爆榴弹` 打 ZBL-08 轮式步战车，三发击毁，但命中展板只显示 `爆炸 -14.8%`。

### 根因：爆炸波及包用估算，漏乘两侧爆炸倍率

| | 公式 | 说明 |
|---|---|---|
| 真实结算（`RVP_VehicleHurtScalingHandler:218`） | `deltaAfterCore × weaponExplosionDamageFactor × vehicleExplosionHitboxMult` | 武器侧 `explosion_damage_factor` 按受击机型 × 受击方 `vehicle_explosion_damage_factor` |
| 面板（`RVP_BaseBullet:4581` 改前） | `resolvedDamage × (1 − 0.5·d/radius)` | **只乘了估算距离衰减，两侧倍率全漏** |

`vt4_dtb10` 的 `explosion_damage_factor` 对轮式 = **2.0** ⇒ 面板恒为真实值的 1/2 左右（14.8% ↔ 实际 ~30%），与三发击毁吻合。ZBL08A 未配 `vehicle_explosion_damage_factor`（=1），所以差异全部来自武器侧 ×2。

### 修法：面板数值改用「实测血量差」

| 位置 | 改动 |
|---|---|
| 直击包（`applyEntityHitDamage`） | hurt 前记 `healthBeforeHit`，hurt 后用 `before − after` 作 `reportedDamage`（替换估算的 `finalDamage`） |
| 爆炸波及包（`triggerExplosion`） | `blastTargets` 快照时同批记 `blastHealthBefore`，结算后 `boomDamage = before − after`；读不到才回退旧估算 |

这样面板百分比恒等于真实掉血，天然覆盖：两侧爆炸倍率、本体距离衰减、装甲保底、命中箱重放、残血封顶、秒杀。

### 同类问题排查

| 通道 | 结论 |
|---|---|
| 直击包 | 有同类偏差（残血/保底/重放），已一并改实测 |
| 近炸（PROXIMITY） | 先直伤（直击包）再爆炸，`excludeEntity` 排除该目标 ⇒ 不重复；两侧都已覆盖 |
| 部件/设备伤害（`accumulateExplosionEquipmentDamage`） | 不进主血量，面板本就不该显示 ✔ |
| ERA 破坏（`destroyModulesByExplosionRadius`） | 不扣血 ✔ |
| 本体面板（`hit_indicator_rvp:false`） | 走本体 `ServerHitVehicleEvent`，不在 RVP 侧 ✔ |
| 调试层（`RVP_BulletHitDebugOverlay`） | 显示的是倍率明细，不是伤害，无需改 |

备份 `_bak/hit_panel_actual_20261022_011312`；`compileJava --offline` BUILD SUCCESSFUL。
