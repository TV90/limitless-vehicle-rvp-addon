# `effects_data.caliber` 语义修正：新增曳光口径 `tracer_caliber`

> 状态：**代码侧待执行**（本文档只做设计）；**数据侧已由本次一并迁移**（见 §五）
> 目标读者：执行代码改动的 agent
> 触发来源：外部开发者反馈 —— `caliber` 不按真实口径填，导致其「按口径分档的特效」无法判定

---

## 一、背景与问题

RVP 武器 JSON 的 `effects_data.caliber` 目前填的是**弹体直径**，不是**身管口径**。例如：

| 武器 | 弹名 | 实际身管口径 | 现填 `effects_data.caliber` |
|---|---|---|---|
| `t90m_3bm59` 等 | 3BM59 APFSDS | **125 mm** | **24.765** |
| `vt4_dtc10` | DTC-10-125 APFSDS | **125 mm** | **24.765** |
| `052d_hpj38` | H/PJ-38 130MM | **130 mm** | **40.765** |
| `ddg51_mk45` | MK-45 MOD4 127MM | **127 mm** | **40.765** |
| `052d_hpj12` | H/PJ-12 30mm | **30 mm** | **15.24** |
| `lav25_apfsds` | M919 25mm | **25 mm** | **19.05** |

这不是"填错了" —— 代码注释里写得很明确（`RVP_DelayedMuzzleSmokeEmitter` 的 javadoc）：

> RVP 的 `effects_data.caliber` 是**弹体直径**，不是身管口径；例如 T-90M 的 125 mm 主炮弹体配置为 24.765 mm。

24.765 这类值是为**视觉尺寸**服务的（脱壳穿甲弹弹芯直径）。问题在于**字段名叫 `caliber`**，语义上被理解成"真实口径"，外部开发者据此做**分口径特效分档**时就会误判（125 mm 主炮被当成 24.765 mm）。

**诉求**：把「视觉尺寸」与「真实口径」拆成两个字段 —— 新增曳光口径承载前者，`caliber` 恢复后者。

## 二、现状机制（改动前必读）

### 2.1 字段定义

`src/main/java/org/ywzj/rvp/weapon/data/RVP_EffectsData.java`：

```java
/** 机枪弹口径覆盖，单位毫米，默认 null；未配置或非正值时按 7.62。 */
@SerializedName("caliber")
private Float caliber;

@SerializedName("tracer_r") / tracer_g / tracer_b          // 曳光颜色
@SerializedName("tracer_length_scale")                       // 曳光长度倍率（已存在）
```

getter：

```java
public boolean hasCaliberOverride() { return caliber != null; }

public float getCaliber() {
    return caliber != null && caliber > 0f ? caliber : 7.62f;   // 默认回退 7.62
}
```

### 2.2 消费点（全仓仅 3 处，已核实）

| # | 文件 | 行 | 用途 |
|---|---|---|---|
| 1 | `client/visual/vehicle/RVP_MuzzleSmokeEmitter.java` | 171 | 炮口烟粒子尺寸 |
| 2 | `client/visual/vehicle/RVP_DelayedMuzzleSmokeEmitter.java` | 234 | 延迟炮口烟（重炮）尺寸与门槛 |
| 3 | `client/visual/cookoff/RVP_WreckCookoffResolver.java` | 169 | 残骸烤燃判定的口径入参 |

其中 #3 的下游 `RVP_WreckCookoffWeaponPolicy.accepts(...)` 有一处硬阈值：

```java
return Double.isFinite(caliber) && caliber >= 20;   // ≥20 视为可触发烤燃的大口径
```

### 2.3 容易混淆的另一个 `caliber`（★ 不要动）

- **本体顶层 `BaseVehicleWeaponData.caliber`**（默认 `5.8f`）→ 传给 `BulletEntity` / `MissileEntity` → 影响**弹道线宽**（`BulletEntityRenderer`）、**弹孔大小**（`BulletHoleParticle`）、**导弹尾焰与屏幕震动**（`MissileEntity`）。
- 以下两处读的是**本体弹体**的 caliber，**与 `effects_data.caliber` 无关**，本次不涉及：
  - `client/render/VehicleProjectileRenderLogic.java:44`（曳光粗细，读 `bullet.getCaliber()`）
  - `client/render/RVP_BedrockProjectileEntityRenderer.java`（尾焰模型缩放，注释中的 `caliber/1000`）

> 结论：`effects_data.caliber` **不参与曳光线宽计算**，它影响的是炮口烟尺寸与烤燃判定。

## 三、目标

1. 新增字段 `effects_data.tracer_caliber`（曳光口径 / 弹体视觉口径），**完整承接原 `caliber` 的全部既有用途**

4. **向后兼容**：未配置 `tracer_caliber` 的存量数据自动回退到 `caliber`，行为不变

## 四、代码改动清单（1 个类 + 3 个消费点）

### 4.1 `weapon/data/RVP_EffectsData.java`

**(1) 新增字段**（紧跟 `caliber` 之后）

```java
/**
 * 曳光/弹体视觉口径覆盖，单位毫米，默认 null。
 * 未配置或非正值时回退 {@link #caliber}，再回退 7.62。
 * 仅影响炮口烟尺寸与烤燃判定等视觉/特效路径，不参与弹道物理。
 */
@SerializedName("tracer_caliber")
private Float tracerCaliber;
```

**(2) 新增 getter 与判定**

```java
public boolean hasTracerCaliberOverride() {
    return tracerCaliber != null;
}

/** 曳光/弹体视觉口径：优先 tracer_caliber，其次 caliber，最后 7.62。 */
public float getTracerCaliber() {
    if (tracerCaliber != null && tracerCaliber > 0f) {
        return tracerCaliber;
    }
    return getCaliber();
}
```

**(3) 修正 `caliber` 的 javadoc**（这是本次最重要的文档修正）

```java
/**
 * 真实身管口径，单位毫米，默认 null。
 * 仅作语义数据，供按口径分档的外部逻辑使用；
 * 【不参与】曳光、炮口烟等视觉尺寸计算 —— 那是 {@link #tracerCaliber} 的职责。
 */
@SerializedName("caliber")
private Float caliber;
```

### 4.2 三个消费点改读新值

| # | 文件 | 改动 |
|---|---|---|
| 1 | `RVP_MuzzleSmokeEmitter.java:171` | `sanitizeCaliber(rvpData.getEffectsData().getCaliber())` → `sanitizeCaliber(rvpData.getEffectsData().getTracerCaliber())` |
| 2 | `RVP_DelayedMuzzleSmokeEmitter.java:234` | `rvpData.getEffectsData().getCaliber()` → `...getTracerCaliber()` |
| 3 | `RVP_WreckCookoffResolver.java:169` | `rvp.getEffectsData().getCaliber()` → `...getTracerCaliber()` |

⚠️ 三处必须**全部**改。若只改一部分，`caliber` 改成真实值后：
- 炮口烟尺寸会变（如 125 mm 走大口径分支）
- `caliber >= 20` 的烤燃判定会变化（见 §六影响表）

**(4) 顺带更新注释**：`RVP_DelayedMuzzleSmokeEmitter:236` 现有注释「RVP 的 caliber 可能是脱壳弹体直径」应同步改为「RVP 的 **tracer_caliber** 是脱壳弹体直径」；`RVP_MuzzleSmokeEmitter` 中提及 `effects_data.caliber` 的注释同步改为 `tracer_caliber`。

## 六、顺序、兼容性与影响

### 6.1 必须「先代码、后数据」

| 顺序 | 结果 |
|---|---|
| **只改数据**（`caliber` 变真实值，消费点仍读 `caliber`） | ⚠️ 炮口烟尺寸变化；`caliber >= 20` 烤燃判定变化（见下表）。**不要单独上数据** |
| **只改代码**（新字段生效，数据未迁） | ✅ 安全 —— `tracer_caliber` 缺省 ⇒ 回退 `caliber` ⇒ 行为与改动前完全一致 |
| **两者都上** | ✅ 目标状态：视觉不变、`caliber` 语义正确 |

### 6.2 烤燃判定影响表（若消费点未改读新字段）

`RVP_WreckCookoffWeaponPolicy.accepts` 阈值为 `caliber >= 20`：

| 组 | 原口径值 | 阈值结果 | 改真实值后 | 是否变化 |
|---|---|---|---|---|
| 坦克炮弹（24.765） | 24.765 | ✅ true | 105/120/125 | 不变 |
| 40.765 组（130/127） | 40.765 | ✅ true | 130/127 | 不变 |
| 30 组（M61A1 实际 20） | 30 | ✅ true | 20 | 不变 |
| **15.24 组**（20~35 mm） | 15.24 | ❌ false | 20/25/30/35 | ⚠️ **变 true** |
| **19.05 组**（25~30 mm） | 19.05 | ❌ false | 25/30 | ⚠️ **变 true** |

⇒ **这一列「变化」正是必须把 3 个消费点全部改读 `getTracerCaliber()` 的原因**；改全之后该表全部回到"不变"。

### 6.3 向后兼容

- `tracer_caliber` 未配置 ⇒ `getTracerCaliber()` 回退 `caliber` ⇒ **存量未迁移数据零影响**
