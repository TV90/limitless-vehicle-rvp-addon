## 0. 已定版的三条决策（用户 2026-10-21 确认，实现不得偏离）

| # | 决策 | 含义 |
|---|---|---|
| D1 | **追踪期自动跟随伺服** | 导引头一旦捕获候选，武器站就跟着目标转（`aim()`）；dwell 满才落锁。**就是要"自动锁定延迟"的手感** |

## 1. 目标语义（一句话）

> **IR 锁定（armed）= 同一个目标连续 `D` tick 待在"该导引头自己的跟踪包线"内。**

不是"开导引头计时 20 tick"，也不是"站级锁定后计时"。目标离开包线 ⇒ 进度清零（允许 `G` tick 短暂脱锁宽限：不涨不降）。

### 1.1 跟踪包线（按是否有头瞄区分）

| 弹型 | 包线（角度） | 中心轴 | 依据 |
|---|---|---|---|
| **无头瞄**（`enable_ir_hmd:false`） | 视场半角 `max_lock_angle / 2` | 武器站**当前瞄准轴** `worldVec()`（= 准星方向） | `RVP_IrLockHelper.isTargetWithinAcquireLimits` → `launch.maxLockHalfAngle()`；对应本体 `Infrared.findTarget` 的锥轴 |
| **有头瞄**（`enable_ir_hmd:true`） | 万向架/离轴范围 单侧 `max_off_axis_lock_angle` | 中立安装轴 `worldVec(0,0)`，或按 `off_axis_stacks_with_station_rotation` 叠加站旋转 | `RVP_IrLockHelper.isTargetWithinHoldLimits` → `launch.maxOffAxisLockAngle()`；HMD 的 `clampIrScanDirection` 已把扫描方向钳在该锥内 |

两种都必须同时满足既有非角度门：距离 ∈ `lock_target_distance_range`、离地高 ∈ `lock_altitude_range`、视线通畅（`hasClearLineOfSight`：遮挡方块 + `SightObstruction` + `TargetObstruction`）。

### 1.2 状态机

```
                ┌────── seekerOn=false / 非IR弹 / 目标死 / 换弹种 ──────┐
                ▼                                                        │
   OFF ──(开导引头+选中IR弹)──► SEARCH ──(捕获候选)──► TRACKING ──(dwell≥D)──► ARMED
                ▲                  ▲                    │                      │
                │                  └──(超G仍无候选)──────┘                      │
                └─────────────────(离开hold包线超H)────────────────────────────┘
```

- **TRACKING**：站自动跟随候选（D1）；**不写站级锁、不播锁定音、不画锁定视觉**（D2）。
- **ARMED**：唯一发射授权来源；此时才写站级锁 + 播锁定音 + 画锁定视觉。
- **ARMED → 结束**：目标死亡 / 离开 hold 包线超 `H` tick / 关导引头 / 换武器 / 换弹种 / 换站。
- **候选粘滞**：已有候选仍有效时不换目标（防止伺服跟随导致左右横跳），只有候选失效才重选。

### 1.3 数值

| 符号 | 字段（在 `RVP_GuidanceDataIR`） | 默认 | 说明 |
|---|---|---|---|
| `D` | `seeker_lock_dwell_tick` | **20**（1 秒） | 连续跟踪多少 tick 落锁；AI 同用此值 |
| `G` | `seeker_dwell_grace_tick` | **3** | 追踪期短暂掉出包线不清零（不涨不降） |
| `H` | `seeker_lock_hold_grace_tick` | **6** | 锁定后超包线保活（吸收现有 `IR_RELOCK_GRACE_TICKS=6` 与 HMD 的 20） |

全部可缺省 ⇒ **在用的 18 个 IR 武器 JSON 一个都不改也能按新语义跑**（旧副本 `kd_88a` 同样走默认值）。

## 2. 现状事实（先理解，避免改错地方）

### 2.1 继承关系

| 类 | 位置 | 说明 |
|---|---|---|
| `AbstractVehicleWeapon` | 本体 | 所有车载武器基类 |
| `VehicleMissile` | 本体 `vehicle/weapon/VehicleMissile.java:21` | 本体导弹，**RVP 弹不是它的子类** |
| `RVP_WeaponBase` | `weapon/core/RVP_WeaponBase.java:45` | `extends AbstractVehicleWeapon<RVP_WeaponData>` |

推论：本体 `tickFireControl` 的 `missileWeapon`（`WeaponUnit.java:560-566`）只认 `instanceof VehicleMissile`，**对 RVP 弹恒为 null** ⇒ 本体那段 `Infrared.findTarget` / `Radar.findTarget` 对 RVP 是**死代码**。

### 2.2 20 tick「预热」的真实位置

| 项 | 位置 | 事实 |
|---|---|---|
| 计数器 | `ywzj_vehicle WeaponUnit.java:109` | `private int lockCoolingTick;` |
| 累加 | `WeaponUnit.java:621-623` | 在 `isSeekerOn() && lockedEntity == null` 分支每 tick +1 |
| 归零 | `WeaponUnit.java:746` `toggleSeeker()` | 开/关导引头、弹药打光自动关 |
| **RVP 真正吃这个门控处** | `ywzj_rvp mixin/WeaponUnitTickFireControlMixin.java:98` | `if (getLockCoolingTick() <= 20) return;` |

⇒ 语义是"开导引头后一次性等 1 秒"，与"目标在包线内持续多久"完全无关。

### 2.3 现在 IR 锁怎么产生的（三条路径，全要改）

**路径 A：导引头自动搜索（非 HMD）** — `WeaponUnitTickFireControlMixin:84-135`

```java
if (sensorType == IR && self.getLockedEntity() != null) { ...记忆...; return; }  // :90-94 ← 泄漏
if (self.getLockedEntity() != null) { return; }                                  // :95-97 ← 泄漏
if (self.getLockCoolingTick() <= 20) { return; }                                  // :98-100
entity = rvp$resolveIrLockWithHysteresis(self, rvpWeapon);                        // :105 → :157-176
if (entity != null) self.setLockedEntity(entity);                                 // 直接落锁
```

**路径 B：HMD 头瞄（`enable_ir_hmd:true`）** — `client/state/RVP_ClientHmdState.java`
`:804-940` 每 tick 扫描，命中即 `confirmIrLock(...)`（`:972`）**立刻锁**；锁定后靠 `IR_LOCK_GRACE_TICKS=20`（`:49`）做超锥保活。写的是 `weaponUnit.setLockedEntity(...)`。

**路径 C：EO 传感器代捕获** — `RVP_IrLockHelper.usesIrAcquireOnEo(...)`：传感器为 `EO` 且当前是 IR 发射武器且非 HMD 弹时，走与 A 相同的自动搜索；EO 自己的锁定（`RVP_ClientHmdState` 的 `eo_locked` 通道）也写同一个 `lockedEntity`。

### 2.4 泄漏点（本方案核心修复对象）

| # | 位置 | 现状 |
|---|---|---|
| L1 | `WeaponUnitTickFireControlMixin:90-97` | 站级已有锁（EO/RF/HMD/手动）⇒ 直接 return，等同"IR 已锁定" |
| L2 | `RVP_WeaponBase.passesShootLockGates()` `:156-223`（`:182`） | IR 用 `unit.getLockedEntity()`/外置雷达锁，经 `resolveUsableIrLaunchTarget` 校验 ⇒ 任何来源的站级锁都能过 IR 发射门 |
| L3 | `RVP_ProjectileWeapon.dispatchShots()` `:177-183` | 服务端 `lock = rootUnit.getLockedEntity()`（RF 时取雷达锁）⇒ EO/RF 锁直接被当导弹目标；`:184-196` 离轴终检只查角度不查来源 |

## 3. 总体设计

```
┌──────────────────────── 客户端（权威） ────────────────────────┐
│ RVP_IrSeekerTracker（新增，每 tick）                            │
│   ├─ 扫描/校验候选（包线 + 距离/高度/LOS）                        │
│   ├─ dwell / armed / hold 状态（RVP_IrSeekerStateTable）          │
│   ├─ TRACKING & ARMED 时：unit.aim(candidateCenter)  ← D1        │
│   ├─ ARMED 时：写站级 lockedEntity（仅给 HUD/同步/音效/伺服）      │
│   └─ 状态跃迁时：发 C2SIrSeekerArmed                              │
│ RVP_ClientHmdState（改）：HMD 锁定前先喂 dwell，不再 instant lock │
│ WeaponUnitTickFireControlMixin（改）：只喂候选，不再直接落锁       │
│ HUD（改）：锁定视觉只在 armed 时画（D2）                          │
└───────────────────────────────────────────────────────────────┘
                              │ 跃迁包
┌──────────────────────── 服务端（校验） ────────────────────────┐
│ RVP_ServerIrSeekerArmedTable（新增，key=根站+weaponId）           │
│   ├─ 收包：存活 + 包线复算（服务端可算）                          │
│   └─ 发射：IR 只取本表 armed 目标；无 ⇒ 拒射                      │
│ RVP_ServerIrSeekerTracker（新增）：AI 炮手 dwell（D3，必做）       │
└───────────────────────────────────────────────────────────────┘
```

**为什么必须新开通道**：`WeaponUnit.lockedEntity` 是站级概念，同时被 RF/SARH 制导、`RVP_MachinegunLeadSolver` 提前量、GPS 雷达上行、HUD、`RVP_ClientSeekerTone` 音效、导弹 target 共用。EO/RF 必须继续能写它，所以只能**另立 IR armed 状态**，把站级锁降级为"cue + 显示"。

## 5. 客户端实现

### 5.1 `client/state/RVP_IrSeekerTracker.java`（核心）

挂载点：`client/RVP_ClientEvents.java` 客户端 tick，紧跟 `hmdState.tick();`（当前 `:535`）。

```
tick(Minecraft mc):
  unit = 当前操作根武器站；weapon = 解包后的当前 RVP 武器
  若 unit==null / !seekerOn / !isIrLaunchWeapon / (非HMD 且传感器非 IR/EO):
      reset(unit); 若之前 armed: 清站级锁(只清自己写的) + 发包(false); return

  data = weapon.getData(); D/G/H = RVP_GuidanceDataIR.resolve*(data)
  st = stateFor(unit, data.getWeaponId())
  若 st.weaponId != 当前 weaponId: reset(st)

  // 1) 候选：粘滞优先
  best = st.candidateId 存活且仍在包线 ? 该目标 : 重新扫描
  if 重新扫描:
      for e in mc.level.entitiesForRendering():        // 同 HMD 扫描源，避免 ±range 立方体
          skip 自身/玩家/乘员/死亡/PartEntity/超距离
          if !passesEnvelope(unit, e, data): continue
          ang = RVP_HmdTargetingMath.effectiveAngularMissDeg(seekerPos, seekDir, e.getBoundingBox())  // guidance/RVP_HmdTargetingMath
          if ang > envelopeHalfAngle + OUTLINE_TOLERANCE_DEG: continue
          score = ang*0.7 + dist*0.0003；载具优先（同 HMD 排序）
      best = 最优者
      // seekDir: 非HMD = unit.worldVec()；HMD = clamp 后的 HMD 扫描方向

  // 2) dwell
  if best == null:
      if st.armedId != -1: 走 ARMED 维持逻辑
      else if gameTime - st.lastInEnvelopeTick > G: st.dwellTicks = 0; st.candidateId = -1
      st.phase = SEARCH
  else:
      if best.id != st.candidateId: st.candidateId = best.id; st.dwellTicks = 0
      st.dwellTicks++; st.lastInEnvelopeTick = gameTime
      st.phase = TRACKING
      unit.aim(RVP_AimPointResolver.resolveLargestObbCenter(best))   // ← D1：追踪期就跟随
      if st.dwellTicks >= D: arm(st, best)

  // 3) ARMED 维持
  if st.armedId != -1:
      t = level.getEntity(st.armedId)
      if t==null || !t.isAlive(): unarm()
      else if passesHoldEnvelope(unit, t, data):
          st.lastArmedInEnvelopeTick = gameTime
          unit.aim(RVP_AimPointResolver.resolveLargestObbCenter(t))  // 锁定后持续伺服
      else if gameTime - st.lastArmedInEnvelopeTick > H: unarm()
```

**注意 D1 带来的副作用**：因为站会自己追目标，一旦捕获候选，目标基本会一直留在包线内 ⇒ dwell 实际等于"捕获后延迟 D tick 落锁"。这是用户要的效果，不要再加"必须手动压准星"的限制。

### 5.2 `passesEnvelope` / `passesHoldEnvelope`

- 非 HMD 跟踪门：`RVP_IrLockHelper.isTargetWithinAcquireLimits(unit, e, data)`（内含 `maxLockHalfAngle` + 距离 + 高度 + LOS）
- HMD 跟踪门：`RVP_IrLockHelper.isTargetWithinHoldLimits(unit, e, data)`（`maxOffAxisLockAngle` + 距离 + 高度 + LOS）
- 保持门（两者相同）：`isTargetWithinHoldLimits`
- 角/距/高/LOS 任一不过 ⇒ 不在包线内（走 `G` 宽限）

### 5.3 改造 `WeaponUnitTickFireControlMixin`

| 现状 | 改法 |
|---|---|
| `:90-94` `sensorType==IR && lockedEntity!=null` ⇒ 记忆并 return | **删除该短路** |
| `:95-97` 任意锁 ⇒ return | **只保留给 RF 分支**（ARH TWS 自动锁维持现状），IR 不再早退 |
| `:98-100` `lockCoolingTick <= 20` ⇒ return | **移进 RF 分支内部**；IR 由 dwell 取代 |
| `:102-105` IR/EO 分支 → `rvp$resolveIrLockWithHysteresis` 并写锁 | 改为 **只调 `RVP_IrSeekerTracker.feedCandidate(...)`**（或整个逻辑迁进 tracker，mixin 只留一行转发），**不再 `setLockedEntity`** |

### 5.4 改造 `RVP_ClientHmdState`（HMD 路径）

- `:866-935` 扫描循环保留（轮廓容差、载具优先、`clampIrScanDirection`），但 `confirmIrLock(...)`（`:972`）改为 **`RVP_IrSeekerTracker.feedHmdCandidate(unit, weapon, bestTarget, effectiveAngle)`**：只有 tracker 的 dwell 达标才真正 `confirmIrLock`。

### 5.5 EO 传感器代捕获如何处理

`usesIrAcquireOnEo` 保留"用 EO 瞄准方向做搜索"的能力，但**取消锁定授权**：EO 传感器下 tracker 仍按非 HMD 包线扫（锥轴 `unit.worldVec()`），dwell 从 0 累积。
EO 的 `lockedEntity` 只能当**候选提示**（同分时的 tie-break 加权），**不能减少 dwell、不能替代 armed**。

## 8. AI 炮手（D3：必须等 dwell）

`RVP_GunnerWeaponActions:188/277/315` 直接 `weaponUnit.shoot(...)`（服务端），不经客户端门控；若 L3 只认同步表，AI 会永久拒射。

**实现**：新增 `entity/gunner/ai/RVP_ServerIrSeekerTracker.java`

```
在 AI 选定开火目标、且当前武器是 IR 弹时，每 tick 调：
  if 目标 != 上次目标: 计数清零
  if passesEnvelope(unit, target, data)  // 服务端可算（同 §5.2 helper）
         dwell++
  else   dwell = 0
  if dwell >= D:

```

- 调用点：AI 的瞄准/开火决策处（`RVP_GunnerWeaponActions` 内 `shoot` 之前），或在 `RVP_GunnerRadarActions` 的锁定流程之后统一 tick。

- AI 与玩家共用 `D`（不新增 AI 专用字段），因为 AI 站本来就自动指向目标，实际延迟就是 D tick。

## 13. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 手感：自动跟随后 dwell 只是延迟 | 用户明确要这个效果（D1），不视为问题 | — |
| 伺服把候选锁死 | 站自转追一个错误候选（如诱饵） | `G` 宽限 + 候选粘滞只在仍有效时成立；换候选需旧候选失效 |
| 站级锁被 tracker 误清 | EO/RF 锁被 unarm 清掉 | 只清 `lastWrittenStationLockId` 匹配项（§7.1） |
| 双端不同步 | 服务端表过期 | 收包复算包线 + 存活校验 + `weaponId` 防串弹 |
| AI 拒射 | 忘改 AI 路径 | §8 独立步骤，用例 15 必测 |
| HMD 20t 保活与统一字段冲突 | 两常量语义重叠 | 统一到 `seeker_lock_hold_grace_tick`，HMD 弹数据显式写 20 |
| 适配器回归 | 新增子类可能影响既有 GPS/ARM/HITL 解析 | 只新增类型分支，不动既有；用例 14 + 全量武器加载自检 |
