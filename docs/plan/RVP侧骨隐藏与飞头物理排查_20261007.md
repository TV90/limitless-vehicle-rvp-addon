> 日期：2026-10-07　范围：`ywzj_rvp`（RVP 源码）/ `data/rvp/vehicles/*.json`
> 背景：三车（VT4 / T-90M / ZTZ99B）飞头已配好，但**炮口焰 `turret_muzzle_flash` 仍然会跟着飞头一起显示**；

## 一、为什么纯数据路线失效（已逐层核对到字节码）

**结论：不是缺功能，而是「排除表算出来是空」。**

### 1. 本体运行时 jar 里功能齐全（E 盘 `mods/ywzj_vehicle-1.20.1-0.6.0.jar`，2026-10-02 构建）

| 位置 | 证据（`javap -p -c`） |
| --- | --- |
| `VehiclePartRender.render` | 调 `VehiclePart.getExcludedBoneNames()`，随后 `BakedModelInstance.getBone(String)` + `putfield BoneState.visible`（渲染前置 false，finally 恢复） |
| `VehiclePart` | 含 `collectExcludedBoneNames(PartUnit)` 两个私有静态方法，`initializePart` 里 `invokestatic` 填充 `excludedBoneNames` |
| `PartUnit.isDetachable()` | `data.isDetachable() && renderBoneName != null && !isBlank() && structureGroup != null`（与源码逐条一致） |

### 2. 渲染库确实尊重 `visible`

`BakedBedrockModel.renderBone(instance, boneIndex, ...)` 开头：

```
33: getBone(boneIndex) -> BoneState
40: ifnull 53          // bone == null → return
45: getfield BoneState.visible
50: ifne 54            // visible != 0 → 继续
53: return             // visible == false → 直接 return（子树也不画）
```

⇒ `visible=false` 的骨（含其子树）**一定**不会被画。

### 3. 排除「骨被烘焙折叠」

`RVP_VehicleModelFactory.createStaticBakerOptions()`（:46-49）在 `bedrock_backend == "rvp"` 时：
```java
preservedBones.addAll(new BedrockModel(pojo).getBoneMap().keySet());   // 全部骨名
```
⇒ RVP 后端**什么骨都不折叠**，`getBone("turret_muzzle_flash")` 必非 null。而且 `turret_muzzle_flash` 在渲染模型里确实位于 `$weapon0` 子树内（VT4: `$weapon0_1 ← $weapon0_0 ← $weapon0`；99B: `$weapon0_1_hurt ← $weapon0_1 ← $weapon0_0 ← $weapon0_base ← $weapon0`）。

### 4. 唯一可能失效的环节

```java
// PartUnit.combineAndInit  :130-135
for (PartUnit<?> partUnit : partUnitsView.values()) {
    if (structureGroup != null && structureGroup.children.contains(partUnit.structureGroup)) {
        attPartUnits.add(partUnit);
```
```java
// VehiclePart.collectExcludedBoneNames
for (PartUnit<?> attached : partUnit.getAttPartUnits())
    if (attached.isDetachable()) excludedBoneNames.add(attached.getRenderBoneName());
```

即：**排除项只来自「结构骨层级上的直接子部件」这一私有推导**。幽灵部件方案要求 `structure_bone` 的 group 恰好挂在该部件 group 的 `children` 上——这条链**没有日志、没有开关、没有可观测手段**，一旦不成立就静默失效。已经赌过一次，不再继续赌 ⇒ 改代码是正解。

## 二、RVP 侧实现方案（推荐）

### 数据字段

部件级（与 `render_bone` 同级）：

```jsonc
{
  "id": "turret", "type": "ywzj_vehicle:weapon", "structure_bone": "turret",
  "render_bone": "$weapon0",
  "rvp_hide_render_bones": ["turret_muzzle_flash"],   // ← 新增：这些渲染骨在部件脱离后不画
  ...
}
```

语义：**仅作用于脱离后的 `VehiclePart`**（即飞头残件），整车不受影响（整车继续由 `static` 动画压成 scale 0 隐藏）。

### 落地 4 处改动

**① `ext/PartUnitDataExt.java`** —— 加 getter
```java
List<String> ywzj_rvp$getHideRenderBones();
```

**② `mixin/PartUnitPojoMixin.java`** —— 加 JSON 字段（沿用该类既有模式）
```java
@SerializedName("rvp_hide_render_bones")
@Unique
public List<String> ywzj_rvp$hideRenderBones = List.of();

@Override
public List<String> ywzj_rvp$getHideRenderBones() {
    return ywzj_rvp$hideRenderBones == null ? List.of() : ywzj_rvp$hideRenderBones;
}
```

**③ `mixin/PartUnitDataMixin.java`** —— 构造器 TAIL 拷贝到运行时（与 `rvp_no_cockpit_view` 完全同款）
```java
@Unique private List<String> ywzj_rvp$hideRenderBones = List.of();

@Inject(method = "<init>(Lorg/ywzj/vehicle/custom/part/data/PartUnitPojo;)V", at = @At("TAIL"), remap = false)
private void ywzj_rvp$init(PartUnitPojo pojo, CallbackInfo ci) {
    if (pojo instanceof PartUnitPojoExt ext) {
        this.ywzj_rvp$noCockpitView = ext.ywzj_rvp$isNoCockpitView();
        List<String> bones = ext.ywzj_rvp$getHideRenderBones();          // ← 新增
        this.ywzj_rvp$hideRenderBones = bones == null ? List.of() : List.copyOf(bones);
    }
}

@Override
public List<String> ywzj_rvp$getHideRenderBones() { return ywzj_rvp$hideRenderBones; }
```

**④ 新增 `mixin/VehiclePartHideRenderBonesMixin.java`**（client / common 皆可，代码双端安全）
```java
@Mixin(value = VehiclePart.class, remap = false)
public abstract class VehiclePartHideRenderBonesMixin {

    @Unique private List<String> ywzj_rvp$cachedHidden = null;

    @Inject(method = "getExcludedBoneNames", at = @At("RETURN"), cancellable = true, remap = false)
    private void ywzj_rvp$appendHiddenBones(CallbackInfoReturnable<List<String>> cir) {
        VehiclePart self = (VehiclePart) (Object) this;
        PartUnit<?> unit = self.getPartUnit();
        if (unit == null || !(unit.getData() instanceof PartUnitDataExt ext)) {
            return;
        }
        List<String> extra = ext.ywzj_rvp$getHideRenderBones();
        if (extra.isEmpty()) {
            return;
        }
        if (ywzj_rvp$cachedHidden == null) {                 // 只在配置变化时重建（渲染热路径免分配）
            List<String> merged = new ArrayList<>(cir.getReturnValue());
            for (String b : extra) {
                if (b != null && !b.isBlank() && !merged.contains(b)) merged.add(b);
            }
            ywzj_rvp$cachedHidden = List.copyOf(merged);
        }
        cir.setReturnValue(ywzj_rvp$cachedHidden);
    }
}
```
并在 `ywzj_rvp.mixins.json` 注册（建议放 `client` 数组；该类只引用 common 类型，放 `mixins` 也安全）。

### 为什么选这个注入点

- 复刻本体的隐藏/恢复语义（`VehiclePartRender` 自己在 render 前后管 `visible`），**不碰渲染顺序、不新增渲染 pass**；
- 与「幽灵部件」相比是**显式配置**，可 grep、可日志、可单点关掉；
- 落点在被改动的类（`VehiclePart`）上，改动面最小。

### 落地后建议顺手清掉幽灵骨（可选）

`vt4/t90m/ztz99b`：
- 结构模型删掉 `{ "name": "turret_muzzle_flash", "parent": "turret" }`（骨数 37/37/39 → 36/36/38）；
- 车辆 JSON 删掉 `muzzle_flash` 幽灵部件；
- **保留 `turret` 上的 `"render_bone": "$weapon0"`**（飞头本体）。
备份：`*.structure.json.bak_20261007` 已在。

## 三、「飞头陷地」排查

### 3.1 残件碰撞盒是怎么来的（本体，无 RVP 参与）

```java
// VehiclePart.initializePart
VehicleCubeOBB sourceCube = partUnit.getLargestCube();      // PartUnit:192-203 取 partCubeOBBs 体积最大者
this.bottomOffset = sourceCube.offset().subtract(0, sourceCube.height / 2, 0);
this.vehicleCubeOBBs = List.of(<由 sourceCube 长宽高合成的单 cube>);
this.mainCubeOBB = 那个 cube;
this.curbWeight = 1000; physicsInfo.mass = 1000; physicsInfo.friction = 2000f;
physicsInfo.center = new Vec3(0, halfH, 0);
```
`PhysicsEngine.tick` 用 `physicsCube()` = `getMainCubeOBB()`，以它的表面采样点（`cubePoints()`）与方块求交（`collectContacts`）；渲染端 `VehiclePartRender` 用 `pPoseStack.translate(-bottomOffset)` 反推，使**最大 cube 的底面 = 实体原点 = 碰撞盒底面**。

三车实测该盒：

| 车 | `getLargestCube()` | 盒尺寸（格） |
| --- | --- | --- |
| T-90M | `turret` 的 63.7×13.275×31.825（BB）cube | **3.98 × 0.83 × 1.99** |
| VT4 / ZTZ99B | `turret` 的主 cube | 同量级 |

⇒ 尺寸与视觉一致、盒底与视觉底对齐，**静态分析下它应该正常落地**。

### 3.2 找到的一处 RVP 侧旁路缺陷（建议修，但与"陷地"未必直接相关）

`RVP_PhysicsOnlyCollisionEventHandler.rebuildIfPending()` 的就绪门槛是 `centerOffset != null`：

```java
if (vehicle.centerOffset == null) return;      // initData 完成标志
```

而 `VehiclePart.initializePart` 把 `centerOffset = Vec3.ZERO`（`:62`）——**非 null** ⇒ **每个脱落残件都会跑一遍 `rebuildPhysicsOnlyCubes()`**，也就是"残件被当成整车处理"：

1. `buildPhysicsOnlyCubes(part)` 用**源载具**的 `structure_model` + `physics_only_bone` 去结构模型里取骨；
2. 本包**只有 t90m** 配了 `physics_info.physics_only_bone = "virtual"`，而 t90m 结构模型里**确实有一根叫 `virtual` 的骨**（4×1.5625×7.75 的悬挂车体代理盒）；
3. 于是 `stripPhysicsOnlyBodyCubes(part, cubes)` 会试图从**残件**的 `vehicleCubeOBBs` 里剔 cube。

> ⚠️ 按 `sameCubeTemplate`（要求 x/y/z/w/h/d 全等 + group 链逐级 pivot/rotation 相同）我算下来**不该命中**（尺寸差 0.009 > EPSILON 1e-6），所以它大概不是本次直接原因；但这条路径本身是缺陷，建议加早退：
> ```java
> if (vehicle.centerOffset == null || vehicle instanceof VehiclePart) return;
> ```

另：残件**不跑 `initData()`**（`VehiclePart.initData()` 被覆写成只置 `dataInitialized = true`）⇒ `physicsInfo` 是 `new PhysicsInfo()` 的默认值（`density = 8`、`liquidDamping = 0.1`、`canDestroyBlock = false`；`mass/friction/center` 已被覆盖）。

### 3.3 需要的一个判据（决定怎么修）

进游戏打爆一台，按 **F3+B** 看残件：

| 现象 | 指向 |
| --- | --- |
| 绿框贴地、模型却埋进地里 | 渲染与碰撞盒错位（`bottomOffset` / `-bottomOffset` 那一步），改渲染端偏移 |
| 绿框也穿到地下、持续下落不停 | 接触检测失效（`cubePoints` 为空 / OBB 中心无效），从 `collectContacts` 侧修 |
| 只有 T-90M 会穿、VT4/99B 正常 | 就是 3.2 那条 physics-only 旁路，加早退即可 |
| 停在"半埋"不动 | 落地判定的容差/倾斜补正问题（`rotAndFallByGravity` 的 `angleDepth/angleWidth` 补正） |

### 3.4 备选"稳"法（若上面都查不出）

给残件在 `initializePart` 阶段**用部件自身的 `partCubeOBBs` 包围盒**（而非单个最大 cube）重建碰撞盒，并在 RVP 侧用一个开关字段（如 `rvp_part_physics_padding`）兜底把盒向下/向上扩一点，避免"薄盒 + 高枢轴"导致的视觉错位。此方案改动更大，先看 3.3 的判据再定。

## 五、「红框（武器）/黄框（部件）碰撞箱差异」假设的核查结论（2026-10-07 追加）

**假设**：本体炮塔是红色武器碰撞箱、RVP 坦克炮塔主体是黄色部件碰撞箱，推测"穿地只针对武器碰撞箱"。

### 结论：**不成立。** 三条硬证据

1. **红/黄只是配色分支，底层数据同一份。**
   `VehicleRender.renderHitbox` 里是
   ```java
   if (partUnit instanceof WeaponUnit)        → 红 (1,0,0)
   else if (partUnit instanceof DecorationUnit) → 品红 (1,0,1)
   else                                        → 黄 (1,1,0)
   ```
   而 `WeaponUnit` **没有覆写** `getOBBs()` / `getPartCubeOBBs()`；`PartUnit.getOBBs()`（`:188-190`）= `partCubeOBBs.stream().map(VehicleCubeOBB::obb)` ⇒ **三分支读的都是同一份 `partCubeOBBs`**。

2. **RVP 坦克的炮塔线框本来就该是红色。**
   扫了 RVP 全部 **14 台**坦克的 `turret` 部件，**全部** `"type": "ywzj_vehicle:weapon"`（`abramsx/bmpt72/bukm3/cssa5/lav25/lavad/m1a2sep/m1agds/ps1sm/t84bm/t90m/vt4/zbl08a/ztz100/ztz99b`）⇒ 炮塔 = `WeaponUnit` ⇒ 红框。
   看到的大量黄框来自**爆反 / 顶盖 / 烟幕 / 车轮**等 `generic` 部件（RVP 坦克特有、数量多）；再加上 RVP 自己的 `VehicleRenderRenderHitboxMixin` 会把"失效模块骨"的 cube 画成**近黑色** ⇒ 叠加后观感很花，容易误判成"主体是黄色"。

3. **残件物理链路里没有任何按部件类型分支的代码。**
   - 残件碰撞盒只在 `VehiclePart.initializePart:65-88` **一处**产出，来源 `partUnit.getLargestCube()`；
   - `PartUnit.getLargestCube():192-203`、`PartUnit.detach():497-527`、`PhysicsEngine` 全都只看 `partCubeOBBs`，**不看 `WeaponUnit`**；
   - 已 grep 全部调用点：`instanceof WeaponUnit`（本体 20 处，全在 GUI / 事件 / 渲染）、`getPartCubeOBBs()`、`getLargestCube()`。

**顺带纠正一个观察口径**：残件上**只会出现蓝框（`mainCubeOBB`）和绿框（`vehicleCubeOBBs`）**，红/黄框不可能出现在飞出去的炮塔上——因为 `VehiclePartRender:33` 调的 `VehicleRender.renderHitbox(part, …)` 里 `part.getPartUnits()` 是空的。**若在残件上真能看到红/黄框，请截图**，那说明还有一条没找到的路径。

### 记录一个真实（但不改变结论）的口径差异

| | `partCubeOBBs` 的填充 |
| --- | --- |
| `WeaponUnitData.initStructureModel` | `yTurnGroup.cubeOBBs`（`turret` 骨）+ `xTurnGroup.cubeOBBs`（`turret_barrel` 骨）⇒ **含炮管骨** |
| `PartUnitData.initStructureModel` | `structureGroup.cubeOBBs` ⇒ **只有自己那根骨** |

⇒ 只有"武器站"的 OBB 集合天然含炮管。但 VT4 / T-90M / ZTZ99B 三车的 `getLargestCube()` 都仍取到**炮塔体 cube**（体积最大），所以残件盒没有变化。

## 六、代码层兼容方案（零新增 Mixin，全部走 public API）

**有利条件（已逐项核过可见性）**：
- `AbstractVehicle.physicsEngine` **public**、`curbWeight` / `defenseStats` **public**；
- `mainCubeOBB` 是 `protected`，但**有 public getter** `getMainCubeOBB()`；
- `VehicleCubeOBB` 的 `x/y/z/width/height/depth` **public**，且有 **public `rebuild()`**（重建 obb + 采样点）、`offset()` public；
⇒ **可以在不新增 accessor / 不新增 Mixin 的前提下原地改残件物理盒。**

### 兼容①（推荐）：残件盒校正为「部件全部 cube 的并集包围盒」

在 `EntityJoinLevelEvent`（**复用 RVP 现有 `RVP_PhysicsOnlyCollisionEventHandler`**，加一个 `instanceof VehiclePart` 分支）里：

1. `var cubes = part.getPartUnit().getPartCubeOBBs();`
2. 用每个 cube 的 `offset()` 与 `width/height/depth` 在载具本地系求并集盒 `(minX..maxX, minY..maxY, minZ..maxZ)`；
3. 换成"以底面中心为原点"的口径写回残件那个 cube（`part.getMainCubeOBB()`）：
   `x = -W/2; y = 0; z = -D/2; width = W; height = H; depth = D;`
4. 调 `cube.rebuild()`（重建 extents / `cubePoints` / `offset`）。

> ⚠️ 并集包含炮管 ⇒ 盒的 Z 会长到 ~8 格。`bottomOffset`（渲染用）不用动（炮塔体 cube 底面通常就是并集底面，视觉对齐不变），但**上线前必须实测**。
> 若不想改变盒形状，可只做变体：**只把最薄的那一维补到 ≥ 1 格**。

### 兼容②：残件灌本体的 `physicsInfo`

残件目前不跑 `initData()`，`physicsInfo` 是 `new PhysicsInfo()` 默认值（`density=8`、`canDestroyBlock=false`、`liquidDamping=0.1`）。
在同一个分支里：
```java
CommonAssetsManager.vehicleDataManager().getVehicleData(part.getVehicleId())
        .ifPresent(data -> part.physicsEngine.physicsInfo = data.getPhysicsInfo().copy());
part.curbWeight = part.physicsEngine.physicsInfo.mass;   // 若不想沿用 1000
```
（`physicsEngine` / `physicsInfo` / `curbWeight` 均 public ⇒ 无需 accessor。）

### 兼容③（兜底，防穿透）：落地钳制

每 tick 对残件做一次"脚下方块顶面"检查，若 `position.y` 低于该顶面则夹住并把 `deltaMovement.y` 清零。
放 RVP 一个新事件处理器（纯 Java，`ServerTickEvent` + `ClientTickEvent`，与 `RVP_PhysicsOnlyCollisionEventHandler` 同款写法）。

### 兼容④（最小改动）

仅对"最薄维度 < 1 格"的残件盒把该维扩到 1 格 —— 专治"薄盒单 tick 穿透"这一类。

**建议落地顺序**：② + ③（低风险、纯增益）→ ①/④（等确认"框贴地但视觉埋"之后再上）。

## 七、✅ 根因定案：**不是穿地，是"血量 -1 → 落地撞击被 discard"**（2026-10-07 实测确认）

**用户实测**：本体车残骸 **1000/1000 血**、正常落地；RVP 车残骸 **-1 血**、**一碰到地板直接消失**。

### 完整因果链（逐行）

| # | 位置 | 事实 |

- **RVP 所有"可脱离部件"都一样**：ZTZ99B / VT4 / T-90M 的炮塔，**以及 `cssa5 / lav25 / lavad / zbl08a` 的悬挂轮**（它们本来就配了 `render_bone`）⇒ 落地即消失。

### 修复方案

#### 方案 A（推荐，零 Mixin、零玩法影响）：残件入世界时补正血量

位置：**复用现有 `event/RVP_PhysicsOnlyCollisionEventHandler`**（`EntityJoinLevelEvent` 已有 `instanceof AbstractVehicle` 分支），加：

```java
if (entity instanceof org.ywzj.vehicle.entity.misc.VehiclePart part && part.getHealth() <= 0f) {
    float h = CommonAssetsManager.vehicleDataManager()
            .getVehicleData(part.getVehicleId())              // 源载具数据
            .map(BaseVehicleData::getMaxHealth)               // vt4 = 1200
            .filter(v -> v > 0f)
            .orElse(1000f);                                   // 兜底同本体
    part.setMaxHealth(h);      // ⚠️ 顺序不能反
    part.setHealth(h);         // ⚠️ setHealth 会 clamp 到 [0, maxHealth]，maxHealth=-1 时会被钳回 -1
}
```

- 全部 public API（`ContainerCraft.setHealth/setMaxHealth/getHealth/getMaxHealth`；`BaseVehicleData.getMaxHealth():337`）⇒ **不需要 accessor / 不需要新 Mixin**。
- 只作用于 `VehiclePart`，**完全不碰正常战斗的伤害分配**。
- 建议顺带一并做 §六 的**兼容②**（灌源载具 `physicsInfo`），反正同一个分支。

#### 方案 B（纯数据，最"正"但有副作用，需实测）

给 RVP 载具中**会脱离的部件**补 `"max_health": 1000`（同本体）。
- ✅ 残骸有真实血量、语义与本体一致、落地扣血不消失。
- ⚠️ **副作用**：`PartUnit.isDefensive()` = `health > 0` ⇒ 会激活本体 `DamageSystem.hurt:65-72` 的"部件扣血"分支（`hitPartUnit.hurt(...)` 且 `amount = partUnitDamage × damageTransferCoefficient`）⇒ **RVP 车正常战斗的伤害分配可能被改变**（RVP 自己走 `RVP_BoneCumulativeDamageTable` / `RVP_DamageApplier` / hitbox factor）。
- ⇒ 若要走这条：**先只给 1 台车 1 个部件加**，打几炮比对伤害数字/装甲表现，确认无变化再铺开。

#### 方案 C（可选增强，1 个 Mixin）

残件对"撞击伤害"免伤：`@Mixin(AbstractVehicle.class)` → `@Inject(method="hurt", at=HEAD, cancellable=true)`，若 `this instanceof VehiclePart` 且伤害源是 `vehicleCollision` ⇒ `ci.cancel()` + `setReturnValue(false)`。
**必须配方案 A**（否则被子弹打一下照样 `discard`）。

**建议**：**A（+ §六 兼容②）** → 想更彻底再叠 C；B 作为"以后统一补数据"的长期项，先验证副作用。

> **照抄本体口径只补 `turret` 等主要部件 = 完全符合本体实践，不存在"不一致"问题**。

### 8.2 数据侧写的副作用 —— 逐条算过，比想象的小

`DefenseStats`（`vehicle/pojo/DefenseStats.java`）默认值：`damage_threshold = 50`、`impact_multiplier = 0.1`、**`damage_transfer_coefficient = 1.0`**。
本体/RVP 的部件都没有写 `defense_stats` ⇒ 全部走这三个默认值。

命中部件后（`DamageSystem.hurt:65-73`）：
```java
if (hitPartUnit != null && hitPartUnit.isDefensive() && !hitPartUnit.isDetached()) {
    float partUnitDamage = amount;
    if (partUnitDamage < 0.1) partUnitDamage = 0;
    else if (amount < hitPartUnit.getDefenseStats().damageThreshold) partUnitDamage = 0.1f;   // ← 默认 50
    hitPartUnit.hurt(damageSource, partUnitDamage);
    amount = partUnitDamage * hitPartUnit.getDefenseStats().damageTransferCoefficient;         // ← 默认 1.0
}
```

| 后果 | 说明 |
| --- | --- |
| ① 车体伤害 | `amount = partUnitDamage × **1.0** = amount` ⇒ **完全不变**（`amount ≥ threshold` 时） |
| ② 小伤害被钳 | `amount < damage_threshold(默认 50)` ⇒ 部件只吃 0.1 ⇒ **车体也只吃 0.1**（`amount` 被整体改写）。⚠️ 这就是本体"打不穿只吃 0.1"的装甲手感；**RVP 车级特意把 `damage_threshold` 设成 0.1（= 关掉阈值），所以部件级要沿用 0.1 才跟你们现状一致** |
| ③ 部件会被打坏 | 部件血量归零 ⇒ `PartUnit.isDestroyed()` ⇒ `VectorUtil.hitPartUnit:183` **跳过已损毁部件**（子弹可穿透）+ HUD 标红 + 与 `bone_modules` 联动的逻辑 |
| ④ 残件物理 | `VehiclePart.defenseStats = partUnit.getDefenseStats()` ⇒ 残件 `impactMultiplier` 仍是默认 0.1，**落地撞击伤害不变** |

### 8.3 推荐的三种数据侧写法

```jsonc
// 写法 1：完全照抄本体（残骸有血 + 采用本体那套部件装甲阈值手感）
{ "id": "turret", "max_health": 1000 }

// 写法 2（推荐，最贴合 RVP 现状）—— 两个字段服务对象不同，别混：
//   max_health    → 目标【残骸】：残骸血量唯一来源（不写 ⇒ -1 血 ⇒ 一落地就被 discard）
//   defense_stats → 目标【普通载具】：抵消 max_health 打开"部件分支"带来的手感变化；**与残骸无关**
//                   （残骸 partUnits 为空 ⇒ hitPartUnit 恒 null ⇒ 残骸永远读不到它）
{ "id": "turret", "max_health": 1000,
  "defense_stats": { "damage_threshold": 0.1 } }        // 与 RVP 车级 damage_threshold:0.1 对齐

// 写法 3：连"部件会被打坏"都不想要 ⇒ 给个大血量（数值回避，不推荐；该诉求用代码侧更干净）
{ "id": "turret", "max_health": 100000,
  "defense_stats": { "damage_threshold": 0.1 } }
```

**建议**：数据侧就走 **写法 2**，并且**顺手给悬挂轮也补一个**（本体漏的），这样 `cssa5/lav25/lavad/zbl08a` 的轮子残骸也不会落地蒸发。
如果只想要"最小改动 + 零玩法影响"，仍用 §七 的**方案 A（代码侧只给 `VehiclePart` 补血）**。

### 8.4 补充：这个 50 阈值到底在哪些伤害通道上生效（逐条核过 `getDirectEntity()`）

`DamageSystem.hurt` 里 `hitPartUnit` **只在下面这一个分支被赋值**：
```java
if (damageSource.getDirectEntity() instanceof Projectile projectile) {
    Vec3 closestHitPos = VectorUtil.closestHitObbPosition(vehicle, position, position.add(projectile.getDeltaMovement()));
    if (closestHitPos != null) {
        hitPos = closestHitPos;
        hitPartUnit = VectorUtil.hitPartUnit(vehicle, position, ...);
    }
}
```
⇒ **只有"直接实体是 `Projectile`"的伤害才会解析出命中部件**，也就只有这些通道会进"部件扣血 + 50 阈值"分支：

| 伤害通道 | DamageSource 构造（RVP/本体） | `getDirectEntity()` | 会不会进部件分支（开启 `max_health` 后） |
| --- | --- | --- | --- |
| **RVP 弹体直击** | `Sources.bullet(access, **this(子弹)**, owner, loc)`（`RVP_BaseBullet:3670`） | **子弹（Projectile）** | ✅ **会** |
| **RVP 近炸** | `Sources.explosion(access, **this(子弹)**, getOwner(), pos)`（`RVP_BaseBullet:4490`） | **子弹（Projectile）** | ✅ **会** |
| **撞击 / 落地摔** | `Sources.vehicleCollision(access, **载具**, driver, …)`（`DamageSystem:142`） | **载具**（非 Projectile） | ❌ 不会 |
| **AOE 爆炸（VehicleExplosion）** | `Sources.explosion(access, **getOwner()**, vehicle, pos)`（`VehicleExplosion:93`） | **发射者**（非 Projectile） | ❌ 不会 |

**⇒ 两个结论**：
1. **"落地摔"这条路从头到尾不吃 50 阈值**（`hitPartUnit` 恒为 null，伤害直接打在残件自己的 `health` 上）—— 这也正是"只给残件补血"就能修掉它、且**不会带来任何阈值手感**的原因（§七 方案 A）。
2. 但只要部件有了正血量，**RVP 的直击与近炸两条主战通道就会开始吃 50 阈值**。要"只让残骸有血、不动战斗手感"，就必须显式压平：`"defense_stats": { "damage_threshold": 0.1 }`。

### 8.5 ★ 作用对象辨析：部件级 `damage_threshold` **只作用于"普通载具"，对残骸无效**

关键在 `VectorUtil.hitPartUnit`：它**只从 `vehicle.getPartUnits()` 里解析命中部件**（`util/VectorUtil.java:165-195`）：
```java
List<PartUnit<?>> partUnits = new ArrayList<>(vehicle.getPartUnits());
for (PartUnit<?> partUnit : partUnits) { ... hitOBB(partUnit.getOBBs(), start, end) ... }
return closestPartUnit;      // 没有部件 → null
```
而 **`VehiclePart.initData()` 被覆写成空**（`VehiclePart:136-138`），所以残骸的 `partUnits` **永远是空列表**
（`partUnits` 只在 `AbstractVehicle.initData(BaseVehicleData):454` 里被填充，残骸走不到那一步）。

⇒ **在残骸上 `hitPartUnit` 恒为 `null` ⇒ "部件扣血 + 阈值"分支永远不进入**；
⇒ **在普通载具上** partUnits 一大堆，弹体命中炮塔/ERA/机枪等部件就会解析出来 ⇒ 只要该部件 `isDefensive()`（= 有正血量）就进分支。

| 部件 `defense_stats` 字段 | 对**普通载具** | 对**残骸** |
| --- | --- | --- |
| `damage_threshold`（默认 50） | ✅ 生效（`DamageSystem.hurt:65-73`） | ❌ **无效**（`hitPartUnit` 恒 null） |
| `damage_transfer_coefficient`（默认 1.0） | ✅ 生效（同上，改写 `amount`） | ❌ **无效** |
| `impact_multiplier`（默认 0.1） | ✅ 生效（车体撞击伤害） | ✅ **也生效** —— `VehiclePart.initializePart:89` 有 `this.defenseStats = partUnit.getDefenseStats()`，而 `DamageSystem.impactHurt` 读的正是 `vehicle.defenseStats.impactMultiplier` |

**⇒ 结论（很重要，会影响方案选择）**：
- 写部件 `max_health` 的**主要影响面是"正常载具的战斗手感"**（弹体打部件、`amount < 50` ⇒ 车体只吃 0.1），**残骸本身只是顺带被修好**（残骸的生死只看 `health`，不吃阈值）。
- 因此若走数据侧又要"零战斗影响"：`"defense_stats": { "damage_threshold": 0.1 }` 是**必需**的（且不要动 `impact_multiplier`，否则会改残骸落地撞击伤害）。
- **⇒ `defense_stats.damage_threshold` 不是"给残骸配的"**：它与 `max_health` 写在**同一份 `parts[]` 条目**里，但生效对象**只有普通载具**，残骸永远读不到它。写它的唯一理由是"保护整车手感" —— 属于 `max_health` 的**副作用税**；**走代码侧（§七 方案 A）则完全不需要这个字段**。
- 若只想改残骸、完全不碰正常战斗 ⇒ 用 §七 方案 A（代码侧只给 `VehiclePart` 补血，天然不经过这条分支）。

### 8.6 追问：既然部件阈值只管普通载具，那为什么还要配？会被 RVP 的 `armor_min_damage` 覆盖吗？

#### ① 为什么必须配 `max_health`
因为**残骸的血量唯一来源就是部件数据**：`VehiclePartSpawner:20` → `PartUnit.detach()` →
`VehiclePart.initPart()` → `initializePart(partUnit, copyHealth=true)`：
```java
this.setMaxHealth(partUnit.getMaxHealth());
this.setHealth(partUnit.getHealth());
```
→ `setDestroyed()` → `setHealth(getMaxHealth())`。**部件没写 `max_health` ⇒ 残骸 = -1 血 ⇒ 落地被 discard。**
所以走数据侧修法**没有别的入口**，`max_health` 是必须的；`defense_stats` 是"用来抵消副作用的"。

#### ② 会被 `armor_min_damage` 覆盖吗 —— **不会，而且顺序是反的**

| 层 | 位置 | 读哪一份数据 |
| --- | --- | --- |
| RVP 装甲层 | `RVP_VehicleHurtScalingHandler.applyArmor()`，挂在 `VehicleAttackEvent`（`AbstractVehicle:624`），**在 `DamageSystem.hurt` 之前** | 载具 JSON **顶层** `armor_min_damage` / `armor_max_damage` |
| 本体部件阈值 | `DamageSystem.hurt:65-73`，**在事件之后** | `parts[].defense_stats.damage_threshold` |

RVP 的"互斥"只针对**车级**那一个（`RVP_VehicleHurtScalingHandler:366-380` 注释 + `hurtWithShieldedThreshold`）：
```java
// 装甲生效 → 屏蔽本体 threshold，避免重放跨分支把伤害钳成 0.1
if (RVP_VehicleHitboxFactorManager.INSTANCE.isArmorConfigured(self)) hurtWithShieldedThreshold(self, source, adjustedAmount);
else self.hurt(source, adjustedAmount);
...
private static void hurtWithShieldedThreshold(AbstractVehicle self, ...) {
    DefenseStats original = self.defenseStats;         // ← 只换**载具级**的引用
    DefenseStats shielded = new DefenseStats();
    shielded.damageThreshold = DAMAGE_FLOOR;           // 0.1
    self.defenseStats = shielded;
    try { self.hurt(source, amount); } finally { self.defenseStats = original; }
}
```
而该处注释还写明：**"`damage_transfer_coefficient` 目前仅部件级结算读取，载具级副本一并拷贝以防本体后续扩展读取"**
⇒ **RVP 只动载具级 `DefenseStats`，完全不碰部件级** ⇒ 部件级阈值不会被 RVP 屏蔽/覆盖。

**⇒ 反过来的风险才要命**：部件分支在 RVP 之后执行，是**最后一道**，
所以**部件阈值会把 RVP 装甲层算出来的 `desiredFinal` 再钳一次**（`amount < 50` ⇒ 变成 0.1）——
也就是"部件阈值把 RVP 的 `armor_min_damage`/`armor_max_damage` 结果吃掉"，而不是被它覆盖。
⇒ 所以部件上**必须**显式写 `"defense_stats": { "damage_threshold": 0.1 }`（= 放弃钳制），或者干脆走代码侧、完全不碰部件数据。

#### ③ 还有一个必须实测的点
RVP 的伤害补偿数学是 `damageSystemScale = predicted / amount`、`adjustedAmount = desiredFinal / damageSystemScale`
（`RVP_VehicleHurtScalingHandler:216-225`）—— 这套反推是在**"部件从不吃伤害"**的前提下标定的。
部件一旦有血，命中部件时 `amount` 会被部件分支改写 ⇒ 这个比值会失真 ⇒ **数据侧方案上线前必须实测伤害数值**（这正是推荐代码侧方案的另一条理由：残骸 `partUnits` 为空 ⇒ 根本不进部件分支 ⇒ 零干扰）。
