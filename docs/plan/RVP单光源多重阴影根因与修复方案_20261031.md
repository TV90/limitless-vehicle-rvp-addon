# RVP 单光源多重阴影：根因与修复方案

日期：2026-10-31。范围：explosion（爆炸）、muzzle（炮口）、engine（发动机）的环境表面照明，以及复用同类遮挡算法的烟雾受光。

**当前实现见第 8 节。** 用户反馈第 7 节的首轮修复仍有静止重影，且方块、实体都会出现，因此首轮不能视为实机修复成功。第 1～7 节保留调查及实施经过；第二轮正式投影改为真实三维碰撞几何，原始资源完整保留。

## 1. 结论

三类光源共用的 `visibility`（光路可见性）函数存在两个叠加缺陷：

1. **光路只检查 8 个孤立位置。** 两点之间没有检查，细遮挡物可能被跳过。随着受光像素变化，这 8 个位置会分别扫过同一遮挡物，于是出现多条分离的暗带，相当于把遮挡物轮廓盖了数次章。
2. **命中判断把可见表面后方无限延伸为实心。** 只要采样点比相机看见的遮挡表面更远，就判定被挡，没有限制两者相隔多远。因此，有些暗带本身就是错误遮挡；单纯加采样数，会把暗带连成一大片错误暗区。

这两个问题可以在**一盏光、一根遮挡条、无粒子、无光晕、无喷焰**的情况下独立复现，三类真实参数预设得到完全相同的阴影形状。它们足以解释“三类光源都出现重复阴影”，不需要以重复注册光源为前提。

用户尚未单独隔离现场光源，因此不能据此断言现场所有阴影都只有这个原因。多个真实光源从不同方向照射时，同一物体出现多个投影仍是正常现象；验收应分别覆盖单灯和多灯。

重建使用的观察空间是“以相机为基准的三维坐标”，前方 Z 为负。例如 `blocker.z=-4`、`point.z=-9` 会被现有判断视作遮挡，哪怕真实光路线段与物体根本没有相交。

采样关系可写为：`Pᵢ = (1-tᵢ) × (P + 0.08N) + tᵢ × L`，`tᵢ=i/9`。其中 P 是受光表面位置，N 是表面朝外方向，L 是光源位置。每个固定比例都会把同一遮挡物映射到不同的一批受光像素；相邻比例没有覆盖到的位置重新变亮，构成重复暗带。


诊断读取当前生产 `.vsh` / `.fsh` 文件，在隐藏 OpenGL（显卡绘图接口）上下文中编译运行并回读真实像素，不启动游戏。对照算法只替换内存字符串中的 `visibility` 函数，磁盘资源始终只读。

本轮显卡：NVIDIA GeForce RTX 4070 Laptop GPU。记录：`build/screen-light-shadow-diagnostic/20261031_032252_063/result.txt`。

控制条件：

- 画面 512×64；受光平面位于相机前 10 格。
- 唯一遮挡条位于前方 4 格，投影覆盖第 250～253 列，贯穿画面高度。
- 唯一光源位于观察空间 `(1.5,0,-2)`，光心在屏幕内，`LightCount=1`。
- 分别使用 `RVP_LightParameters.explosion(4)`、`muzzle(125,false)`、`engine()`；保留各自半径、颜色、强度、表面受光权重。
- 不经过光源管理器、事件注册、Bloom（亮部向周围扩散的光晕）、喷焰或粒子路径；读取表面光贡献。
- 有遮挡与无遮挡各画一次，按亮度比识别暗区；排除遮挡条本体及邻接法线变化区。
- 几何参考直接计算受光点到灯的线段与遮挡条平面是否相交，并沿用生产的 0.08 格法线偏移；不把该偏移造成的位置变化混入本次比较。

| 算法 | 阴影像素列区间 | 与几何参考不一致的像素数 |
| --- | --- | ---: |
| 直接几何求交参考 | `133..138`，一条 | 0 |
| 当前生产：8 点、无界深度 | `171..175`、`201..205`、`218..222`、`230..234`、`239..242`、`245..247`，六条 | 33 |

生产 8 点结果的 33 个错误包含 27 个不应变暗的像素，以及实际阴影位置漏掉的 6 个像素。因此不能以“多条变成一条”作为唯一验收条件，还必须检查阴影位置和宽度。

有限厚度对照采用 0.001 格深度容差和 0.01 格厚度，仅用于此平面场景证明原因；**这两个数不能直接当作所有车辆、远景、薄物体的生产参数**。对照的循环上限为 2048，同样仅用于诊断，不应原样上线。

## 4. 推荐修复

### 4.1 两个缺陷一起修

将固体表面与烟雾的光路遮挡统一改为“覆盖投影像素的线段检查＋有限深度范围判断”：

1. 将受光点到光源的线段投影到屏幕，先处理近裁剪面和画面边界，避免除以接近零的数。受光点的法线偏移与遮挡容差分开定义，不能用增大偏移来掩盖断影。
2. 使用 DDA（逐格遍历算法，即按顺序访问线段穿过的屏幕像素），不再只检查固定比例的 8 个位置。细遮挡条即使落在旧的两采样点之间，也必须有机会被检查。
3. 每个被访问像素对应一小段光路。使用投影后的 `Q=位置/clip.w` 和 `k=1/clip.w` 插值，再用 `Q/k` 恢复光路位置；这是透视正确的插值，不能直接把屏幕比例当作三维线段比例。
4. 比较该小段光路的最近/最远深度与遮挡表面的有限深度范围。只有范围重叠才算命中；“比表面更远”本身不再足以判遮挡。
5. 单层深度没有记录物体背面，厚度只能是有明确上下限的近似值。应根据深度精度、像素覆盖的世界尺寸和局部连续表面变化确定，并用薄杆、厚墙、斜面分别校准；不能随相机距离无限增长，也不能跨深度断层借用背景厚度。
6. 沿用 `scenePosition` 对近景与 Distant Horizons（DH，远景地形）的独立重建，再统一到相机坐标。继续区分天空、手持物遮罩、普通表面；不比较两套投影的原始 0～1 深度数值。
7. 固体表面传入法线偏移后的起点；烟雾传入烟面片自己的位置。两者调用同一段遮挡核心，避免后续只修其中一套。

### 4.2 性能也是上线条件

当前最多八灯。若把每像素 8 次查询直接换成数百次查询，1080p/更高分辨率可能出现明显卡顿。本轮的 2048 步原型只证明方向，尚未进行生产性能验收。

建议分两步实现：

1. 先接入完整像素遍历，建立可对照的正确性版本和显卡计时，统计每盏光的屏幕光路长度、实际查询次数与提前命中比例。保留半径外、背向光表面的提前退出。
2. 若在目标画质下超出约定耗时，加入每帧共用的分层深度范围。它把一片像素的最近/最远表面距离逐层汇总，光路深度与整片范围不相交时跳过整片，有可能相交时才向细层检查。汇总必须覆盖全部子像素，不能靠稀疏抽样，否则细遮挡会再次丢失。近景/DH 先完成坐标统一再汇总，天空和手持物须保留有效性标记。

实现中必须有硬查询预算和“查询完整/因离屏中止/因预算耗尽”状态。**预算耗尽不等于命中，也不等于完整无遮挡**，不得把两者悄悄混用。建议首版对未完成光路保留未加阴影的表面光贡献，并累计诊断计数；这会允许局部漏光，因此标准验收场景必须做到预算中止为零。离屏沿用现有保守抑制策略，但单独标记，不能伪装成检测到真实遮挡。

性能阈值在目标机器和分辨率上确定，测量 1 灯、8 灯及 DH/光影组合的中位值与高耗时帧；此次没有把小诊断画面的耗时冒充整机游戏性能。若需要分层深度，应在资源创建前补齐并确认其具体资源清单。

### 4.3 不适合作为修复的方法

- 只把 8 改成 32/64/128：没有消除无界深度错误，且增加成本；64 点对照已经反证。
- 只模糊、随机扰动采样位置或增加时间混合：可能把条纹变成模糊暗区、噪点或拖影，没有纠正错误光路。
- 合并或删除三类光、限制只能有一盏投影灯：本例一灯即可复现，还会改变正常多光源效果。
- 只调亮度、照亮半径或光晕半径：无法修复错误遮挡；应继续保持照亮与光晕两套控制。
- 把相机到灯的方块碰撞射线当作完整修复：它不检查当前受光表面到灯的路径，也不包含同样的实体/DH 几何。

## 6. 验收与实施顺序

1. **冻结对照**：记录当前生产资源哈希及单灯诊断输出，隔离当前工作区已经存在的其它修改；不要重置或覆盖它们。
2. **确认新资源清单**：按上节的另名方案确认后再创建资源。先实施表面与烟雾共同核心，再切换 Java 注册入口。
3. **几何正确性**：爆炸、炮口、发动机各单独一灯；每种都测试画面左/右两侧、1/2/4 像素细条、不同深度、光源距离、视野和奇数窗口尺寸。与直接几何求交逐像素比较，同时检查漏影和错误暗区，不能只数阴影条数。
4. **正常多灯**：两盏不同位置的光应保留各自正确投影；八灯场景无残留槽位、无跨帧旧影。不能为了消除重复暗带而抹掉真实多光源投影。
5. **材质与边界**：厚墙、薄杆、斜面、载具、玩家、接触面、天空、手持物、光心离屏、近裁剪面穿越；移动光/相机时没有周期性断影，原有方块相机遮挡和喷焰遮挡规则继续单独验证。
6. **渲染组合**：原版、DH、光影、DH＋光影；DH 正/反深度、不同分辨率/投影；Bloom 开/关均检查，避免把光晕外扩误当成表面漏光。烟雾接受正确光照，但烟雾本身仍不投射实体式阴影。
7. **性能与输入生命周期**：1/8 灯计时、预算中止计数；暂停、切世界、窗口缩放和资源重载。所有新显存目标跟随现有状态恢复及释放规则，不复用旧深度。

## 8. 2026-10-31 第二轮：使用真实三维遮挡

### 8.1 首轮不足

用户补充“光源、遮挡物和相机静止也有多道阴影”“方块和实体都会”。因此不能把问题归为移动残影，或只修一类方块。首轮虽然消除了平面细条的八次重复采样，但仍用相机只看得见的一层深度猜测物体厚度。它缺少背面、侧面和离屏几何；平面条纹测试通过，不能证明完整立体物体的投影正确。


| 可核实的行为 | 本轮采用的原则 |
| --- | --- |
| 基础表面光恢复受光位置和法线，用 `max` 合并能量；没有沿相机深度做八步投影 | 表面在哪里与光路被谁挡住必须分开处理；保留原有的多灯贡献方式 |
| 以真实方块信息构建 32³ 的三维光场 | 遮挡依据来自世界几何，不再重复使用相机正面轮廓 |
| 高级阴影使用独立数据及外部光影桥接 | 独立管理遮挡数据，再供共同材质读取；参考包没有提供外部光影内部的完整阴影程序，不能宣称逐行移植 |

本轮实现使用 RVP 现有 Forge 渲染事件与本体碰撞查询，不新增 Mixin。

### 8.2 当前实际运行路径

| 代码位置与方法 | 当前行为 |
| --- | --- |
| `RVP_LightGeometryPass.prepare`、`fillCells`、`section` | 每盏有效环境光周围缓存 64³ 格（各方向约 32 格）；读取客户端已加载区块的真实方块碰撞形状，不强制加载区块。相同逻辑刻、相同区段仅扫描一次 |
| `RVP_LightGeometryPass.shape`、`putShape` | 保存半砖、楼梯等形状的多个小盒，而不是把它们填成完整方块；静态形状去重，动态形状按位置读取 |
| `RVP_LightGeometryPass.collectBodies`、`addBody` | 普通实体使用插值后的碰撞盒；载具使用本体现有的可旋转结构碰撞盒，每车最多取 16 个较大的盒，所有实体合计最多 48 个；未修改结构模型 |
| `rvp_light_visibility.glsl`，`rvpTraceGeometry` | 检查受光位置到光心的完整三维线段。方块按逐格遍历检查真实盒，实体直接与旋转盒求交；同一个体积不再被当成几份相机轮廓 |
| 同文件，`rvpLightPathVisibility` | 正式模式 1 使用三维几何；模式 2 表示数据不可用，保留受光。模式 0 只供历史屏幕深度回归，正式绘制不回退到它 |
| `RVP_ScreenLightPass.capture`、`render` | 移除“相机到光心被挡就删掉整盏环境光”的全局过滤；对每个受光面分别检查路径。光晕与发光核心仍按各自可见性规则裁剪 |
| `RVP_SmokeLightPass` | 烟雾、炮口贴图面片与固体表面绑定同一份几何；烟雾本身仍不写入遮挡数据 |
| `RVP_ScreenFrameResources.State`、`RVP_LightGeometryPass.UnpackState` | 保存/恢复六个纹理与采样器；几何上传另行保存行距、跳过区域、字节序和 PBO（其他渲染流程使用的显卡上传缓冲），防止整数形状编号错行 |
| `RVP_ScreenLightDebugCommands` | 新增 `isolate explosion\|muzzle\|engine\|off`，可只提交一类的一盏环境光，排除正常多灯投影；`status` 显示真实提交列表、几何来源和本帧数据准备耗时 |

方块数据使用一张 2048×1024 的二维整数纹理，八灯按四列两行排列，每灯占 512×512；每灯内部再平铺 64 个 Z 切片。形状表为 4096×2 浮点纹理。这样兼容 Minecraft 原有的二维采样器绑定，不依赖它未支持的数组纹理接口。

首轮分层深度构建器保留用于历史对照，正式渲染已不再构建它。`RVP_LightOcclusionPass` 仍提供显式像素统计命令；正常每帧不把显卡结果读回 CPU。

### 8.3 验证含义与边界

新增 512×512 的完整立体箱体＋地面场景：独立 CPU 参考直接对完整箱体求交；同一箱体再分别编码为八个方块局部形状和一个实体盒，交给真实 `ShaderInstance` 及正式 GLSL 运行。覆盖三类正式预设、光在左右两侧、八个光源槽位、实体旋转及适用灯位掩码。每个三维场景要求只有一个连通阴影，同时限制错误/遗漏像素，不能仅靠数阴影条数验收。

在这个场景，首轮相机深度方案仍遗漏 650～1093 个阴影像素；真实方块形状与几何参考一致，实体盒有 5 个边界像素误差，均只有一块连通阴影。比较排除了紧贴物体轮廓、表面法线本身不确定的一圈像素。这说明三维输入修复了测试覆盖的几何缺口，不等同于已经捕获并验收用户世界的全部现场情况。

历史 144 组平面深度用例保留为对照，另有显卡状态、近景/DH（远景地形）各自正反深度、烟雾受光、发光核心和独立光晕回归。显卡上传专项使用外部 PBO、非默认行距/跳过区域及反字节序，检查整数值与调用方状态都恢复正确。

最终验证记录：

- `build/light-geometry-final-validation-20261031-c.log`：`build`、`screenEffectStateGpuRegression`、`lightingFrameGpuRegression`、`motorFlameDepthGpuRegression`、`explosionSmokeDepthGpuRegression` 全部通过，OpenGL 错误为 0；1060 项单元测试，0 失败/错误/跳过。旋转盒与未旋转等效盒只有 1 个相切边界像素不同，八个槽位逐像素一致。

仍有明确范围：

- 方块投影取每盏灯周围约 32 格的客户端已加载碰撞几何；超过网格或未加载的 DH 远景没有完整遮挡数据，会保留光照，不制造轮廓假影。照亮半径和光晕半径仍保持原值。
