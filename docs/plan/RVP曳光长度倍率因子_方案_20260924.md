# RVP 机枪曳光"长度倍率因子"方案（调查 + 设计）

> 日期：2026-09-24　范围：`ywzj_rvp`（**不需要改本体**）　状态：**只调查与设计，未实施**
> 相关盘点：`docs/plan/机枪曳光参数盘点_20260924.md`

## 〇、结论先行

1. **是的，长度目前完全由速度推导，没有任何独立旋钮**：
   `长度 = min(0.3 × 当前速度, 已飞距离 × 0.8)` —— 想改长度只能动 `projectile_data.velocity`，
   而那会**连带改掉弹道手感与提前量**，所以实际上"改不动"。
2. **可以加倍率因子，且改动很小（1 个数据字段 + 4 处代码）、零兼容性风险**
   （默认 1.0 ⇒ 未配置的武器**行为完全不变**）。
3. **不需要碰本体**：RVP 的 39 把 `rvp:machinegun` 全部走 RVP 自己的渲染器与弹体实体，
   加字段即可生效。⚠️ 只有 **vt4 用的 2 把本体机枪**（`gun_7.62mm` / `gun_14.5mm`）覆盖不到（见 §四·方案 C）。

## 一、现状链路（已逐行核实）

### 1.1 渲染端：长度是当场算出来的

`src/main/java/org/ywzj/rvp/client/render/VehicleProjectileRenderLogic.java:39-58`

```java
static void renderBullet(RVP_BulletEntity bullet, float partialTicks, PoseStack poseStack,
                         MultiBufferSource bufferSource, int packedLight) {
    BedrockModel model = BedrockModelLoader.getModel(InternalAssets.BASIC_BULLET_MODEL);
    poseStack.pushPose();
    float width = Math.min(0.04f * bullet.getCaliber() / 7.62f, 0.2f);   // ← 粗细：caliber 推导
    Vec3 bulletPosition = bullet.getPosition(partialTicks);
    double trailLength = 0.3 * bullet.getDeltaMovement().length();       // ← 长度：速度推导
    double disToEye = bulletPosition.distanceTo(bullet.getStartPos());
    trailLength = Math.min(trailLength, disToEye * 0.8);                 // ← 再被"已飞距离×0.8"钳制
    poseStack.mulPose(Axis.YP.rotationDegrees(Mth.lerp(partialTicks, bullet.yRotO, bullet.getYRot()) - 180.0F));
    poseStack.mulPose(Axis.XP.rotationDegrees(Mth.lerp(partialTicks, bullet.xRotO, bullet.getXRot())));
    poseStack.translate(0, 0, trailLength / 2.0);
    poseStack.scale(width, width, (float) trailLength);                  // ← 长度就是 Z 轴缩放
    if (disToEye > 1.0) { /* energySwirl 材质 + tracer RGB */ }
    poseStack.popPose();
}
```

要点：
- **长度 = Z 轴缩放值**，没有模型自身的长度参与（`BASIC_BULLET_MODEL` 是个单位弹体）。
- `getDeltaMovement().length()` 是**当前**速度 ⇒ 受 `projectile_data.drag`（RVP 里是 `cannonFriction`）影响，
  **飞行中速度衰减 → 尾迹会逐渐变短**。这一点决定了"倍率"的语义（见 §三·决策 3）。
- `disToEye` 实为"离出生点的距离"（客户端 `startPos` 在 `readSpawnData` 里被设为出生位置）。
- `0.8 × 距离` 这条**上限**是防"出膛就有长尾巴"的：出膛瞬间长度≈0，飞远后封顶。

### 1.2 数据端：`effects_data` 是视觉参数的挂靠点

`weapon/data/RVP_EffectsData.java` 里已有 `caliber` / `tracer_r|g|b`（第 121-135 行，getter 在 278-300 行），
因此**新字段加在 `effects_data` 下最自然**：
`effects_data.tracer_length_scale`。

### 1.3 客户端怎么拿到值（**本方案的关键**）

渲染是纯客户端行为，但 JSON 只在服务端解析。现有 `caliber` / `tracer_rgb` 是这么过河的：

`entity/projectile/RVP_BulletEntity.java`
```java

    ...

    this.tracerR  = effects.getTracerR();
    ...
}

// 304-318 行：写 spawn data（随实体生成包下发）
@Override public void writeSpawnData(FriendlyByteBuf buffer) {
    super.writeSpawnData(buffer);
    buffer.writeFloat(cannonFriction);
    ...
    buffer.writeFloat(caliber);
    buffer.writeFloat(tracerR); buffer.writeFloat(tracerG); buffer.writeFloat(tracerB);
    ...
}
// 320-338 行：客户端读取，顺序必须与 write 严格一致
@Override public void readSpawnData(FriendlyByteBuf buffer) {
    super.readSpawnData(buffer);
```

⇒ **新字段必须照抄这套"字段 + initFromWeapon + writeSpawnData/readSpawnData"三件套**，
否则服务端配了、客户端还是 1.0（渲染无变化）。

## 二、方案 A（推荐）：条目级 `effects_data.tracer_length_scale`

### 2.1 语义

```java
float scale = bullet.getTracerLengthScale();                 // 新字段，默认 1.0，clamp [0, 8]
double trailLength = 0.3 * bullet.getDeltaMovement().length() * scale;
trailLength = Math.min(trailLength, disToEye * 0.8);         // 上限不变
```

**为什么把倍率乘在基长上、不动上限**：这样 `scale > 1` 不会让"出膛瞬间"出现长尾巴，
观感仍是"从无到有、随距离增长"，只是**封顶值**变成 `0.3×速度×倍率`。
代价：倍率越大，**越晚才看得出效果**（达到封顶需要飞 `0.375 × 速度 × 倍率` 格）。

### 2.2 改动清单（5 处，逐位置）

#### ① `weapon/data/RVP_EffectsData.java` —— 新增字段与访问器

紧跟现有 `tracer_b`（第 135 行附近）加字段：

```java
/**
 * 机枪曳光长度倍率，默认 1.0（= 现状）。
 * 生效公式：长度 = min(0.3 × 当前速度 × 本倍率, 已飞距离 × 0.8) 格。
 * 0 表示不显示曳光；非法值（NaN/无穷）按 1.0 处理；上限 8。
 * 仅 RVP 机枪 Renderer 生效（本体机枪不经过本渲染器）。
 */
@SerializedName("tracer_length_scale")
private Float tracerLengthScale;
```

紧跟现有 `getTracerB()`（第 298-300 行）加：

```java
public boolean hasTracerLengthScaleOverride() {
    return tracerLengthScale != null;
}

/** 曳光长度倍率；未配置或非法返回 1.0，下限 0、上限 8。 */
public float getTracerLengthScale() {
    if (tracerLengthScale == null
            || Float.isNaN(tracerLengthScale)
            || Float.isInfinite(tracerLengthScale)) {
        return 1f;
    }
    return Math.max(0f, Math.min(tracerLengthScale, 8f));
}
```
> 命名与钳制风格对齐同类字段（`getMissileNativeTrailParticleScale()` 就是 `null/NaN/Inf → 1f` + `max(.., 0)`）。

#### ② `entity/projectile/RVP_BulletEntity.java` —— 字段 + 读入 + getter

```java
// 字段区（43-46 行那段旁边）
```

本期**不给任何武器 JSON 加字段** ⇒ 默认 1.0 ⇒ **全部 39 把机枪观感与改动前一模一样**。

### 2.3 效果预估（射速/速度取现值）

| 武器 | velocity | 现长度上限 | ×1.5 | ×2.0 | ×3.0 | 达到上限所需飞行距离（×2.0 时） |
| --- | --- | --- | --- | --- | --- | --- |
| `mbt_762` / `mbt_127` | 10 | 3.00 格 | 4.50 | 6.00 | 9.00 | 4.5 格 |
| `f16_m61a1` 等 30mm | 16 | 4.80 格 | 7.20 | 9.60 | 14.40 | 7.2 格 |

## 三、设计决策（请用户确认口径）

| # | 决策点 | 选项 | 默认建议 |
| --- | --- | --- | --- |
| 1 | 倍率乘在哪 | (a) 乘基长、上限不变 ← 推荐；(b) 倍率同时放大 `0.8×距离` 上限；(c) 直接给绝对长度 `tracer_max_length`（格） | **(a)** |
| 2 | 是否同时放开上限 | 本期**不做**；若将来要"恒定长尾迹"，再单独讨论 | 不做 |
| 3 | 速度取值 | (a) 沿用**当前速度**（阻力会让尾迹变短，现状）；(b) 改用**出生速度**（长度恒定、不随阻力衰减） | **(a)**（切 (b) 会同时改变现有所有武器观感，需用户点头） |
| 4 | 取值范围 | `[0, 8]`；`0` = 曳光不可见（可当"无曳光弹"用）；NaN/Inf → 1.0 | 同左 |
| 5 | 字段名 | `effects_data.tracer_length_scale`（与 `missile_native_trail_particle_scale` 命名风格一致） | 同左 |

### 方案 B（可选增强）：客户端全局倍率

在 `config/RVP_ClientConfig.java` 加一项（`ywzj_rvp-client.toml`）：

```java
tracerLengthGlobalScale = builder
        .comment("机枪曳光长度全局倍率，与武器 JSON 的 effects_data.tracer_length_scale 相乘。",
                 "默认 1.0（不影响任何武器）；仅客户端渲染，联机时各玩家可各调各的。")
        .defineInRange("tracerLengthGlobalScale", 1.0D, 0.0D, 8.0D);
```
+ 静态 getter（照抄 `getThermobaricShakeIntensity()` 的 `INSTANCE != null ? ... : 1.0F` 写法）。
渲染端最终：`scale = 条目倍率 × 全局倍率`。

**用途**：不进游戏改文件、不重启数据包，改 toml 就能整体试参数；试好了再落到 JSON。
**代价**：多一个配置项与一条"两个倍率相乘"的心智负担。→ **建议做成可选**，若只想要一个旋钮就跳过。

### 方案 C（不做，仅记录）：让本体机枪也吃倍率

vt4 的 `gun_7.62mm` / `gun_14.5mm` 走**本体** `BulletEntityRenderer`（公式完全相同但代码在本体），
要覆盖只能 MixIn 本体渲染器。**不建议**：
- 本项目约定"Mixin 默认拒绝，逐级排除 JSON 数据层 → 继承/接口 → Forge 事件 → 网络包 → Accessor"；
- 这里要改的是"某 mod 渲染方法内的一个局部变量"，**无数据层可走**，属最后手段；
- 收益只有 vt4 那两把同轴机枪。

⇒ 记为**不做**；若用户需要，替代方案是把那两把在本体里配 `velocity`（本体现在也行）。

## 四、验收标准

1. **零回归**：不加新字段时，39 把机枪的曳光长度与改动前**完全一致**（默认 1.0 生效）。
2. **生效正确**：给某把武器写 `"tracer_length_scale": 2.0` 后，飞远时长度约为原来的 2 倍，
   且**出膛瞬间依然很短**（`0.8×距离` 上限仍在起作用）。
3. **边界**：`0` → 看不到曳光；`-1`、`1e9`、`NaN` 不崩、按 1.0（或钳到 8）处理。
4. **双端一致**：专用服务器下，其他玩家看到的长度与配置一致（验证 spawn data 同步到位）。
5. **构建**：`compileJava` BUILD SUCCESSFUL；现有测试无新增失败。

## 五、验证方法（建议顺手加一条单元测试）

把公式抽成纯函数，便于单测而不必开游戏：

```java
// VehicleProjectileRenderLogic 内
static double resolveTracerLength(double speed, double travelDistance, float scale) {
    double len = 0.3 * speed * scale;
    return Math.min(len, travelDistance * 0.8);
}
```
断言：
- `resolveTracerLength(16, 100, 1f) == 4.8`
- `resolveTracerLength(16, 100, 2f) == 9.6`
- `resolveTracerLength(16, 5, 2f) == 4.0`（被 `5×0.8` 上限截住）
- `resolveTracerLength(16, 100, 0f) == 0.0`

游戏内目视：单机给 `f16_m61a1` 写 2.0，对天空连射，与 1.0 对比；再写 0 确认曳光消失。

## 六、风险清单

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **spawn data 不成对** | 只加写入或只加读取 → 后续字段全部错位（`bounceLeft` 等读出垃圾） | 同一次提交内成对修改；改完通读 `writeSpawnData`/`readSpawnData` 两边顺序逐行对照 |
| 数据包需重启 | 载具包 JSON 是**启动时加载** | 交付说明里写清"改 JSON 要重启" |
| 顺手改动全局常量 | 把 `0.3` 或 `0.2` 改成可配会改变**所有**武器观感 | 本期只加"乘数"，不动既有常量 |
| 倍率过大 | `mbt_762`（velocity 10）×3 = 9 格 | clamp 上限 8；文档给效果预估表 |
