### 2.2 `autoTraceRuntimeState`：纯诊断逻辑，每帧每车无条件执行

`client/render/RVP_CustomMountRenderLogic.java:158` 无条件调用：

```java

```

函数体（`:638` 起）**没有任何 `DEBUG_ENABLED` 前置判断**，只有「写文件」那一步被 `putIfAbsent` 拦住：

```java

    WeaponResolution resolution = resolveCurrentWeaponForDisplay(localWeaponUnit); // :650 分配密集
    ...
```

> **已修（2026-09-14）**：用户决策"封装成 debug 命令"。`autoTraceRuntimeState` 首行已加
> `if (!DEBUG_ENABLED.get()) return;` 前置短路，改由**既有命令** `/rvpdebug custommount on` 控制。
> 既有设施本就完整（`RVP_DebugCommands:181-226` 有 `custommount on|off|status|dump|clear|bolts`），
> 缺的只是这条自动追踪不认那个开关。能力保留：`on` 会先 `clearDebugLog()` 清 `AUTO_TRACE_KEYS`，
> 之后每个「载具实体+载具类型+当前武器」组合首次出现仍记录一次。降级已登记进
> `docs/调试与修复规范.md` §4 功能丢失/降级表。

**注意**：`AUTO_TRACE_KEYS` 是 `ConcurrentHashMap` 静态表（`:63`），键含载具 id + 武器 id，长会话会缓慢增长（建议一并改为弱引用或按载具清理）。

### 2.3 `resolveMounts`：每帧三重集合分配 + O(n²) 查表

```java

...
for (RVP_CustomMountConfig config : configs) {
    ResolvedMount resolved = resolvedMounts.stream()
```

`resolveMounts`（`:255` 起）内部每次 `new ArrayList<>()` + `new HashMap<>()`；`:204` 每条目再 `new ArrayList<>(missileBones.size())`；`:213` 又 `new ArrayList<>(hiddenRackBones)`。
**修法建议**：`render` 循环里改用「一次遍历建查找表」或把 `resolveMounts` 的返回改成与 `configs` 等长的数组按 index 直接取，消除 stream+线性查找；集合可复用。
**同时**：`:304` 的 `resolveForCurrentWeapon` 会**再调一次** `resolveMounts`，被 `shouldSuppressDefaultWeaponDisplay`（`WeaponUnitCustomMountSuppressMixin:24`）逐武器站调用 → 同帧重复解析（**本次未处理**）。

> **已修（2026-09-14，第一批）**：① `render` 改为每帧建一次 `IdentityHashMap<config, resolved>` 查找表
> （消除 O(配置数²)，且用 IdentityHashMap 严格保持原 `entry.config() == config` 的身份语义）；
> ② `resolveMounts` 各集合按规模预分配、`updatedByConfig` 改 `IdentityHashMap`、去掉多余列表改为
> **原地 `resolved.set(i, replacement)`**。
> **核实**：`RVP_CustomMountConfig` 虽是 record（`equals` 为值相等），但含 `configOrder`（解析时 `order++`）
> → 同一载具内不存在值相等的两条配置，故哈希语义在此类型上与原实现等价、不改变匹配结果。
> **注：已通过编译验证**（`compileJava` BUILD SUCCESSFUL / 93 测试类 0 失败）；**仍需实机回归**多联挂架的发射→重挂显隐顺序与弹药数。

### 2.4 `createBakedInstance()`：每帧每挂架重建实例 + 逐骨正则匹配

`RVP_CustomMountRenderLogic.java:217`：

```java
BakedModelInstance attachmentInstance = attachmentModel.createBakedInstance();
applyAttachmentPose(attachmentInstance, hiddenRackBones, partiallyHiddenMissiles);
```

本体实现（`ywzj_vehicle/.../VehicleBedrockModel.java:85-95`）：

```java
BakedModelInstance instance = bakedModel.createInstance();
instance.resetPose();
for (BoneState bone : instance.getBoneIndexes()) {
    bone.illuminated = ILLUMINATED_BONE_PATTERN.matcher(bone.name()).matches(); // 逐骨正则
}
```

**为什么慢**：每帧每挂架 = 新建实例 + 全骨遍历 + **每根骨一次 `Pattern.matcher(...)`（分配 + 匹配）**。挂架模型骨数越多越重；同帧多挂架线性叠加。
**修法建议**：把 `BakedModelInstance` 按（模型 + 条目）缓存复用，只做「骨可见性」的原地更新；`illuminated` 是静态属性，不需每帧重算（本体的正则结果只取决于骨名，可一次算好缓存）。
**风险**：~~低~~ —— **实测后上调**：全文件 `setBoneVisible(..., true)` 调用 **0 次**（`applyAttachmentPose:539` 只会设 `false`），
骨骼可见性完全依赖「每帧新建实例」复位 → 直接缓存会让**发射过的挂架骨重挂后不再显形**。
若要做，必须配套：每帧 `resetPose()` + 对 `rack_bones`/`missile_bones` **全集双向**显式设可见性。

> **⚠️ 实测后降级（2026-09-14，本项不应再称为"挂架最大头"）**：统计作者包 `assets/rvp/models/bedrock/entity/weapon_mount/*.json`
> 共 33 个挂架模型，**骨数 2~7 根（平均 2.8、最大 7）**——即每次 `createBakedInstance()` 只有约 3 次正则匹配与
> 一个小对象深拷贝。**绝对成本是微秒级、属噪声**，为它引入"骨可见性复位"这类有功能风险的结构性改动**不划算**。
> 结论：**本项建议不做**（或仅在未来真的实机测出挂架热点时再评估）。原先把它列为"收益最大的一块"是**基于骨数很多的错误假设**。
> 挂架路径真正值得修的浪费（`autoTraceRuntimeState` 每帧白跑 + 反射每帧重查 + O(n²)与集合分配）**已在本次会话全部修完**。

### 2.5 每帧每挂架一次反射元数据查询

`client/render/RVP_CustomMountRenderLogic.java:316` / `:328`（在 `render` 的条目循环内被 `:187` 调用）：

```java
private static VehicleCubeGroup resolveMountAnchorGroup(WeaponUnit mountUnit) {
    return RVP_ShootBoltQueueResolver.findXTurnGroup(mountUnit);
}
```

`mount/RVP_ShootBoltQueueResolver.java:235-243`：

```java
field = net.minecraftforge.fml.util.ObfuscationReflectionHelper.findField(WeaponUnit.class, "xTurnGroup");
field.setAccessible(true);
```

**为什么慢**：`findField` 每次都要遍历字段（含 SRG 名映射）并做 `setAccessible` 校验——纯元数据查询，**结果恒定却每帧每挂架重算**。
**修法建议**：`findXTurnGroup` 改为静态 `Field` 惰性缓存一次（`static volatile Field` + 失败标记），后续只 `get(unit)`。**零行为变化，改动最小。**

> **已修（2026-09-14，第一批）**：新增私有 `resolveXTurnGroupField()`——双重检查锁 + `volatile` 缓存 +
> `xturnGroupResolveFailed` 失败记忆（解析失败只告警一次并永久走 structureGroup 降级）。
> 取值路径仍为 `field.get(unit)`，结果不变。**验证：`compileJava` BUILD SUCCESSFUL（1m19s）、93 测试类全绿。**

#### 2.5.1 影响面核实（2026-09-15，因该容器类历史 bug 较多而专项复核）

`RVP_ShootBoltQueueResolver` 的主职责是**出弹点数据层定版**（`applyTemplateBolts`，数据包加载期写入
模板 bolts），历史上曾实现"运行时出弹队列 + 拉取式应用器"方案（`PENDING`/`ensureApplied`/`MISS_RETRY`/
S2C 整表同步），因**配置/队列表就绪时序竞态**导致"放置后不应用 / 重进回退挂点"而废弃
（存档于 gitee 提交 `709815d7`）。故本次改动必须确认它**不碰那条链路**。

**核实结论（静态证据）：**

| 核查项 | 事实 | 结论 |
|---|---|---|
| `findXTurnGroup` 调用方 | 全模块仅 **1 处**：`RVP_CustomMountRenderLogic:331`（`resolveMountAnchorGroup`，渲染侧挂架锚点） | 纯渲染侧 |
| 数据层写入链路是否经过它 | `applyTemplateBolts` → `computeStationBolts` → `bindPivot` / `appendBoneBolts`，锚点骨来自 `structure_bone + "_barrel"`，**全程不调用 `findXTurnGroup`** | **与出弹点写入/重进取值零交集** |
| `WeaponUnit.xTurnGroup` 字段归属 | 类级元数据（`WeaponUnit.class`），与载具实例无关；`field.get(unit)` 按传入实例取值 | 缓存 `Field` 后取值语义逐字一致 |
| 线程安全 | `volatile` + `synchronized` 双检锁；写侧原子、读侧无锁可见 | 正确（同 `RVP_WeaponSwitchSyncHelper` 既有先例） |
| 失败降级路径 | `resolveXTurnGroupField()` 返回 null → `unit.getStructureGroup()`（原实现同路径） | 降级行为不变 |

**唯一可观察的语义差异**：解析失败从"每次调用重试 + 每次刷一条 WARN"变成"**只重试一次、只告警一次、
之后永久走 structureGroup**"。风险评估：`WeaponUnit` 是本模组的类、字段名固定，`findField` 失败只可能
源于字段被改名/移除（此时重试亦无用，原实现同样永久降级）或模块访问被拒（`setAccessible` 抛
`InaccessibleObjectException`，此时原实现每次同样失败）→ **两者行为等价，无实际功能风险**。
若要彻底消除该差异，可给缓存加复位入口（挂资源重载钩子）；当前无证据表明必要。

## 三、服务端每 tick 全实体扫描（已复核；**2026-09-14 实测量级后降级为低嫌疑**）

> **⚠️ 优先级修正（2026-09-14 晚）**：本节原先标为「P1 高嫌疑」，但**未做量级估算就给优先级是不成立的**。
> 逐项量化后结论是：**O(实体) 的每 tick 扫描本身不构成帧率/TPS 问题**（详见本节末"量级评估"）。

> 单机下服务端与客户端同 JVM，服务端 tick 变重会直接表现为掉帧/顿卡。

### 3.5 量级评估（2026-09-14 补充，据此降级）

- **裸扫描**：`level.getEntities().getAll()` 是 O(E) 指针遍历 + `instanceof` 判定。E 为数千级时单次约**微秒级**；
  两个 handler × 每维度 ≈ 几十微秒 / 50 ms tick 预算 → **不到 0.1%**，不足以造成可见掉帧。
- **CIWS 谓词逐项核实**（`GunnerTargeting:408-409`、`GunnerEntity:382-383`）：
  `isInterceptableRvpProjectile` = 3 个 `instanceof`；`isCiwsTargetOnCooldown` = `HashMap.containsKey(int)`；
  `collectTargetEntities` 用 `getBoundingBox()`（vanilla 为缓存字段）与 `intersects`（纯算术）。
  → 单实体判定约百纳秒级；即使 E=5000、2 台炮手车也是 **亚毫秒~1 ms/tick 量级**，仍未到"卡"的门槛。
- **所以本节三个 handler 都不应作为掉帧的默认嫌疑**；它们的价值仅在于：
  ① CIWS 是**唯一一处"没跟扫描间隔节流"的不一致**（常规索敌 `GunnerBrain:302` 有 `% scanIntervalTick`，CIWS 在 `:297` 没有）→ 属代码一致性问题，值得顺手对齐，但不是性能事故；
  ② 若将来实机测出服务端 tick 压力大，再回来按"换遍历源为全量载具登记表"处理（见 §7.4）。
- **判定手段（已核实命令存在）**：`/forge tps` 看每维度 TPS/MSPT —— 若 MSPT 只有几毫秒，本节可直接结案。
  ⚠️ **`/forge track` 对本节无用**：已读 Forge 1.20.1 源码（`net/minecraftforge/server/command/TrackCommand.java`），
  它只跟踪 **BlockEntity / Entity 的 tick**（`TimeTracker.BLOCK_ENTITY_UPDATE` / `ENTITY_UPDATE`），**不覆盖 Forge 事件处理器**。

## 七、修复风险与功能影响评估（2026-09-14 补充，已逐条核实源码）

### 7.1 零功能影响（可放心做）

| 项 | 为什么无影响 |
|---|---|
| `findXTurnGroup` 反射缓存 | 只把「恒定的元数据查询」挪到静态缓存一次，后续仍走 `field.get(unit)`，取值路径与结果完全一致。**唯一可观察差异**：解析失败时的 `LOGGER.warn`（`:241`）从"每次调用刷一条"变成"一条"，属噪音减少。（仓库内已有同类先例：`RVP_WeaponSwitchSyncHelper` 惰性缓存反射字段） |

### 7.2 会去掉现有能力，需你决定

**`autoTraceRuntimeState` 加调试短路**——我原先的建议有误导，纠正如下：

`autoTraceRuntimeState` 经 `appendTraceLog`（`:822`，`synchronized`）**无条件落盘**，只在 `AUTO_TRACE_KEYS.putIfAbsent`（`:657`）按 `载具id|载具类型|当前武器` 去重；**写文件前没有 `DEBUG_ENABLED` 判断**。也就是说它是**常开诊断**：不需要你预先开开关，它就会自动抓到"每台车每种武器第一次出现"的挂架状态快照。

**用户决策（2026-09-14）：封装成 debug 命令 → 已按选项 3 落地。**
`autoTraceRuntimeState` 首行加 `if (!DEBUG_ENABLED.get()) return;`，改由既有命令 `/rvpdebug custommount on` 控制；默认关闭时零开销。原选项其余两条仅作记录：
- ~~保留原样~~（接受每帧成本）；
- 只优化不删：把 `toString()` 换成直接用 `ResourceLocation` 拼 key、复用同帧已算过的 resolve 结果——**该优化仍可作为后续补充**（进一步降低开启调试时的成本）；
- ~~改成开关控制~~ → **已采用**。降级已登记 `docs/调试与修复规范.md` §4（复现挂架问题前需先 `/rvpdebug custommount on`）。

### 7.3 有真实功能风险，必须配套改（不能只做一半）

**① `createBakedInstance()` 缓存复用 —— 会出"已发射挂架骨永久隐藏"的 bug。**

`applyAttachmentPose`（`:539-552`）**只会把骨设成 `visible = false`**：

```java
for (String boneName : hiddenBones) { setBoneVisible(instance, boneName, false); }
```

而全文件 `setBoneVisible(..., true)` 的调用次数是 **0**（已 grep 确认）。也就是说**骨骼可见性完全依赖"每帧新建实例"来复位**。若把实例缓存复用，第 1 发导弹打出去后那根骨被设 false，**重新挂弹后也不会再显形**。
→ **配套要求**：复用实例的前提是每帧**先显式把所有相关骨置回 true**（或对 `rack_bones`/`missile_bones` 全集逐个设置可见性，双向都设），再叠加"本体逐骨正则 `illuminated` 只算一次"的缓存。**必须实机回归：多联挂架发射→重挂→骨的显隐顺序**（EA-18G 四联、rafale 三联、j16d 双联）。

**② `resolveMounts` 去 O(n²) 必须用身份比较。**

原代码是身份比较：`entry.config() == config`（`:166`）。若改用 `HashMap<config, resolved>`，而 `RVP_CustomMountConfig` 是 record/有 `equals`，就会**走值相等**——两个字段相同但不同实例的条目可能互相顶替，导致**挂架取到别的条目的状态**（渲染错位/弹药数不对）。
→ **配套要求**：用 `IdentityHashMap`，或改成按下标直取（`resolveMounts` 返回与 `configs` 等长的数组）。**必须实机回归**同上三条。

### 7.4 属行为变更，需要单独决策（不建议简单节流）

**服务端三处全实体扫描**——注意别把"节流"和"改遍历源"混为一谈：

- **干扰物 `tick()` 内部是每 tick 推进状态机**（`machine.onTick()`，`RVP_CountermeasureRuntimeManager:166`）→ 若给 `RVP_CountermeasureEventHandler` 加 `%N` 节流，**抛洒/装填节奏会被拉长**，属行为变更，不建议。
- **正解是换遍历源，但有个坑**：管理器已有 `STATES = Map<UUID, VehicleCountermeasureState>`（`:62`），看似可替代扫描；但 `onVehicleJoin`（`:69-73`）**对没有干扰物配置的载具直接 return**，所以 `STATES` 只含"配了干扰物的车"；而 `tick()` 里的 `tickRadarChaffJam(vehicle)` 是**对所有载具**执行（代码注释明确"含无干扰物配置的中继雷达载具"）——即"任何锁定被箔条遮蔽目标的雷达都应脱锁"。
  → 若直接把扫描换成遍历 `STATES`，**没配干扰物的载具会失去"箔条遮蔽导致雷达脱锁"**，是真功能丢失。
  → **安全做法**：新增一张**全量载具登记表**（join 时登记所有 `AbstractVehicle`，不按配置过滤）再遍历它，与现扫描等价；或保留扫描但对**无配置载具**也建轻量记录。维修侧 `RVP_MaintenanceRuntimeManager:46` 同理（也有 `STATES`，需一并核对其 join 是否也做了配置过滤）。
- **CIWS 索敌**：加节流 = 拦截反应变慢（CIWS 是时间敏感功能），属行为变更；更安全的方向是"先判本车是否有适用武器再进全扫描"，但**判定口径需先确认**（`findCiwsTarget` 的结果被所有武器类型的索敌路径复用，不能想当然地按"是否有 CIWS 武器"早退）。

### 7.5 小结

- **可以立刻做、不碰功能**：7.1 的两项。
- **要你拍板**：7.2 的 auto-trace 保不保。
- **能做完但必须配套改 + 实机回归**：7.3 的挂架两项（挂架渲染正是掉帧最大头，值得做，但不能只改一半）。
- **建议单独立项、先测试档验证**：7.4 的服务端扫描（要动时序/登记表）。

| 渲染**遍历全部事件逐个绘制**，无渲染数量上限 | `client/gui/RVP_HitIndicatorOverlay.java:467`（`renderHitAnimation`） |

单个事件在 2.6 s 窗口内每帧都在画，其中：
- 带弹体模型的事件 → **一次 `model.renderToBuffer(...)`**（Bedrock 模型，见 `renderProjectileModel:739-762`）；
- `renderFragments:628` → **5 条破片线**，且**循环体内每次 `new Vector3f` + `new Quaternionf`**（`:644-646`，每事件约 10~15 个临时对象）；
- 另有爆点圆盘 / 曳光线。

**结论**：**一帧的绘制次数 ≈ 最近 2.6 秒内该载具的命中次数**。10 发/s → 约 26 次/帧；
机炮级射速（m61a1 量级）直接顶到 **128 次/帧**（含上百次模型绘制与上千个临时对象）。
这与用户记忆中的"一帧重复渲染 40 次"是**同一种病**。

**注**：文档 `RVP命中提示UI调研与设计方案_20260811.md` §7.1 记的"直击+爆炸重复渲染**同一发**弹体模型"那个
BUG **已修**（`hasDirectHit` 判定 `:459-466` + `hasProjectileModel` 守卫 `:505/:573`）。
所以现在的性质是"**多发各画一遍、且无渲染上限**"，不是"同一发画两遍"。

**可选修法（都会动观感，需用户拍板）**：
① 渲染层只画最近 K 个事件（如 8 个），其余仍计入伤害数字 —— 最坏情况 128→8；
② 高频武器（机炮类）不逐发绘制动画，聚合为单次提示；
③ 保底优化（不动观感）：把 `renderFragments` 循环内的 `Vector3f`/`Quaternionf` 提到循环外复用。
（文档 `RVP命中提示UI调研与设计方案_20260811.md` §6.1 早已把"多段伤害聚合"列为待定决策点，本次可一并定。）

### 10.2 自定义挂架 —— 按条目数重复整段网格提交

`RVP_CustomMountRenderLogic.render` 条目循环内每条目 `createBakedInstance()` + `renderToBuffer` + `renderSpecialBones`（`:217-243`）。
EA-18G 有 5 条条目、rafale 6 条。属"每帧固定重复"，不是随数量爆炸。
**2026-09-14 实测修正**：同帧通常只有 1 条条目匹配当前武器而真正提交绘制；且挂架模型骨数仅 2~7 根（见 §2.4），
故**这条路径的量级很小，不构成帧率问题**。挂架路径的实质浪费已在本次会话修完（§2.2 诊断白跑 / §2.5 反射重查 / §2.3 O(n²)与分配）。
唯一残留的"结构性"可选项是同帧 `resolveMounts` 被调用两次（`render` 一次 + `shouldSuppressDefaultWeaponDisplay` 经 `WeaponUnit.render` HEAD 逐武器站一次）——
单次都很便宜，收益小，**建议不做**。

### 10.3 每个标记一次独立 draw call（不合并批次）

`client/RVP_ClientEvents.java:592-651`：每个 marker 单独 `Tesselator` begin → `drawWithShader` → end。
**标记数 = draw call 数**，不合并成一个缓冲批次。

### 10.4 每个接触/目标一次绘制（无上限）

`client/gui/RVP_ScopeOverlay`（`:459-489` 遍历全部雷达探测目标，逐个 `worldToScreen` + 文本）、
`RVP_RadarOverlay`（`:134-146` 逐接触 `fill`/`drawLine`）、`RVP_ArmOverlay`（逐 contact）。

### 10.5 爆炸 / 核爆特效 —— 有上限，但每特效多次状态切换

`client/nuclear/RVP_ExplosionVisualManager`（`MAX_ACTIVE_DEBRIS_CHUNKS = 64`、`MAX_DEBRIS_CELLS_PER_EXPLOSION`）
