# 舰船持久区块保活方案（rvp_persistent_chunk_lease）

> 状态：**方案定稿，代码未实施**（数据侧由本 agent 已改）
> 日期：2026-10-03
> 适用：ywzj_rvp（Minecraft 1.20.1 Forge）

---

## 一、问题现象（用户实测）

| # | 现象 |
|---|---|
| 1 | 舰船**必须先被扫到一次**，之后驶出视距才能继续被扫到 |
| 2 | 若舰船从未被接触过（例如玩家已远离到千里之外再重新放置搜索平台），**即使目标在雷达扫描范围内也扫不到** |
| 3 | 飞机/直升机只要**运动过**，就能被超视距主动扫到；**停在地上也扫不到** |
| 4 | 结论收敛：**与机型无关，与"上一次被扫到/离开之前，载具是否在运动"有关** |

---

## 二、根因

### 2.1 雷达能看到目标 ⇔ 客户端存在该实体

RVP phase 雷达遍历的是客户端实体表（`RVP_ClientRadarTickHandler.mergedClientEntities()` = `entitiesForRendering()` ∪ `serverEntities`），本体雷达同理。来源只有两条：

1. **原版实体追踪**：`clientTrackingRange(32)` = 32 区块 = **512 格**（各类载具完全一致，非差异点）；
2. **本体超视距广播克隆**：`AllEvents` 每 5 tick 遍历 `level.getEntities().getAll()`，即**只覆盖服务端当前已加载的实体**。

⚠️ RVP 自己的远距载具同步（`S2CRemoteVehicleVisualSnapshot`）产生的代理**不加入 `ClientLevel`**（源码注释原文），因此**雷达看不到它** —— 该机制与本问题无关。

⇒ **服务端不加载 ⇒ 不广播 ⇒ 客户端无实体 ⇒ 雷达扫不到。**

### 2.2 服务端为什么会"不加载"——票据超时（字节码实证）

RVP 远距载具租约（`RVP_RemoteVehicleChunkLeaseService` + `RVP_ChunkPathLoadManager`）为本体的 **`TicketType.POST_TELEPORT`** 票据提交区块加载。反编译 MC 1.20.1 `DistanceManager` / `TicketType` 得到两个决定性事实：

**① `POST_TELEPORT` 的超时 = 5 tick**

```
TicketType.<clinit>:
  ... "post_teleport" → iconst_5 → TicketType.create(name, comparator, 5)
  ... "portal"        → sipush 300
  ... "start"/"dragon"/"player"/"forced"/"light" → 两参 create（timeout = 0，永不过期）
```

`DistanceManager.tick()` 每 tick 执行：

```java
++this.ticketTickCounter;
for (entry : this.tickets.long2ObjectEntrySet()) {
    for (Ticket<?> ticket : entry.getValue()) {
        if (ticket.isTimedOut(this.ticketTickCounter)) {   // now - createdTick > timeout
            it.remove();                                   // ← 票被移除，区块可卸载
        }
    }
}
```

⇒ **POST_TELEPORT 票据必须每 ≤5 tick 被重新提交，否则失效。**

**② 重复提交同一张票 = 有效续期**

```
DistanceManager.addTicket(long pos, Ticket<?> newTicket):
    SortedArraySet<Ticket<?>> set = getOrCreateTicketSet(pos);
    Ticket<?> existing = (Ticket<?>) set.add(newTicket);   // 同 key 时返回集合内的旧元素
    existing.setCreatedTick(this.ticketTickCounter);        // ← 计时被刷新
```

⇒ 只要**持续提交**，票就永不过期。这也正是本体 `AbstractVehicle` 里 `uav` 载具**每 tick** 调用 `EntityUtil.keepChunkLoaded` 的原因。

### 2.3 根因合体：静止目标会"停止提交"

`RVP_ChunkPathLoadManager.allocateRequests` 只从**新路径**的连续前缀往外扩：

```java
int nextIndex = allocation.grantedChunks.size();
if (nextIndex >= allocation.input.desiredChunks().size()) continue;   // 没有新区块 ⇒ 不再提交
```

- **运动目标**：路径每 tick 沿速度方向滚动 ⇒ 不断产生新的 `ChunkPos` ⇒ 持续提交新票 ⇒ 区块**永不卸载**；
- **静止目标**：`collectSupercoverChunks` 因 `horizontalMotionSqr < MIN_MOTION_SQR` 直接**退化为"当前一格"** ⇒ 第一次提交后 `grantedChunks` 即满 ⇒ 之后**每次都被 `continue` 跳过** ⇒ 票不再刷新 ⇒ **5 tick 后过期** ⇒ 区块卸载 ⇒ 服务端丢失该实体 ⇒ **雷达永远扫不到**（无论飞机还是船）。

⇒ 精确解释现象 3、4：**不是机型特权，而是"路径动画不滚动"**。

## 三、目标与非目标

**目标**
- 让标记了 `rvp_persistent_chunk_lease` 的载具**永久保持服务端加载**（只要服务器在运行），从而任何雷达/搜索平台在 4096 格内都能**主动发现**它，无需预接触。

**非目标**
- 不改雷达的扫描/高度门/矩阵（那是另外的独立机制）。
- 不改 RVP 既有的远距可视租约、快照协议、客户端代理渲染。
- **不**使用 `uav: true`（见 §6.3）。
- 不追求"让从未加载过的载具被凭空唤醒"（见 §5 局限）。

## 四、设计

### 4.1 字段

| 项 | 值 |
|---|---|
| 字段名 | `rvp_persistent_chunk_lease` |
| 位置 | 载具 JSON **顶层**（`data/rvp/vehicles/<id>.json`），与 `rvp_radar_rcs_factor` 同级 |
| 类型 | `boolean`，缺省 `false`（未配置 = 行为与改动前**完全一致**） |
| 语义 | 该载具在其存在期间持续保活所在区块（服务端） |

### 4.2 机制

服务端**每 tick** 对每个已加载的、标记为 `true` 的 `AbstractVehicle` 调用**本体 public API**：

```java
EntityUtil.keepChunkLoaded(vehicle, vehicle.position());
```

- 与本体 `AbstractVehicle:550` 的 `if (uav)` 分支**同一行代码**，只是不篡改 `uav` 标志；
- `keepChunkLoaded` 提交 `POST_TELEPORT`（半径 3），内部提交两次（`position` 与"沿视线前探"位置，静止时二者同格，幂等）；
- ⚠️ **必须每 tick 调用**：`POST_TELEPORT` 超时为 **5 tick**（§2.2①），节流超过 4 tick 会漏保；
- **无状态、零清理**：载具被移除后不再被遍历到 ⇒ 票自然过期 ⇒ 区块正常卸载。不需要任何 `SavedData`、不需要 remove 配对、不污染存档。

### 4.3 为什么不用 `uav`、也不用自建 TicketType

| 方案 | 结论 |
|---|---|
| **`uav: true`** | ❌ `uav` 有 5 处副作用（隐藏乘客渲染 / 取消过载计算 / 保留 FakePlayer / 可被 `UavControllerItem` 劫持 / 自身保活）。语义完全不符。 |
| **自建 `TicketType(timeout=0)`** | ⚠️ 理论可行（提交一次永久有效，开销最低），但 **票永不过期 ⇒ 必须显式 `removeRegionTicket` 清理**，载具移除/存档异常时会残留"僵尸加载区块"。本方案选**自动过期**的无状态路线，更安全。 |
| **`ServerLevel.setChunkForced`** | ⚠️ 会**持久化**进存档（可跨重启），但同样需要显式解除、且强制加载等级更高。列为可选增强（§5.2）。 |

## 五、局限（**必须先知道**）

### 5.1 只能"保持"，不能"唤醒"

handler 通过 `level.getEntities().getAll()` 遍历 ⇒ **只能看到已加载的载具**。

- ✅ 载具一旦被加载（**玩家放置载具的瞬间必然满足**），即刻开始每 tick 保活 ⇒ 之后**永久不再卸载**（即使玩家去往千里之外、区块本应卸载）；
- ❌ 若服务器**重启**后该区域无人靠近，载具尚未实例化 ⇒ handler 看不到它 ⇒ 保活链断裂 ⇒ 仍然需要一次"接触"才能重新进入保活。

> 即：**运行期间完全解决（现象 1/2/3/4 全部覆盖）**；**重启后首次仍需一次接触**。

### 5.2 可选增强 B+（跨重启，需用户拍板）

在载具**首次加入世界**时（`EntityJoinLevelEvent`）对它所在区块执行一次 `ServerLevel#setChunkForced(pos, true)`（原版机制，写入 `ForcedChunksSavedData`，**重启后自动加载**），并在载具移出世界（`EntityLeaveLevelEvent`）时 `setChunkForced(pos, false)` 解除。

- ✅ 跨重启生效；提交一次即可，无每 tick 开销
- ⚠️ 写存档；若载具被外部手段删除而未触发 leave 事件，会残留永久加载区块
- ⚠️ `setChunkForced` 的加载等级高于 POST_TELEPORT（完整 tick）

**本方案默认不含 B+**。需要跨重启时再单独实施。

## 六、改动清单

### 6.1 `src/main/java/org/ywzj/rvp/config/RVP_VehicleExtendedConfigManager.java`（改，6 处）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `record VehicleExtendedConfig(...)`（约 :570） | 末尾新增 `boolean persistentChunkLease` 字段（并补 javadoc） |
| 2 | 同 record 的 `EMPTY` 常量 | 追加 `false` |
| 3 | 同 record 的 `isEnabled()` | 追加 `\|\| persistentChunkLease` |
| 4 | `parseVehicle`（约 :310） | 新增 `boolean persistentChunkLease = parsePersistentChunkLease(obj);`；**早退判定的 `&&` 链追加 `&& !persistentChunkLease`**；构造参数末尾追加 |
| 5 | 新增私有静态方法 | `parsePersistentChunkLease(JsonObject)` —— 顶层 bool，缺省/非布尔一律 `false` |
| 6 | 新增 public 静态查询 | `isPersistentChunkLease(AbstractVehicle vehicle)`，照 `getTurnDepthScale` 的写法：`return INSTANCE.get(vehicle).persistentChunkLease();` |

> ⚠️ **第 3、4 处是本方案最容易翻车的地方**：`parseVehicle` 的"全空即 EMPTY"早退判定与 `isEnabled()` 必须**同步**纳入新字段。该文件 :341 已有同款教训的注释（"本字段必须纳入 parseVehicle 的'全空即 EMPTY'早退判定，否则只配此字段的载具配置会静默失效（§45 审计教训）"）。只配 `rvp_persistent_chunk_lease` 的载具若漏改，会静默失效且不报错。

### 6.2 新建 `src/main/java/org/ywzj/rvp/event/RVP_PersistentChunkLeaseEventHandler.java`（新增）

骨架照 `event/RVP_LinkedUavEventHandler.java`（同款 `ServerTickEvent` + 载具快照遍历）：

```java
@Mod.EventBusSubscriber(modid = RVP_MOD.MOD_ID, bus = Mod.EventBusSubscriber.Bus.FORGE)
public final class RVP_PersistentChunkLeaseEventHandler {

    @SubscribeEvent
    public static void onServerTick(TickEvent.ServerTickEvent event) {
        if (event.phase != TickEvent.Phase.END) return;
        MinecraftServer server = ServerLifecycleHooks.getCurrentServer();
        if (server == null) return;
        for (ServerLevel level : server.getAllLevels()) {
            tickLevel(level);
        }
    }

    private static void tickLevel(ServerLevel level) {
        // 先快照：遍历中实体列表可能变动（照 RVP_LinkedUavEventHandler 的既有做法）
        List<AbstractVehicle> vehicles = new ArrayList<>();
        for (Entity entity : level.getEntities().getAll()) {
            if (entity instanceof AbstractVehicle vehicle) vehicles.add(vehicle);
        }
        for (AbstractVehicle vehicle : vehicles) {
            if (RVP_VehicleExtendedConfigManager.isPersistentChunkLease(vehicle)) {
                EntityUtil.keepChunkLoaded(vehicle, vehicle.position());
            }
        }
    }
}
```

要点：
- `ServerTickEvent` **天然只在服务端触发**，无需额外 `isClientSide` 判断；
- **必须每 tick，禁止加节流**（§4.2）；
- **不对 `isDestroyed()` 做特判**（与本体 `uav` 分支一致）：残骸也应保持加载，以便 `RVP_LinkedUavEventHandler.expireWreckEarly` 能正常遍历到并按时清理；
- 遍历成本与 `RVP_LinkedUavEventHandler.tickVehicles` 同量级（一次全实体 instanceof 扫描 + 命中项一次 HashMap 查询），可接受。

### 6.3 不涉及

- `ywzj_rvp.mixins.json`：**无需改动**（新增的是 Forge 事件类，不是 mixin）。
- 本体任何文件：**只读**。
- 雷达 / 可见性矩阵 / 快照协议 / 客户端渲染 / `RVP_CommonConfig`：**均不动**。

## 八、验证

### 8.1 构建通过后

1. 启动游戏/服务器，**放置一艘 052D**（此时它必然被加载 ⇒ 保活启动）。
2. 驾驶另一艘船（或飞机）驶离 **>512 格**（超出原版追踪），再远至 **>1000 格**。
3. 用搜索平台（例：052D 自身雷达，`max_scan_distance 4096`）扫描 ⇒ **应能持续看到该 052D 的雷达接触点**。
4. **对照实验**：把 `rvp_persistent_chunk_lease` 临时改为 `false`，同样的操作 ⇒ 应重现"扫不到"。

### 8.2 反证（可选）

对停放舰船所在区块执行 `/forceload add <x1> <z1> <x2> <z2>`（不装模组也能生效）⇒ 若雷达立刻能扫到，同样证明"**加载即可见**"这一根因判断。

### 8.3 观察项

- 服务器 TPS / tick 耗时：标记载具数量 × 2 次 `addRegionTicket`/tick。少量舰船应为零头。
- 载具被摧毁并清理后，其区块应能**正常卸载**（无需人工干预）。

## 九、风险与回退

| 风险 | 说明 | 应对 |
|---|---|---|
| 每 tick 提交开销 | 每条标记载具 2 次 `addRegionTicket` | 只对**显式标记**的载具生效；数量可控。禁止用节流"优化"（会失效） |
| 漏改 EMPTY / isEnabled | 只配该字段的载具**静默失效** | §6.1 第 3、4 处为交付自查项 |
| 语义污染 | 该字段只做"保区块"，不引入 `uav` 任何副作用 | 代码评审确认未触碰 `uav` |
| 重启后失效 | §5.1 固有局限 | 需要则实施 §5.2 B+ |

**回退**：删除新增 handler 类 + 撤销 `RVP_VehicleExtendedConfigManager` 的 6 处改动即可；数据侧字段是无害的未知字段，可保留。备份见 `ywzj_rvp/_bak/`。

## 十、替代方案对照

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 修 `RVP_ChunkPathLoadManager`：静止目标也每 tick 重签 | 改动上游租约核心，影响弹药/支援机等所有消费方 | ❌ 风险外溢大 |
| **B. 车辆级字段 + 每 tick `keepChunkLoaded`** | 本方案 | ✅ **采用** |
| B+. 追加 `setChunkForced` 持久化 | 跨重启 | ⏸ 可选，单独评估 |
| C. 只改数据（提高巡航高度 / 雷达门限） | 与本现象无关（已证伪） | ❌ |
| D. 每 tick `remove` + `add` 配对 | 冗余 —— `addTicket` 本身就会刷新 `createdTick`（§2.2②），无需 remove | ❌ 不必要 |
