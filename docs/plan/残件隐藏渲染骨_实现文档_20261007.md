# 残件（飞头）隐藏渲染骨 —— 实现文档

> 日期：2026-10-07　目标仓库：`ywzj_rvp`
> 现象：VT4 / T-90M / ZTZ99B 死亡飞头后，**炮口焰 `turret_muzzle_flash` 会跟着残件显示**。
> 已排除的纯数据方案：结构模型加零 cube 幽灵骨 + 幽灵部件（实测无效，原因见 §1）。
> 本文给 **两套实现**：**方案 A = 完全不新增 Mixin（推荐）**，方案 B = 一个 Mixin（备选）。

---

## 1. 根因（已核到运行时 jar 与渲染库字节码）

| # | 事实 | 证据 |
| --- | --- | --- |
| 1 | 整车渲染时，特殊骨（`special_bone_effects`）在**主通道被隐藏**，只在 `renderSpecialBones` 里用专用渲染类型单独画 | `VehicleBedrockModel.renderToBuffer(instance,…)` 首行 `setSpecialBoneVisible(instance, false)` |
| 2 | 残件渲染**不走** `VehicleBedrockModel`，而是直接 `modelInstance.renderSingleBone($weapon0 …)`，**没有** `setSpecialBoneVisible(…)` | `VehiclePartRender.render`（本体，jar 内一致） |
| 3 | 所以炮口焰那 5 个 96×96 面片会**当普通几何**被画出来（还用载具贴图的 cutout 渲染类型） | 同上 |
| 4 | 残件**不跑动画控制器**，`static` 动画压不下去（`VehiclePart` 未实现 `IAnimationEntity`，`VehiclePartRender` 也不调 `applyAnimationPose`） | — |
| 5 | 本体留的"排除骨"通道理论可用但依赖私有推导，实测拿不到内容 | `VehiclePart.getExcludedBoneNames()` ← `collectExcludedBoneNames()` ← `PartUnit.getAttPartUnits()` ← `PartUnit.combineAndInit` 里 `structureGroup.children.contains(...)` |

**⇒ 结论：唯一可靠的杠杆是"残件渲染时自己把该骨置 `visible=false`"（渲染库 `renderBone` 遇 `visible==false` 立即 return，含整棵子树），或提前把特殊骨从主通道里摘掉。**

### 为什么纯数据做不到
- `state_hidden_bones`（RVP）注入在 `VehicleRender.render` 上，管不到 `VehiclePartRender`；
- JS 动画脚本 / `part_bindings` / `switchable_animations` 都只在整车动画实例上跑，残件没有；
- 把 `turret_muzzle_flash` 改挂到 `$weapon0` 子树之外 ⇒ 整车时它就不再跟随炮管俯仰（`special_bone_effects` 用的是它自己的骨变换）⇒ 表现坏掉。
- ⇒ **必须改代码，但可以不写 Mixin。**

## 2. 方案 A（推荐）：覆盖注册自定义 `VehiclePart` 渲染器

**零新增 Mixin。** 新增 2 个纯 Java 类 + 改 2 处现有文件。

> 为什么能覆盖成功：RVP 的 `RVP_ClientBootstrap.registerVehicleRenderers()` 在 **`FMLLoadCompleteEvent` 里又调用了一次**（`onLoadComplete`），此时本体 `ClientSetupHandler`（`FMLClientSetupEvent`）早已执行 ⇒ `EntityRenderers` 表里最后写入的是 RVP 的注册，**顺序有保证**。

### 2.1 新增 `client/render/RVP_PartHiddenBonesCache.java`

```java
package org.ywzj.rvp.client.render;

import net.minecraft.resources.ResourceLocation;

import java.util.Collections;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

/** 残件隐藏骨配置：vehicleId -> (partId -> 渲染骨名列表)。数据包重载时整体重建。 */
public final class RVP_PartHiddenBonesCache {

    private static volatile Map<ResourceLocation, Map<String, List<String>>> TABLE = Map.of();

    private RVP_PartHiddenBonesCache() {}

    public static void clear() { TABLE = Map.of(); }

    public static void put(ResourceLocation vehicleId, Map<String, List<String>> byPartId) {
        Map<ResourceLocation, Map<String, List<String>>> copy = new HashMap<>(TABLE);
        copy.put(vehicleId, Map.copyOf(byPartId));
        TABLE = Map.copyOf(copy);
    }

    /** 取该载具该部件的隐藏骨；无配置返回空表。渲染热路径只读 volatile 字段，不分配。 */
    public static List<String> get(ResourceLocation vehicleId, String partUnitId) {
        Map<String, List<String>> byPartId = TABLE.get(vehicleId);
        if (byPartId == null) return List.of();
        List<String> bones = byPartId.get(partUnitId);
        return bones == null ? List.of() : bones;
    }
}
```

### 2.2 新增 `client/render/RVP_VehiclePartRender.java`

```java
package org.ywzj.rvp.client.render;

import com.github.mcmodderanchor.simplebedrockmodel.v2.common.model.runtime.BakedModelInstance;
import com.github.mcmodderanchor.simplebedrockmodel.v2.common.model.runtime.BoneState;
import com.mojang.blaze3d.vertex.PoseStack;
import net.minecraft.client.renderer.MultiBufferSource;
import net.minecraft.client.renderer.entity.EntityRendererProvider;
import net.minecraftforge.api.distmarker.Dist;
import net.minecraftforge.api.distmarker.OnlyIn;
import org.ywzj.vehicle.client.render.entity.vehicle.VehiclePartRender;
import org.ywzj.vehicle.entity.misc.VehiclePart;

import java.util.List;

/**
 * 残件（脱落部件）渲染器：先按载具 JSON 的 {@code rvp_part_hidden_bones} 把指定渲染骨隐藏，再走本体渲染。
 * <p>
 * 起因：本体 {@code VehiclePartRender} 直接 {@code renderSingleBone} 而不做
 * {@code setSpecialBoneVisible(false)}，导致特殊骨（炮口焰等）被当普通几何画出来；
 * 又因残件不跑动画控制器，{@code static} 动画压不下去。这里在渲染前置 visible=false，
 * 渲染库 {@code renderBone} 会连同整棵子树一起跳过。
 */
@OnlyIn(Dist.CLIENT)
public class RVP_VehiclePartRender extends VehiclePartRender {

    public RVP_VehiclePartRender(EntityRendererProvider.Context context) {
        super(context);
    }

    @Override
    public void render(VehiclePart part, float entityYaw, float partialTick, PoseStack poseStack,
                       MultiBufferSource bufferSource, int packedLight) {
        // 注意：VehiclePart 没有 getPartUnitId()，用公开的 getPartUnit().getId() 取（两者都存在）
        org.ywzj.vehicle.vehicle.part.PartUnit<?> unit = part.getPartUnit();
        List<String> hidden = unit == null
                ? List.of()
                : RVP_PartHiddenBonesCache.get(part.getVehicleId(), unit.getId());
        BakedModelInstance instance = part.getVehicleModelInstance();
        if (!hidden.isEmpty() && instance != null) {
            for (String boneName : hidden) {
                BoneState bone = instance.getBone(boneName);
                if (bone != null) {
                    bone.visible = false;      // 不需要恢复：残件渲染器是本实例的唯一消费者
                }
            }
        }
        super.render(part, entityYaw, partialTick, poseStack, bufferSource, packedLight);
    }
}
```

> ⚠️ 取值口径已核对：`VehiclePart` **没有** `getPartUnitId()`；`AbstractVehicle.getVehicleId()`（public）与
> `PartUnit.getId()`（public）可用，代码里按上面的写法取，**不需要再加 accessor**。
> 另外 `part.getPartUnit()` 在极端情况下可能返回 null（部件数据未就绪），已做空判断。

## 3. 方案 B（备选）：一个 Mixin

若不想覆盖渲染器注册（怕将来本体改动/被其它 addon 抢注册），可以走数据层 + Mixin：

1. `ext/PartUnitDataExt`：加 `List<String> ywzj_rvp$getHideRenderBones();`
2. `mixin/PartUnitPojoMixin`：`@SerializedName("rvp_hide_render_bones") @Unique public List<String> ywzj_rvp$hideRenderBones = List.of();` + getter（照抄同文件 `rvp_no_cockpit_view` 的写法）。
3. `mixin/PartUnitDataMixin`：`@Unique` 字段 + 在既有的 `<init>(PartUnitPojo)` TAIL 注入里 `List.copyOf` 拷入 + getter。
4. 新增 `mixin/VehiclePartHideRenderBonesMixin`：

```java
@Mixin(value = VehiclePart.class, remap = false)
public abstract class VehiclePartHideRenderBonesMixin {

    @Unique private List<String> ywzj_rvp$cachedHidden = null;

    @Inject(method = "getExcludedBoneNames", at = @At("RETURN"), cancellable = true, remap = false)
    private void ywzj_rvp$appendHiddenBones(CallbackInfoReturnable<List<String>> cir) {
        VehiclePart self = (VehiclePart) (Object) this;
        PartUnit<?> unit = self.getPartUnit();
        if (unit == null || !(unit.getData() instanceof PartUnitDataExt ext)) return;
        List<String> extra = ext.ywzj_rvp$getHideRenderBones();
        if (extra.isEmpty()) return;
        if (ywzj_rvp$cachedHidden == null) {
            List<String> merged = new ArrayList<>(cir.getReturnValue());
            for (String b : extra) {
                if (b != null && !b.isBlank() && !merged.contains(b)) merged.add(b);
            }
            ywzj_rvp$cachedHidden = List.copyOf(merged);
        }
        cir.setReturnValue(ywzj_rvp$cachedHidden);
    }
}
```
5. 注册到 `ywzj_rvp.mixins.json`；数据写成部件级 `"rvp_hide_render_bones": ["turret_muzzle_flash"]`（写在 `parts[0] turret` 上）。

**两方案对比**

| | 方案 A（覆盖渲染器） | 方案 B（Mixin） |
| --- | --- | --- |
| 新增 Mixin | **0 个**（只改现有 1 个 mixin 的方法体） | 1 个 |
| 新增/改动文件 | 新增 2 类、改 2 处 | 新增 1 类、改 4 处 |
| 配置粒度 | 载具级 map（一个部件一条） | 部件级字段（跟 `render_bone` 同级） |
| 风险 | 依赖覆盖注册成功（已在 `FMLLoadCompleteEvent` 兜底） | 依赖本体 `getExcludedBoneNames` 语义不变 |
| 建议 | **首选** | 覆盖注册不奏效时的兜底 |

## 5. 残件「一落地就消失」—— ✅ 已由**数据侧**修复（2026-10-07）

**现象**：RVP 车残骸血量 **-1**，落地瞬间消失；本体车残骸 **1000/1000**，正常落地。

**根因链**（逐行证据见 `RVP侧骨隐藏与飞头物理排查_20261007.md` §七）：

1. `PartUnitPojo.maxHealth` 默认 **-1**（= "未配置"）；RVP 全部载具的部件都没写 `max_health`（文件里那 1 处是**载具级**的）。
2. `AbstractVehicle.setDestroyed():1402-1406` = `setHealth(getMaxHealth())` ⇒ 残骸血量 -1。
3. `ContainerCraft.setHealth():119-121` 会 `clamp(health, 0, getMaxHealth())` ⇒ maxHealth=-1 时怎么设都还是 -1。
4. `AbstractVehicle.initData` 本有兜底（`getHealth()<0` ⇒ 用载具级 `max_health`），但 **`VehiclePart.initData()` 被覆写成空** ⇒ 对部件不生效。
5. 落地 ⇒ `PhysicsEngine:609`（`velocityDiff > 0.5`）⇒ `DamageSystem.impactHurt` ⇒ `hurt(vehicleCollision, …)` ⇒ `AbstractVehicle.hurt():633-635`：`getHealth()<=0 && isDestroyed()` ⇒ **`discard()`**。

### 5.1 已落地的数据修改（**不需要再写代码**）

给**所有"会脱离"的部件**（有 `render_bone` 且其 `structure_bone` 带 cube）补两个字段：

```jsonc
{ "id": "turret", "render_bone": "$weapon0",
  "max_health": 1200,                                 // = 该车载具级 max_health
  "defense_stats": { "damage_threshold": 0.1 } }       // 与 RVP 车级的 0.1 对齐 ⇒ 不改整车手感
```

| 车 | 部件 | `max_health` |
| --- | --- | --- |
| `vt4` / `t90m` / `ztz99b` | `turret` | 1200 |
| `cssa5` / `lavad` | `suspension_wheel0~7` | 800 |
| `lav25` / `zbl08a` | `suspension_wheel0~7` | 900 |

合计 **35 个部件**；已同步 开发源 + `run/client_1|2|server` + E 盘整合客户端。
**幽灵部件 `muzzle_flash` 不配**（零 cube ⇒ 不生成残骸，配了无意义）。

**为什么两个字段都要**：

- `max_health` 是残骸血量的**唯一来源**（`VehiclePartSpawner → PartUnit.detach() → VehiclePart.initPart() → initializePart(copyHealth=true)`）；
- `defense_stats.damage_threshold: 0.1` 是"副作用税" —— 部件有正血量后 `PartUnit.isDefensive()` 变真，整车被**弹体直击 / 近炸**时才会进入 `DamageSystem.hurt:65-73` 的部件分支；默认 50 会把 `amount < 50` 的命中钳成 0.1（改手感），写 0.1 即放弃钳制。
  ⚠️ 该字段**只对普通载具生效，残骸读不到**（残骸 `partUnits` 为空 ⇒ `hitPartUnit` 恒 `null`）。

### 5.2 ⚠️ 上线后要实测的两点

1. **"部件被打坏"这条路径被打开了**：部件血量归零 ⇒ `PartUnit.isDestroyed()` ⇒ `VectorUtil.hitPartUnit:183` 跳过它（**弹体可穿透**）+ HUD 标红。现状（血 -1）下这条路是关闭的 ⇒ **打几炮看伤害数字/装甲表现是否与之前一致**；若不可接受，改小血量或回到代码侧。
2. **RVP 伤害补偿数学**：`damageSystemScale = predicted / amount`（`RVP_VehicleHurtScalingHandler:216-225`）是按"部件从不吃伤害"标定的；`damage_transfer_coefficient = 1.0` 时 `amount` 不变 ⇒ 理论上无影响，仍需实测确认。

> 代码侧备选（**本次未采用**）：在 `event/RVP_PhysicsOnlyCollisionEventHandler` 的 `EntityJoinLevelEvent` 里给 `VehiclePart` 补血 —— 完全不影响整车战斗，但需要在残件入世界时插一段逻辑；数据侧已达成同样效果，故不做。

### 7.2 可行性反汇编证据（simplebedrockmodel 2.5.1 deobf jar）

- `BakedModelInstance.renderSingleBone(PoseStack,int,…)` 自身不查 visible，直接委托 `BakedBedrockModel.renderBone`（12 参）两条 pass（`iconst_1`/`iconst_0`）都过同一检查点；
- **12 参 `renderBone` 是整个 BakedBedrockModel 类中唯一读 `BoneState.visible` 的地方**（字节码偏移 47-53：`getBone(I)` → `ifnull` → `getfield visible` → `ifne`，false 即 return），检查在 `renderChunkForPass`（画本骨，偏移 117）**之前**、子树递归（偏移 120-172）**之前** ⇒ 本骨+整棵子树零 quad，且发光/普通两条 pass 都被挡；
- 本体 `VehicleBedrockModel.setSpecialBoneVisible` 写的就是同一字段（`putfield BoneState.visible`，jar 反汇编），整车路径运行佐证同链；
- 附带：`BakedModelInstance.rayTraceCubes` 也读 visible ⇒ 被隐藏骨同步退出射线检测（炮口焰为纯视觉骨，无命中语义，可接受）。

### 7.7 炮口白烟被殉燃黑烟覆盖修复（2026-10-07，用户实测报告）

**症状**：面对远处殉燃上浮黑烟，近处炮口白烟（`RVP_WreckMuzzleSmokeParticle`，19979b25 引入）被整批盖在下面。

**根因**：两种烟分属**两个自定义 `ParticleRenderType` 批次**（绑不同贴图，必然两个 key），1.20.1 `ParticleEngine` 对自定义批不做距离排序、批间先后与距离无关（HashMap keySet，单 JVM 内 identity hash 稳定 → 批序每帧相同）。殉燃黑烟 `RVP_MchrSmokeRenderType.RENDER_TYPE` 为 `depthMask(true)`（写深度，MCHR 历史行为），而炮口白烟 `depthMask(false)`——**白烟批先画时不写深度 → 黑烟批后画时深度缓冲里没有白烟 → 远处黑烟整批通过深度测试盖住近处白烟**。

**修复（1 处）**：`RVP_WreckMuzzleSmokeParticle.renderType` 的 `begin()` 改 `depthMask(true)`（写深度，对齐殉燃烟/爆炸烟 MCHR 语义）——此后无论两批谁先画，深度缓冲按真实前后正确互挡（批序无关）。改黑烟为只测不写修不好（黑烟后画时依旧没有白烟深度可依）；同批距离排序不可行（贴图不同无法共用 RenderType，自定义批无排序，不上 Mixin）。

**已知代价（与 MCHR 爆炸烟现状同款）**：白烟渐隐期仍以全深度挡住后面物体；对同帧后画的半透明切片按深度剔除。

验证：build 772/0/0，冒烟 `Done (5.391s)!` 无新增错误；实机观感（白烟遮挡黑烟、白烟对载具遮挡无回归）待用户确认。回退：`renderType` 恢复 `depthMask(false)`。

**修正轮（同日 18:50，用户实测"多块半透明白烟叠加后载具被挡死"）**：写深度的半透明在渐隐期形成幽灵深度（alpha 已低、深度仍全量），多块叠加把载具彻底挡死——写深度语义本身错误，正确参照即火箭尾迹/冲刷烟修复 `d7141aac`（"原 true 挡死后续粒子与载具"→改只测不写 + 层间 α 分摊）。但直接回退会复发"黑烟盖白烟"（跨批无排序，深度缓冲无白烟可依）。**最终方案：白烟按 alpha 分桶双渲染批**——不透明期（`alpha ≥ 0.4`，类内常量 `FADE_DEPTH_ALPHA` 可调）走写深度批（跨批遮挡仲裁，用户认可的不透明覆盖）；渐隐期走只测不写批（alpha 混合自然透出载具）。粒子 `tick()` 按 alpha 切换 `renderType`（字段去 final + `textureIndex` 定位同贴图，工厂 `renderType(texture, depthWrite)`/`createRenderTypes(depthWrite)` 参数化，照 `RVP_MchrSmokeRenderType.forTexture` 既有模式）；黑烟零改动。已知边界：不透明期对同帧后画半透明切片按深度剔除（MCHR 爆炸烟同款）；渐隐期与黑烟跨批轻微混合错序（低 alpha 损失小）。验证：build 772/0/0，冒烟 `Done (2.164s)!` 无新增错误，进程杀净复验 0。

**终稿（同日 19:50，用户二次实测截图"浓烟区也透出背景与载具"）**：分桶方案仍不完备——写深度批**内部**烟块互相深度剔除（先画的块写深度、后画的块被剔），炮口烟柱多块叠加的"增浓"失效，浓烟区实际只剩单块 alpha（emitter 实测 0.51~0.78）的遮挡力，故仍透。至此结论：白烟在 ParticleEngine 内**写深度也不对（层间自剔+剔穿后画载具切片）、不写深度也不对（跨批被黑烟盖）**——引擎自定义批无距离排序是死结，唯一正解是**脱离 ParticleEngine 自绘**。新类 `RVP_WreckMuzzleSmokeSelfRenderer`（@EventBusSubscriber CLIENT）：粒子不再 engine.add，改入静态活动列表；ClientTick END 统一 tick（世界切换清空、上限 2048 防失控）；`RenderLevelStageEvent.AFTER_PARTICLES` 阶段（**恒晚于黑烟批**）按相机距离**降序排序**后按贴图分组自绘（粒子 shader + 光照层 + alpha 混合 + depthMask(false)；billboard 数学复用 `SingleQuadParticle.render`）。效果：层间叠加正确增浓、载具 alpha 混合软遮挡、白烟恒在黑烟之前。粒子类回退分桶为单批（depthMask(false) 仅作误入引擎兜底），构造器改包内可见、新增 `isGone()`/`textureIndex()`/`distanceSqrTo()` 包内接口；殉燃控制器 `RVP_WreckCookoffController` 的炮口灰烟同步接入同一管线。已知边界：白烟贴图 16 组间顺序与距离无关（同色系观感影响小）；自绘粒子不进热成像白热通道（自定义批时代亦不被提白，无回归）。验证：build 772/0/0，冒烟 `Done (2.655s)!` 无新增错误，进程杀净复验 0。回退：三文件还原即回引擎批次路线（不再推荐）。
