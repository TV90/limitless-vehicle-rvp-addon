# 本体载具包自解压机制调研 —— RVP 未来打包载具包进 jar 的可行性

> 日期：2026-10-12　性质：**纯调研，不实施**。目标：摸清本体（ywzj_vehicle）把 `default_vehicle` 载具包打进 jar 并在启动时自解压/版本比对的完整机制，评估 RVP 未来把 `limitless_vehicle/rvp` 打进 jar 的路径、代价与坑。
> 本体仓库只读，本文所有行号基于 `ywzj_vehicle` 0.6.1（73d7e86 系）。

---

## 1. 结论摘要

1. 本体机制 = **jar 内静态资源 + 启动时版本比对 + 落盘覆盖 + 当作资源包挂载**，四段全部在 mod 构造/资源仓库阶段完成，无黑科技；
2. 本体敢这么干的前提是 **default_vehicle 只有 32MB**；RVP 包 **512MB**（models 305MB + textures 205MB），照抄会让 RVP jar 增重约 250~350MB——**体积是第一决策变量**；
3. 扫描器**原生支持 `limitless_vehicle/*.zip` 直接作包**（不必解压）——这是"不打 jar"的轻量替代发布路径；
4. 版本比对是**字符串字典序 compareTo**，`0.6.9 > 0.6.10` 这类误判真实存在，打包前必须定版本号规范；
5. RVP 侧 `RVP_VehiclePackInstaller` 已逐行同构本体逻辑，**唯一缺口是 jar 里没有 `/rvp` 资源**（当前每次启动 WARN missing + 假 "Installed"）——未来打包只需补资源+构建链，Java 侧几乎零改动。

---

## 2. 本体机制全链（源码行号索引）

### 2.1 资源打包方式：零魔法

`ywzj_vehicle/src/main/resources/default_vehicle/`（32MB：assets + data + pack.png + vehicle_pack.meta.json）**作为普通 resources 被 gradle 原样打进 jar**。build.gradle 对它**零特殊处理**（无 processResources 过滤/拷贝任务；仅有 data 生成器与 modMetadata 两个无关 srcDir）。jar 实测：`default_vehicle` 475 个 entry 合计 30.9MB（源 32MB，贴图/音频已压缩格式压缩率≈0）。

### 2.2 启动时序

```
Mod 构造（YwzjVehicle.java:29-32）
  └─ VehiclePackLoader.INSTANCE.packType = dist ? CLIENT_RESOURCES : SERVER_DATA   // 双端各取
  └─ VehiclePackLoader.INSTANCE.scanVehiclePacks()                                  // ★ 自解压发生在这里
       └─ checkDefaultVehiclePack()                                                 // ★ 版本比对+落盘
AddPackFindersEvent（AllEvents.java:68-72, MOD bus）
  └─ event.addRepositorySource(VehiclePackLoader.INSTANCE)                          // 注册为资源包仓库源
资源仓库构建 → loadPacks() → vehiclePacksAsResource() → 挂载为 Forge 资源包
```

时序保证：自解压（mod construct）**先于**资源包仓库构建（AddPackFindersEvent），落盘的文件下一阶段即被当作资源包扫描挂载，无缝衔接。

### 2.3 自解压决策树（`VehiclePackLoader.checkDefaultVehiclePack()`，:82-108）

| 游戏目录 `limitless_vehicle/default_vehicle` 状态 | 行为 |
| --- | --- |
| 不存在 | 直接 `copyModDirectory("/default_vehicle", …)` 从 jar 整拷（首次安装） |
| 存在，磁盘 meta.version **≥** jar meta.version | return（不动，用户目录为准） |
| 存在，磁盘版本旧 **或 meta 读取失败** | ①整包备份到 `limitless_vehicle_backup/default_vehicle_<yyyyMMddHHmmss>`；②`deleteFiles` 清空；③从 jar 整拷覆盖 |

注意三处细节：
- **版本比较是字符串 `compareTo` 字典序**（:93）——`"0.6.9".compareTo("0.6.10") > 0` 会把 0.6.9 误判为新于 0.6.10 而拒绝升级。版本号必须固定位数（如日期式 `20261012`）或此处改造；
- `copyFolder`（GetJarResources.java:71-93）**先清空目标再复制**，无原子性：复制中途崩溃=半包状态（但备份发生在清空之前，可手工回滚）；
- 备份**无清理策略**：每次升版都整包备份一份，只增不减。本体 32MB 无所谓，RVP 512MB 会快速堆积。

### 2.4 GetJarResources 工具族（util/GetJarResources.java，注释注明参考 TaCZ）

| 方法 | 行为 | 坑 |
| --- | --- | --- |
| `readModFile(path)`(:59) | `YwzjVehicle.class.getResource` 读 jar 内文件流；**URL null 时返回 null** | 调用方必须判 null，否则 meta 比对静默走"重装"分支 |
| `copyModDirectory(src, target)`(:45) | getResource→URL→`copyFolder`；**URL null 时静默 return，无任何日志** | jar 缺资源=假安装且零痕迹（RVP 版至少 WARN） |
| `copyFolder(uri, target)`(:71) | **先 `deleteFiles` 清空目标**，再 Files.walk 全量复制（REPLACE_EXISTING） | 非原子；URI 相对化解析，dev 环境 URL 指向文件目录而非 jar，行为一致 |
| `deleteFiles(path)`(:95) | walkFileTree 全删 | — |

### 2.5 扫描器与资源包挂载

- `scanVehiclePacks(path)`(:220-251)：遍历 `limitless_vehicle/` **一级子目录 + *.zip**（zip 不解压直接作包，:183-218 从 zip 内读 meta）；`vehicle_pack.meta.json` 必需，**namespace 全局唯一**（重复直接拒），`dependencies` 可选（modId→VersionRange，对已装 mod 校验，:253-270）；
- `vehiclePacksAsResource()`(:110-153)：每个包构造成 `PathPackResources`（按 meta.namespace 取路径）→ 套 `DelegatingPackResources` → `Pack.readMetaAndCreate(…, Position.BOTTOM, PackSource.BUILT_IN)`——即每个载具包=一个内建资源包，`data/` 走服务端 SERVER_DATA、`assets/` 走客户端 CLIENT_RESOURCES（由 2.2 的 packType 分端）；
- meta.json 字段（本体默认包实例）：`namespace / title / description / version / date / license / authors (+dependencies 可选)`。

### 2.6 dev 环境行为

mod 构造时 `class.getResource("/default_vehicle/…")` 在 dev 下指向 `build/resources/main/…`（gradle processResources 输出），与生产 jar 同一 API 路径，逻辑无需分支。注意 **run/ 沙盒的游戏目录也有 limitless_vehicle/**，dev 下版本比对同样生效——改了 resources 里的包却没 bump version 不会重装。

## 3. RVP 侧现状

- `RVP_VehiclePackInstaller.ensureInstalled()`（RVP_MOD.java:45 构造期调用）**已逐行同构本体逻辑**：meta 版本比对（同为字符串 compareTo）→ 旧包备份到 `limitless_vehicle_backup/rvp_<ts>` → 清空 → `copyModDirectory("/rvp", …)`；
- 差异：①用 `RVP_MOD.class` 取资源（对齐）；②jar 缺 `/rvp` 时 WARN "resources missing" 但仍打 "Installed" 完成日志（**假安装**，本体会静默）；③备份目录同名不同前缀；
- **当前 RVP jar 未打 `/rvp`** → 每次启动必现 `resources missing` WARN+假 Installed（8 月测试服日志、今晨冒烟日志均可复现）——未来打包后此告警自然消失。

## 4. RVP 打包可行性评估

### 4.1 体积账（第一决策变量）

| 项 | 本体 default_vehicle | RVP rvp 包 |
| --- | --- | --- |
| data（weapons/vehicles 等 JSON） | — | **8.2MB** |
| assets | 32MB（合计） | **503MB**：models 305MB（全在 bedrock/，JSON 高压缩）+ textures 205MB（PNG 低压缩）+ sounds/display 等 ~2MB |
| jar 实测增重 | **30.9MB** | 粗估 **250~350MB**（JSON 压缩率高、PNG 近乎不压） |

本体 jar 现重 15.9MB；RVP jar 加到 ~300MB 级别后，分发/更新成本、Forge 加载内存（资源包按需读流，不常驻，影响可控）都要计入。

### 4.2 路径对比

| 方案 | 做法 | 优点 | 代价/风险 |
| --- | --- | --- | --- |
| **A. 照抄本体**：资源放 `src/main/resources/rvp` | 零 Java 改动 | 与本体完全同构 | 503MB 资产**不能进 git**（现状 authoritative 包也不进），resources 目录需要构建前填充；jar 巨大；每次 build 全量拷贝 |
| **B. gradle 构建期打包**（推荐）：processResources/自定义 task 从 `limitless_vehicle_authoritative/rvp` 复制进 jar | 构建链小改 | 源不进 resources、开发工作流不变（仍改权威包）；版本可由 meta 自动生成 | 打包体积问题依旧；CI/离线构建需保证 authoritative 在位 |
| **C. 发布 zip**：不出 jar 内资源，把 rvp 包打 zip 让用户放 `limitless_vehicle/` | 扫描器**原生支持**（:230），RVP installer 反而可删或保留兜底 | 零 jar 增重；更新=换 zip；与现行"用户手动同步目录"工作流最接近 | 仍需用户手动放置；无版本自动升级（可配启动器） |
| **D. 资产拆分**：data+必备 assets 打 jar，重型贴图/模型按需下载 | — | jar 可控 | 需自建下载/校验逻辑，工程量大，不建议首期 |

### 4.3 无论选哪条都要先定的事

1. **版本号规范**：`vehicle_pack.meta.json` 的 version 走字符串 compareTo——建议改用日期式（`20261012`）或固定三段位数，并在 RVP installer 里**改成语义化比较**（本体侧不动，RVP 自己的 installer 可控）；
2. **备份策略**：RVP 包 512MB，沿用"每次升版整包备份"会让 `limitless_vehicle_backup` 膨胀——建议 RVP installer 限制保留最近 1 份或对 assets 只备份 data；
3. **假安装静默失败**：打包落地时同步修 `RVP_VehiclePackInstaller`——jar 缺资源时 throw 而非假 "Installed"，并补成功/失败两种完成日志；
4. **namespace 冲突**：rvp 包 namespace=`rvp`，与游戏目录内可能存在的旧 `limitless_vehicle/rvp` 同名——扫描器对重复 namespace 直接拒绝**后到者**（:234-237），语义上 jar 自解压先落盘再扫描故不冲突，但用户手工残留的同名目录会引发"版本旧→被备份重装"的隐藏行为，需在文档/日志里可辨识；
5. **开发工作流迁移**：现在 weapons 进 git、vehicles/ 直接同步游戏目录；打包后 vehicles 改动也走"改权威包→build→jar 分发"，**用户侧更新节奏从"同步目录"变成"换 jar"**——两套并存期要明确哪边是权威。

---

## 5. 建议路线（供拍板，未实施）

1. **短期**：维持现状（目录同步），先把 §4.3-3 的假安装修掉（独立小提交）；
2. **中期**：走**方案 B**——gradle task 从 authoritative 复制 `rvp` 进 jar + installer 补语义化版本与备份限额；首发可只打 `data`（8.2MB）验证链路，assets 观察体积后再决定全量或拆分；
3. **长期备选**：若 jar 体积不可接受，**方案 C（zip 发布）**零成本兼容——扫描器已原生支持，作为 jar 包的降级/补充通道。
