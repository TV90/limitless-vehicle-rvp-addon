# 载具放飞无人机与母车/无人机切换控制可行性调研

## 目标

希望实现类似战争雷霆的玩法：

- 载具可主动放飞一架无人机
- 玩家可在母车与无人机之间切换操控
- 切回母车时尽量恢复到原座位/原控制位

本调研仅分析现有本体代码是否具备基础，不涉及代码实现。

## 结论

结论是可行，但核心工作量不在“生成无人机”，而在“母车与无人机之间的控制切换状态机”。

以当前本体架构看，最稳妥的方案不是新写一套独立无人机系统，而是复用已有 `uav=true` 载具分支，并补一层：

- 母车放飞无人机
- 绑定母车与无人机关系
- 从母车切换到无人机
- 从无人机切回母车原座位
- 无人机操控期间母车进入安全保持状态

## 现有基础

### 1. 已有无人机载具体系

本体已有 `uav` 字段，说明“无人机”不是一个完全独立的实体系统，而是普通载具体系中的一个分支。

相关位置：

- `ywzj_vehicle/custom/vehicle/BaseVehicleDataPojo.java`
- `ywzj_vehicle/custom/vehicle/BaseVehicleData.java`
- `ywzj_vehicle/entity/vehicle/AbstractVehicle.java`

关键点：

- 数据层可声明 `uav: true`
- 实体层会把该标志落到 `AbstractVehicle.uav`
- `uav` 会影响交互、假操作员、回位与保区块等行为

### 2. 已有无人机实例

默认载具 `quadcopter` 已经是一台本体无人机：

- 类型：`rotary_wing_vehicle`
- 参数：`uav: true`
- 默认带一个观瞄位
- 默认不带武器

这说明：

- 本体已经能正常创建、同步、控制无人机载具
- 无人机飞行动力学复用旋翼机体系

### 3. 已有无人机控制器

本体已存在 `UavControllerItem`：

- 可与无人机配对
- 可通过 `UUID` 重新接管指定无人机
- 会定期记录无人机位置用于重连

这说明：

- “重新切换到无人机控制”这条链已经有基础
- 不需要从零设计无人机接管入口

### 4. 已有假操作员与回位逻辑

无人机上机时，本体会：

- 记录操作者原位置
- 在原位置生成 `FakePlayer`
- 把真实玩家传送到无人机位置并骑乘无人机

无人机下机或销毁时，会尝试把玩家送回原位置。

这说明：

- 现有本体已经支持“操作者离开原位、远程接管无人机”的体验雏形
- 只不过当前回位目标是“原地/假人位置”，不是“母车原座位”

## 为什么说“放飞无人机”本身不难

载具生成链路本体已经具备：

- 载具数据可 `construct(...)`
- 生成后可直接 `addFreshEntity(...)`

也就是说，母车放飞一架无人机并不是实体技术难题，本质上只是：

1. 确定要放飞的无人机 `vehicleId`
2. 计算放飞位置与朝向
3. 服务端创建并生成该 `uav` 实体
4. 建立母车与无人机的绑定关系

## 真正的难点

### 1. 玩家切到无人机后，母车会失去操作员

当前玩家一旦骑乘无人机，就会离开母车座位。

这意味着：

- 母车驾驶位/武器位会被清空
- 母车进入无人操作状态
- 如果母车是飞机、直升机或需持续输入维持姿态的载具，可能马上出现姿态失稳问题

所以真正要补的是：

- 母车在无人机操控期间如何保持安全状态

### 2. 现有回位逻辑不会自动回母车座位

当前本体无人机的“退出控制”只会：

- 回到假操作员位置
- 或回到记录的原位置

但战争雷霆式切换要求的是：

- 回到母车原座位
- 恢复原控制位与可能的武器位上下文

这部分当前本体没有现成功能，需要新增。

### 3. 缺少母车与无人机的从属关系

当前 `UavControllerItem` 只关心：

- 目标无人机 `UUID`
- 目标无人机最近位置

它并不知道：

- 这架无人机属于哪台母车
- 原来从母车的哪个座位切出来
- 应该切回哪台母车的哪个位置

因此必须新增一层运行时状态。

### 4. 母车状态变化会影响回切

实际游玩中还会遇到这些情况：

- 母车移动到远处
- 母车被摧毁
- 原座位被别人占用
- 无人机被击毁
- 玩家掉线重连

这些都需要定义切换失败的兜底逻辑。

## 推荐方案

### 方案 A：复用现有 `uav` 体系，补母车/UAV切换状态机

推荐程度最高。

思路：

1. 母车触发“放飞无人机”
2. 服务端生成一架绑定 UAV
3. 记录：
   - `parentVehicleUuid`
   - `parentSeatIndex`
   - `parentWeaponUnitIndex` 或等价控制位信息
   - `ownerPlayerUuid`
4. 玩家切到 UAV 后：
   - 真正骑乘 UAV
   - 母车进入安全保持态
5. 玩家切回母车时：
   - 优先尝试重新骑乘母车
   - 恢复原 seat / weapon unit
   - 失败则回退到母车附近安全位置

优点：

- 最大限度复用现有本体无人机逻辑
- 风险较低
- 更贴近当前架构

缺点：

- 仍然需要补完整的状态管理和回切逻辑

### 方案 B：真正的远程代理控制

即玩家身体始终留在母车，只把输入与视角远程代理到 UAV。

优点：

- 体验上最像纯遥控

缺点：

- 现有输入链是建立在“玩家实际骑乘当前载具”基础上的
- 需要额外重定向输入、HUD、武器控制、视角、锁定、网络同步
- 工程量和风险显著更高

当前不建议作为第一版。

## 推荐实现顺序

### 第 1 步：先打通最小闭环

- 母车可放飞一架 UAV
- 玩家可切到 UAV
- UAV 被摧毁或手动退出后，玩家可回到母车附近

### 第 2 步：补回母车原座位

- 新增 `parentVehicleUuid`
- 新增 `parentSeatIndex`
- 新增切回母车接口
- 切回时优先恢复原座位/原控制位

### 第 3 步：母车安全保持

按载具类型分别做：

- 地面载具：驻车/停止
- 直升机：自动悬停或缓降
- 固定翼：自动平飞或低速保持

### 第 4 步：扩展玩法

- 限制同时存在的 UAV 数量
- 弹射/回收逻辑
- 母车挂点或舱位库存
- 战术地图一键切换与状态显示

## 需要新增的关键状态

建议至少新增这些运行时字段或等价结构：

- `ownerPlayerUuid`
- `parentVehicleUuid`
- `parentSeatIndex`
- `parentControlSlot`
- `launchSourcePos`
- `uavState`
  - `STOWED`
  - `DEPLOYED`
  - `CONTROLLED`
  - `LOST`
  - `RETURNED`

## 风险与兜底建议

### 1. 母车不存在

处理建议：

- 切回失败
- 玩家回到 UAV 下机点附近

### 2. 原座位被占

处理建议：

- 尝试母车其他安全座位
- 或落到母车旁安全位置

### 3. UAV 被击毁

处理建议：

- 自动断开控制
- 优先回母车，失败再回地面安全位置

### 4. 玩家重连

处理建议：

- 需要保留母车/UAV 绑定状态
- 登录后可选择重新接管 UAV 或回母车

## 最终判断

这个玩法在当前本体框架下是现实可行的。

最推荐的路线是：

- 不新建独立无人机系统
- 复用现有 `uav=true` 载具体系
- 补一层母车/UAV切换状态机

如果后续进入设计阶段，优先级建议是：

1. 母车放飞 UAV
2. 切到 UAV
3. 切回母车原座位
4. 母车安全保持

第一版不建议追求完全远程代理控制，否则会把输入、视角、HUD、武器链全部抬到更高复杂度。

## 扩展方向：分体式防空载具与无人机雷达数据链

### 目标场景

希望实现类似战争雷霆中的分体式防空载具：

- 玩家驾驶一辆本身没有雷达的防空导弹发射车
- 发射车可部署一台“雷达车无人机”
- 雷达车无人机负责搜索、探测、锁定
- 发射车通过数据链接收该雷达车的态势数据
- 发射车即使本身没有雷达，也可把对方的雷达当成外置雷达使用

当前阶段只考虑：

- 发射车与其部署出的雷达车无人机之间的数据链

暂不考虑：

- 友军之间的跨载具公共数据链
- 多个平台互相转发中继

### 先给结论

这个方向是可行的，而且和前面的“母车/UAV 切换控制”天然可以共用一套绑定关系。

但它和单纯“放飞无人机”不同，关键难点不在 UAV 实体本身，而在：

- 如何把雷达车的探测结果安全地喂给发射车
- 如何让发射车的锁定/发射/制导链承认这个外部雷达源
- 如何区分“共享搜索态势”和“共享正式锁定/照射”

### 现有代码链为什么不能直接支持

当前本体的雷达链默认是“武器站只认自己名下的雷达”。

具体表现：

1. `WeaponUnit` 只会把自己子部件中的 `RadarUnit` 收进 `radarUnits`
2. `WeaponUnit.getRadarDetectedEntities()` 只汇总自己这些本地雷达
3. `WeaponUnit.fireControlLock()` 雷达锁定时默认只取 `getMainRadarUnit()`
4. `ClientRadarAction` 服务端路由也只会把锁定/探测写回当前武器站的主雷达
5. 导弹发射前后的多处逻辑都会默认认为“锁定雷达”属于当前武器站

这意味着：

- 即使雷达车无人机真的探测到了目标
- 发射车如果没有本地雷达
- 这些探测结果也不会自然出现在发射车的 `WeaponUnit` 里

所以“分体式防空”不能只做一个 UAV，还必须额外做一层“外部雷达代理”。

## 推荐的总体思路

### 核心思想

不要把雷达车无人机伪装成发射车本地的物理雷达部件。

更稳的思路是：

- 雷达车仍然是一台独立载具
- 它保留自己的 `RadarUnit`、搜索、锁定、NCTR、扫描扇面等完整逻辑
- 发射车只通过数据链“借用”这台雷达车的探测结果与锁定结果

也就是说，逻辑上是：

- 实体独立
- 数据共享
- 锁定与制导允许跨载具引用

### 为什么不建议伪装成本地雷达

如果强行把雷达车的数据复制进发射车本地雷达，虽然表面上简单，但后续会出现这些问题：

- 雷达位置变假了，距离、方位、扫描范围都不再真实
- 雷达车和发射车的朝向、天线姿态会混掉
- SARH/ARH 的“真正照射源/中继源”语义会不清楚
- 后续扩展到友军数据链时会越来越难维护

因此第一原则应是：

- 外部雷达就是外部雷达，不伪装成发射车本地部件

## 最推荐的实现层次

### 第 1 层：共享搜索态势

这是最低成本、也最适合作为第一阶段验证的层次。

共享内容：

- 探测到的目标实体 ID
- 最后探测位置
- 探测时间戳
- 敌我识别/NCTR 结果
- 目标基础运动信息

效果：

- 发射车即使没有本地雷达，也能在战术地图/雷达列表/HUD 中看到雷达车发现的目标

这一层解决的是“看见目标”，不保证一定能直接完成发射闭环。

### 第 2 层：共享锁定结果

这一层是在“共享搜索态势”之上，再共享：

- 当前被雷达车正式锁定的目标
- 锁定状态是否稳定
- 是否仍在搜索/火控雷达覆盖内

效果：

- 发射车可以把这个外部锁定目标当成自己的“有效锁定目标”
- 发射前锁定门槛可通过

这一层解决的是“能否发射需要锁定的导弹”。

### 第 3 层：共享持续照射/中继

这一层主要服务于：

- 半主动雷达导弹
- 主动雷达导弹的主动截获前中继段

共享内容：

- 哪一部外部雷达正在为哪个目标提供连续锁定/照射
- 这个照射是否还有效
- 数据链是否还在线

效果：

- 发射车可以发射本身需要雷达中继的导弹

这一层解决的是“导弹飞出去以后还能不能继续吃外部雷达数据”。

## 对不同导弹类型的意义

### 1. IR / EO / TV / GPS

这类制导与雷达车关系较弱。

其中：

- IR/EO/TV 更依赖实体锁定或观瞄链
- GPS 不需要雷达

所以分体式防空的重点不在它们。

### 2. ARH 主动雷达弹

这是最适合先支持的一类。

原因：

- 发射前需要目标分配
- 中段通常只需要外部雷达继续提供目标态势/锁定
- 弹载雷达开机截获后，可自行接管

这和“雷达车负责发现和中继，发射车负责打出去”非常契合。

### 3. SARH 半主动雷达弹

这是第二阶段再做更稳妥。

原因：

- 它要求目标始终被有效照射
- 如果雷达车丢锁或数据链中断，导弹就会失去制导基础

所以 SARH 不只是“共享一个锁定目标 ID”就够了，还要共享持续照射状态。

## 针对当前代码的最佳接入方式

### 不推荐的做法：直接复制探测结果到发射车 `radarUnits`

原因：

- 现有 `WeaponUnit` 的 `radarUnits` 是本地结构关系
- 直接塞外部结果会让“这个雷达到底属于谁”变得模糊
- 后面要支持多个外部雷达源时会很乱

### 推荐做法：新增“有效雷达视图”层

建议在 `ywzj_rvp` 侧新增一层 helper，而不是改写本体概念。

例如可以设计出这些等价能力：

- `getEffectiveSearchRadars(weaponUnit)`
- `getEffectiveLockRadar(weaponUnit)`
- `getEffectiveRadarDetectedEntities(weaponUnit)`
- `getEffectiveLockedRadarEntity(weaponUnit)`

含义是：

- 先看发射车本地雷达
- 再看已绑定且在线的雷达车无人机
- 最终返回“当前对发射车有效的雷达视图”

这样有几个好处：

- 不需要把外部雷达硬塞进本体 `radarUnits`
- 本地雷达与外部雷达可以同时存在
- 后续扩展到友军数据链时，这一层还能继续复用

## 数据链应挂在哪一层

### 最推荐：挂在“母车/UAV 绑定关系”之上

既然前面已经建议做：

- `parentVehicleUuid`
- `ownerPlayerUuid`
- `parentSeatIndex`

那分体式防空最自然的做法就是继续在这组关系上加：

- `linkedLauncherVehicleUuid`
- `linkedRadarVehicleUuid`
- `datalinkChannelId` 或等价关系键
- `datalinkRole`
  - `LAUNCHER`
  - `RADAR_RELAY`

这样一来：

- 放飞 UAV
- 切换控制
- 数据链配对

都能共用同一套主从关系。

### 为什么不建议一开始就做“全局友军数据网”

因为当前阶段需求很明确：

- 只是发射车与自己放出的雷达车之间互联

如果一开始就上升到“全队共享战场态势”，会立刻引入：

- 友军鉴权
- 多源冲突
- 优先级
- 中继层级
- UI 过滤与来源标识

这会把第一版复杂度拉高很多。

更稳的顺序是：

1. 先做母车与直属雷达车 UAV 的一对一数据链
2. 再把这套“有效雷达视图”抽象成可支持友军来源的通用框架

## 建议新增的数据状态

建议在 `ywzj_rvp` 侧为“分体式防空数据链”准备一组运行时状态或等价结构：

- `launcherVehicleUuid`
- `radarVehicleUuid`
- `linkOwnerPlayerUuid`
- `linkState`
  - `DISCONNECTED`
  - `SEARCH_ONLY`
  - `LOCK_AVAILABLE`
  - `GUIDANCE_ACTIVE`
- `lastHeartbeatTick`
- `maxLinkDistance`
- `shareSearchTracks`
- `shareLockTarget`
- `shareIllumination`

还建议额外维护：

- `linkedTargetEntityId`
- `linkedLockSourceRadarIndex`
- `linkedLastKnownTargetPos`
- `linkedNctrLabel`

## 推荐的行为语义

### 发射车

发射车在数据链有效时：

- 可显示雷达车提供的搜索目标
- 可对这些目标发起锁定请求
- 锁定请求本质上是发给雷达车，让雷达车尝试正式锁定
- 一旦雷达车锁定成功，发射车把该目标视为“有效外部锁定目标”

### 雷达车无人机

雷达车在数据链有效时：

- 继续独立执行扫描和锁定
- 可响应发射车的“请求锁定/请求解锁”
- 持续把探测态势、锁定状态、NCTR 结果推送给发射车

### 导弹

导弹发射后，制导源判定应区分：

- 自持阶段：导弹自身已接管，不再依赖雷达车
- 外部中继阶段：仍依赖雷达车数据链

其中：

- ARH 更适合第一批支持
- SARH 应在“外部照射有效性”明确后再接入

## 第一版最推荐的落地路径

### 路径 A：先做“外部雷达搜索 + 外部锁定 + ARH”

这是最推荐的第一版。

原因：

- 最贴合分体式防空玩法
- 能快速做出“发射车无雷达也能依靠雷达车打 ARH”的闭环
- 对连续照射的要求比 SARH 低

第一版建议能力：

- 发射车可部署雷达车 UAV
- 战术地图和 HUD 能显示雷达车探测结果
- 发射车可请求雷达车锁定目标
- 锁定成功后，发射车可发射 ARH
- ARH 在主动截获前把雷达车视为外部中继雷达

### 路径 B：第二阶段再上 SARH

等到外部中继逻辑稳定后，再补：

- 雷达车持续照射
- 数据链中断判定
- SARH 丢照射后的失锁/自毁/转惰性飞行逻辑

## 关键难点与风险

### 1. 发射车没有本地雷达时，很多旧逻辑会默认失败

例如旧代码里会直接：

- 读取 `getMainRadarUnit()`
- 读取 `getRadarUnits()`
- 读取 `getRadarDetectedEntities()`

这意味着：

- 只做 UI 共享是不够的
- 真正要支持发射，必须把这些关键判定迁移到“有效雷达视图”

### 2. 锁定请求不能再直接走原版 `ClientRadarAction`

因为原版服务端消息会把锁定写回当前武器站的主雷达。

而分体式防空里需要的是：

- 发射车发起请求
- 雷达车执行锁定

所以后续实现时更适合新增一套 `RVP` 自己的数据链锁定消息。

### 3. 数据链必须有失效条件

否则就会变成不合理的“无限距离上帝雷达”。

至少应考虑：

- 最大链路距离
- 雷达车是否存活
- 发射车是否存活
- 数据链是否启用
- 是否还属于同一绑定关系

第一版可以不做地形遮挡与无线电视距，但必须预留参数入口。

## 推荐的参数化方向

既然你不喜欢硬编码，后续如果真的实现，建议把这些做成参数：

- `datalink_enabled`
- `datalink_role`
- `datalink_max_distance`
- `datalink_share_search`
- `datalink_share_lock`
- `datalink_share_illumination`
- `datalink_requires_same_owner`
- `datalink_allow_friendly_network`

这样未来从“母车与直属雷达 UAV”扩展到“友军数据链”时，不需要重写整套系统。

## 最终建议

如果要把“分体式防空”做成一个可持续扩展的体系，最佳路线是：

1. 复用现有 UAV 载具体系做雷达车无人机
2. 在 `ywzj_rvp` 侧新增“外部雷达数据链”状态层
3. 再在 `ywzj_rvp` 侧新增“有效雷达视图” helper
4. 第一版先支持：
   - 搜索态势共享
   - 锁定结果共享
   - ARH 发射闭环
5. 第二版再支持：
   - 连续照射共享
   - SARH
   - 更广义的友军数据链

一句话总结就是：

- 不要把雷达车当成本地雷达部件
- 要把它当成“外部雷达源”
- 然后让发射车通过数据链去借用这个外部雷达源

这条路线最符合你要的分体式防空思路，也最适合后续逐步扩展到友军数据链。

## 代码实现计划

这一节不是最终代码，而是面向实际开发的落地计划，重点说明：

- 哪些东西放在 `ywzj_rvp`
- 哪些地方通过 mixin 接入本体
- 第一版先打通什么
- 每一阶段的验收标准是什么

### 总体原则

继续遵守一个核心原则：

- 尽量不直接改 `ywzj_vehicle`
- 主要在 `ywzj_rvp` 侧通过 ext、helper、network、mixin 接入

原因：

- 现有 `RVP` 已经大量采用“ext 接口 + mixin 挂状态 + helper 重定向逻辑”的模式
- 例如：
  - `WeaponUnitPendingRadarLockExt`
  - `WeaponUnitPendingRadarLockMixin`
  - `RVP_RadarRoleHelper`

因此分体式防空和外部雷达数据链最适合沿用同一套扩展方式。

## 第一部分：无人机与母车的运行时绑定

### 目标

先让“母车放飞 UAV、切到 UAV、再切回母车”变成一个明确的运行时状态系统。

### 建议新增

#### 1. 新的 ext 接口

建议新增类似这些接口：

- `AbstractVehicleUavLinkExt`
- `WeaponUnitExternalRadarLinkExt`

其中：

- `AbstractVehicleUavLinkExt` 负责母车/UAV 绑定信息
- `WeaponUnitExternalRadarLinkExt` 负责发射车武器站与外部雷达链关系

#### 2. 对应的 mixin

建议新增：

- `AbstractVehicleUavLinkMixin`
- `WeaponUnitExternalRadarLinkMixin`

挂载的最小字段建议包括：

- `parentVehicleId` / `parentVehicleUuid`
- `linkedUavVehicleId`
- `linkedLauncherVehicleId`
- `linkedRadarVehicleId`
- `parentSeatIndex`
- `parentPartUnitIndex`
- `datalinkState`
- `datalinkTargetEntityId`
- `datalinkLockRadarPartIndex`

#### 3. 为什么先挂在实体/武器站运行时状态上

因为当前本体：

- 玩家输入、锁定、发射，基本都围绕“当前玩家所在载具 + 当前 operator part unit + 当前 weapon unit”
- 所以最自然的做法是让：
  - 载具实体知道自己是不是“某台母车放出的 UAV”
  - 武器站知道自己有没有“外部雷达链”

## 第二部分：新增统一的外部雷达 helper

### 目标

避免到处直接读：

- `weaponUnit.getMainRadarUnit()`
- `weaponUnit.getRadarUnits()`
- `weaponUnit.getRadarDetectedEntities()`

改成通过一层统一 helper 访问“有效雷达视图”。

### 建议新增

建议新增一个中心 helper，例如：

- `RVP_ExternalRadarLinkHelper`

它至少要提供这些能力：

- `getEffectiveSearchRadars(WeaponUnit unit)`
- `getEffectiveLockRadar(WeaponUnit unit)`
- `getEffectiveLockedEntity(WeaponUnit unit)`
- `getEffectiveDetectedObjects(WeaponUnit unit)`
- `requestLinkedRadarLock(WeaponUnit launcherUnit, Entity target)`
- `isLinkedRadarIlluminating(WeaponUnit launcherUnit, Entity target)`

### 这层 helper 的职责

它的职责不是替代本体雷达，而是统一决定：

- 当前武器站应该看本地雷达
- 还是看外部雷达
- 或两者都看

优先级建议：

1. 先保留本地雷达能力
2. 再合并外部雷达结果
3. 如果本地没有可锁定雷达，则回退到外部雷达

这样以后：

- 普通单车
- 双雷达车
- 分体式防空车

都能走同一套“有效雷达视图”。

## 第三部分：新增数据链网络消息

### 为什么不能直接复用 `ClientRadarAction`

因为 `ClientRadarAction` 当前的语义是：

- 玩家当前操作的武器站
- 把消息写回这个武器站自己的主雷达

而分体式防空要的是：

- 玩家在发射车上操作
- 但锁定动作实际由雷达车执行

所以必须新增 `RVP` 自己的数据链消息。

### 建议新增的消息

#### 1. C2S 请求消息

建议新增：

- `C2SDeployLinkedUav`
- `C2SSwitchToLinkedUav`
- `C2SSwitchBackToParentVehicle`
- `C2SRequestLinkedRadarLock`
- `C2SClearLinkedRadarLock`

作用分别是：

- 放飞雷达车 UAV
- 切到 UAV 操控
- 切回母车
- 请求外部雷达锁定某目标
- 清除外部雷达锁定

#### 2. S2C 状态同步消息

建议新增：

- `S2CUavLinkState`
- `S2CExternalRadarSnapshot`
- `S2CExternalRadarLockState`

作用分别是：

- 同步母车/UAV 当前关系
- 同步雷达车共享过来的探测目标快照
- 同步外部雷达锁定是否存在、目标是谁、来源是哪部雷达

### 消息风格建议

建议复用现有 `RVP_Network` 风格：

- `encode/decode/handle`
- 服务端定时广播快照
- 客户端单独维护一份状态缓存

和下面这些现有实现保持一致：

- `RVP_RemoteAmmoSyncService`
- `S2CRemoteAmmoSnapshot`
- `S2CHitlLinkState`

## 第四部分：服务端数据链同步服务

### 目标

需要一个服务端定时服务，专门负责：

- 遍历已建立数据链的发射车/雷达车对
- 把雷达车当前的探测态势压成轻量快照
- 同步给发射车所属玩家

### 建议新增

建议新增一个服务类，例如：

- `RVP_ExternalRadarSyncService`

职责：

1. 每隔若干 tick 扫描当前存在的数据链
2. 校验链路有效性：
   - 母车存在
   - UAV 存在
   - 双方未被移除
   - 距离未超限
3. 构造快照：
   - 探测目标 ID
   - 最后位置
   - 距离/高度/速度
   - NCTR
   - 是否当前被外部雷达正式锁定
4. 发送到客户端状态缓存

### 为什么建议用“快照同步”

因为最稳。

好处：

- 不需要让发射车客户端直接去读另一台车的所有复杂对象
- 可以控制同步频率
- 很适合后面扩展成友军数据链

## 第五部分：客户端状态缓存

### 目标

客户端需要一份单独状态，供：

- 战术地图
- 雷达列表
- BVR/HUD
- 发射前锁定检查

统一读取。

### 建议新增

建议新增：

- `RVP_ClientExternalRadarState`

里面维护：

- 当前链接的雷达车实体 ID
- 当前探测目标快照集合
- 当前外部锁定目标
- 最后更新时间
- 是否链路中断

### 读取原则

UI 层不要直接去扫描世界里的雷达车对象。

而是统一读：

- 本地武器站雷达结果
- `RVP_ClientExternalRadarState`

最终经过 helper 合并后显示。

## 第六部分：接入 UI 与战术地图

### 优先接入的界面

第一批优先接：

- `RVP_TacticalMapScreen`
- `RVP_ScopeOverlay`
- `RVP_RadarOverlay`

原因：

- 这几个地方最能直观看到数据链是否工作

### 具体接法

#### 1. 战术地图

在 `RVP_TacticalMapScreen` 中：

- 把“雷达目标列表来源”改为优先读有效雷达视图
- 外部雷达目标需要标记来源
- 最好给链接雷达车加一个单独标识

#### 2. BVR 与 Scope

在 `RVP_ScopeOverlay` 中：

- BVR 锁定框下的 NCTR
- 锁定目标的检测对象
- 锁定来源雷达

都应支持来自外部雷达链。

#### 3. 本体雷达面板

如果后续要统一体验，可以让雷达面板也能显示：

- 本地雷达目标
- 外部雷达目标

但第一版不一定要把这两者彻底混在一起。

## 第七部分：接入锁定与发射链

### 目标

真正让“发射车没有雷达，也能借雷达车完成发射”成立。

### 第一批必须改的点

#### 1. 锁定请求

当前锁定流程大量走：

- `WeaponUnit.fireControlLock()`
- `ClientRadarAction`

第一版建议不要硬改原版语义，而是在 `RVP` 侧追加：

- 当当前武器站没有本地锁定雷达，但存在外部雷达链时
- 锁定请求改走 `C2SRequestLinkedRadarLock`

#### 2. 发射前锁定门槛

当前 `VehicleMissile` / `RVP_WeaponBase` 一类逻辑，很多地方会直接检查：

- `unit.getLockedEntity() != null`

第一版要做的不是全盘替换，而是明确改这些“导弹发射门槛点”：

- 允许“有效外部锁定目标”也视为满足门槛

#### 3. 导弹中段制导

ARH 第一版关键点是：

- 发射前到主动截获前
- 导弹要能承认“外部锁定雷达仍在跟踪目标”

对应地，类似下面这些地方要逐步迁移到 helper：

- `RVP_MissileEntity`
- `RVP_GuidanceSeekerUtil`
- 以及仍直接读 `getMainRadarUnit()` 的旧逻辑

## 第八部分：分阶段实施顺序

### Phase 1：母车/UAV 基础绑定

内容：

- 放飞 UAV
- 切到 UAV
- 切回母车
- 新增运行时绑定状态

验收：

- 母车能稳定放飞雷达车 UAV
- 玩家能在两者之间切换
- UAV 销毁/母车销毁/切回失败时有兜底

### Phase 2：外部雷达搜索共享

内容：

- 服务端快照同步
- 客户端外部雷达状态缓存
- 战术地图与 HUD 显示外部探测目标

验收：

- 发射车无本地雷达时，也能看到雷达车发现的目标

### Phase 3：外部锁定共享

内容：

- 外部锁定请求消息
- 外部锁定状态同步
- 发射门槛承认外部锁定

验收：

- 发射车可请求雷达车锁定目标
- 锁定成功后，发射车可通过锁定门槛

### Phase 4：ARH 发射闭环

内容：

- 导弹中段读取外部雷达链
- 主动截获前允许外部雷达中继

验收：

- 发射车无本地雷达时，可借雷达车发射 ARH 并稳定进入末段接管

### Phase 5：SARH 与更广义数据链

内容：

- 连续照射有效性
- 丢链处理
- 友军共享扩展

验收：

- SARH 能依赖雷达车持续照射
- 后续能平滑扩展到友军数据链

## 最终的一句话实施计划

可以把整件事概括成下面这条开发路线：

1. 给母车和 UAV 建立稳定的主从绑定状态
2. 新增“外部雷达视图”而不是伪装成本地雷达
3. 用独立网络消息同步外部探测和外部锁定
4. 先把 UI 看见目标打通
5. 再把发射门槛和 ARH 中继打通
6. 最后再做 SARH 和友军数据链

这就是当前最稳、最符合现有代码结构、也最适合渐进开发的实现计划。

## 扩展参数设计：指定其它载具模板作为 Deployable UAV

### 目标

支持下面这种玩法：

- 山毛榉导弹发射车本身没有雷达
- 但它的配置文件里可以指定“大鸟雷达车”作为自己的 deployable UAV
- 部署后，生成出来的是一台独立的“大鸟雷达车”实例
- 这台实例进入“从属 UAV / 数据链雷达车”状态
- 玩家可以在山毛榉和大鸟之间切换操作
- 山毛榉把大鸟的雷达作为外置雷达使用

### 设计原则

这里推荐的不是：

- 把“大鸟雷达车”这个车型永久改成 `uav=true`

而是：

- 让“大鸟雷达车”保留为正常载具模板
- 只有当它被某台母车以 deployable UAV 方式放出来时
- 该实例才进入“从属 UAV 模式”

这样有几个好处：

- 同一个载具模板可以独立使用，也可以作为母车的 deployable UAV 使用
- 不会把车型本体逻辑污染成“只能当 UAV”
- 更适合后续扩展“雷达车 / 侦察车 / 干扰车”等多种从属车

### 推荐参数方向

建议在母车配置里新增一组参数，例如：

- `deployable_uav_enabled`
- `deployable_uav_vehicle_id`
- `deployable_uav_role`
- `deployable_uav_spawn_offset`
- `deployable_uav_spawn_yaw_mode`
- `deployable_uav_single_instance`
- `deployable_uav_allow_control_switch`
- `deployable_uav_auto_link_datalink`

其中语义建议如下：

- `deployable_uav_enabled`
  - 是否启用可部署 UAV 能力
- `deployable_uav_vehicle_id`
  - 指向要生成的现有载具模板
  - 例如：`rvp:big_bird_radar_vehicle`
- `deployable_uav_role`
  - 该 deployable UAV 的运行时职责
  - 可选：
    - `radar_relay`
    - `recon`
    - `ecm`
    - `strike`
- `deployable_uav_spawn_offset`
  - 部署时相对母车的生成偏移
- `deployable_uav_spawn_yaw_mode`
  - 部署朝向跟随方式
  - 可选：
    - `parent`
    - `operator_look`
    - `fixed`
- `deployable_uav_single_instance`
  - 是否限制同一时间只能存在一台
- `deployable_uav_allow_control_switch`
  - 是否允许玩家在母车与 UAV 间切换控制
- `deployable_uav_auto_link_datalink`
  - 部署后是否自动建立数据链

### 建议的数据链配套参数

既然这类 UAV 主要服务于分体式防空，建议母车配置同步提供：

- `datalink_enabled`
- `datalink_role`
- `datalink_max_distance`
- `datalink_share_search`
- `datalink_share_lock`
- `datalink_share_illumination`
- `datalink_requires_same_owner`

其中：

- 山毛榉发射车通常是：
  - `datalink_role = launcher`
- 大鸟雷达车 deployable UAV 通常是：
  - `datalink_role = radar_relay`

### 推荐行为语义

#### 母车配置指定模板时

母车只负责声明：

- 我要放出的从属载具模板是谁
- 这台从属载具的角色是什么
- 它部署后是否自动进入数据链

#### 运行时真正生成后

服务端再做这些事：

1. 根据 `deployable_uav_vehicle_id` 构造一台现有载具模板实例
2. 给这台实例挂上：
   - `parentVehicleUuid`
   - `linkedLauncherVehicleUuid`
   - `datalinkRole`
   - `deployableUavRole`
3. 如果 `deployable_uav_auto_link_datalink = true`
   - 自动建立母车与这台实例之间的数据链

#### 这样带来的效果

- 模板还是原来的“大鸟雷达车”
- 但这个实例在运行时被视为“山毛榉的从属雷达 UAV”
- 玩家能切过去操控
- 山毛榉能借它的雷达

### 为什么这比“直接把大鸟改成 UAV 车型”更好

因为你要的是：

- 两个独立的载具个体
- 但在某种部署关系下，逻辑上组成一个系统

这更像“实例关系”，而不是“车型属性”。

所以更推荐：

- `载具模板保持独立`
- `运行时实例进入从属 UAV 模式`

## 当前推荐的最小首发版本

如果要尽快开干、又要风险最低，最推荐先做的首发闭环是：

1. 山毛榉配置可指定“大鸟雷达车”模板为 deployable UAV
2. 山毛榉可部署并切到大鸟
3. 大鸟自动和山毛榉建立一对一数据链
4. 山毛榉可读取大鸟的搜索态势
5. 山毛榉可请求大鸟锁定目标
6. 山毛榉可借大鸟雷达发射 ARH

这套一旦跑通，后面再往：

- SARH
- 多车联网
- 友军共享
