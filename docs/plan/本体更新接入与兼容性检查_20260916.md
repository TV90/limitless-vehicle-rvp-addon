## 二、构建与接入

### 2.1 不改本体工作区，用独立工作树

本体工作区当前**不干净**：detached HEAD（`e537552`）+ 有 **staged 的 `build.gradle` 改动**。故：

```bash
cd D:/ywzj/ywzj/ywzj_vehicle
git worktree add "D:/ywzj/ywzj/_tmp_vehicle_e513a11" e513a11        # 独立检出，零风险
git diff --cached build.gradle > /tmp/user_build_gradle.patch       # 导出用户那处改动
cd D:/ywzj/ywzj/_tmp_vehicle_e513a11 && git apply /tmp/user_build_gradle.patch
```

### 2.2 必须沿用用户那处 `build.gradle` 改动

用户 staged 的改动是：**把 ApricityUI 从 `jarJar(modImplementation ...)` 改成 `compileOnly`**（不嵌入发布 jar）。
若用 e513a11 的原始配置构建，产出 jar 会**多嵌入** ApricityUI：

| 配置 | jar 大小 | 内嵌依赖 |
|---|---|---|
| e513a11 原始 | 14.82 MB | ApricityUI + mixinextras + rhino + simplebedrockmodel |
| **应用用户改动后（采用）** | **12.65 MB** | mixinextras + rhino + simplebedrockmodel ✓ 与 rvp 现用 jar 一致 |

### 2.3 构建一律用 `--offline`

联网构建会失败：`jitpack.io` / `maven.neoforged.net` 报 `Remote host terminated the handshake`（TLS 被断），
而 `:jarJar` 的**动态版本**（`strictly '[2.5.1-forge-mc1.20.1,)'`）必须联网查 `maven-metadata.xml`。

```bash
cd D:/ywzj/ywzj/_tmp_vehicle_e513a11
JAVA_HOME="C:/Program Files/Java/jdk-21.0.11" ./gradlew build --offline --console=plain
# → BUILD SUCCESSFUL in 35s（离线走 ~/.gradle 缓存）
```

### 2.4 接入 rvp

```bash
cp ywzj_rvp/libs/ywzj_vehicle-1.20.1-0.5.10-all.jar{,.bak0903}                  # 备份旧的
cp _tmp_vehicle_e513a11/build/libs/ywzj_vehicle-1.20.1-0.5.10.jar \
   ywzj_rvp/libs/ywzj_vehicle-1.20.1-0.5.10-all.jar                              # 就位
```

rvp `build.gradle` 的依赖写法是 `implementation fg.deobf("libs:ywzj_vehicle-1.20.1:0.5.10-all")`
+ `flatDir { dir 'libs' }` → **版本号未变，无需改动**。

## 三、兼容性检查（本次任务的核心）

### 3.1 检查方法（三层，可复用）

| 层 | 方法 | 能覆盖什么 |
|---|---|---|
| ① 编译 | rvp 用新本体跑 `:compileJava` | 所有 `@Mixin(X.class)` 目标类 + 所有公共 API 调用（编译期强校验） |
| ② 类级 diff | 对比新旧 jar 中 `org/ywzj/vehicle/` 的类集合（md5 分类） | 类的**删除**（最危险的破坏性变更） |
| ③ 成员级 diff | 对②中"被修改类"逐个 `javap -p` 对比，求缺失成员 | mixin 的 `method="..."` 字符串目标 + 反射/字段访问（**字符串引用编译期不查**） |

②③ 的脚本：`%TEMP%\diff_vehicle_classes.py`、`%TEMP%\diff_vehicle_members.py`；
中间产物 `_tmp_vehicle_class_diff.txt`、`_tmp_vehicle_member_diff.txt`（工作区根）。

### 3.2 检查结果

| 层 | 结果 |
|---|---|
| ① 编译 | ✅ `:compileJava` 通过（无 error，仅既有 deprecation 提示）；mixin AP 正常写 refmap；`:jar`/`:jarJar`/reobf 全完成 |
| ② 类级 | **删除 = 0**；新增 = 7；修改 = 20（类总数 575 → 582） |
| ③ 成员级 | **缺失成员 = 0，新增成员 = 0** —— 20 个被改类**只是方法体内部实现变化，签名零变更** |

**新增的 7 个类**（均为"船舶"新功能，与 rvp 无交集）：
```
entity/vehicle/VesselVehicle
custom/vehicle/VesselVehicleData(Pojo / $VesselVehicleAttributes)
client/resource/vehicle/VesselVehicleDisplay
client/render/animation/context/VesselVehicleContext
mixin/client/ParticleEngineAccessor          ← 本体自己的 accessor mixin
```

**被修改的 20 个类**（含 rvp 关注点：`AbstractVehicle`、`LocalVehiclePlayer`、
`client/render/entity/weapon/RocketPropelledEntityRenderer`、`PhysicsEngine`、`ClientSetupHandler`、
`client/render/animation/context/VehicleContext`、`item/*`、`all/All*` 注册表等）
—— 成员签名**全部未变**。

### 3.3 结论

> **rvp 的 74 个 mixin（31 公共 + 43 客户端）与全部公共 API 调用，均不需要随本次本体更新而修改。**

理由：类无删除、被改类无签名变化 → mixin 的 `method=` / `@Accessor` 字符串目标与 API 调用点全部保持有效；
编译通过进一步证明类引用与 API 签名成立。

**仍需实机验证的部分**（静态检查覆盖不到）：
- 本体的**方法体行为变化**是否改变了 rvp 依赖的时序/语义（本次 20 个类的实现均有改动）；
- 本体新增 `mixin/client/ParticleEngineAccessor` 等自身 mixin 是否与 rvp 的 mixin **注入点冲突**
  （如双方注入同一方法的不同位置，可能触发 mixin apply 失败或行为叠加）。
