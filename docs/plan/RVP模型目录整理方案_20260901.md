## 1. 目标与范围

`assets/rvp/models/bedrock/entity/` 目前把**载具模型、弹体（弹药）模型、挂架模型**堆在同一层（58 个松散 JSON）；
`assets/rvp/textures/entity/` 同样混放（40 张松散 PNG）。本方案：

1. 弹体模型移入 `entity/ammo/`（该子目录已存在，且有 4 个模型已在内、线上引用正常）；
2. 挂架模型移入新建的 `entity/weapon_mount/`；
3. **同步改写所有引用这些模型路径的 JSON**（display 与 vehicle data 两类引用点）；
4. 弹体贴图移入 `textures/entity/ammo/`（该子目录已存在且有 3 张已在内）并同步改写引用；
5. 载具模型/贴图暂留根目录（可选二期再做 `vehicle/` 子目录）。

**明确不在本次范围**（调研确认互不影响，无需改动）：

| 资产 | 位置 | 与本次移动的关系 |
| --- | --- | --- |
| 结构模型（受击/命中箱） | `data/rvp/models/bedrock/vehicle/*.structure.json`，引用形如 `rvp:vehicle/abramsx` | **独立命名空间**（`rvp:vehicle/*` → `models/bedrock` + `.structure.json` 后缀），与 `entity/` 渲染模型互不引用，**不涉及**。也就不触发 agents.md 的"结构模型修改铁律"——本次只移动文件、只改 `model` 字段字符串，不动任何骨层级/pivot/cube |
| 骨骼动画 | `assets/rvp/animations/bedrock/entity/*.animation.json`，引用形如 `rvp:entity/96l6.animation` | 动画在**独立目录**（`animations/`，非 `models/`），不受影响。注意：动画引用路径与模型路径同名不同根，不要顺手改动画路径 |
| 载具贴图（被弹药 display 直接引用） | `textures/entity/{ah64,j15,j15t,UCAVLauncher}.png` 等 | **按约定保留原地**（§4.3）：这些是载具贴图，弹药 display 直接引用它们（弹体模型 UV 映进载具贴图集） |

## 2. 引用机制（调研结论）

### 2.1 模型如何被引用

display/data JSON 中的 `"model"` 字段值 `"rvp:entity/<路径>"` 按命名空间 + 相对路径解析到
`assets/rvp/models/bedrock/<路径>.json`。因此**移动文件 = 把引用字符串同步改成新相对路径**：

```jsonc
// 移动前：assets/rvp/models/bedrock/entity/missile_pl_12.json
"model": "rvp:entity/missile_pl_12"
// 移动后：assets/rvp/models/bedrock/entity/ammo/missile_pl_12.json
"model": "rvp:entity/ammo/missile_pl_12"
```

子目录引用**已在线上验证可用**：`ammo/`（如 `kd_88a.json` → `rvp:entity/ammo/missile_agm_kd88a`）
与 `lod/`（如 j20a LOD）都在正常工作。

### 2.2 引用点只有两类（已全量交叉核对 64 个模型文件）

| 引用点 | 涉及本次移动 | 说明 |
| --- | --- | --- |
| `assets/rvp/display/weapon/*.json`（武器 display） | ✅ 34 个文件 | 弹体模型（飞行的导弹/炸弹/火箭模型） |
| `assets/rvp/display/decoration/entity/*.json`（装饰物 display） | ✅ 9 个文件 | 挂架模型（装饰物系统） |
| `data/rvp/vehicles/{j15,f22a,rafale,j10c}.json`（载具数据，custom mount 的 `model` 字段） | ✅ 4 个文件 | 挂架模型（机挂渲染） |
| `assets/rvp/display/vehicle/*.json`（载具 display） | ❌ 不涉及 | 引用的是载具模型，本次不移 |

### 2.3 容易误判的引用（不受影响，脚本会自动跳过）

- `ywzj_vehicle:` 前缀的 model（如 `pl_15.json` → `ywzj_vehicle:entity/missile_pl_12`、
  `bmpt_9m120_f.json` → `ywzj_vehicle:entity/missile_akd10`）：指向**本体模组自带模型**，
  解析到本体 jar 的 `models/bedrock/`，与 rvp 包内同名文件无关。
- Java 代码零引用：RVP 渲染器只按 display JSON 的 `model` 字段取模型（`RVP_BedrockModels`
  白名单已删除），无硬编码模型路径，不需要改代码。

## 7. 实施步骤

1. **前置确认**：本文档 §4 移动清单、§6 孤儿处置获得确认。
2. **执行迁移脚本**（默认 dry-run，先看报告再落盘；本机 `python` 是 3.6、`python3` 是商店空壳，
   **用 `py -3`**，与 `scripts/` 下其他 migrate 脚本一致）：
   ```bash
   cd D:/ywzj/ywzj/ywzj_rvp
   py -3 scripts/migrate_model_dirs.py            # dry-run：打印移动与改写计划
   py -3 scripts/migrate_model_dirs.py --apply    # 实际执行
   ```
   脚本职责（`scripts/migrate_model_dirs.py`，已写好）：
   - 按 §4 映射表移动模型文件（git 环境下等价 rename，历史可追溯）；
   - 对 §4.2 全部引用文件做**精确字符串整词替换**（`"rvp:entity/旧名"` → `"rvp:entity/新路径"`，
     保留原 JSON 格式与缩进，避免整文件重排产生噪声 diff）；
   - 跳过 `ywzj_vehicle:` 前缀引用（§2.3）；
   - 输出孤儿模型报告（零引用清单，供 §6 决策），**不自动删除任何文件**。
3. **run 目录同步（本次按约定跳过）**：三个运行副本的 rvp 包仍是过期 0.5.7（且含 `abramsx - 副本`、
   错放位置的 `*.animation.json` 等垃圾）。dev 环境没有"从 jar 安装"链路（`src/main/resources/rvp`
   已不存在，installer 只对发布 jar 生效），游戏直接读 `<gamedir>/limitless_vehicle/rvp/`——
   **需要进游戏验证整理效果时**，记得把仓库包全量复制过去（不要增量合并）。
4. **递增版本**：按 `docs/README.md` 约定，发布/覆盖安装前把 `limitless_vehicle/rvp/vehicle_pack.meta.json`
   的 `version` 递增（当前仓库包 0.5.8 → 建议 0.5.9）。
5. **提交 git**：一个独立 commit（"整理：载具包模型目录 ammo/weapon_mount 子目录化"），
   便于整体回滚。

### Blockbench 工作流注意

模型文件是 Blockbench 导出产物。移动后 `.bbmodel` 工程里的**导出路径**（Export → 保存位置）
需要各自重新指向新子目录，否则下次导出会写回旧位置、出现"复活"的旧路径文件。本次迁移不碰 bbmodel。
