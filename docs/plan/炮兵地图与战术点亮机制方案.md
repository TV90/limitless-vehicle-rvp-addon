# 炮兵地图与战术点亮机制方案

## 1. 目标

基于现有 `RVP_TacticalMapScreen` 做一套炮兵专用地图，满足以下需求：

1. 底图、缩放、拖拽、实体点亮、图标渲染机制与战术地图保持一致。
2. 炮兵地图界面更简洁：
   - 不显示战术地图顶部那排按钮；
   - 不显示 `RADAR` 面板；
   - 不显示 `GPS` 面板；
   - 不需要右键菜单、雷达表格、GPS 录入框等复杂交互。
3. 炮兵地图打开时，玩家依然能操控载具炮塔俯仰与射击。
4. 炮兵地图在地图上渲染当前武器的 `CCIP` 落点，优先支持火箭弹和炸弹。
5. 在武器 `RVP_MiscData` 下增加参数 `artillery_map`，当其为 `true` 时，若当前选中该武器，按打开地图键默认进入炮兵地图。
6. 补强战术地图点亮规则：
   - 友军自动点亮；
   - 雷达扫到点亮；
   - 自身携带/链入无人机点亮；
   - 地面载具开火后 5 秒内，被 1000m 内其它载具点亮；
   - 被标记点亮（先做占位数据链）。

## 2. 现状调研

### 2.1 战术地图主入口

当前地图打开入口在：

- [RVP_ClientEvents.java](D:/ywzj/ywzj/ywzj_rvp/src/main/java/org/ywzj/rvp/client/RVP_ClientEvents.java)

现状逻辑：

- `OPEN_GPS_PANEL` 按键直接 `mc.setScreen(new RVP_TacticalMapScreen())`
- 但在这之前有一条关键判断：

```java
if (mc.screen != null) {
    return;
}
```

这意味着一旦打开任意 `Screen`：

1. `RVP_ClientHitlState.tick(...)` 不再运行；
2. `RVP_ClientHmdState.checkIrHmd()` / `tick()` 不再运行；
3. `RVP_WeaponFireController.syncClientInput()` 不再运行；
4. Bomb / Rocket CCIP 客户端刷新链也会停掉；
5. 一些雷达锁定辅助状态也会停掉。

结论：

- 炮兵地图如果仍然作为普通 `Screen` 打开，**必须在 `ywzj_rvp` 侧对若干客户端 tick 链路做“白名单放行”**，否则无法实现“开图仍可控炮、射击、刷新 CCIP”。

文件：

- [RVP_ClientEvents.java](D:/ywzj/ywzj/ywzj_rvp/src/main/java/org/ywzj/rvp/client/RVP_ClientEvents.java)

  - 放行 CCIP 刷新；
  - 放行必要的雷达/HMD/辅助状态；
  - 对鼠标交互做区域化处理，避免地图拖拽与控炮冲突。

## 3. 推荐实现结构

## 3.1 不建议直接复制一份 `RVP_TacticalMapScreen`

原因：

1. 现有战术地图体量很大；
2. 复制会导致后续：
   - 图标修复要改两份；
   - 点亮规则要改两份；
   - HBM / ammo / radar / GPS 兼容也要改两份。

更稳的结构应是：

1. **抽出共享地图画布基类/共享渲染器**
2. 基于模式切换出：
   - `TacticalMap`
   - `ArtilleryMap`

### 建议拆法

新增：

1. `RVP_AbstractMapScreen`
   - 管地图视野、拖拽、缩放、世界坐标换算
   - 管通用 marker 渲染
   - 管通用 visibility / reveal 收集
2. `RVP_TacticalMapScreen`
   - 保留现有完整 UI
3. `RVP_ArtilleryMapScreen`
   - 只保留简化 UI
   - 额外渲染 CCIP 落点
   - 允许控炮/射击透传

如果不想一下子大重构，也可以先走过渡方案：

1. 第一阶段先新增 `RVP_ArtilleryMapScreen`
2. 内部局部复用 `RVP_TacticalMapScreen` 的渲染辅助方法
3. 第二阶段再抽公共基类

考虑到你现在更在意“先能用、别改炸”，推荐：

- **先做过渡版 `RVP_ArtilleryMapScreen`**
- 但从一开始就把“点亮来源收口”单独抽 helper，避免后面再返工

## 4. 炮兵地图建议行为

## 4.1 打开条件

按下现有地图键时：

1. 读取当前 `WeaponUnit`
2. 读取当前武器 `RVP_WeaponData`
3. 若 `weapon.getData().getMiscData().isArtilleryMap()` 为 `true`
   - 打开 `RVP_ArtilleryMapScreen`
4. 否则
   - 打开 `RVP_TacticalMapScreen`

这样不需要新增键位，行为也符合“选炮兵武器默认进炮兵地图”的需求。

---

## 4.2 炮兵地图界面建议

建议保留：

1. 地图底图
2. 缩放滚轮
3. 拖图
4. 中心回正/跟随自身这两个最基础操作
5. 当前载具、自身、友军、被点亮敌军、飞行弹药图标
6. 当前武器 CCIP 落点

建议去掉：

1. 武器下拉框
2. Radar 面板按钮和整个右侧 Radar 面板
3. GPS 面板按钮和整个右侧 GPS 面板
4. 右键上下文菜单
5. 雷达行表格
6. 地图右键 GPS 快速标记

这样可以把它做成“几乎只有地图画布本体”的简洁地图。

---

## 4.3 开图后仍能控炮与射击

这是最大风险点，建议分两层做。

### 第一层：客户端 tick 白名单放行

在 `RVP_ClientEvents` 里，不再简单以 `mc.screen != null` 一刀切 return，而是改成：

1. 若当前屏幕不是 RVP 地图类，保持原行为；
2. 若当前屏幕是 `RVP_ArtilleryMapScreen`：
   - 仍允许执行：
     - `RVP_ClientHitlState.tick(...)` 中和炮兵武器相关的部分（如无关可不放）
     - `RVP_WeaponFireController.syncClientInput()`
     - Bomb / Rocket CCIP 更新
     - `RVP_ClientSaclosState.tick(...)`（若你希望激光炮兵武器在炮兵图内也能工作）
3. `RVP_ClientRadarLockState.tick()` 同理，对 `RVP_ArtilleryMapScreen` 放行而不是直接 `clear()`

### 第二层：地图交互区域化

炮兵地图的鼠标行为建议如下：

1. 鼠标在地图内：
   - 中键/滚轮用于缩放；
   - 左键拖图；
   - 不触发武器射击；
2. 鼠标不在地图内：
   - 不消费左键；
   - 让武器射击输入继续通过 `AllKeys` 走；
3. 炮塔俯仰/转向：
   - 不建议依赖“鼠标移动直接传给游戏视角”
   - 更稳的是允许**键盘控炮**持续生效；
   - 若要在地图打开状态下继续吃鼠标转塔，需要额外研究 `MouseHandler` / `LocalVehiclePlayer` 这一层，复杂度明显更高。

### 结论

第一版建议定义为：

- **开炮兵图后保证键盘控炮、武器发射、CCIP 刷新可用**
- 鼠标主要用于地图操作

如果你后面坚持“炮兵图打开时鼠标仍能拖塔”，那就属于第二阶段增强项。

## 5. CCIP 落点在炮兵地图上的实现

## 5.1 数据来源

直接使用：

- `LocalVehiclePlayer.instance.getWeaponUnit().weaponHitPos`

和其插值前值：

- `weaponHitPosO`

优点：

1. 不需要新包；
2. 与现有 HUD/准星使用同一份解算结果；
3. 炸弹和火箭弹都已经接好了。

---

## 5.2 渲染方式建议

炮兵地图上增加一个专用 marker：

1. 若当前选中武器满足：
   - `weapon kind == BOMB` 且 `CCIP`
   - 或 ballistic rocket 且有 `weaponHitPos`
2. 则在 `weaponHitPos.x / z` 对应地图位置画一个炮兵落点标记

建议样式：

1. 与 HUD 的 `CCIP` 圈不同，不做大圈；
2. 地图上改为：
   - 十字
   - 外圈虚线小环
   - 可附一条从载具到落点的细虚线

这样更像炮兵射击诸元图，而不是 HUD 准星。

## 7. 战术地图点亮机制改造建议

## 7.1 现有规则

当前等价于：

1. 自己/友军实时可见；
2. 敌对仅雷达点亮。

## 7.2 目标规则

统一改为 5 种来源：

1. `FRIENDLY_REVEAL`
2. `RADAR_REVEAL`
3. `UAV_REVEAL`
4. `FIRE_REVEAL`
5. `MARK_REVEAL`

建议新增一个统一 helper，例如：

- `RVP_TacticalRevealHelper`

职责：

1. 收集某个观察者载具当前的全部 reveal source
2. 输出 `Set<Integer> visibleIds`
3. 供：
   - 战术地图
   - 后续炮兵地图
   - 以后其它态势 UI
   共同复用

这样以后就不会继续把逻辑堆在 `RVP_TacticalMapScreen.refreshTacticalRadarContext()` 里。

## 7.3 地面载具开火暴露

### 目标规则

1. 仅地面载具参与；
2. 开火后暴露 5 秒；
3. 被 1000m 内其它载具点亮；
4. 只影响地图显示，不等于雷达锁定。

### 推荐实现

#### 服务端

利用现成事件：

- [VehicleFireEvent.Post](D:/ywzj/ywzj/ywzj_vehicle/src/main/java/org/ywzj/vehicle/api/event/VehicleFireEvent.java)

在 `ywzj_rvp` 新增服务端记录器，例如：

- `RVP_FireRevealService`

记录：

1. `vehicleId`
2. `dimension`
3. `lastFireGameTick`
4. `sourcePos`
5. 可选：`revealRadius`

事件触发时：

1. 判定 `event.getVehicle()` 是否地面载具；
2. 若是，则写入最近开火时间。

#### 客户端地图侧

有两种方案：

### 方案 A：服务端同步 `fire reveal snapshot`

优点：

- 最准确；
- 观察者不需要自己扫周围所有实体判断。

缺点：

- 需要额外网络包。

### 方案 B：轻量客户端近似

通过现有可见实体/同步实体，再配合服务端打标过来的短生命周期状态。

综合来看，推荐：

- **服务端维护**
- **客户端吃一个小型 snapshot**

因为“谁对谁可见”本来就是服务端态势信息，后续做“标记点亮”也更顺。

---

## 7.4 被标记点亮

当前先做占位，不做完整交互。

建议现在就把数据模型预留成与 `fire reveal` 平行的一类：

1. `markedEntityId`
2. `expireTick`
3. `dimension`
4. 可选 `sourceVehicleId`

第一阶段可不提供 UI 和指令，只要：

1. helper 支持吃 `MARK_REVEAL`
2. packet / state 容器预留接口

这样后面补“标记”时就不用再改地图显示总线。

## 8. 推荐开发顺序

### 阶段 A：最小可用炮兵地图

1. `RVP_MiscData` 加 `artillery_map`
2. 新增 `RVP_ArtilleryMapScreen`
3. 复用战术地图底图/缩放/实体渲染
4. 去掉雷达/GPS 面板与复杂按钮
5. 地图打开链路按当前武器决定进战术图还是炮兵图

交付结果：

- 能打开炮兵地图
- 能看地图、缩放、拖拽

### 阶段 B：CCIP 地图落点

1. 炸弹/火箭读取当前 `weaponHitPos`
2. 在地图渲染 CCIP marker
3. 做基础插值和平滑

交付结果：

- 炮兵图上能看到当前武器落点

### 阶段 C：开图不断控炮

1. `RVP_ClientEvents` 对 `RVP_ArtilleryMapScreen` 放行必要 tick
2. `RVP_ClientRadarLockState` 对炮兵图放行
3. 武器输入、开火、CCIP 刷新保持工作
4. 限制地图控件只在地图区域消费鼠标

交付结果：

- 开图仍能发射和更新落点

### 阶段 D：点亮机制收口

1. 新增 `RVP_TacticalRevealHelper`
2. 将友军/雷达/UAV 逻辑收口
3. 炮兵图和战术图共同改吃 reveal helper

交付结果：

- 两张图点亮链一致

### 阶段 E：开火暴露

1. 服务端记录地面载具开火状态
2. 同步 `fire reveal` 快照
3. helper 合入 `FIRE_REVEAL`

交付结果：

- 地面载具开火 5 秒暴露

### 阶段 F：标记暴露占位

1. 预留 `MARK_REVEAL` 数据结构
2. helper 接入

交付结果：

- 标记逻辑后续可直接接入

## 9. 风险点

## 9.1 最大风险：`mc.screen != null` 全局拦截

这是炮兵地图和普通战术地图最大的分水岭。

如果不改：

1. 开图后可能无法持续发射；
2. `CCIP` 落点不更新；
3. 雷达辅助状态不更新；
4. 部分导引/激光状态也可能停摆。

所以这个不是 UI 细节，而是核心链路问题。

---

## 9.2 鼠标拖图与鼠标控炮冲突

如果你后面想做到“鼠标在地图上还能同时拖塔”，就一定会产生冲突：

1. 鼠标移动到底给地图，还是给炮塔？
2. 左键到底是拖图，还是开火？

所以第一版更合理的定义应是：

- 地图区域内鼠标服务地图；
- 炮击靠键盘控炮 + 开火键；
- 以后再讨论更复杂的交互模式切换。

---

## 9.3 可见性来源继续写死在 `RVP_TacticalMapScreen`

如果继续把“开火暴露”“标记暴露”硬写进 `RVP_TacticalMapScreen`：

1. 炮兵地图还要再抄一遍；
2. 后续态势图功能会越来越散；
3. debug 非常痛苦。

所以这次最好顺手把 reveal source 收口。

---

## 10. 结论

这套需求完全可做，而且**不需要改 `ywzj_vehicle` 本体**，只在 `ywzj_rvp` 落地即可。

最合理的路线是：

1. 新增 `RVP_ArtilleryMapScreen`
2. `RVP_MiscData.artillery_map` 控制默认打开类型
3. 使用当前 `weaponHitPos` 直接渲染炮兵地图 `CCIP`
4. 将点亮逻辑抽成统一 reveal helper
5. 服务端补地面载具开火暴露
6. 标记暴露先预留数据链

如果马上开始做，建议按：

1. 炮兵图壳子
2. CCIP 地图落点
3. 开图不断控炮
4. 点亮收口
5. 开火暴露

这个顺序推进。

## 11. 实际实现补充：偏航优先瞄准（2026-08-29）

### 11.1 问题与根因

炮兵地图原先在每次逆 CCIP 解算后直接调用本体 `WeaponUnit.aim(...)`。该方法会递归把同一个世界瞄准点同时下发给父武器站和子武器站；以 M142 为例，父 `seat` 控制偏航、子 `launcher` 控制俯仰，因此移动地图瞄准点时两轴会同时追踪。父级偏航尚未到位时，子级局部坐标持续随父级旋转变化，表现为发射架俯仰上下跳动。

此外，鼠标移动会持续产生新目标。旧实现通过把 `solution` 设为 `null` 使解算失效，在两次限频解算之间，`LocalVehiclePlayer.tickAim()` 会短暂回落到普通视线瞄准，也会覆盖炮兵目标角并加重跳动。

### 11.2 两阶段控制

实际火控采用目标版本驱动的两阶段状态机：

1. 地图目标或高/低弹道模式变化时递增目标版本；旧解算可以暂存以维持控制连续性，但不得作为最新解显示，也不得据此释放俯仰。
2. 首次进入等待阶段时，捕获操作武器站及其子武器站的**当前实际俯仰角**。连续移动目标期间沿用这组锁定角，不重复捕获。
3. 弹道重算期间继续覆盖普通视线瞄准：俯仰保持锁定，偏航直接按最新地图目标移动，不必等待逆 CCIP 搜索结束。
4. 最新目标版本已有解算结果，且根操作武器站的实际偏航与目标偏航的最短环绕误差不超过 `0.5°` 时，解除俯仰锁并调用本体递归瞄准应用完整弹道解。
5. 已解除后若目标再次变化，则从当时的实际俯仰重新开始上述流程。

### 11.3 同步与兼容

- 锁定阶段使用本体公开的旋转 setter 设置目标角，实际骨骼仍按载具 JSON 中的 `x_rot_speed` / `y_rot_speed` 平滑转动。
- 每次目标角发生变化后调用本体 `updateWorldAimVec()`，确保射击方向、火控状态和显示一致；随后复用本体 `ClientVehicleAction` 同步服务端，不增加 RVP 网络协议。
- 只处理 `rotByAim` 武器站，并递归覆盖与本体 `WeaponUnit.aim(...)` 相同的子武器站范围。
- 根武器站没有可动偏航轴时不启用门控：最新解算完成后沿用原来的同时瞄准行为，避免固定挂架永久等待。
- 换车、换武器、退出炮兵地图或失去有效炮兵上下文时清理捕获角和门控状态。

### 11.4 显示与射击语义

- 炮兵状态栏的 `Snapshot` 只认可目标版本一致的解算结果，因此不会把旧目标的仰角显示在新目标上。
- 本次只改变瞄准轴的动作顺序，不增加射击门控；回转或俯仰运动期间仍按原规则允许开火。
- 未新增 JSON 字段、Mixin 或结构模型修改，`artillery_map` schema 保持不变。

### 11.5 回归验证

使用 M142 分别横向、纵向和斜向连续移动地图瞄准点，并切换高/低弹道：目标变化后发射架应立即停止俯仰，炮塔持续追踪最新偏航；偏航到位后发射架才平滑转向新仰角，全程不得上下跳动。自动化测试覆盖大偏航误差、`±180°` 环绕、`0.5°` 释放、连续更新不重捕获、再次移动重新捕获、等待最新解算和固定挂架旁路。
