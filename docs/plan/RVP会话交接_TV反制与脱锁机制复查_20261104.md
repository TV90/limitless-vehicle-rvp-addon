## 1. 新发现：DIRCM 后 TV 禁止重指定倒计时卡死

实际当前数值在 `dircm/RVP_DircmRuntimeManager.java:49`：

- TV 致盲：60 tick（20 TPS 下 3 秒）。
- 指令线 HITL 致盲：120 tick（6 秒）。
- 两种弹的禁止重新指定：120 tick（6 秒）。

`RVP_DircmRuntimeManager.tickJammedProjectile` 在 505 行递减 `dircmNoRedesignateTick`，随后才检查 `dircmJammed`。这个 helper 内部意图是让两个计时独立运行。

但调用它的 `event/RVP_DircmEventHandler.java:75` 有外部条件：

```java
if (entity instanceof RVP_BaseBullet bullet && bullet.dircmJammed) {
    RVP_DircmRuntimeManager.tickJammedProjectile(bullet);
}
```

到第 60 次推进，TV 的 `dircmJammed` 被清为 false，禁指定剩余 60。之后事件入口不再调用 helper，剩余计时永远没有自然递减机会。`RVP_MissileEntity` 的实体、OBB、坐标指定入口都拒绝 `dircmNoRedesignateTick > 0`。

实际生产事件入口的复现结果，四款 TV 相同：

| 事件推进次数 | dircmJammed | dircmJamRemainTick | dircmNoRedesignateTick |
| --- | --- | --- | --- |
| 60 | false | 0 | 60 |
| 120 | false | 0 | 60 |
| 180 | false | 0 | 60 |

第 180 次后调用真实实体/坐标指定 setter，均被拒绝。对应玩家体验是白闪已经退去，后续重新锁定或指定地面始终不起作用；本地 HUD 还可能先显示“已锁”，更加混乱。

指令线弹的致盲与禁指定恰好同为 120 tick，到干扰结束时两个值都已经为 0，因此未触发这个卡死。本轮检验 `z10_cm502_mil`、`j16_tl17`、`ucav_switchblade`，均恢复手控制导。

DIRCM 初次中断本身没有烟雾那种实体残留：`applyJam` 的 410–418 行确实清目标、清制导记忆、清主动导引头指定，再设置地面替代点；`RVP_GuidanceRuntimeController.java:32` 在 DIRCM 标志下先偏转再返回，不进入惯导回退。恢复时 533–535 行再次清目标和记忆。本轮验证了旧目标不会借记忆继续被追踪。

## 2. 高速脱锁：单独正常，叠加烟雾会绕过

设定来源 `config/RVP_Config.java:50`：

- `guidance.hitlTvBreakLockTargetSpeedKph` 默认 72.0，0 为关闭；当前实际注册是 SERVER 配置 `ywzj_rvp-server.toml`，旧说明中的 common 字样已过时。
- 使用三维 `getDeltaMovement().length() * 72`，单位为 km/h；严格大于阈值才脱锁，恰好 72 不脱锁。下落、爬升速度也计入三维模长。
- 本体车辆 `aiStep` 使用同一格/tick 速度作位移，相关 HUD 也乘 72；没有把 m/s 与格/tick 混用。地面 HUD 有使用水平速度的显示，所以纯垂直分量可能使显示值与该门限读数不同，这是原文档明确的三维口径。
- 只读检查 A1 测试客户端 saves/defaultconfigs，找到的 12 份包含此字段的配置均为 72.0。没有修改任何配置，也不据此推断当前打开的是哪个存档。

`guidance/runtime/RVP_RuntimeHitlTvGuidanceSource.java:46` 触发后调 `RVP_MissileEntity.rvp$markHitlSpeedBreak`（282 行），真正执行 `setTargetEntity(null)`，随后 `setTargetPos(lastTrackedPos)`。因此不再有实体实时记忆刷新。

原生 M1A2SEP 选中 `Key[bone=turret,index=0]`，四款 TV × 活跃/退出两种状态全部通过：阈值下及等于阈值时保留实体；略高于阈值时释放实体并冻结所选 OBB 坐标；目标再横移 5 格，冻结点不变；再次指定高速实体会再脱锁、改用这一次的位置；目标自行降速不会自动恢复实体锁。测试的重新指定仅验证速度判据，没有用此结果声称退出真实远程会话后仍能操作。

叠加烟雾时问题在执行顺序：先 `validateEntity`，只有 valid 非 null 才执行速度分支。烟雾使 valid=null，于是速度闸门被跳过；TV 分支不清实体的旧 bug 又使实时惯导继续。

原生复现四款 TV 相同：M1A2SEP 三维速度设置为 1.1 格/tick（79.2 km/h），目标在烟内横移 3 格，`targetEntity` 仍保留，记忆点横移约 3.0000001 格。不能宣称烟雾与速度反制已经互相独立、叠加正常；应在恢复光学跟踪状态机时一起修复。

## 3. 共用 HUD 不同步

`RVP_ClientHitlState.java:473` 指定时先更新本地实体 ID / OBB，再发送请求；服务器接纳与否没有反馈到这个本地锁。

- 速度脱锁只发送 action-bar 提示，未让客户端清目标。
- `onHitlDircmJam`（157 行）只更新白闪布尔及剩余计时，不清本地指定目标，也没有同步剩余禁止重指定时间。
- `RVP_ClientSaclosState.tickHitlDesignate`（76 行）继续根据本地实体 ID / OBB 计算移动目标点。
- `RVP_HitlDesignateOverlay` 仅因无线电 blocked 等条件隐藏，不以 DIRCM/服务器确认锁定为准。

故服务器真实脱锁、请求被 DIRCM 拒绝时，客户端斜十字仍可能跟着目标走。这部分为源码调用链确认，本轮没有另开图形客户端验证画面。

附带只读核对了无线电/主动 ECM 链路：当前 `RVP_MissileEntity.tickGuidance` 在 blocked/severed 时先返回，位于父类实体记忆更新和运行时惯导之前；没有在这条门后发现与烟雾相同的惯导继续执行路径。这仅是入口审计，不代表完整链路恢复/网络场景验收。
