> **状态：根因已定位并已落修**——2026-09-14 静态排查确认根因是渲染器门控在客户端恒为假、
> 尾焰分支从未执行（详见 §〇）；修法已落码（`./gradlew build` 编译通过），**待实机复测**。
> 参数字段（`engine_nozzle_offset` / `flame_scale`）保留，修好后即生效。
> 需求来源：本体给导弹加了尾焰动画，RVP 导弹想要相同观感。

## 〇、根因结论（2026-09-14 静态排查定案）

**根因：`RVP_BedrockProjectileEntityRenderer.renderMotorFlame` 的门控 `data == null` 在客户端恒为真，
函数每次都在第 91 行提前 return，尾焰渲染代码从未被执行。**

### 证据链

1. `rvpData` **只在服务端赋值**：`RVP_BaseBullet.initFromWeapon()` 第 585 行 `this.rvpData = data;`，
   调用方是开火链路（服务端）。客户端不经过该路径。
2. 客户端 `readSpawnData()`（第 4381 行起）只同步标量：`weaponKind` / `xRot` / `yRot` / `deltaMovement` /
   `flightSpeed` / **`motorBurnEndTick`** / `coldLaunchTimeTick` / `coldLaunchVelocity` / `showMslIndicator` /
   `signatureSize` / `irSeekerGraceUntilTick` …… **不包括 `rvpData`**。
3. 源码两处注释自证：第 595 行「计算发动机熄火 tick，供客户端尾焰控制（**rvpData 不传客户端**）」；
   第 4160 行 `isMotorBurning()`「**客户端 rvpData 为 null**，用生成数据包同步的 motorBurnEndTick」。
4. 因此渲染器第 91 行 `data == null || ...` 在客户端**第一个条件即为真** → 直接 return
   （并顺手清掉 runner 缓存）。`isMotorBurning()` 里精心写的客户端同步分支（`motorBurnEndTick`）
   在渲染路径上**永远不可达**。
5. 与"编译/冒烟通过但实机无尾焰"完全吻合：服务端跑不到渲染分支，纯编译期无法发现恒假门控。

### 其余五个嫌疑方向的判定

| # | 嫌疑 | 判定 | 依据 |
|---|---|---|---|
| 1 | `isMotorBurningNow()` 客户端判定 | **非根因**（但被上面门控挡在门外） | `motorBurnEndTick` 已在 spawn 数据中同步；`getFlightTickCount()` 基于 vanilla `Entity.tickCount`（双端自增），客户端可用 |
| 2 | `AnimationRunner` 创建时机 | **排除** | 本体 `RocketPropelledEntityRenderer` 也是从实体字段读 runner（本体在 `readSpawnData` 创建）；RVP 在渲染器懒创建等价，且 `LoopingState(System::nanoTime)` 与创建时刻无关 |
| 3 | `InternalAssets` 三件套加载时机 | **排除** | `InternalAssets.apply()` 对模型与动画都用 `orElseThrow`（第 77 / 81 行）——要么非空，要么整个资源重载抛异常；渲染器里的 null 检查是**死代码** |

| 5 | `applyPose/blend` 兼容性 | **低嫌疑，待修后复测** | 与本体共用同一份 `PoseBlenders.BLENDER` 与同一套 `VehicleBedrockModel`；本体同路径工作正常 |

## 一、本体实现（调查结论）

尾焰是**模型+动画渲染**，不是粒子。三层：

1. **资源**：本体 jar 内置"尾焰三件套"（`InternalAssets` 全局加载，**不在武器文件里**）：
   - `models/bedrock/effect/rocket_motor_flame.json`（模型，命名空间 `ywzj_vehicle:effect/rocket_motor_flame`）
   - `animations/bedrock/effect/rocket_motor_flame.animation.json`（循环动画）
   - `textures/effect/rocket_motor_flame.png`（贴图）
   源码位置：`default_vehicle/assets/ywzj_vehicle/`（构建时打进本体 jar）。
2. **实体侧（客户端）**：`MissileEntity.readSpawnData` 创建 `AnimationRunner(flameAnimation, context)`
   + `LoopingState(System::nanoTime)` 循环，public 字段挂在弹体；显示门控 `isMotorBurning()`。
3. **渲染**：`RocketPropelledEntityRenderer.render`——super 画弹体模型后：
   `runner.tick()` → `applyPose(blend(bindPose, evaluate()))` → 绕实体 yaw/xRot 旋转 →
   平移 `engine_nozzle_offset`（武器 JSON 配置，惯例 `[0,0,-长度]`，Z- 为尾）→
   缩放 `caliber/1000` → `entityTranslucent + polyMeshCutout` 全亮渲染。

## 二、RVP 实现（资源零成本，不依赖本体导弹基类）

`RVP_BedrockProjectileEntityRenderer`（client 类）追加 `renderMotorFlame`：

- **门控**：`data.getProjectileData().hasRocketEngine()` 且 `projectile.isMotorBurningNow()`
  （两者均为 RVP 侧自有公共 API，与本体 MissileEntity 基类无关——RVP_BaseBullet 继承的是
  本体 AmmoEntity 机炮基类，本体 MissileEntity 的 animationRunner/nozzle 字段不可用也不需要）；
- **资源**：`ClientAssetsManager.INSTANCE.getInternalAssets()` 直取本体三件套（公开全局资源）；
- **动画 runner**：渲染器内 `static WeakHashMap<RVP_BaseBullet, AnimationRunner>`，每发弹
  客户端实例一个循环 runner，弹体销毁弱引用自动清理；不进公共类（Mixin 纪律/dist 安全）；
- **变换**：照搬本体公式（`-entityYaw` → `xRot` 插值 → 喷口平移 → 缩放 → 全亮渲染 + bindPose 复原）；
- **默认喷口 `[0,0,-1.2]`、缩放 `0.2`**：本体典型空空弹（pl_8）量级的固定默认值；
  不使用 `AmmoEntity.getCaliber()`（RVP 未覆写，默认 5.8 不可用）。

### 适用范围 / 参数（2026-09-14 定版）
- 所有 `projectile_data.has_rocket_engine: true` 的弹自动带尾焰（用户确认的全量口径）；
- **逐弹可调字段（已落码）**：
  - `projectile_data.engine_nozzle_offset`：`[x,y,z]` 喷口偏移（实体空间，Z- 为弹尾），默认 `[0,0,-0.5]`；
  - `projectile_data.flame_scale`：尾焰缩放，**默认 `0.3`**（2026-09-15 由 `0.2` 上调）。
    语义同本体 `caliber/1000`，即**数值 ≈ 弹体直径（格）**——本体尾焰模型自身直径约 3.09 格
    （`rocket_motor_flame.json`，cube 49.45×49.45 像素），缩放后约为弹径的 3 倍；PL-12 的 `0.2`
    源于其武器 JSON 未配 caliber、被 `MissileEntity.initMissile` 钳制为 200（200/1000=0.2），
    该基准对多数弹体偏细，故上调。PL-12 实际 `engine_nozzle_offset=[0,0,-1.48]` 可作配参参考；
  - **配参示例（9M723，2026-09-15）**：弹径按 `missile_9m723.json` 的 poly_mesh 算得
    （X/Y 跨度 14.7 像素 = **0.92 格**，与真实 9M723 直径 0.92 m 吻合；长 101.775 像素 = 6.36 格），
    本体等比例值为 `0.92`，取 `flame_scale: 1.15`（约 +25%，观感明显更粗）。
- **双脉冲支持**：`isMotorBurning()` 已覆盖二级脉冲窗口（一级燃烧→熄火间隔尾焰消失→
  二级点火重新出现→燃尽消失；客户端无 rvpData 时走同步的 motorBurnEndTick/SECOND_PULSE_* 同样支持）。

### 尾迹参数（2026-09-15 补齐；含上一版结论的更正）

**尾迹有两条独立来源，"更粗"必须分清改哪一条：**

| 路径 | 生成侧 | 使用的配置字段 | 规模 |
|---|---|---|---|
| **客户端本地尾迹** | 客户端 `RVP_BaseBullet.spawnTrailParticles()` → `spawnMissileNativeTrailParticles()`（`tick()` 的 `isClientSide` 分支） | `effects_data.missile_native_trail_*` | 沿路径线段采样，粒子多、是主要视觉来源 |
| **服务端广播** | 服务端 `broadcastTrailParticles()` → `ServerLevel.sendParticles` | `effects_data.trajectory_particle` | `count=3`、`spread=0.1`（导弹仅在燃烧期发） |

> **⚠️ 更正上一版结论**：`trajectory_particle` **不是**"对 `rvp:missile` 完全无效"。
> 准确说法是：**客户端本地尾迹**（`spawnMissileNativeTrailParticles`）只认 `missile_native_trail_*`，
> 确实不看 `trajectory_particle`；但**服务端广播**那条（`broadcastTrailParticles:4237`）用的正是
> `trajectory_particle`。两者条件不同（服务端那条要求 `heavy && motorPropulsion` 时仅燃烧期发）。

**`missile_native_trail_*` 全字段**（`weapon/data/RVP_EffectsData.java`）：

| 字段 | 含义 | 默认 | 上下限 |
|---|---|---|---|
| `missile_native_trail_enabled` | 原生尾迹开关 | `true` | — |
| `missile_native_trail_particle` | 覆盖粒子 ID | 空（营火信号烟） | — |
| `missile_native_trail_density_scale` | 采样**密度**倍率（只增粒子**数量**） | `1` | ≥ 0 |
| `missile_native_trail_step` | 路径采样间距（格），越小越密 | `0.5` | ≥ 0.05 |
| `missile_native_trail_spawn_interval_tick` | 生成间隔（tick） | `1` | ≥ 1 |
| `missile_native_trail_offset` | 相对弹尾偏移（格） | `3` | ≥ 0 |
| **`missile_native_trail_particle_scale`** | **单个粒子渲染尺寸倍率（2026-09-15 新增）** | `1` | ≥ 0 |
| `missile_native_trail_extra_flame` / `_extra_smoke` | 燃烧期追加火焰 / 烟尘 | `true` | — |

**新增参数 `missile_native_trail_particle_scale` 的实现（零 Mixin）**：

原版 `Level.addParticle(...)` 既不返回实例也无法指定渲染尺寸，故走客户端桥自建粒子：

```
RVP_BaseBullet.spawnMissileNativeTrailParticles
  → RVP_ClientActionsAccess.addScaledParticle(options, x, y, z, scale)   // 双端安全桥
      → [客户端] RVP_ClientActions: particleEngine.createParticle(...) 拿到实例 → particle.scale(scale)
      → [服务端] NOOP（服务端无粒子渲染管线；本方法本就只在客户端 tick 调用）
```

关键依据（已核对 1.20.1 源码）：
1. `LevelRenderer.addParticleInternal` 在 `force=true` 时**直接**调 `particleEngine.createParticle(...)`（跳过
   `distanceToSqr > 1024` 距离裁剪）→ 新路径与原 `level().addParticle(options, true, ...)` **等价**；
2. `ParticleEngine.createParticle(...)` 为 public 且返回实例，内部已 `add(particle)` 入待 Tick 队列
   → 调用后立即缩放，顺序安全（队列在后续 tick 才生效）；
3. **`SingleQuadParticle` 覆盖了 `Particle#scale(float)`**，执行 `quadSize *= pScale`（`quadSize` 即单面粒子
   的渲染尺寸）→ 这一个调用就能同时得到"渲染尺寸放大"；注意基类 `Particle.scale` 只改
   `setSize(0.2×scale, ...)`（碰撞盒），**对渲染尺寸无效**，必须确保粒子是 `SingleQuadParticle` 子类；
4. `CampfireSmokeParticle.tick()` 不重设 `quadSize` → 单次缩放可保持到粒子消亡。

**已知限制**：服务端广播那条（`trajectory_particle`）走原版 `sendParticles`，**无法携带尺寸**
→ 若同时开启两条，会出现"本地粗粒子 + 广播细粒子"混合。缓解手段：把 `trajectory_particle` 设为
`none`（或让 `missile_native_trail_particle` 与之一致），只保留统一的本地尾迹。

#### 尾迹粒子风格：接入视觉工厂的自定义烟团（2026-09-15 新增）

原版粒子（营火烟等）作为尾迹的上限很低：只能整体缩放一个 sprite，寿命/颜色/透明度/扩散都不可配。
故新增 **`missile_native_trail_particle_style`**，可取 `rvp_smoke` 换成**视觉工厂体系里的自定义烟团**：

| 取值 | 说明 |
|---|---|
| 空 / `vanilla`（默认） | 用原版粒子（类型由 `missile_native_trail_particle` 指定），尺寸经 `Particle#scale` 缩放 |
| `rvp_smoke` | 用 `RVP_MchrSmokeParticle`——从 MCHR 的 `MCH_EntityParticleSmoke` **逐条移植**的翻滚烟团，也是视觉工厂默认爆炸烟所用的同一粒子类 |

`RVP_MchrSmokeParticle` 为什么比原版粒子合适（源码事实）：

- **尺寸直接烘进构造**：`mchrScale = size × 0.2`、上限 `size × 2.0`、`quadSize = 0.1 × mchrScale`，
  且每 tick `+0.8` 线性扩散到上限 → "翻滚变大"的观感是内置的，`missile_native_trail_particle_scale`
  只需作用在 `size` 上即可，**不依赖原版 `Particle#scale` 的行为**；
- **8 帧横排 UV 自算**（帧 0 实心圆斑 → 帧 7 破碎）：自带消散动画，比单帧 sprite 更像真实尾迹；
- **天空光全亮**（`getLightColor` 固定 `15 << 20`）：不吃方块光，夜里/阴影下尾迹不糊；
- **颜色/透明度/寿命由构造决定**（灰 0.7~1.0、alpha 1.0、寿命 18~84）；
- 渲染走 `RVP_MchrSmokeRenderType`（直接绑 MCHR 的 `smoke.png`，独立于粒子图集）。

**新增入口**：`RVP_MchrSmokeParticle.ofTrailScaled(level, x, y, z, sizeScale)`——观感同 `ofTrailDefault`，
尺寸按倍率缩放。生成路径与视觉工厂爆炸烟一致（直接 `new` 实例 + `particleEngine.add(...)`，
不经 `ParticleType`/provider 查表），故尺寸完全可控：

```
RVP_BaseBullet.spawnMissileNativeTrailParticles
  → style=rvp_smoke ? RVP_ClientActionsAccess.addTrailSmokeParticle(x, y, z, scale)   ← 服务端 NOOP
  → style=vanilla   ? RVP_ClientActionsAccess.addScaledParticle(options, x, y, z, scale)
```

**9M723 配置**：`missile_native_trail_particle_style: "rvp_smoke"` + `missile_native_trail_particle_scale: 2.0`。

> ⚠️ **该风格与「服务端广播」那条仍不统一**：广播路径走原版 `sendParticles`，只能是原版粒子且无尺寸。
> 若实机观感被稀释，把 `trajectory_particle` 设为 `none` 即可（注意 `broadcastTrailParticles` 里
> 还有 1 个/tick 硬编码的 `ParticleTypes.FLAME`，不受配置控制）。

**9M723 最终取值（2026-09-15 定稿，用户决策：只调粗、不增数量）**：

```json
"effects_data": {
  "missile_native_trail_particle_style": "rvp_smoke",   // 用视觉工厂体系的自定义翻滚烟团
  "missile_native_trail_particle_scale": 2.0            // 烟团尺寸 ×2
}
```

`density_scale` / `step` / `offset` **全部保持默认**（1 / 0.5 格 / 3 格），不在 JSON 中显式写出。
理由：靠粒子数量堆密度会让粒子数随速度线性上升（9M723 最高 12 格/tick、燃烧 3000 tick），
而放大单粒子尺寸的观感收益相同却几乎零成本。先前试过的 `density_scale: 1.8 + step: 0.4`
（≈2.25 倍密度）已撤回。

> ⚠️ **实机验证前提**：载具包配置与 mod jar 都必须更新到最新版。
> 2026-09-15 实测实机 `mods/ywzj_rvp-1.20.1-0.5.9-all.jar` 仍是 **09-05** 的旧构建（不含
