public void onUpdate(){

  if(useTick>0) --useTick;
  if(useTick>0) onUsing(); // 每tick repair(maxHP/100)

**查证中发现的两个补充细节（v1 未写，落地时需知）**：

1. **`repair()` 有下限钳位**：`tpd < 1 → 1`（`:2709` 起）——`maxHP < 100` 的载具整除后每 tick 仍回

## 3 RVP 现状对照

### 3.1 载具血量模型（本体 `ywzj_vehicle`）

- 基类 `ContainerCraft.java:39`：`HEALTH / MAX_HEALTH` 为 `EntityDataAccessor<Float>` 同步，`getHealth()/setHealth(Mth.clamp)、heal()、hurtTick/healthO`（`ContainerCraft.java:115-129,92-105`）。
- `AbstractVehicle extends ContainerCraft`：`maxHealth` 源于 `BaseVehicleDataPojo.maxHealth=100` (`vehicle/custom/vehicle/BaseVehicleDataPojo.java:17`)，可在数据包覆写；`isDestroyed()` + `Destroy` NBT。
- `RepairToolItem.java:96-98`：侍服端 `vehicle.setHealth(min(health+max/100, max))` + `partUnit.setHealth(min(health+max/10, max))`，每 `2t` 一次（`tickCount%2==0 && getTicksUsingItem()>8`），客户端仅播 `FIRE_EXTINGUISH` + `FLAME` 粒子。工具耐久 100。
- **结论**：RVP 服端权威血量、已有 `heal / setHealth`，可直接复用；无需引入 `damageTaken` 概念。

### 3.2 骨骼模块 / ERA（RVP）

- 类型 `BoneModuleType.java:13,26`：`ERA`（可被直击/爆炸百分比破坏）、`TRACK/APS/JAMMER/DIRCM/COUNTERMEASURE/ECM_*` 等。`isBlastDestructible()` 仅 `ERA` 为真。
- 服务端状态 `RVP_BoneModuleStateTable.java:21`：以 `vehicle UUID → bone → Set<BoneModuleType>` 记录**失活**集合（内存表，替代被删 Mixin 注入）。
- 持久化 `RVP_EraStateSavedData.java:24`：世界维度的 `SavedData`，新格式 `Map<bone, List<type>>`，兼容旧 `List<String>`。
- 伤害触发 `RVP_VehicleHitboxFactorManager.java:313,405`：
  - 直击 `tryDestroyBoneModules(vehicle, hitboxRes, damage)`，
  - 爆炸 `tryDestroyBoneModulesByExplosion(vehicle, hitPos, radius)`（阈值表百分比破坏，仅 ERA 参与）。
- 同步 `S2CBoneModuleState.java:21` + `RVP_EraStateEventHandler.java:89`：`TrackingEntity` 广播 + 上车全量推送；客户端 `RVP_ClientBoneModuleState.java:22` 存 `INACTIVE_MODULES` + `ERA_DESTROY_TIMES`，供 JS 动画 `isModuleActive()/isEraActive()` 查询、HUD `RVP_HitIndicatorOverlay.java:484` 展示。
- **关键差异**：MCHR 的 ERA 是 `MCH_BoundingBox.isERA` 物理盒，RVP 是**逻辑骨骼模块**；恢复只需操作状态表并广播，无需重建碰撞盒。

**哪些模块会被打掉（2026-09-02 核对 `RVP_VehicleHitboxFactorManager`）**：

- **直击**（`tryDestroyBoneModules:322`）：遍历命中骨上的**全部模块类型**逐一消耗
  （受骨块 `min_trigger_damage` 门控）——ERA、APS、JAMMER、DIRCM、COUNTERMEASURE、ECM_PASSIVE
  都会被高伤直击打掉；
- **爆炸**（`tryDestroyBoneModulesByExplosion`）：仅 `participatesInBlastDestruction()` 为真的
  **ERA** 参与。

**对维修设计的直接推论**：

1. 快速维修若只恢复 ERA，被打掉 APS 雷达 / 干扰机 / DIRCM 的载具将**永久残废**（扳手只回血不修
   模块）——维修必须覆盖设备类模块；
2. **恢复即自动生效**：所有消费点每 tick 查状态表，维修只需操作
   `RVP_BoneModuleStateTable` + 一次 `syncBoneModuleState(vehicle)` 广播（客户端 JS 动画随之把
   隐藏骨显示回来、HUD 状态刷新），**无需触碰任何 Runtime Manager**；
3. `__vehicle__` 虚拟骨（无骨骼 ECM）不在命中箱、**永不被摧毁**，天然无需维修（HUD 已有
   "始终可用"特判）；
4. ⚠️ **v1 伪代码缺口**：`RVP_BoneModuleStateTable` 目前**只有 destroy 没有恢复 API**
   （仅有整表替换 `setInactiveModules`），需按 §4.3 新增 `restoreModule`；v1 所写
   `RVP_EraStateSavedData.markDirty()` 也不需要——persist 在状态表内部自动完成。

## 4 移植方案（推荐）

### 4.1 设计目标

- 保留 MCHR 手感：驾驶位一键触发；`useTime` 内每 tick 回 `1%`；`waitTime` 冷却；触发时**随机恢复 25% 已毁 ERA 骨块**。
- **（v2.1）模块维修全部渐进式、可 counter**：
  - **设备类**（APS/JAMMER/DIRCM/COUNTERMEASURE/ECM_PASSIVE/ECM_ACTIVE/TRACK）：每个已毁模块
    每次维修**独立按概率恢复**（默认 25%）——部分恢复有意义：每根 APS 雷达骨就是一个扫描扇区
    （ne/nw/se/sw 各管一个方位），修 1 根即恢复该方位的探测/拦截；单台干扰机 25% 概率修回意味着
    "打掉设备"依然有持续价值，修回是渐进的、非确定性的；
  - **ERA**：维持 MCHR 的**按数量比例**恢复（25% 向上取整、至少 1 块）——几十块的消耗品语义。
- 适配 RVP 血量与模块模型；数据驱动（每载具可配开/关、时长、冷却、回血曲线、恢复比例/概率）。
- 零 Mixin、双端安全、`@OnlyIn(CLIENT)` 隔离经 `RVP_ClientActions` 桥接（如需）。

### 4.2 数据模型（JSON）

> **✅ 落码采用统合写法（2026-09-02）**：维修是状态级设备，配置并入 `bone_modules` 体系，
> 新增模块类型 `MAINTENANCE`。**规范写法**挂在虚拟骨骼 `__vehicle__`（载具级能力、永不可被击毁），
> 与无骨骼 ECM 的 `__vehicle__` 先例完全同构；也可绑定实体骨（如发动机）——骨块被直击打掉则
> 维修失效（对抗性设计，模块失效后快修无法触发）。顶层 `maintenance` 块保留为**别名**
> （自动映射到 `__vehicle__`，等价）。

规范写法（`data/rvp/vehicles/<id>.json` 的 `bone_modules`）：

```json
{
  "bone_modules": {
    "__vehicle__": {
      "modules": ["MAINTENANCE"],
      "maintenance": {
        "use_time_ticks": 20,
        "wait_time_ticks": 300,
        "heal_per_tick_percent": 1.0,
        "heal_parts": false,
        "module_repair": {
          "repairable_types": ["ERA", "APS", "JAMMER", "DIRCM", "COUNTERMEASURE", "ECM_PASSIVE", "ECM_ACTIVE"],
          "era_recover_fraction": 0.25,
          "era_recover_min": 1,
          "device_recover_chance": 0.25
        },
        "require_max_altitude": -1
      }
    }
  }
}
```

- `heal_per_tick_percent` 对应 MCHR 的 `maxHP/100`；`heal_parts` 控制是否同步回部件（默认关，保持 RVP 扳手分工）。
- **（v2.1）`module_repair` 子块**：
  - `repairable_types`：允许维修的模块类型白名单（缺省=上例全集）；想禁止修某类（如不允许修 ECM）
    从中删除即可——被删类型的毁坏不可通过快速维修恢复；
  - `era_recover_fraction/min`：ERA 按数量比例恢复，对应 MCHR `(size+3)/4`——随机洗牌后取
    `ceil(size*fraction)`，至少 `min` 块；
  - `device_recover_chance`：设备类每台已毁模块每次维修的**独立恢复概率**（0~1，默认 0.25）。
    四向 APS 雷达全毁时一次维修期望修回 1 根（=1 个方位扇区）；单台干扰机每次维修 25% 修回。
    概率语义避免"向上取整导致单设备必回"的过强问题。
- 例：`mi28.json` 可设 `use_time=20, wait=600` 以示重型机冷却更长；不配 `module_repair` 时
  默认 `era 25% + 设备概率 25%`。

### 4.3 服务端运行时

新建 `org.ywzj.rvp.vehicle.RVP_MaintenanceRuntimeManager`（参考 `RVP_ApsRuntimeManager`）：

- 状态：`Map<UUID, MaintenanceState>`，`MaintenanceState { int cooldown, useRemain, int useTime, int waitTime }`。
- 驱动：订阅 `TickEvent.ServerTickEvent` 或 `VehicleTickEvent`（若有）每 tick `tick(vehicle)`：
  - `cooldown>0 → --cooldown`
  - `useRemain>0 → --useRemain; heal(vehicle, healPerTick); if(useRemain==0) clearUsingFlag`
- 治疗：`vehicle.heal(maxHealth * healPerTick/100)` 或 `setHealth(clamp)`；若 `heal_parts` 则遍历 `vehicle.getPartUnits()` 同步回血（`max/10` 或同比例）。
- **模块恢复（v2.1，触发瞬间执行一次）**：设备类按概率、ERA 按数量比例，全部渐进式：

  **前置 A —— 状态表补恢复 API**（v1 缺口，现状只有 destroy）：
  ```java
  // RVP_BoneModuleStateTable 新增：恢复骨块的某模块；返回 true 表示之前确实失效、本次恢复成功。
  // 恢复后若该骨失效集合为空则整键移除；成功时照 destroy 惯例自动 persist(vehicleId)。
  public static boolean restoreModule(UUID vehicleId, String boneName, BoneModuleType type)
  ```

  **前置 B —— 同步方法提可见性**：`RVP_VehicleHitboxFactorManager.syncBoneModuleState(vehicle)`
  目前是**实例私有方法**（`RVP_VehicleHitboxFactorManager.java:397`），维修 Manager 无法调用；
  提升为 `public static`（实现不变：`S2CBoneModuleState` 广播 TRACKING_ENTITY + 上车全量）。

  ```java
  // —— 触发瞬间：模块恢复 ——
  UUID vehicleId = vehicle.getUUID();
  var cfg = maintenanceConfig(vehicle).moduleRepair();
  Map<String, Set<BoneModuleType>> inactive = RVP_BoneModuleStateTable.getInactiveModules(vehicleId);

  // ① 设备类：逐台独立掷骰（概率 device_recover_chance，默认 0.25）。
  //    部分恢复有明确语义：每根 APS 雷达骨 = 一个扫描扇区，修 1 根恢复 1 个方位；
  //    单台干扰机 25% 修回——打掉设备仍有持续价值，修回渐进且非确定。
  for (var boneEntry : inactive.entrySet()) {
      for (BoneModuleType type : boneEntry.getValue()) {
          if (type != BoneModuleType.ERA && cfg.repairableTypes().contains(type)
                  && vehicle.getRandom().nextFloat() < cfg.deviceRecoverChance()) {
              RVP_BoneModuleStateTable.restoreModule(vehicleId, boneEntry.getKey(), type);
          }
      }
  }
  // ② ERA：MCHR 手感——随机洗牌取 ceil(n * fraction)，至少 min 块
  List<String> destroyedEraBones = filter(inactive, values.contains(ERA) && cfg.repairableTypes().contains(ERA));
  if (!destroyedEraBones.isEmpty()) {
      int n = Math.min(Math.max((int) Math.ceil(destroyedEraBones.size() * cfg.eraRecoverFraction()), cfg.eraRecoverMin()),
                       destroyedEraBones.size());
      Collections.shuffle(destroyedEraBones, vehicle.getRandom());
      for (int i = 0; i < n; i++) RVP_BoneModuleStateTable.restoreModule(vehicleId, destroyedEraBones.get(i), BoneModuleType.ERA);
  }
  // ③ 一次广播：客户端 JS 动画恢复渲染骨、HUD/APS/干扰机等消费端下 tick 自动重新生效（全部查表）
  RVP_VehicleHitboxFactorManager.syncBoneModuleState(vehicle);
  ```

  > 设计取舍（v2.1）：设备类**不用数量比例 + 向上取整**——那会导致"单台设备必回"（ceil(1×0.25)=1），
  > 等价于全修；改用**独立概率掷骰**，期望恢复 = n × chance，多扇区车（APS 四向）呈现"修一部分方位"、
  > 单设备车呈现"概率修回"，打掉设备的博弈价值全程保留。ERA 保持数量比例是因为它是大基数消耗品，
  > MCHR 的"至少修 1 块"手感要保留。两者均可按车配置。

- 持久化：`cooldown/useRemain` 写入 `vehicle.getPersistentData()` 或 `RVP_EraStateSavedData` 扩展；`SavedData` 随世界存档，跨重启不丢。模块恢复的持久化**无需额外处理**——`restoreModule` 内部走状态表既有 `persist()` 链路（与 destroy 对称）。
- 校验：`canUse(vehicle, player)` → `enabled && cooldown==0 && !isDestroyed() && seatId ∈ allowSeats && (!require_on_ground || vehicle.onGround()) && player.distance<16`。

## 7 风险与验证

- **平衡**：`useTime=20` 共 20% 在 RVP 高伤害环境可能过强/过弱，建议首版 `use=20 wait=300 heal=1%` 对齐 MCHR，后续按 `docs/RVP伤害倍率与爆炸.md` 联调。
- **（v2.1）模块维修平衡**：设备类为**独立概率恢复**（默认 25%/次）——打掉设备仍有持续博弈价值
  （对方需要多次维修窗口才能修回，且可能一直修不回单台设备）；若仍嫌强，可调低
  `device_recover_chance`（0.1 = 更难修回）、把类型移出 `repairable_types`（永久不可修），
  或在 `bone_modules` 给设备骨加高 `min_damage`（如 30~50）让"打掉设备"本身更难。
  部分恢复有明确游戏语义：APS 雷达骨 = 扫描扇区，修 1 根恢复 1 个方位的探测/拦截。
- **（v2）恢复不 resurrect 非法骨**：状态表在载具加载时经 `retainValidBones` 清理过无效骨名，
  恢复只作用于现存失效集合的子集，不会复活已被清理的骨；`__vehicle__` 虚拟骨永不失效、天然不在集合内。
- **（v2）恢复后客户端表现**：`syncBoneModuleState` 一次广播后，JS 动画（`rvp_isEraActive`/`isModuleActive`）
  下一帧恢复渲染骨；若某车动画脚本缓存了状态未响应，属脚本侧问题，验证时单列。
- **滥用**：需 `seatId` + 距离 + `isDestroyed` 校验；CD 必须服务端权威，客户端仅预测。
- **存档**：`SavedData` 未正确 `setDirty()` 会导致重启丢 CD；需单测 `write/read NBT`。模块恢复的存档
  走状态表既有 persist 链路，与 destroy 同路径，重启一致性已有保障。
- **同步**：`PROTOCOL` 递增后旧客户端连新服会被拒，需在更新日志注明（当前 "5"，本功能落地升 "6"）。
- **性能**：每 tick 仅对载具实体集遍历，`heal` 为 O(1)；模块恢复仅触发时 O(n)（n=失效骨数，个位到几十），
  可忽略。

   **实体骨绑定语义**：MAINTENANCE 骨被直击打掉 → 快修无法触发（模块失效不可用快修复自身，
   该能力即告失去——对抗性设计，虚拟骨缺省形态不受影响）。
