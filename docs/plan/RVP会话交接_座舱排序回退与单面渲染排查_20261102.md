## 原始问题排查：已确认与未证明的区别

### 1. 本地玩家的补画会被自身隐藏事件取消

- RVP_RenderLivingHandler.java:18、25 两个 Pre 订阅调用 shouldHide；:36 对本地玩家第三人称且模型 hasCockpitDepthFix 时直接返回 true。
- RVP_CockpitPassengerRenderer.java:94 的补画仍调用真实 PlayerRenderer.render，没有“正在补画”的上下文豁免。
- 已查当前实际 Forge 47.4.13 mapped jar 的 PlayerRenderer 字节码：render 首先发 RenderPlayerEvent.Pre，被取消立即 return；Forge 的 LivingEntityRenderer 同样有 Pre 取消入口。
- 因此在该分支条件满足时，正常绘制被取消，补画也再次被取消。这是可由调用链确认的旧逻辑缺陷，不需要先假设是 GL 深度挡住。
- 这一分支仅针对本地玩家，不能拿它解释远端玩家或其它生物的全部偶发消失。部分视角是否实际进入该分支仍要结合运行时相机状态确认。

### 2. 普通玻璃会提前写深度，实体显示依赖实际提交顺序

- 本体 ModRenderTypes 的两类透明材质未设 write mask；已核对实际0.6.2依赖字节码，只有炮口材质设置 COLOR_WRITE。
- Minecraft CompositeStateBuilder 默认是 LEQUAL_DEPTH_TEST + COLOR_DEPTH_WRITE。RVP_RenderTypes.java:60、125 的普通透明材质同样沿用深度写入，只把面剔除设为 CULL。
- 已核对 MultiBufferSource.BufferSource.getBuffer：未在 fixedBuffers 注册的材质一旦切换会 endBatch 上一材质；世界实体迭代不提供玻璃与所有生物的全局透明排序。
- 所以一旦玻璃先实际提交，它的半透明片元也会占据最近深度，之后处于后方的生物像素会被 LEQUAL 拒绝；实体先提交则可以被玻璃混合覆盖。这是能解释顺序相关“有时显示/有时不显示”的机制，但本轮没有录到用户场景的逐 draw 证据。

### 3. F-22 的专用路径不能直接套用普通玻璃结论

- 根包 f22a display:18–27 的 $canopy0/$canopy1 均标 cockpit_depth_fix；它们是纯 poly_mesh（136/8个 polys），没有子骨。F-22 display 未配置 distance_hidden_bones/no_cull_bones，vehicle 未显式 hide_passenger 或 uav。
- 回退后对应 RVP_RenderTypes.java:81、146 是 CULL + COLOR_WRITE + 原有 VIEW_OFFSET_Z_LAYERING；若运行时确实命中这条路径，玻璃本身不写深度，不能把所有 F-22 现象都归因为“玻璃写深度”。
- 另已查 BufferBuilder.setQuadSorting：只有 QUADS 才计算排序点。TRIANGLES 即使 RenderType 的 sortOnUpload=true 也没有因此自动获得面排序；这是原始模型透明排序的限制，尚不能单独证明它就是本次人物消失原因。
- 本轮没有取得用户游戏帧的事件取消记录、实际材质路由及 draw 顺序，未把静态候选原因当成完整实机根因，也未声称新的全局延后方案可行。
