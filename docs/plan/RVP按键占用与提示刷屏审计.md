# RVP 按键占用与提示刷屏问题审计

> 审计日期：2026-09-05。范围：`RVP_ClientEvents.onClientTick` 全部按键消费循环 +
> `RVP_Keys` 注册键位 + 各处理器在"不适用场景"下的反馈行为。
> 起因：SBW 同装时 N 键（SBW 火箭筒切弹头）被 RVP 放飞无人机逻辑拦截并刷
> "未在载具中"提示；头瞄键单兵状态同类问题。

---

## 一、问题定性

两类过度行为：

1. **提示刷屏**：操作与当前载具/状态无关时，仍弹 actionbar 提示（"当前载具没有无人机"、
   "未在载具中"等）。玩家不需要被提醒"这个键在这台车上没用"。
2. **事件阻断**：处理器在不适用场景下未及时 return，后续逻辑（发包/置状态/取消事件）
   仍然执行——轻则无效包打到服务端，重则与其它 mod 同键位功能互相阻断。

**应当的形态**：按键处理第一步做**适用性判定**（在不在载具、这台载具有没有对应部件/
系统），不适用则**静默 return**——不提示、不发包、不置状态。提示只在"操作被受理但因
其它原因失败"时才有价值。

---

## 二、逐键审计

以下按键消费均位于 `RVP_ClientEvents.onClientTick`（`consumeClick()` 边沿检测循环），
服务端入口多为对应 C2S 包的 `handle`。判定"适用场景"用的上下文：
`lvp.onVehicle()`（是否在载具）、载具类型、载具上是否存在对应部件/系统。

| # | 键位 | 功能 | 不适用时的当前行为 | 问题级别 | 修复方向 |
|---|------|------|--------------------|----------|----------|
| 1 | N（放飞无人机） | 放飞可部署无人机 | 单兵/无无人机载具：提示"未在载具中"/"当前载具没有无人机"，且**阻断 SBW 同键功能** | **严重**（跨 mod 阻断） | 客户端守卫前置：不在载具、载具无 `deployable_uav` 配置、无可用无人机时**静默 return**（不发包、不提示）；服务端同口径静默拒绝 |
| 2 | M（切换无人机） | 切换无人机操控 | 同上，提示"当前载具没有无人机" | **严重**（同 N） | 同上 |
| 3 | 头瞄键（HMD） | 头盔显示切换 | 单兵状态：同类提示与阻断（用户报告，待逐条核实） | 高 | 同 #1 模式：仅当乘坐载具且该载具 display 配置了 HMD 时才处理 |
| 4 | B（快速维修） | 载具维修 | 已有 `lvp.onVehicle()` 守卫，但**未校验载具是否配置了 maintenance** | 中 | 载具未配置 maintenance 时静默 return（避免无效 C2S 包） |
| 5 | 干扰物键组（热焰弹/箔条/ECM/烟雾） | 发射干扰物 | 载具无干扰物部件时：当前行为待核实（大概率发包后被服务端忽略，客户端无提示则可接受） | 低 | 若有提示刷屏则同样加静默守卫 |
| 6 | FUNCTIONAL ↑/↓（可变后掠翼，新增） | 后掠切换 | 已按"先解决配置"讨论定稿：不适用载具静默 return | ✅ 新代码已按此实现 | — |
| 7 | DEBUG_OVERLAY / custommount 等调试键 | 调试开关 | 全局可用，设计如此 | 无问题 | — |

## 三、跨 mod 冲突机制分析（SBW N 键被阻断的原理）

RVP 与 SBW 各自注册了绑定 N 的 `KeyMapping`。Minecraft 中**同键位的多个 KeyMapping
都会各自累计 clickCount**，理论上互不阻断。SBW 被阻断的可能路径：

1. RVP 的 N 键处理器在**不适用场景下仍然发送了 C2S 包**，服务端回包/状态变化干扰了
   SBW 的客户端状态（需实测确认）；或
2. RVP 处理器在处理时**抛出异常/提前 return 失败**，导致同 tick 内后续逻辑（含其它
   mod 在同一事件处理器链上的逻辑）被跳过；或
3. RVP 与 SBW 注册了**同一个 KeyMapping registry 名**（`rvp_uav` vs SBW 的键冲突归类），
   玩家在键位设置里看到冲突并"解决"后，其中一个键位被改绑。

**结论**：无论具体是哪条路径，修复方向一致——RVP 按键处理器在"不适用"时必须
**尽早静默 return**，既不发包也不提示，把键位还给其它 mod。

## 四、修复原则（供实施参照）

```java
// 每个功能键消费循环的标准形态：
while (XXX_KEY.consumeClick()) {
    if (!guard()) continue;   // 适用性判定：不满足=静默吞掉，无任何输出
    doAction();               // 满足才发包/执行
}
```

- `guard()` 检查顺序：是否在载具 → 载具类型 → 载具有无对应部件/系统 → 是否驾驶员（按功能定）；
- **任何一步不满足都直接跳过本次点击**，不提示、不发包、不置状态；
- 服务端 C2S handler 同口径再校验一次（客户端校验仅为省流量，服务端才是权威）。

## 五、遗留与后续

1. 逐键修复需先补齐各键的"适用场景"数据来源（如载具是否配置了 deployable_uav、
   maintenance、HMD），涉及 `RVP_VehicleExtendedConfigManager` 的字段——部分已有，部分需补；
2. 修复后逐键实机验证：不适用载具按=完全无反应；适用载具按=正常触发；
3. SBW 同装回归：N 键在单兵/无无人机载具上应完全归 SBW 使用。
