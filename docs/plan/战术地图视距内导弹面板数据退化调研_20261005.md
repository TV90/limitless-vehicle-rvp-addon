# 战术地图视距内导弹面板数据退化调研（2026-10-05）

> 现象：选中在飞导弹后，视距外面板显示 `[TGT] AGM-109C 巡航导弹 | V 183 km/h`（正确实时）；
> 视距内退化为 `[TGT] MSL | V 72 km/h`（通用标签 + 冻结初速）。
> 结论：**RVP 侧问题**，选中面板在视距边界切换数据源，本地实体分支的名称/速度两个来源都劣化；
> 且速度分支存在一处**疑似写反的死代码**，实时数据其实早已在客户端手上。

---

## 一、面板的两条数据源（按 entityId 无缝切换）

渲染：`RVP_TacticalMapScreen.renderSelectedMarkerInfo`（:2048-2081），数据载体 `MarkerHit`
（:154-186，字段 displayName/speedKmh/gpsAmmo/targetPos），每帧重建。
选中态迁移：`syncSelectedMarkerHit`（:3867-3880）按同一 int entityId 重绑——所以跨边界
"看起来是同一个目标"，但字段来源整体被替换。

| | 视距外（快照条目） | 视距内（真实客户端实体） |
|---|---|---|
| 注册 | `registerRemoteAmmoHit` :3824-3837 | `renderLocalProjectiles` :1252-1272 → `registerMarkerHit` :3807-3822 |
| 切换开关 | `hasTrackedAmmoEntity` :1785-1797（`mc.level.getEntity(id)!=null` 即让位） | 同左（本地接管） |
| 名称 | `resolveRemoteAmmoDisplayName` :3937-3950：weaponId → lang 全名（"AGM-109C 巡航导弹"） | `resolveMarkerDisplayName` :3906-3918 → NCTR 短标签链 → **"MSL"** |
| 速度 | `entry.speedKmh()`：服务端每 5 tick 实时值（:3834） | `resolveEntitySpeedKmh` :3952-3965 → **客户端冻结 deltaMovement × 72** |
| GPS | `entry.guidancePos()` 服务端实时 | `bullet.getTargetPos()`——readSpawnData 出生快照（RVP_BaseBullet.java:5195-5199） |

## 二、"MSL" 的出处（名称退化链）

`resolveMarkerDisplayName`（:3906-3918）第一步就调 `resolveModernNctrLabel`（:3231-3253）
→ `RVP_RadarContactHelper.resolveBulletRadarLabel`（RVP_RadarContactHelper.java:251-269）
→ `RVP_WeaponData.resolveMissileNameOnRadar(Float.MAX_VALUE)`（RVP_MiscData.java:128-130）
→ 默认雷达名表 **≥20 格 ⇒ 硬编码 "MSL"**（RVP_MiscData.java:171，`createDefaultRadarNames()`），
现役武器 JSON 无一覆盖 `missile_name_on_radar` → 命中后**直接短路**，走不到 :3914-3915 的
武器全名分支。

要点：weaponId **已经**随 spawn data 同步到客户端（本体 AmmoEntity.java:182/193），
`resolveWeaponDisplayName`（:3920-3931）本地就能解析全名——只是选中面板的名称解析顺序
让 NCTR 分类标签优先，两条路径名称语义不一致（航迹列表用分类短标签是雷达语义，选中面板
却是信息详情语义）。

## 三、72 km/h 的出处（速度冻结链）

`resolveEntitySpeedKmh`（:3952-3965）：

```java
if (!entity.level().isClientSide()) {          // :3956 客户端实体恒 false → 死代码！
    ... return remoteEntry.speedKmh();         // 本可拿到每 5 tick 实时速度
}
return bullet.getCurrentSpeed() * 72.0;        // :3962 实际执行
```

72 km/h = 1.0 格/tick × 72（72 = 20 格/s × 3.6）。该 1.0 是**客户端实体冻结的 deltaMovement**：

- 出生时一次性写入：服务端 `writeSpawnData` 把当时 deltaMovement/currentFlightSpeed 写进
  生成包（RVP_BaseBullet.java:5125-5128），客户端 `readSpawnData` 恢复（:5168-5175）；
- 此后永不更新：`RVP_BaseBullet.tick()` 客户端分支早退（:1801-1808，"motion server-only"）、
  本体 `AmmoEntity.tick()` 客户端只 tickLerp 位置（本体 AmmoEntity.java:83-96）、
  实体注册 `setShouldReceiveVelocityUpdates(false)`（RVP_Entities.java:125）关闭速度同步包；
- 冻结值 = 出膛初速：`ddg51_rgm109.json:25 "velocity": 1` → `resolveMuzzleSpeed` = 1.0 格/tick
  （RVP_ProjectileSpawner.java:96-98）→ 发射时刻即被本地跟踪的客户端副本固化 72 km/h。
  （若弹是飞入追踪带的，冻结值将是穿越时刻速度——表现为"固定 183"而非 72，可反证本例
  导弹自发射起就在本地追踪带内。）

**关键事实**：视距外的实时速度来源 `S2CRemoteAmmoSnapshot`（每 5 tick 全量、6144 格范围、
**不过滤视距内弹**，RVP_RemoteAmmoSyncService.java:27-28/53-58/77）对视距内导弹同样在刷新，
客户端 `RVP_ClientRemoteAmmoState` 里始终有该弹的实时条目——面板的本地分支只是没用它。
本体广播克隆链也带真实速度（ServerBroadcastEntities.java:95/113），但 RVP 克隆被
`isVisualOnlyRvpAmmo` 排除在面板之外（:1534/1792），与此现象无关。

## 四、根因（两条，均在 RVP 侧）

1. **名称退化**：选中面板本地分支让 NCTR 分类标签链优先于武器全名链，默认雷达名表
   无 JSON 覆盖时恒回 "MSL"（RVP_MiscData.java:171），与视距外的 weaponId→lang 全名路径不对称。
2. **速度冻结**：`resolveEntitySpeedKmh` :3956 条件 `!entity.level().isClientSide()` 在客户端
   恒 false，"优先查快照实时速度"是死代码（疑似笔误，意图应为客户端实体时查
   `RVP_ClientRemoteAmmoState.getEntry`），实际恒回退到出生即冻结的客户端 deltaMovement。

## 五、修复方向（待用户确认后实施）

- **速度/GPS**：反转 :3956 条件（或直接改逻辑：客户端实体优先查
  `RVP_ClientRemoteAmmoState.getEntry(dimension, entityId)`，命中即用实时 speedKmh/guidancePos，
  无条目再回退现值）。数据已在客户端，零新增包。
- **名称**：选中面板（MarkerHit）的名称解析改为武器全名优先（复用 :3920-3931 现成方法），
  NCTR 短标签保留给航迹列表/HUD 场景；或至少全名解析失败才回退 "MSL"。
- 回归面评估：`resolveEntitySpeedKmh`/`resolveMarkerDisplayName` 的其它调用点（雷达航迹、
  TWS 等）是否应保持原语义——实施时逐点核对，避免选中面板修好把航迹标签改花。
