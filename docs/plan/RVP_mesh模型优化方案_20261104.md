# RVP mesh 模型优化调研与分阶段方案（2026-11-04）

> 2026-11-04 主世界复测更新：用户反馈七八台 TEL 转头仍卡后，确认 `3ffe1590` 的 dense 入口只接受 raw AR builder，主世界 `BufferBuilder` 持有者被跳过；此前 GUI CPU 数据不能证明游戏内优化生效。已在 `8a038a14` 补接 AR 公开 `IAccelerationHolder`，验证过滤/不可用回退。独显主世界八车转头帧时间中位数 8.78→3.60 ms，P95 9.96→4.80 ms（独立超平坦世界，8 区块视距，非用户完整存档）。最新现状见《RVP会话交接_Mesh主世界入口修复与独显复测_20261104.md》；下文保留首轮调研经过。

调研之后，用户已授权“尝试修复”。当前已实现 P1：修正不透明批次分类，并为大块不透明 mesh 接入 AR 原有 dense 提交。已完成原生客户端局部 CPU 测量，尚无主世界 FPS / GPU 采样。用户实测样本为 IRIS-T SLM TEL：多台同屏时卡顿明显，静止视角帧率较高，转动视角时大幅下降。该现象优先于推测，但单凭现象不能判定是透明排序、缓存失效或 GPU 算力不足。

`audit_irist_mesh.py` 只读解析模型，复刻 float32 的 `(-x,y,z)/16`、闭合点剔除、quad/fan 三角化、重合点阈值。输出 `irist_slm_tel_mesh_audit.json` 包含每骨骼数据和原文件 SHA-256。它未执行真实骨骼 toAttach 矩阵，也未经过纹理透明面过滤，所以三角化后数据为静态估算，不等同 GPU 实际提交计数。

**已确认的代码事实**

1. SBM 已经有 mesh 加速和几何缓存。`BakedGeometryChunkRenderer.renderVertexChunk` 优先进入 AR，失败才尝试 Sodium / 普通 CPU 路径。`AcceleratedRenderer.renderCachedVertices` 以几何 chunk 和 buffer graph 缓存 mesh，首次建立后提交变换矩阵与实例属性。普通缓存键未直接包含相机矩阵，不能说每次转头必然重烘焙。带 decal 的特殊 consumer 另有相机矩阵参与相等比较，但还没有证据表明 TEL 主体使用该路径。
2. SBM 2.6.0 的 `BedrockGeometryBaker` 已剔除 polygon 首尾重复点，发射三角形前也跳过位置相同的角。此前怀疑“77,502 个闭合三角形会被重复拆出零面积三角形”的方向不成立。不得把删除闭合端点宣传为减少一半实际三角形的优化。
3. RVP 存在不透明材质的批次分类错误。`RVP_RenderTypes.java:18` 的 `POLY_MESH_CUTOUT_CULLED` 使用 NO_TRANSPARENCY / CULL / TRIANGLES，却把 `sortOnUpload` 设为 true（第 34 行）；no-cull cutout 和 cube cutout 同样如此。现有 `BedrockModelRenderTypesMixin` 将本体 mesh cutout 路由到该 RenderType。AR 的 `RenderTypeUtils.getDrawType/isTranslucent` 正是读取这个标志，因而会把该不透明 mesh 分入 TRANSLUCENT。A1 强制透明加速开启，所以不能据此声称它必然退回 CPU；也没有证据说明 AR 正在对这些三角形逐面排序。这是独立应修的兼容问题，但其对转头掉帧的贡献尚未实测。
4. AR 缓存了源几何，但仍逐帧展开实例。1.0.14 的 `MeshUploadingProgramDispatcher` 为每个实例保留顶点输出区间；dense 路径 compute shader 按 `meshCount * meshSize` 计算变换并写输出缓冲。少于 sparse_threshold 且没有强制 dense 时，sparse 路径还在 CPU 上逐顶点写 varying offset。SBM 的默认 `build(collector)` 没有强制 dense。A1 的阈值是 64，几台同型高面数模型通常仍落在 sparse 分支，需运行时计数验证。它不是完整硬件实例化，源几何缓存并没有让逐帧开销只剩几个矩阵。
5. SBM 2.6.0 已有 `StaticMeshRenderer`、`StaticMeshBufferSource`、`MeshGeometryProvider`、缓存预算和资源失效管理，适合验证刚性部件常驻 VBO。它的 MATERIAL 批次能减少材质/缓冲切换，但 `MeshBatchRenderer.drawWorld` 仍每实例调用 draw，不能宣传为硬件实例化。`MeshSink.buildBuffer` 也仍输出展平顶点，API 本身没有自动实现完整属性顶点去重。
6. RVP 将全部模型骨骼标为保留和可动画，不能简单取消：轮转、发射架展开、弹药隐藏、炮口定位、部位损伤和脱落都依赖逻辑骨骼。TEL 主要负担集中在两个大刚性块，首批优化不应先破坏骨架或重做美术模型。

**最初分阶段方案（P1 已完成，实际实现与验证见末尾）**

| 阶段 | 意图与改动点 | 预期影响与验收 |
| --- | --- | --- |
| P0：建立可比基线 | 同一场景 1 / 4 / 8 台 TEL，预热后固定视角和小幅连续转头，保持可见数量基本一致；记录帧时间中位数、P95/P99，Render thread 的 JFR 采样及必要 GPU 时间 | 区分 CPU 提交、GPU 顶点处理、首次可见缓存和地形更新；没有基线不能承诺 FPS 倍率 |
| P1：纠正批次分类 | 仅把 opaque/cutout 对应 RenderType 的 sortOnUpload 改 false，保留原有 CULL、shader、光照和真实透明材质 | 修正确定的兼容问题；A/B 核对主世界、预览、热成像和命中展板，不把分类修复等同性能根因已解决 |
| P1：比较 AR 原有路径 | 先做 BASEVERTEX / INDIRECT 独立对照；大 chunk 再比较默认 sparse 与公开 `IMesh.Builder.build(collector, true)` 的 dense 构建 | 优先利用既有 AR API，避开大 mesh 的 CPU offset 循环；dense 仍有 GPU 展开，可能受 dispatch 开销影响，必须以测量决定 |
| P2：刚性 mesh 专用路径 | 在 RVP 模型/渲染扩展中，优先对满足大小和材质条件的刚性 chunk 复用 SBM StaticMesh API；车体、发射架独立缓存，轮组等保持现有路径 | 让常驻局部几何直接绘制，减少 AR 每帧展开的额外传输；两个大块已覆盖约 83% 面数。权衡新增 draw call，验证后才扩面 |
| P3：索引化 | 若 P2 后仍受顶点量/显存带宽限制，为捕获/上传层增加完整顶点属性去重与索引缓冲；优先向上游 API 扩展，不强改私有字段 | 有约 62.65% 顶点记录压缩潜力，但真正 GPU 执行次数受索引局部性等影响；不是简单开关，也不是必需首步 |
| P4：LOD | 若大量远距离载具仍吃紧，复用项目已有 LOD 选择机制，近处原模、远处简模并设切换回差 | 能实际降低三角形数；需要另行制作和验证模型资源，不能擅自减面/覆盖用户模型；不作为本轮首选 |

AR 配置的 sparse_threshold 合法区间是 16～128，不能建议填 1。即便调到 16，1/4/8 台场景也不必然进入 dense。若做大 mesh 专用 dense，应按顶点量、材质和实际 buffer graph 使用公开构建 API，保留独立缓存生命周期，避免第一次普通缓存构建把同一 mesh 继续锁在 forceDense=false。此分支接入方式需验证，不能直接往 SBM 的全局缓存中塞不同语义的条目。

P2 的缓存键应包含资源代次、模型、chunk/刚性组、材质、拓扑、LOD，以及确实改变几何的状态；相机、世界位置和普通运行时骨骼姿态不进几何 key。姿态只更新矩阵，光照/overlay 走实例属性，导弹消耗隐藏独立几何。不要把整台活动载具接入 SECTION 合批，否则活动姿态会反复触发重建。

优先扩展已有 `RVP_VehicleBedrockModel` / `RVP_VehicleRender`，使用 `getBakedModel().meshChunks()` 等公共数据和 SBM 渲染接口。不硬编码 IRIS-T ID；首个测试样本是 TEL，但启用条件应由 mesh 规模和材质决定，若需要制作端选择，字段应归 display。暂不新增 Mixin 或修改本体；如公开 API 最终不足，应先记录具体缺口和替代方案，再按 agents.md 处理。

必须保留当前单面 CULL、骨骼/OBB/武器定位、剩余弹药隐藏、部位脱落、动画和乘员状态。缓存只用于渲染几何，不接管服务端逻辑。透明、发光、炮口、受击闪色与特效分通道；不支持的通道走既有路径。StaticMesh 返回 PENDING 代表该次绘制已被接管，不能同时 fallback 导致双画；只有 UNSUPPORTED 才回退。首次上传、切换材质/贴图、F3+T、模型卸载都要验证缓存回收和无闪烁。

**回归与性能判据**

- 保持分辨率、渲染距离、VSync、帧率上限、光影开关、场景天气一致；缓存预热后，各组重复同样的小角度转头路径，另测“转向此前不可见车群”作为冷缓存场景。记录实际可见载具数，避免把看到更多地形当作同量测试。
- 用 JFR/现成性能工具先定位 Render thread 热点。需进一步诊断时在 RVP 边界统计路径选择、提交 chunk/顶点数、cache miss 和上传字节，不能逐面日志刷屏，也不为调研盲目新增 Mixin。
- GPU 计时采用异步 query，避免 glFinish 制造测量卡顿；CPU 与 GPU 数据分开，不能从 CPU 帧时单独判断显卡瓶颈。
- 验证无 AR、A1 AR 1.0.14、当前上游 1.0.15 对照；Oculus 无光影、有光影/阴影及不兼容环境回退。当前主测以用户实际版本为准，不把升级依赖当作修复已完成。
- 功能覆盖发射架展开、转轮/转向、8 枚弹药依次隐藏、部位损伤/脱落；GUI 改装预览、命中回放、热成像、远程相机均不得污染主世界的矩阵、FBO、viewport 或深度状态。
- 每个阶段单独 A/B，只有转头 P95/P99 和多车帧时间改善且无功能回退，才继续扩展。客户端渲染优化不应改变 TPS；完整主世界场景基准仍未执行，本次局部验证见下文。

## P1 实施与原生验证（2026-11-04）

- `RVP_RenderTypes` 的三种 opaque/cutout RenderType 将 `sortOnUpload` 设为 false；保留现有 CULL、shader、深度状态与真正透明材质。单面剔除保持。
- `RVP_VehicleBedrockModel` 只在资源创建时统计最大 chunk 顶点数；渲染时通过组合包装原来的 `MultiBufferSource`。骨骼遍历、动画、可见性与特殊骨绘制继续复用本体/SBM。
- 可选桥仅在检测到 AR 后加载。只处理原始 `AcceleratedBufferBuilder` 和主体单面不透明 mesh，不插手透明、双面、decal、多路消费、特殊骨等路径。未安装 AR 时继续原有渲染。
- 默认 `[mesh] acceleratedDenseMesh=true`、`acceleratedDenseMinVertices=32768`；文件为客户端 `config/ywzj_rvp-client.toml`。阈值单位是单个 mesh 顶点记录数，不是载具面数。开关 false 可作 A/B，批次分类修复仍保留。
- 实际没有改写 SBM 内部缓存，也没有另造顶点格式或 GPU 几何缓存。dense 描述复用同一 GPU buffer、offset 和 size，只设置 forceDense，并沿用 AR Builder 公开的 COUNTER 分配独立提交 ID。
- 两个必须保留的细节：AR 会每批重建 builder，包装器必须沿用其 RenderType/布局 equals/hashCode，不能比较对象地址；AR MeshUploads 按 mesh ID 保留首次描述，dense 与普通提交必须用独立 ID，否则开关不生效或污染其它通道策略。这两点已在真实运行中验证并修正，正式代码没有缓存增长问题。
- 编译坐标为官方 AR 1.0.14 `curse.maven:accelerated-rendering-1314021:8448250`，仅 compileOnly/testImplementation；不嵌入、不自动安装 AR。入口还会核对构造/方法/ID 分配字段，签名不匹配时回退。零新增 Mixin，零本体修改。

原生独立客户端直接读取根包 TEL 的模型与贴图，以当前 A1 的 AR 1.0.14 配置运行。1/4/8 台，各自 dense 开/关共 6 组，连续改变视角矩阵与 launcher 姿态并切换弹药骨可见性。验证实际 dispatcher 保留的策略和提交策略一致，OpenGL 错误为 0；几何缓存从普通路径 32 条增加到 A/B 两种消费者共 64 条后保持稳定，不随帧数增长。每台 233,598 条顶点中 193,776 条进入 dense，约 82.95%。三对开关截图逐像素、逐字节一致。未安装 AR 的独立客户端也通过相同 6 组绘制，三对截图一致。

CPU 局部测量：960×540、每组 45 帧，丢弃前 15 帧，剩余 30 帧中位数，单位 ms。该实验是独立模型屏幕，**不是主世界 FPS 测试，不含 GPU 时间，不能换算帧率提升倍数**；游戏地形、遮挡和其它模组仍可能主导用户场景。
