本文档记录 `052d` 在载具包中的渲染模型 / 结构模型 / 动画 / 部件对应关系，文末给出**碰撞箱别名与倍率表**（倍率暂全填 1，待平衡）。

> 解析基于 2026-10-01 的模型文件（渲染模型 **32 骨** / 结构模型 **17 骨** / 载具部件 **11 个**）。
> 骨骼树可用 `scripts/parse_bone_tree.py <模型json路径>` 重新生成。
> 蓝本：**无同类船**（本包第一艘 `vessel_vehicle`），命名与写法参照本体 `default_vehicle` 的 `assault_boat` + 包内 `m1agds` / `ps1sm` 的配置范式。

### 出弹点（bolt）怎么来的 —— 2026-10-02 排查「垂发只能从一根管发射」

**本体铁律**（`WeaponUnitData.initStructureModel` + `buildBolts`）：

```java
yTurnBone = getBoneMap().get(structure_bone);                 // 偏航骨
xTurnBone = getBoneMap().get(structure_bone + "_barrel");     // 炮口/俯仰骨
if (xTurnBone == null) {                                      // ← 取不到
    bolts = [ Bolt(ZERO, 第一个 yTurn OBB.depth/2, 0, 0) ];    //   兜底：只造【1 个】炮闩
    return;                                                    //   ★ 提前 return
}
buildBolts(xTurnBone, xTurnBone, ZERO, namedBones);            // ← 该骨【每个 cube = 一根炮管 = 一个出弹点】
```

发射侧（`AbstractVehicleWeapon.onClientFire`）：`RIPPLE` ⇒ 用 `getCurrentBolt()` 单发 + `countFire(1)` 递增索引 ⇒ **逐管循环**。

⇒ 原来把三个垂发站的 `structure_bone` 直接填成 `hq9_barrel`（16 cube 那根）⇒ 本体去找 `hq9_barrel_barrel` = null ⇒ **兜底单点**，16 个 cube 全白摆。`rvp_structure_bolt_bones` 也救不了（它是 `@At("TAIL")` 注入，被上面那个 `return` 跳过）。

**改法**（数据侧，不动 Java）：给每个垂发加一根**空偏航骨**，`_barrel` 挂成它的子骨：

```
hq9        (顶层, 0 cube, rotation [90,0,0])
└─ hq9_barrel (16 cube)
```

载具 JSON 里对应站 `structure_bone: hq9`（`yj19`/`yj20` 同理）。同理 `weapon5` 的仰角骨从 `weapon5_0` 改名 **`weapon5_barrel`**（本体只认 `_barrel` 后缀）。

⚠️ **`rotation` 必须放在父骨上，不能放 `_barrel` 上**：`buildBolts` 会先把 cube 中心按**该骨自身的 rotation** 旋转一次，而 `worldBoltPosition` 又用 `globalTransform().rotation()`（**链条里含自身旋转**）再转一次 ⇒ 骨自身带旋转会让出弹点被**转两次**、偏离 cube。放到父骨上：链条乘积不变（父∘子），但 `_barrel` 自身回到单位阵 ⇒ 出弹点与 cube **精确重合**。

改造后的出弹点总数：`weapon0` 1 ／ `weapon2` 1 ／ `weapon3` 6 ／ `weapon4` 6 ／ `weapon5` 1 ／ **`hq9` 16 ／ `yj20` 8 ／ `yj19` 8** = 47。

⚠️ 三张命中表**不需要**为空偏航骨 `hq9`/`yj19`/`yj20` 加条目（0 cube 没有 OBB，永远打不到）。

**雷达必须被武器站“引用”才算数**（2026-10-01 排查「好像没有雷达」）

雷达 HUD（`RVP_RadarOverlay`）的循环是 `weaponUnit.getRadarUnits()`，而 `radarUnits` **只在一个地方被填充**：
本体 `WeaponUnit.combineAndInit()` 遍历 **`data.getSubPartUnitIds()`**，命中 `RadarUnit` 才 `radarUnits.add(...)`。

⇒ **只在 `parts` 里写一个 `type: ywzj_vehicle:radar` 的部件是没用的** —— 还必须有一个**武器站**把它列进 `sub_part_unit_ids`，否则 `radarUnits` 恒空、**HUD 一个像素都不画**。
全包 21 台带雷达的车全都写了，052d 是唯一漏的（它只有雷达部件、没有引用）。已给 4 个座位站（`weapon0/2/3/4`）各加 `"sub_part_unit_ids": ["radar"]`（一船一雷达、四个座位共用，同 ea18g/j16/mi28 多座共用同一雷达的写法）。

其它前置：`radarUnit.isOn()` 必须为 true —— **雷达构造时 `on = true`，默认就是开的**；开关是 **`3`** 键（`AllKeys.TOGGLE_RADAR`）。`isUiHide()` 由部件的 `ui_hide` 决定，未写 = false。
雷达位置读 UI 预设：`radars["<雷达 part id>"]` 优先，回退 `radar`；未配置预设时用硬编码默认值（圆心 `(屏宽/2+128, 屏高-80)`）。
⚠️ **`anchor: "right"` 的 `computeY = 屏高 + offset_y`**（不是"距顶"）⇒ **offset_y 越负越靠上**；本车已由 `-80`（几乎贴物品栏）改成 **`-400`**（同 ps1sm）。x 同理：`computeX = 屏宽/2 + offset_x`。

**三个视角/落点字段（都在 `pivotOffset + 字段值` 的同一坐标系下）**

| 字段 | 公式 | 用途 |
| --- | --- | --- |
| `seat_offset` | **`bb/16`（不减枢轴）** | 玩家落点/座舱（`worldSeatPosition()` 还会再减 `eyeHeight`≈2 格） |
| `operator_view_offset` | `(bb − pivot)/16` | 操作员视角（第三人称跟随点） |
| `optical_sight_offset` | `(bb − pivot)/16` | **观瞄镜位置** |

⚠️ **`optical_sight_offset` 必须写**：代码 `worldOpticalSightPosition()` 里若为 null 会**直接 fallback 到操作员视角** ⇒ 开镜镜头落错位置。
本车 2026-10-01 排查「观瞄视角不对」时的根因就是这个字段**没写**（全包只有 052d 没写），而 `seat_offset` 是对的（所以"座舱视角对、观瞄视角不对"）。
由于同一个 bb 点同时是观瞄点与座舱点，**`operator_view_offset` 与 `optical_sight_offset` 填了相同的值**。
**⚠️ 该字段极易丢，改完必须 grep 校验**（2026-10-01 第二次踩）：052d 的 4 个 `optical_sight_offset` 曾**整批消失**，症状就是「观瞄位置不对」——因为 `worldOpticalSightPosition()` 一旦为 null 就 fallback 到 `worldOwnerViewPosition()`（操作员视角点）。四个站的值 = 各自 `operator_view_offset`（同一个 bb 点）。

### ⚠️ 观瞄到底随不随炮管俯仰（2026-10-02 更正：**双骨件站不随**）

> 本节此前写的"`crt`/`crt_ui` 下观瞄照样随炮管俯仰"是**错的**，已作废重写。

`WeaponUnit.updateRot()`：

```java
structureGroup.rotation = base × yaw(yRot);
if (xTurnGroup == structureGroup) {                      // ← 单骨件才把俯仰也写进本站组
    structureGroup.rotation = structureGroup.rotation × pitch(xRot);
    return;
}
xTurnGroup.rotation = base × pitch(xRot);                // ← 双骨件：俯仰只进【炮口骨组】
```

开镜相机的取位（`LocalVehiclePlayer.cameraPosition`，**恒传 `1.0F`**，此时 `getViewGroupRotation` 直接返回组的**实时** `rotation`）：

| `optical_sight_type` | 相机取位函数 | 基准组 | 偏航 | **俯仰** |
| --- | --- | --- | --- | --- |
| `operator` | `worldOwnerViewPosition()` | `structureGroup`（偏航骨）| ✓ | **✗** |
| 其余（`crt`/`crt_ui`/`none`/`optical_scope`） | `worldOpticalSightPosition()` → `worldPositionWithSelfRot` | `structureGroup`（偏航骨）| ✓ | **✗** |

（`worldOpticalSightPosition` 里那条 `OPERATOR → worldPositionWithGroupRot(offset, xTurnGroup)` 分支虽然含俯仰，但**相机在 OPERATOR 下走的是 `worldOwnerViewPosition`，根本不会调它**。）

⇒ **两条路都读 `structureGroup`，而双骨件的俯仰只写在 `xTurnGroup` 上 ⇒ 观瞄不会随炮管俯仰。**
⇒ 只有 **单骨件站（`xTurnGroup == structureGroup`）** 才会随俯仰 —— 这正是包内直升机/飞机的做法：`ah64.sighting_system`、`j15.sighting_system`、`mi28.sighting_system(2)`、`lav25.commander_machine_gun` 全是**没有 `_barrel` 兄弟骨的单骨件**（都配 `crt` + `optical_sight_offset`）。

⚠️ **与「多管出弹」互斥**：多管出弹要求 `structure_bone + "_barrel"` **存在**（每 cube 一个炮管），而观瞄随俯仰要求它**不存在**。同一个站不能既要 6 根管又要观瞄随俯仰 —— `weapon3/4`（6 联装反潜深弹）正卡在这个冲突上。

本车现状：`weapon0/2/3/4` 都是**双骨件** ⇒ 观瞄**只随偏航、不随俯仰**。要满足「HPJ-38 / 反潜深弹观瞄随炮管俯仰」需二选一：
- **A（数据侧）**：把该站并成单骨件（炮管 cube 并进基座骨、删掉 `_barrel`）⇒ 随俯仰 ✓，但**该站失去多管出弹点**（HPJ-38 本来 1 根管，无损失；`weapon3/4` 会从 6 点掉回兜底 1 点）。
- **B（RVP Mixin）**：给 `WeaponUnit.getViewGroupRotation` 加「本站 `structureGroup` 也乘俯仰」的开关（如 `rvp_optical_sight_follow_pitch`）⇒ **两骨件也能随俯仰，且保住多管出弹**，是唯一能同时满足 `weapon3/4` 的路子。

**另一条路：`rvp_optical_sight_pivot`（RVP 扩展）** —— `WeaponUnitOpticalSightPivotMixin`：配置后把观瞄基准枢轴整体替换成**渲染模型某个骨块的 pivot（像素）**，并把非 OPERATOR 型的路径从"本站自身旋转"改成"只随父部件旋转（`worldPositionWithBaseRot`）"。适合"观瞄挂在 `guanmiao` 之类渲染骨上、只想跟炮塔不想跟自身的站"。全包只有 `t84bm.commander_machine_gun` 用了（`pivot=[12.4054, 42.2098, 6.9971]` + `optical_sight_offset=[-1.5253375, 0.4868875, 0.31268125]`）。052d 用不到（四个站都是"观瞄跟着本站一起转"）。


**俯仰限位（`rot_info`）**

⚠️ **`x_rot_min` = 仰角（负值）、`x_rot_max` = 俯角（正值）**，与直觉相反。2026-10-01 曾写反并修正：

| 站 | 俯 | 仰 | 写法 |
| --- | --- | --- | --- |
| `weapon0`（近防炮） | 10° | 85° | `x_rot_max: 10, x_rot_min: -85` |
| `weapon2`（主炮） | 5° | 70° | `x_rot_max: 5, x_rot_min: -70` |
| `weapon3` / `weapon4`（反潜深弹） | 10° | 60° | `x_rot_max: 10, x_rot_min: -60` |
| `weapon5`（近防发射器） | 10° | 85° | `x_rot_max: 10, x_rot_min: -85` |

参照：`m1agds.turret` = `10 / -50`（俯 10 仰 50）、`ps1sm.turret` = `5 / -85`（俯 5 仰 85）。

⚠️ **观瞄类型（`optical_sight_type`）**

四个座位站（`weapon0` / `weapon2` / `weapon3` / `weapon4`）统一 **`crt_ui`**；四个从属站不写（它们不直接对外开镜，观瞄由主站决定）。

> `crt_ui` 是 **RVP 的语法糖**（`PartUnitTypeScopeCompatMixin`）：解析时被**改写成 `"crt"`**，并**自动补 `"rvp_disable_crt_effect": true`** ⇒ 观瞄用 CRT 电视模式但**关掉 CRT 后处理特效**，等于"纯 UI 镜"。
> 本包用 `crt_ui` 的另外 6 台全是防空/雷达车（96l6 / bukm3 / cssa5 / lavad / m1agds / ps1sm），坦克与飞机则用 `crt`。
> 本体枚举只有 4 个合法值：`none` / `operator` / `optical_scope` / `crt` —— **`crt_ui` 仅在 `ywzj_vehicle:weapon` / `auto_weapon` 类型上生效**（mixin 里有命名空间与路径判断）。

### 4.1 三个垂发是「弹舱（weapon_bay）」，不是「发射动画」（2026-10-01 修正）

> 初版把 `hq9_bay` / `yj19_bay` / `yj20_bay` 挂在 `event_animations` 的 `<站>_fire` 上 —— **这是错的**：

## 八、动力与航速（2026-10-01 排查「最多 5 kph」）

### 8.1 结论：船的极速由 **`liquid_damping` 的水阻**决定，不是由 `max_speed_forward`

`VesselVehicle.tickMove()` 只做一件事：`motion < max_speed_forward` 时给速度**加**一个每 tick 增量

```
Δv = forward_force × (power/100) / mass / 400          （格/tick，PhysicsHelper.accelerationPerTick）
```

但每 tick 结束时 `PhysicsEngine.motionByBuoyancy()` 会把**整个速度向量**乘一次衰减（**线性水阻**）：

```
damping = 1 − liquid_damping × submergedRatio
v ← (v + Δv) × damping      ⇒      终速 v∞ = Δv × (1−ds) / (ds)
```

`submergedRatio` 由 `physics_info.density` 决定（浮力平衡点）：`density = 0.2` ⇒ 约 **0.226**。

⇒ **`forward_force` 只决定终速，不决定加速快慢**。加速的时间常数固定为

```
τ = 1 / (liquid_damping × submergedRatio)   （tick）
```

### 8.2 本车实测/复算

原值 `forward_force = 4,500,000`、`mass = 7,000,000`、`liquid_damping = 0.1`：

```
Δv = 4500000/7000000/400 = 0.001607 格/tick
v∞ = 0.001607 × 0.9774 / 0.0226 = 0.0694 格/tick = 5.00 kph   ← 与实测完全吻合
```

**这就是「到 5 kph 就上不去」的原因**：不是被 `max_speed_forward = 0.75` 卡住，而是水阻与推力的平衡点就在 5 kph。

### 8.3 现值（2026-10-01 定稿）：极速 **54 kph ≈ 30 节**，0 → 满速 **15 s**

> 换算：`格/tick = kph ÷ 72` ⇒ **54 kph = `max_speed_forward: 0.75`**。
> 终速 `v∞` 必须**高于**门控（留 ~15% 余量），否则永远爬不到上限、只会无限逼近。

| 字段 | 初值 | 现值 | 说明 |
| --- | --- | --- | --- |
| `max_speed_forward` | 0.75 | 0.75 | **54.0 kph ≈ 30 节**（门控 = 第一道天花板）|
| `max_speed_backward` | 0.3 | 0.3 | 21.6 kph |
| `density` | 0.2 | **0.5** | 吃水只由它定 ⇒ 主 cube 半潜、+2.68 格（见 §8.5）|
| `liquid_damping` | 0.1 | **0.0135** | ★ **唯一的"加速时间"旋钮** ⇒ τ = 148 tick = 7.4 s（见 §8.4）|
| `forward_force` | 4,500,000 | **16,400,000** | 终速 v∞ ≈ 0.862 格/t = 62.1 kph（15% 余量）|
| `backward_force` | 1,500,000 | **6,570,000** | 终速 ≈ 0.345 |
| `friction` | 14,000,000 | **14,000,000**（= mass × 2）| **开阔水面完全不参与**，只管搁浅/贴岸（见 §8.7）|

实测曲线（`liquid_damping 0.0135`）：1 s→7.9 kph、3 s→20.7、5 s→30.5、10 s→46.0、**15 s→53.9（到顶）**，稳态 53.8~54.0。
倒车同一套参数：**14.9 s 到 21.6 kph**。

**实际极速 = `min(max_speed_forward, v∞)` —— 两个天花板缺一不可**：只抬门控 ⇒ 卡在水阻平衡点；只抬力 ⇒ 卡在门控。
`k = (1−ds)/ds`，`ds = liquid_damping × submergedRatio`（平衡时 `submergedRatio = density`）⇒ 现值 `ds = 0.00675`、**`k = 146`** ⇒ mass 7e6 时 **每 1 格/tick 终速 ≈ 1.53e8 N**，即 `F ≈ 目标格/tick × 1.15 × 1.53e8`。
例：54 kph(`0.75`)→16.4M ✓｜60 kph(`0.8333`)→18.3M｜72 kph(`1.0`)→21.9M。

⚠️ **改航速会连带改掉头时间**（`yawStep ∝ motion`，满舵转向率正比于航速）：

| 极速 | 满舵转向率 | 掉头一圈 | 想维持 21 s 所需的 `turn_depth_scale` |
| --- | --- | --- | --- |
| **0.75（现，54 kph）** | 0.86°/tick | **21 s** ✓ | 0.083（现值，正是照 54 kph 定的）|
| 0.5（36 kph） | 0.57°/tick | 31.5 s | 0.0553（等效 depth 6.67）|
| 1.0（72 kph） | 1.13°/tick | 16 s | 0.111 |

### 8.4 `liquid_damping` = **加速时间**旋钮（`forward_force` 只能定终速）

```java
// PhysicsEngine.motionByBuoyancy()
double damping = Mth.clamp(1 - physicsInfo.liquidDamping * submergedRatio, 0, 1);
velocity = velocity.scale(damping);          // 每 tick 把【整个速度向量】乘这个系数
```

⇒ 一阶系统，**时间常数 `τ = 1/(liquid_damping × submergedRatio)` 与推力无关**。到达门控的时间 ≈ `τ × ln(v∞/(v∞ − max_speed_forward))`（15% 余量时系数 = **2.04**）。

⇒ **要"加速更慢"，唯一旋钮是调小 `liquid_damping`**；调小 `forward_force` 只会把终速一起压低（结果永远到不了极速，而不是慢慢到）。反过来说，调小 `liquid_damping` 后**所需推力也同比变小**。

| `liquid_damping` | `ds` | τ | **0→满速（54 kph）** | 配套 `forward_force` | `backward_force` |
| --- | --- | --- | --- | --- | --- |
| 0.1（原值） | 0.0500 | 1.0 s | 2.0 s | 127,105,000 | 50,842,000 |
| 0.05 | 0.0250 | 2.0 s | 4.0 s | 61,923,000 | 24,769,000 |
| 0.03 | 0.0150 | 3.3 s | 6.8 s | 36,777,000 | 14,711,000 |
| 0.02 | 0.0100 | 5.0 s | 10.2 s | 24,394,000 | 9,758,000 |
| 0.015 | 0.0075 | 6.7 s | 13.5 s | 18,249,000 | 7,300,000 |
| **0.0135（现）** | 0.00675 | 7.4 s | **15.1 s** ✓ | **16,400,000** | **6,570,000** |
| 0.01 | 0.0050 | 10.0 s | 20.3 s | 12,136,000 | 4,854,000 |

（表内 `forward_force` / `backward_force` 均按"终速留 15% 余量"反解，`density` 恒 0.5。）

⚠️ **代价**：`liquid_damping` 是**整个速度向量**的阻尼，同时管着 ① 受冲击后的垂向浮沉衰减 ② 松油门后的滑行减速 ⇒ 调到 0.0135 后船会**滑得更远、上下点头衰减更慢**（更"重"也更"飘"）。嫌晃就把值往回抬 —— 0.02 对应 10.2 s，也算接近"15 秒左右"。

### 8.5 吃水（泡在水里多深）只由 `density` 决定

`PhysicsEngine.motionByBuoyancy()`：

```
buoyancyForce = G × mass × displacedFluidMass / (density × 1000 × physicsCubeVolume)
```

平衡时 `buoyancyForce = G × mass` ⇒ `displacedFluidMass = density × 1000 × V`；水的 `fluidDensity = 1000` ⇒

```
吃水比例 submergedRatio = displacedVolume / V = density        ← mass 完全约掉，跟重量无关！
```

⇒ **想吃水更深：把 `density` 调大**（唯一旋钮）。`mass` 不影响吃水（平衡式两边约掉），`liquid_damping` 也不影响（只管阻尼）。

**跑的是主 cube**（`main_structure` 那个 14.69 × 8.93 × 120.78 格的 cube），所以吃水按**它的高度**换算：

| `density` | 吃水比例 | 水线在 cube 底以上 | 相对 0.2 下沉 | 对应 `forward_force`（54 kph，`liquid_damping` 0.0135）|
| --- | --- | --- | --- | --- |
| 0.2（原） | 0.200 | 1.79 格 | — | 7,000,000 |
| 0.25 | 0.250 | 2.23 格 | +0.45 格 | 8,610,000 |
| 0.30 | 0.300 | 2.68 格 | +0.89 格 | 10,260,000 |
| 0.40 | 0.400 | 3.57 格 | +1.79 格 | 13,700,000 |
| **0.50（现）** | 0.500 | 4.47 格 | **+2.68 格** | **16,400,000** ✓ |

⚠️ **步进是 cube 高的 1/16 = 0.558 格**：浮力只按 16 层采样（`samplesY = 16`），每层同 y ⇒ 吃水实际上是**按层跳**的。所以 `density` 别用小步（0.02 那种可能肉眼看不出变化），建议一次 ≥0.05。

⚠️ **`density` 会连带改航速模型**：`ds = liquid_damping × density` 变大 ⇒ `k = (1−ds)/ds` 变小、`τ = 1/ds` 也变小 ⇒ 同一个力推出来的终速变低、加速变快。所以**改 `density` 必须同步重算 `forward_force`**（上表最后一列）。

**硬约束**：`density` 必须 ≤ 1 —— `VesselVehicleData:44` 里 `density > 1` 会被**静默改成 0.3**；`density ≤ 0` 则 `motionByBuoyancy()` 直接返回、**完全不浮**（沉底）。

### 8.6 冷发射（弹射出筒 1 s 后点火）

两个字段配合（都是**站级**，写在 `parts[]` 里）：

| 字段 | 现值 | 含义 |
| --- | --- | --- |
| `cold_launch_time_tick` | **20** | 弹射段时长（tick）。这段时间内**不点火**（`RVP_ProjectileMotion` 取 `max(ignition_delay_tick, cold_launch_time_tick)`）|
| `cold_launch_velocity` | **[0, 1.5, 0]** | 弹射初速，**按载具主 cube 的三轴分解** |

**方向约定（`MissileEntity` / `RVP_ProjectileMotion.applyPreIgnitionVelocity`）**：

```java
Vector3f[] axes = carrier.getMainCubeOBB().obb().getAxes();   // [0]=x(右), [1]=y(上), [2]=z(前)
launchVelocity = axes[0]*v.x + axes[1]*v.y + axes[2]*v.z;
return carrier.getDeltaMovement().add(launchVelocity);       // ← 硬置，覆盖本 tick 速度
```

⇒ **`[0, +y, 0]` 是向上弹射**。反证：本体 `j36` 的机腹弹舱用 `[0, -1, 0]`（向下弹出再点火），说明 `axes[1]` 确实是"上"。

⚠️ **RVP 弹药的 `gravity` 默认是 0**（`RVP_ProjectileData.gravity` 缺省 `0f`，且代码里已不再默认施加 `-G`）⇒ 冷发射段是**匀速上升**：

```
冷发射段上升高度 = cold_launch_velocity.y × cold_launch_time_tick
```

所以 0.5 × 20 = **10 格**（太低，几乎出不了筒）；现值 1.5 × 20 = **30 格**（≈30 m，与真实 VLS 弹射高度同量级）。

包内先例：`9k720` / `irist_slm_tel` = **1.5**（tick 10）、本体 `htf5980` = **2.0**（tick 15）。052D 因为延迟给足了 1 s，用 1.5 刚好。

### 8.7 `friction` 只在【搁浅 / 贴岸】生效，开阔水面完全不参与

```java
// PhysicsEngine.decelerationByFriction(touchPoints)
if (!touchPoints.isEmpty() || suspensionGrounded) {
    // 减去 accelerationPerTick(friction, mass) = friction / mass / 400
}
```

- `touchPoints` = `collectContacts()` 采到的**方块**接触点；`suspensionGrounded` 只对**悬挂车**为真（船没有悬挂）。
- **船浮在水上时两者都不成立 ⇒ `friction` 一个 tick 都不生效**。水里的阻力**只由 `liquid_damping` 负责**。
- ⇒ 这正是"把 `friction` 调小、052d 却照样窜出去"的原因 —— 它压根不是推力，也不是水阻。
- 它真正管的是：**搁浅、压上岸、贴岸摩擦**（本体轮式 `friction = mass × 2`，重车/履带常更高）。
- 现值 **14,000,000 = `mass × 2`**（本体突击艇 `250 / 500` 同比例）。注意它同样要 `/mass/400` 换算：`14e6 / 7e6 / 400 = 0.005 格/tick²` ≈ **0.36 kph/s** —— 靠岸减速其实很弱，硬挡主要靠方块碰撞。
