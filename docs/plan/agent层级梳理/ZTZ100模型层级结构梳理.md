## ZTZ100 结构特点

- 根骨骼名为 `ZTZ100`（渲染）／`bone`（结构），与载具 id `ztz100` 都不同，配置动画控制器时注意区分
- **渲染骨与结构骨的 pivot 是 1:1 对齐的**（这辆车的模型做得规整，映射关系可以直接抄）：

  | 结构骨 | 对应渲染骨 |
  | --- | --- |
  | `turret` | `$weapon0` |
  | `turret_barrel` | `$weapon0_1` |
  | `turret_machine_gun_barrel` | `$weapon0_2` |
  | `commander_machine_gun` | `$weapon1` |
  | `commander_machine_gun_barrel` | `$weapon1_0`（末端 `$weapon1_0_0`） |
  | `laser_weapon` | `$weapon4` |
  | `aps_l` / `aps_l_barrel` | `aps_l` / `aps_l_0` |
  | `aps_r` / `aps_r_barrel` | `aps_r` / `aps_r_0` |
  | `ERA0 ~ ERA5` | `$ERA0 ~ $ERA5`（同序号对齐） |

- **激光武器是全包第一个真正的激光器**：`laser_weapon`（结构）↔ `$weapon4`（渲染），武器数据 `ztz100_laserweapon.json` 的类型是 `rvp:laser`（其余车上的 `*_laser` 都是激光**制导导弹**，不是激光器）。结构骨 `laser_weapon_barrel` 是 1 像素方块，纯发射点标记

## 推荐碰撞箱别名与倍率占位

本节用于给后续 `hitbox_display_name` 与 `hitbox_damage_factor` 配置提供一份直接可抄的参考表。

约定：

- "推荐别名"面向游戏内命中 debug 显示，优先保证短、直观、好读
- **"伤害倍率"已按 VT4 的同部位取值预填**（VT4 的 `hitbox_damage_factor` 是这套表的来源，它与 T90M 的对应部位取值一致），可直接整体抄进 `hitbox_damage_factor`，再按需要细调
- ERA 别名只写部位、不保留编号语义；车体 ERA 左 3 右 3，具体叫"车体爆反"还是"首上爆反"请按模型上实际位置定
- `virtual` 为预留虚拟命中区 → **不参与命中箱配置**（2026-09-17 定案，理由见下方「关于 `virtual` 的实测分析」）

### 关于 `virtual`（物理专用区）——2026-09-17 实测分析

你怀疑"打车体出现默认碰撞箱是虚拟命中区不稳"，**方向对了，但根因不是"不稳"，而且把它写进 `hitbox_damage_factor` 会出问题**。逐条给证据。

**① `virtual` 与其它命中骨的几何关系（ZTZ100 结构模型）**

| 骨 | X | Y | Z |
| --- | --- | --- | --- |
| `virtual` | -29 ~ 29 | **0 ~ 25** | -69.7 ~ 71.3 |
| `track`（左/右两条） | -27.1~-17.4 / 17.9~27.6 | 0 ~ 20.4 | -68.2 ~ 64.3 |
| `Engine` | -28.9 ~ 28.8 | 5 ~ 29.4 | -70.2 ~ -29.7 |
| `vehicle_body` | -29.9 ~ 29.8 | **7 ~ 27.4** | -35.2 ~ 36.3 |
| `Lower_front` | -29.8 ~ 29.7 | 7 ~ 15.4 | 34.8 ~ 69.3 |

对 `virtual` 的 204450 个体素（1 像素网格）逐点判定"是否被任何其它命中骨覆盖"：

- **未覆盖 40167 个 = 19.6%**；
- 按高度分布极度集中：**Y0 = 5518、Y1~Y4 各 5518、Y5~Y6 各 3978**，Y7 以上每层只剩 116~232（Y24 有 1605）。
- 也就是说：**车身底部中央那一条（两条履带之间、车体地板以下，Y 0~7 ≈ 底部 0.44 格）被 `virtual` 独家覆盖**，其它命中骨最低只到 Y=5（`Engine`）／Y=7（`vehicle_body`）。

**② 为什么这里有"默认碰撞箱"**

`RVP_VehicleHitboxFactorManager.VehicleHitboxConfig.resolve()`（:767-771）有一段**早退**，先于命中候选循环：

```java
if (!RVP_PhysicsOnlyCollisionHelper.getPhysicsOnlyCubes(vehicle).isEmpty()
        && RVP_PhysicsOnlyCollisionHelper.closestNonPhysicsOnlyHitPosition(vehicle, s, e) == null
        && RVP_PhysicsOnlyCollisionHelper.closestPhysicsOnlyHitPosition(vehicle, s, e) != null) {
    return HitboxDamageResult.disabled();   // ← factor=1.0、hitBoneName=null
}
```

含义：**只碰到 `physics_only_bone`、没碰到任何真实命中箱 → 直接返回 `disabled()`**。而 `hitBoneName == null` 时，`resolveHitboxDisplayName()`（:393-403）返回的是 `entity.rvp.<载具id>`（载具名翻译 key），这就是你看到的"默认碰撞箱"。顺带一提：走这条路 **factor 固定 1.0，ERA / 装甲倍率全都不生效**。

所以打车体底部、或任何只穿过"虚拟独有区"的低伸角射击，都会稳定复现"默认碰撞箱"——**不是随机不稳，是几何上必然**。

**③ 这不是 ZTZ100 独有的问题**

同样算法跑 T90M / VT4：`virtual` 区未覆盖率 **T90M 22.2%、VT4 18.6%**（两者 `virtual` 也都是 Y 从 0 起、车体骨从 Y≈7 起）。这是这套模型体系的既有特征。

**④ 把 `virtual` 写进 `hitbox_damage_factor` 会怎样（重要）**

- **在 physics-only 生效时：写了也不起作用** —— 早退分支在候选循环之前，`closestNonPhysicsOnlyHitPosition` 会跳过 physics-only 的 OBB，所以命中虚拟区仍然返回 `disabled()`。
- **在 physics-only 缓存为空时：会反噬**。`getPhysicsOnlyCubes` 挂在 `WeakHashMap` 上、由 `tickVehicles/tickClientVehicles` 重建，代码里还专门写了"physics-only 初始化失败不允许阻断实体"的防御（`RVP_PhysicsOnlyCollisionHelper:83`）→ 说明**存在为空/未就绪的窗口**。此时早退分支不成立，`virtual` 就作为普通命中骨进入候选，而它是**包住全车的最外层大盒子**，近端交点永远最近 → **会抢在所有分部位命中箱之前，全车都判成"车体 0.7"**。
- 这正好能解释"不稳"：**同一辆车、同一位置，随 physics-only 缓存是否就绪而给出不同结果**。

**⑤ 全包现状（旁证）**：34 台载具里 7 台配了 `physics_only_bone: virtual`（bmpt72 / lav25 / lavad / m1a2sep / t84bm / t90m / zbl08a），而 **把 physics-only 骨写进 `hitbox_damage_factor` / `hitbox_display_name` / `bone_modules` 的：0 台**。ZTZ100 若照你现在改的写，会是全包第一例。

### 关于"用 `virtual: 车体` 当探针"的可行性评估（2026-09-17 追加）

你的思路是：配 `virtual: 车体`，若偶发的"显示载具名"里偶尔变成显示"车体"，就说明是纯物理盒在作祟。**思路方向对，但这个探针做不出判定，而且信号方向是反的。** 证据如下。

**先看清"显示载具名"一共有几个出口** —— `hitBoneName == null` 时 `resolveHitboxDisplayName()`（:393-403）返回 `entity.<ns>.<id>`，就是载具名。全链路共 **7 个出口**：

| # | 位置 | 条件 | 触发前提 |
| --- | --- | --- | --- |
| ① | `:152-155` | `cfg == null \|\| !cfg.isEnabled()`（该车没配/配置没加载） | 任意车 |
| ② | `:159` | `cfg.structureModel` 为空 | 任意车 |
| ③ | `:163` | 结构模型实例取不到（未就绪） | 任意车 |
| ④ | `resolve` 首段 | `hitbox_damage_factor` 与 `bone_modules` 都空 | 任意车 |
| ⑤ | `resolve:767-771` | **physics-only 早退 → `disabled()`** | **仅配了 `physics_only_bone` 的车** |
| ⑥ | `resolve` 循环后 | `candidates.isEmpty()`（射线穿过车但没相交任何已配置骨） | 任意车 |
| ⑦ | `resolve` 循环末 | 所有候选都 `passThrough()`（该骨 ERA 模块已全失效） | 有小模块的车 |

**探针的两个致命问题**：

1. **会漏判（假阴性）**。出口⑤的早退**发生在候选循环之前**，`factorByBoneName` 里那条 `virtual` 根本不参与计算。所以**纯物理盒真正在作祟时，你看到的恰恰是"载具名"，永远不会是"车体"** → "没看到车体 ⇒ 不是物理盒"这个推论**不成立**。
2. **信号方向相反**。只有 `getPhysicsOnlyCubes` 为空时才不早退，此时 `virtual` 作为**包住全车的最外层盒**抢走**每一次**命中 → "车体"会**全量出现**（而不是偶发）。所以"看到车体"实际说明的是"**物理盒这条路这次没生效**"（缓存空窗口），即物理盒状态确实不稳定，但表现是"没拦截"而非"回退"。
3. 附带代价：探针期间一旦进入那个窗口，**所有命中数据都是废的**（全判 `virtual`），反而干扰你原本要观察的现象。

**结论（2026-09-17 补：已按几何逐方向推演，见下）**：

**① 别用别名探针——它在原理上不可能探到出口⑤。**
出口⑤的定义就是"**射线没碰到任何真实命中箱**"。既然所有真实骨都没被碰到，那么**任何**真实骨的别名都不会显示；而 `virtual` 那条配置又被早退挡在候选循环之外。**两个方向都堵死 → 不存在任何别名配置能看到出口⑤。** 这不是精度问题，是结构性不可能。

**② 真配上倍率会怎样——按来弹方向逐条推演**（`virtual` 是包住车体的盒，但其"最外层"只在部分方向成立）

| 来弹方向 | 谁先与射线相交 | 结果 |
| --- | --- | --- |
| **正前（沿 +Z 平射车体）** | `virtual` 前缘 Z **71.3** ＞ `Lower_front` 69.3 ＞ `Upper_front` 67.3 ＞ `Periscope` 53.3 | **`virtual` 抢先命中 → 每次都是"车体 / 0.7"**，你精心调的 `首上 0.7`、`首下 0.55`、`潜望镜 0.8` **全部失效** |
| **正下方 / 低伸角擦底** | `virtual` Y0 最低 | 同上，**`virtual` 抢先** |
| 正后 | `Engine` 后缘 Z **-70.2** 比 `virtual` 的 -69.7 略外 | 发动机舱正常 ✓ |
| 侧面（车体高度） | `vehicle_body` X ±**29.9**、`ERA` X ±29.2~34.8，都在 `virtual` 的 ±29 **外侧** | 侧甲 / 爆反正常 ✓ |

### A. 一号位主炮两个弹种被写成了"只能靠改装工具切换"（已修）

### B. 二号位激光武器站"固定向前"（已修）

两个叠加的根因：

1. **`commander_laser.rot_info` 写成了 `x_rot_speed: 0 / y_rot_speed: 0`**。子站的瞄准本身是被父站驱动的（`WeaponUnit.aim()` 末尾 `subWeaponUnits.forEach(u -> u.aim(worldPos))`；`LocalVehiclePlayer:281` 也会显式给子站下发瞄准点），但 `tickRot` 走的是
   `Mth.approachDegrees(当前, 目标, 转速)` —— **转速为 0 就永远停在原位**，表现就是"固定向前"。
   → 修正为 `x/y 转速 3`；**射界**（2026-09-17 用户定稿）：`y_rot_max 140 / y_rot_min -140`（水平 ±140°）、`x_rot_min -25`（仰角 25°）/ `x_rot_max 10`（俯角 10°）。
   ⚠️ **`x` 的正负是反的**：本体 `RotInfo` 里 **负数 = 仰角（抬升）**、正数 = 俯角（下压）。佐证：`m142.launcher` 是 `x_rot_min -85 / x_rot_max 5`（火箭炮抬 85°、压 5°）、`bmpt72.missile` 是 `-30 / 5`。
2. **控制器只绑了 `$weapon4` 的 `y` 轴**，俯仰没有任何渲染输出。
   → 已补 `x` 绑定。依据 `BoneBindingNode.applyPartBinding` → `builder.setRotation(boneIndex, axis, angle)`：**part_bindings 是按"轴"分别下发的**，同一根骨写两条（`axis: y` + `axis: x`）不会互相覆盖，可同时吃偏航与俯仰——所以**不需要**在渲染模型补 `$weapon4_0`。

渲染/结构两侧的层级事实（决定"能不能自动跟随"）：

| 侧 | 事实 |
| --- | --- |
| 渲染模型 | `$weapon4` 的父骨是 **`$weapon0`（炮塔）**，与 `$weapon1`（重机枪站）是**兄弟** → **不会**自动继承重机枪站的旋转，必须靠 part_binding 驱动 |
| 结构模型 | `laser_weapon` 的父骨同样是 `turret`，与 `commander_machine_gun` 兄弟 → 同样要靠自身 `rot_info` 转动 |

参考范式：`bmpt72` 的 `missile` 站（`base: turret` + `parent_weapon_unit_aim: true` + `x_rot_speed` 与炮塔一致）——全包所有 `parent_weapon_unit_aim: true` 的地面站都是这个形状。

### C. 激光站被写成了"同轴副武器"（已修）

初版把激光的引用写成 `{"id": "rvp:ztz100_laserweapon", "part_unit_id": "commander_laser", "secondary": true}` —— 这是 **同轴副武器**的写法。

**`secondary` 的真实语义**（本体 `WeaponUnit.combineAndInit`）：命中的武器对象被塞进父站的 `secondaryWeapons` 列表（`currentSecondaryWeaponIndex`），与主武器列表**分开管理**。**全包只有同轴机枪用它**（abramsx / m1a2sep / t84bm / t90m / vt4 / ztz100 的 `turret_machine_gun`，无一例外）。

`weapons` 条目的三种形态与落点（`WeaponUnit:249-355`）：

| 形态 | 落点 | 全包用例 |
| --- | --- | --- |
| `{"id": X, "part_unit_id": Y, "secondary": true}` | 父站 `secondaryWeapons`（副武器组） | **仅同轴机枪**（`1` 键开火 / `2` 键切） |
| `{"id": X, "part_unit_id": Y}` | 父站 `weapons`（主槽列表，**滚轮**切） | bmpt72 / lavad / ps1sm 的 `missile`、ah64 的 `auto_cannon` |

| `["A","B"]` 嵌套数组 | 多弹种槽（本体 `WeaponInfoSerializer` → `saveId="multi_weapons"`），**F** 键在槽内换弹种 | 各车主机炮 |

**按键对照（本体 `AllKeys` + `InputHandler` + `ClientVehicleSwitchWeapon`）**：

| 输入 | 消息 | 服务端 | 作用 |
| --- | --- | --- | --- |

| **F** `MULTI_WEAPON_SWITCH` | `MULTI` | `cycleMultiWeapon(…)` | **在选中的多弹种槽内换弹种** |
| **2** `SECONDARY_WEAPON_SWITCH` | `SECONDARY` | `switchWeapon(true, …)` | 切副武器组 |
| **1** `SECONDARY_WEAPON_SHOOT` | — | — | 副武器开火 |
| 左键 `MAIN_WEAPON_SHOOT` | — | — | 主武器开火 |

### F. 当前射速（2026-09-17 修正版）

> ⚠️ **本节曾写错**：我最初按"`shoot_interval` 单位 = tick"给出"主炮 15 s/发、激光 1 发/秒"，
> 用户以"火神炮同样 `shoot_interval: 20` 却很快"质疑后复核，**结论是 `shoot_interval` 根本不是射速字段**。

**`shoot_interval` 在代码里有三种读法（同一字段，单位自相矛盾）**：

| 读它的地方 | 当作什么 | 证据 |
| --- | --- | --- |
| **开火闸门 `isCoolingDown()`**（权威） | **毫秒** | `System.currentTimeMillis() - lastShootTime < getShootInterval() - (客户端 0 / 服务端 20)`；`lastShootTime` 亦为 `currentTimeMillis` |
| 抛壳音延迟 | tick | `AbstractVehicleWeapon:232` → `shootInterval / 20 * 1000` |
| 点射轮间隔 | 毫秒 | `RVP_WeaponFireController.startBurstVolleyAfterFirstShot` → `max(1, shootIntervalMs / 50L)` |

**`20` 毫秒 vs 1 tick = 50 毫秒 → 它不构成任何限制**：FULL_AUTO 按住时**每 tick 尝试一发 = 20 发/秒（1200 rpm）**。
所以"火神炮很快"与"激光器"是**同一个速度**——我先前说激光 60 rpm 是错的。

**真正的射速由 `max_capacity` + `reload.time` 决定**（`reload.time` 单位是 **tick**，`AbstractVehicleWeapon.tickReload()` 每 tick 递减）：

| 武器 | `shoot_interval` | `max_capacity` / `reload` | **实际射速** |
| --- | --- | --- | --- |
| **DTC-251 穿甲** | 300（≈0.3 s，非瓶颈） | 1 发 / 120 tick = **6 s** | **约 6 秒 / 发（10 rpm）**，另需 1 s 蓄力 |
| **DTB-251 高爆** | 300 | 同上 | **约 6 秒 / 发（10 rpm）** |
| **10KW 激光器** | 20（不构成限制） | 500 发 / 100 tick = 5 s | **爆发 20 发/秒**，持续射速见下 |
| *M61A1 火神炮（对照）* | 20 | 150 发 / 100 tick = 5 s | 爆发 20 发/秒；150 发打完装填 5 s → 长按均速 ≈12 发/秒 |

**持续射速由过热决定**（`RVP_WeaponHeatManager`：每发 +`heat_count`，冷却**每 tick 固定 −1 = 20 热/s**）：

```
持续射速上限 = 20 / heat_count   （发/秒）
```

激光 `heat_count: 10` → **持续约 2 发/秒**（爆发 2.5 秒打满 500 热后转为此速率）。

### H. 为什么激光"射速慢 + 看不到过热"（2026-09-17 第四轮 · 用户实测反馈）

**不是 `charge_tick` 的问题。** 它只是"蓄力/预转时长"，且只被 CHARGE / RAILGUN / MINIGUN 三种模式读取
（`RVP_WeaponFireController.tick:244-259`、`canShootNow:308-315`）；FULL_AUTO / SEMI_AUTO 在
`passesFireModeChargeGate:226` 直接 `return true`。激光是 `FULL_AUTO` + `charge_tick: 0` → **全程不参与**。

#### H.1 真凶一：站级槽让客户端冷却换成"代理自己的默认数据"

`commander_machine_gun.weapons` 的第二项 `{"part_unit_id": "commander_laser"}` 是**站级槽**。
本体 `WeaponUnit:305` 为它创建 `VehicleWeaponAgent`，而该代理构造时用的是
**`new BaseVehicleWeaponData()`**（`VehicleWeaponAgent:19`）——**本体默认数据，不是激光武器的数据**：

| 字段 | 代理（默认数据） | 激光武器 JSON |
| --- | --- | --- |
| `shoot_interval` | **100**（毫秒） | 20 |
| `max_capacity` | 64 | 500 |

客户端 `handleShoot` 取到的 `getCurrentWeapon()` 就是这个代理，走**本体 `doClientShoot()`**
（代理未覆盖），其 `isCoolingDown()` 用 **100 ms** 判定，而非激光的 20 ms。

> **⇒ 这就是"同样 `shoot_interval: 20`，火神炮快、激光慢"的原因**：火神炮是**直接武器**
> （走 `RVP_WeaponBase.doClientShoot()`，用自己数据的 20 ms，每 tick 都能通过），
> 激光被代理的 100 ms 卡住 → 客户端发包上限 **约 10 发/秒**。

#### H.2 真凶二：服务端仍在计热 → 秒级过热 → 射速被压到稳态

服务端 `RVP_LaserWeapon.shoot()` 走的是真实武器，每发 `+heat_count: 10`，而冷却**固定 20 热/秒**（每 tick −1）：

```
净热速率 = 10 × 射速 − 20   （热/秒）
```

- 射速 10 发/秒 → 净 **+80 热/秒** → 约 **6 秒**打满 `max_heat_count: 500` → 过热
- 过热瞬间再 `+overheat_extra_heat: 30`；必须等热量掉回 500 以下才能射下一发
  → **稳态约每 0.5 秒一发（≈2 发/秒）**

**体感 = 打几秒后突然变慢/断续**（用户描述的"射得特别慢"）。

#### H.3 为什么热量条不动

`RVP_WeaponBase.onClientFire:217-221` 显式跳过单机的客户端计热：

```java
boolean singlePlayer = Minecraft.getInstance().hasSingleplayerServer();
if (!singlePlayer) { fireController.onShotFired(); }   // 单机：客户端不计热
```

其注释假设"单机时服务端武器与本端武器是同一对象、共享同一热状态"，但服务端与客户端实体是
**两个实例**（分属 `ServerLevel` / `ClientLevel`），`HeatState` 挂在武器实例上
→ **单机下 HUD 读的是客户端那份（恒为 0）**。所以"看不到过热"，而服务端其实已在按过热限速。

> 本节为**源码推算**，未实机验证。

#### H.4 验证方法（一条改动即可定性）

把 `fire_data.heat_count` 改成 **`0`**（`max_heat_count` 保持 500，热系统仍"启用"但不加热）
→ 若射速立刻明显变快，即证实限速来自过热。

#### H.6 武器级过热 vs 站级过热：实现对比（2026-09-17 第五轮 · 用户指出 UI 显示 0）

**两套共用同一个 `RVP_WeaponHeatManager`**（加热 / 冷却 / 判定逻辑完全相同），差异只有**两处**：

| | **武器级**（`fire_data.heat_count` / `max_heat_count`） | **站级**（载具 JSON 的 `vehicle_heat_count` / `vehicle_max_heat_count`） |
| --- | --- | --- |
| 参数来源 | `RVP_FireData`（武器 JSON） | `RVP_VehicleWeaponHeatConfig`（载具 JSON 的 weapons 条目，`parseWeaponSlot:119-126`） |
| 参数是否跨端 | 武器 JSON 双端各自加载 ✓ | **只在服务端载具 JSON 里** → 由 `S2CVehicleRvpConfig.apply:101-127` 下发**载具 JSON 原文**后在客户端重新解析填充 |
| **HeatState 存放位置** | **`RVP_WeaponBase.localHeatState`**（`:46` 实例字段，`new HeatState()`） | **`VEHICLE_HEAT`**（`RVP_WeaponHeatManager:14`，`static WeakHashMap<AbstractVehicle, Map<SlotKey, HeatState>>`） |
| 分支判定 | `resolveSpec:93-94`（载具级 resolve 返回 null 时回落） | `resolveSpec:85-91`（载具级配置 enabled 时优先） |
| UI 读取 | `RVP_HeatHudOverlay:50-57` → `unwrap(activeWeapon)` 后取 `getFireController().heatRatio()` | 同一个 HUD、同一个 `heatRatio()`，只是 `resolveSpec` 走载具级分支 |

**共同缺陷：热量值本身没有任何网络同步。** `network/` 下无 Heat 相关包；
`S2CVehicleRvpConfig` 同步的是**配置**（载具 JSON 原文 → 客户端重新解析出 `heat_count`/`max_heat_count`），
**不是当前热量**。

**客户端唯一的热量写入点**是 `RVP_WeaponBase.onClientFire:217-221`（服务端回包触发），而它：

```java
boolean singlePlayer = Minecraft.getInstance().hasSingleplayerServer();
if (!singlePlayer) { fireController.onShotFired(); }   // ← 单机直接跳过
```

其注释假设"单机时服务端武器与本端武器是同一对象、共享同一热状态"。
**但 `localHeatState` 是武器实例字段，而服务端实体与客户端实体分属 `ServerLevel` / `ClientLevel`，
是两个 Java 对象** → 单机下客户端这份**没有任何加热来源**，恒为 0。

**⇒ 这解释了"UI 显示 HEAT 0%，但实际已经过热限速"**：
- `hasHeat()` 为 true（`max_heat_count: 500 > 0`）→ 卡片会显示
- 但比例取自客户端那份恒 0 的状态 → 永远 "HEAT 0%"
- 而**服务端**那份在正常累加 → 真的会过热、真的在限速

**⚠️ 关于"站级 UI 正常、武器级 UI 恒 0"的真正机制（2026-09-17 定论，已由用户实测确认）**：

用户实测：**同一个单机环境，M1A2 主炮（站级过热）显示正常，ZTZ100 激光（武器级过热）恒显示 0**。
关键事实：**M1A2SEP 是全包唯一一台配站级过热的载具**
（`vehicle_heat_count: 500 / vehicle_max_heat_count: 1750`，写在 `turret` 的 weapons 条目里），
而它的武器 JSON（`m1a2sep_m829a2` 等）**连 `heat_count` 字段都没有**。

**分水岭在 key 的相等语义**：MC 的 `Entity` **覆写了 `equals`/`hashCode`，按实体 id 比较**
（反编译源 `Entity.java:347-357`）：

```java
public boolean equals(Object pObject) {
    if (pObject instanceof Entity) { return ((Entity)pObject).id == this.id; }
    return false;
}
public int hashCode() { return this.id; }
```

- **站级**：HeatState 存在 `VEHICLE_HEAT`（**`static`** `WeakHashMap`，key = 载具实体）→
  单机下客户端实体与服务端实体 **id 相同 → `equals` 为 true → 命中同一条目**
  → 服务端算出的热量，客户端 HUD 直接就能读到 ✓
- **武器级**：HeatState 存在 `RVP_WeaponBase.localHeatState`（**武器实例字段**）→
  客户端武器实例与服务端武器实例是**两个对象、字段各自一份、无同步** → 客户端恒 0 ✗

> 这也解释了 `RVP_WeaponBase.onClientFire:213-215` 那句注释的来历："单机时服务端武器与本端武器是
> 同一对象、共享同一热状态"——**观察到的现象是对的（站级确实共享），但解释错了**：
> 共享不是因为有"同一对象"，而是 **`static` map + `Entity.equals` 按 id 命中**。

**结论：武器级与站级的差异不在"配置写哪儿"，而在"热量状态存哪儿"。**
站级恰好享受了 `static` map + id 相等带来的跨端共享，武器级没有。

**修法（方案 2 已落修，2026-09-17）**：
1. ~~零代码：改用站级配置~~ —— 未采用，改为直接根治。
2. **✅ 根治已实施**：新增 `RVP_WeaponHeatManager.WEAPON_HEAT`

### J. 激光热量重配（旧值是按错误射速配的）

**射速定案（代码级，2026-09-18 复核）**：

```
InputHandler.handleShoot:300  →  weaponUnit.getCurrentWeapon()          // 玩家开火
WeaponUnit:1249 getCurrentWeapon()  →  proxyWeapon(weapons.get(idx))    // ★ 解包
WeaponUnit:1237 proxyWeapon()       →  while (weapon instanceof VehicleWeaponAgent)
                                        weapon = agent.getWeaponUnit().getCurrentWeapon();
```

⇒ **玩家开火路径拿到的是真实武器实例**（`rvp:ztz100_laserweapon`），
`isCoolingDown()` 用武器 JSON 的 `shoot_interval`（20 ms）→ **每 tick 一发 = 20 发/s**。
`VehicleWeaponAgent`（`new BaseVehicleWeaponData()` → 100 ms / 64 发）**只影响 AI 等未解包路径**。
（更正此前"站级槽玩家侧只有 10 发/s"的说法。）

**旧值 `heat_count 60 / max 200 / extra 0` 在 20 发/s 下**：
净热 = 60×20 − 20 = **1180 热/s**，200 容量的条 **0.17 秒**就满 → 立刻过热锁死，
之后每轮只能打 0.17 秒、冷却 10 秒 —— 这正是用户看到的"射速被卡"。

**新值（已写入 `data/rvp/weapons/ztz100_laserweapon.json`）**：

```json
"fire_data": {
  "fire_mode": "FULL_AUTO",
  "heat_count": 2,
  "max_heat_count": 120,
  "overheat_extra_heat": 30
}
```

| 量 | 值 | 推导 |
| --- | --- | --- |
| 净热率 | 20 热/s | `heat_count × 射速 − 20` = 2×20 − 20 |
| 连射到过热 | **6 秒** | `max_heat_count / 净热率` = 120 / 20 |
| 过热后恢复 | **≈1.55 秒** | `(overheat_extra_heat + 1) / 20` = 31 tick |

**通用调参表**（射速 20 发/s，冷却固定 20 热/s）：

| 想要的连射时长 | `heat_count` | `max_heat_count` | `overheat_extra_heat` |
| --- | --- | --- | --- |
| 4 秒 | 2 | 80 | 30 |
| **6 秒（当前）** | **2** | **120** | **30** |
| 10 秒 | 2 | 200 | 30 |
| 6 秒但恢复更慢 | 3 | 240 | 60 |
| 永不过热（禁用过热） | 1（净热 0） | 任意 | — |

> ⚠️ `heat_count` 为 **int**（`RVP_FireData`），最小"能过热"的值是 **2**（=1 时净热恰为 0）。
> ⚠️ 上述时长基于"玩家开火 = 20 发/s"。**专用服务器**上客户端/服务端各自算冷却，以服务端为准，时长一致。
