## 已确认的现状

1. `src/main/java/org/ywzj/rvp/entity/projectile/RVP_MissileEntity.java:141`：两类制导映射为 DESIGNATE/MOUSE，共用 HITL 初始化、链路与相机入口。
2. 同文件 `:722` 至 `:767`：RADIO 链路把服务器玩家列表的 viewDistance × 16 当距离门槛；超过后累计 40 tick 置 severed 并关闭 HITL。20 TPS 时为 2 秒。默认异常回退 128 格。此门槛旨在避免后续 `level().clip` 长射线同步加载沿途区块，并非真实无线电射程。
3. 同文件 `:673`：`hitl_max_control_dist` 虽写入 hitlControlRange，但超距分支只从 tickHitlSession 返回，没有关闭控制；不能将配置值直接描述为当前有效硬上限。控制时间 hitlLife 递减，转向/指定输入会刷新；长途 DESIGNATE 模式还需核实心跳与空闲超时语义，避免观看途中无输入失活。
4. `src/main/java/org/ywzj/rvp/client/state/RVP_ClientHitlState.java:303`、`:330`：客户端从 ClientLevel 按 ID 取导弹；一旦已见导弹消失，立即 clear()。初次同步的 80 tick 等待不覆盖飞行中的跟踪丢失。`:294` 附近还依赖玩家持续骑乘母车，母车实体与骑乘关系也必须保留。
5. `src/main/java/org/ywzj/rvp/mixin/CameraTVMissileMixin.java:62`：目前主要修改 Camera.setup 后的位置与方向，并未建立远程地形订阅。
6. `src/main/java/org/ywzj/rvp/entity/projectile/RVP_BaseBullet.java:2310`：导弹继承的动态路径保活默认开启；`RVP_ChunkPathLoader` 与 `RVP_ChunkPathLoadManager` 已有预取、预算、entity-ticking 检查和等待机制。这是服务端飞行保护，不等于把远处地形和实体发送给观察玩家。
7. `src/main/java/org/ywzj/rvp/virtualflight/server/RVP_VirtualMissileEligibility.java:93`：虚拟中段明确排除 HITL/线导；不能用虚拟弹道替代操作者正在观察的真实导弹。
8. 根开发包只读核对到 7 份 HITL 配置，分属上述两类，均写有 hitl_max_control_dist=2000；HITL_TV 的控制 tick 为 400，HITL_CLOS_TV 为 600。未修改任何配置。

## 1.20.1 原版边界的本机字节码验证

使用 JDK 21 javap 检查本机 Forge 1.20.1-47.4.13 mapped jar：

- `ChunkMap$TrackedEntity.updatePlayer(ServerPlayer)` 按玩家真实位置计算距离，并取 min(实体有效跟踪距离, ChunkMap.viewDistance × 16)，超距调用 ServerEntity.removePairing。仅提高 EntityType.clientTrackingRange 无法绕过此上限。
- `ClientChunkCache.replaceWithPacketData(...)` 先检查 storage.inRange；范围外输出 Ignoring chunk since it's not in the view range 并返回 null。因此只发远程区块包也不足以完成适配。

PR 对应实现已读：DetachedBodyStreamer、TrackedEntityMixin、ClientChunkCacheMixin、LevelRendererOriginMixin、ClientDetachedView。PR 的操作者发现逻辑依赖 DetachedBodyVehicle 与其乘客，不能原封不动拿来识别导弹。PR 用副缓存救回远程中心以外的身体附近区块，并调整实体配对；其中 body 降载及无人机唤醒机制不属于本次建议范围。

RVP 既有 `server/remotevisibility/RVP_RemoteVehicleVisualSyncService` 是远距载具快照授权与代理体系，不是完整地形/通用实体流，不能直接视为已实现 HITL 远程观察。

## 建议适配分层

1. 会话：独立服务记录操作者 UUID、导弹 UUID/实体 ID、维度及会话序号，服务端验证所有权与当前控制状态。两类 HITL 共用，限制每人一个活动观察会话。
2. 区块：复用现有弹体路径保活，再增加导弹附近有界的可视区块窗口，随弹移动、前向预取、按差量与预算发送。保留玩家/母车正常加载与骑乘状态，处理远近窗口重叠。
3. 实体：保障活动导弹及其观察窗口内的真实目标持续同步；完整处理生成、移动、数据更新和移除，防止原版跟踪撤销与补发互相打架。已有远距代理与真实实体必须去重，否则会出现双影或锁错目标。
4. 客户端：为该会话处理远程区块缓存、光照、卸载以及绘制中心，避免仅有坐标而无地形或缓存槽冲突。优先独立管理类、网络和事件；必须触及原版边界时，按 agents.md 逐项论证最小注入，实施前列出具体目标方法和不可替代原因。本轮没有新增注入。
5. 链路：解除与渲染视距的耦合，让武器控制距离成为明确、可测试的限制；保留 RADIO/FIBER 区别及 ECM/DIRCM 等既有规则。无线电遮挡查询必须不触发同步加载/生成，可分段、缓存并限额；未加载的中间地形需明确状态策略，不能默认宣称无遮挡，也不能因一次数据未就绪直接永久断联。
6. 生命周期：进入时协调区块、实体与相机就绪；区分短暂同步未就绪、真实断联和导弹销毁。爆炸、手动退出、死亡、离车、换维度、下线与服务器停止均回收会话，释放额外订阅/票据，并恢复本体视图。

## 验证建议与未决项

- 两种操控模式分别覆盖越过旧视距边界、远距地面/移动载具打击、退出后返回母车画面、爆炸回收、ECM 和遮挡断联、多人独立观察。
- 比较已生成地形与新地形、高速连续跨区块；监测 MSPT、新增区块请求、每秒发送量和会话清理后的票据/缓存数，不以编译或空服 Done 代替客户端验收。
- 画面半径决定额外常驻区块数量；速度决定持续换入速度；新地形生成可能成为瓶颈。航程不需要整段常驻加载，但不能在实现前承诺零开销或任意距离稳定。
