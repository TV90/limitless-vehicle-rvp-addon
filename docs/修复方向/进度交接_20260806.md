## 2. 崩溃机制（一句话 + 详细文档）

**崩溃链**：RVP 公共数组 mixin 改脏 8 个本体类（`AbstractVehicle`、`WeaponUnit`、`MissileEntity`、
`RadarUnit`、`Radar`、`AbstractVehicleWeapon`、`ServerHitVehicleEvent`、`FixedWingVehicle`）→ Forge
对被改脏类 `COMPUTE_FRAMES` **全量重算所有方法栈帧** → 重算到带毒方法（常量池引用
`@OnlyIn(CLIENT)` 的 `LocalVehiclePlayer`）→ `RuntimeDistCleaner` 拒绝加载 → 崩。

**推论（关键，决定阶段 2 可行性）**：任何让这 8 个带毒类变 dirty 的 mixin（含 `@Accessor`、
`@Inject`、`@Overwrite`）都会触发崩溃。**因此阶段 2 恢复功能不能用任何针对这 8 类的 mixin，
只能走非 mixin 路径。**

带毒方法精确清单（16 个，来自 `build/javap_out/poisoned_methods.txt`）：
- `AbstractVehicle`: `afterVehicleRot` / `onLeaveVehicle` / `setSeats`
- `FixedWingVehicle`: `tickSound`
- `MissileEntity`: `updateOwner`
- `ServerHitVehicleEvent`: `lambda$onServerMessageReceived$0`
- `RadarUnit`: `tickDetect`
- `WeaponUnit`: `tickRemoteRot` / `tickFireControl` / `fireControlLock` / `worldOwnerViewPosition`
- `AbstractVehicleWeapon`: `currentAimHitPosition` / `onClientFire`
- `Radar`: `getClientLevelEntities` + 2 lambda

## 8. 经验教训（本次会话总结）

1. **崩溃根因是"帧重算时解析 @OnlyIn(CLIENT) 类型"**，不是本体 bug。排查时先看
   `RuntimeDistCleaner` 拒绝的类，再反查谁改脏了它——**不要一上来就怀疑本体逻辑**。
2. **公共数组 mixin = 服务端毒药**：任何针对"公共类含 @OnlyIn(CLIENT) 引用"的 mixin 都会在
   服务端炸，即使目标方法是惰性死代码。新写 mixin 前先扫目标类常量池（`javap` 或解包 grep）。
3. **`@Accessor` 同样改脏目标类**——想"只加接口不改方法"也不行，照样全类重算帧。
4. **责任归因原则**：本体单独跑正常 → 一定是 RVP 引入的触发条件；RVP 的 mixin 改脏是唯一变量。
5. **修复要分层**：先"让系统跑起来"（改配置/可逆），再"恢复功能"（逐项、记录），避免一次大改。
6. **交接文档 > 聊天记录**：关键中间产物（中毒方法清单、对照表、命令）必须落盘，
   否则长会话上下文丢失就前功尽弃。
7. **`instanceof` 降级 vs 强转**：RVP 对扩展接口的引用应一律用 `instanceof`，禁止直接强转
   （强转在 mixin 缺失时抛 ClassCastException，instanceof 只静默失效）。
