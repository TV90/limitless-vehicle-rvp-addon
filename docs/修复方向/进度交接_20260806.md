## 2. 崩溃机制（一句话 + 详细文档）

**崩溃链**：RVP 公共数组 mixin 改脏 8 个本体类（`AbstractVehicle`、`WeaponUnit`、`MissileEntity`、
`RadarUnit`、`Radar`、`AbstractVehicleWeapon`、`ServerHitVehicleEvent`、`FixedWingVehicle`）→ Forge
对被改脏类 `COMPUTE_FRAMES` **全量重算所有方法栈帧** → 重算到带毒方法（常量池引用
`@OnlyIn(CLIENT)` 的 `LocalVehiclePlayer`）→ `RuntimeDistCleaner` 拒绝加载 → 崩。

**推论（关键，决定阶段 2 可行性）**：任何让这 8 个带毒类变 dirty 的 mixin（含 `@Accessor`、
`@Inject`、`@Overwrite`）都会触发崩溃。**因此阶段 2 恢复功能不能用任何针对这 8 类的 mixin，
只能走非 mixin 路径。**

带毒方法精确清单（16 个，来自 `build/javap_out/poisoned_methods.txt`）：
- `AbstractVehicle`: `afterVehicleRot` / `onLeaveVehicle` / `setSeats`
- `FixedWingVehicle`: `tickSound`
- `MissileEntity`: `updateOwner`
- `ServerHitVehicleEvent`: `lambda$onServerMessageReceived$0`
- `RadarUnit`: `tickDetect`
- `WeaponUnit`: `tickRemoteRot` / `tickFireControl` / `fireControlLock` / `worldOwnerViewPosition`
- `AbstractVehicleWeapon`: `currentAimHitPosition` / `onClientFire`
- `Radar`: `getClientLevelEntities` + 2 lambda

## 4. 移除的 28 个 mixin 详细清单（功能丢失依据）

> 每个条目 = 恢复该功能时的索引。恢复方式候选（非 mixin）：继承覆写 → Forge 事件 → 网络包+独立管理类 → 数据层 JSON。

### 4.0 恢复决策准则（恢复每个功能前必读，顺序执行）

**Step 1 — 判定目标类是否带毒**（决定能不能用 mixin）
- 判定方法：解包本体 jar → 在目标类字节码里 grep `LocalVehiclePlayer`（或其他 `@OnlyIn(CLIENT)`
  类型，如 `net/minecraft/client/Minecraft`、`EntityRenderDispatcher` 等）。本体已解包在
  `build/scan_tmp/`，RVP 已解包在 `build/rvp_scan_tmp/`。
- 结论分流：
  - **带毒类（常量池含客户端类型）→ 永不打公共数组 mixin**，`@Inject`/`@Accessor`/`@Overwrite`
    一律禁（都会触发全类重算帧 → 崩）。**不带毒类 → 可正常打 mixin**（现有 20 个保留公共
    mixin + client 数组全是安全案例）。
  - 已知带毒公共类黑名单：`AbstractVehicle`、`FixedWingVehicle`、`MissileEntity`、
    `ServerHitVehicleEvent`、`RadarUnit`、`WeaponUnit`、`AbstractVehicleWeapon`、`Radar`
    （完整 46 类带毒名单见 `修复方案总结.md` 第 5 节）。

**Step 2 — 按"实例化控制权"分流**（决定恢复手段）

| 恢复手段 | 适用条件 | 示例 |
|---|---|---|
| 继承覆写（最干净） | RVP **自控实例化**的类：RVP 实体/武器 extends 本体带毒类，覆写方法时重写成双端安全逻辑 | `RVP_MissileEntity extends MissileEntity`、`RVP_WeaponBase extends AbstractVehicleWeapon` |
| 独立管理类 + 网络包 | 本体装配系统**实例化**部件（`WeaponUnit`/`RadarUnit`），RVP 无法替换实例 | 锁定状态旁路 `Map<WeaponUnit,状态>`、发射架部署、联动 UAV |
| Forge 事件 | 本体行为有事件可挂 | 伤害系数（`LivingHurtEvent`） |
| 数据层 JSON | 行为可数据化 | 武器数据字段 |
| 反射（最后手段） | 本体私有字段无 getter、功能不可放弃 | `weaponBayUnits` / `currentWeaponIndex` 访问（注意 SRG 重映射脆弱性） |
| 永久降级（记录即可） | 本体封闭路径 + 无事件/无接口 | Radar 扫描过滤（RadarSignatureMixin） |

> 注意：**不要"完全复制本体类"**（在 RVP 包造副本类）。本体装配系统只会实例化本体类，
> 副本类无法介入，且破坏 `instanceof` 与数据流。正确做法是"继承 + 重写安全逻辑"，不是"复制"。

**Step 3 — 恢复后验证与记录**
1. 每恢复一项 → 构建 → 部署 → 启动验证（`Done`）→ 在 `../调试与修复规范.md` 第 4 节
   功能丢失表追加"已恢复"记录（日期/手段/验证结果）。
2. 若引入新 mixin：先过 Step 1 带毒判定，再决定放公共数组还是 `client` 数组；
   公共数组目标必须双端安全。
3. 恢复顺序参考第 7 节优先级（P0 武器核心 → P1 炮手 → P2 雷达/UAV/装甲）。

**4.6.4 D 组 2 个"无替代"功能的 RVP 侧等效方案**

**D-1 命中提示报文显示真实伤害（ServerHitVehicleEventMixin）→ 可被 A9 吸收，等效 ~100%**
- 原机制：HitboxDamageFactorMixin（A9）在 hurt 中算 `displayDamage` 写入接口 →
  ServerHitVehicleEventMixin 在报文构造时读出写入 `damage`。
- 等效方案：**恢复 A9 时把 RVP 伤害系数直接应用到服务端实际伤害**（调用 public
  `DamageSystem.hurt` 前改好 damage 值）→ `HitVehicleEvent.damage`（final）本身就是系数后
  伤害 → 客户端显示的报文伤害天然正确 → **ServerHitVehicleEventMixin 不再需要**，功能被吸收。
- 结论：不用单独实现，随 A9 一起恢复即可，无需 RVP 自写报文逻辑。

**D-2a 雷达行为接管（RadarUnitMixin 行为注入）→ RVP 低频自扫描 + 直接写本体雷达结果，近似等效 ~80-90%**
- 原机制：HEAD-cancel 拦截 `tickTargets/tickDetect`，让 RVP 逻辑接管扫描。
- 等效方案（分三层，逐层增强）：
  1. **基础**：RVP 低频扫描管理器（TickEvent，间隔若干 tick）遍历附近实体，按 RVP 规则
     过滤目标 → `ServerVehicleWarn` 告警（服务端已可感知）。
  2. **增强**：本体 `RadarUnit.getDetectedEntities()` 返回**同一实例**的 public Map，
     `RadarUnit.detect(Entity)` 也是 public——RVP 可直接往本体雷达结果里
     `put` RVP 弹体目标（若本体客户端 UI 读该 Map 同步数据，RVP 弹体即出现在雷达 UI 上）。
     此步需实测本体是否同步 detectedObjects 到客户端。
  3. 若本体 UI 不同步该 Map，退化为 RVP 自建告警 + 客户端渲染叠加。
- 结论：用户可感知的"雷达发现 RVP 弹体/告警来袭"可等效；"本体雷达 UI 精确显示 RVP 弹体"
  取决于本体同步机制，实测后定。

**D-2b 本体导弹 ARM 增强（MissileEntityMixin）→ 核心不受影响，仅本体导弹附加行为降级**
- **关键事实**：RVP 导弹（`RVP_MissileEntity → RVP_BaseBullet`）已有**完整自有 ARM 逻辑**
  （`RVP_BaseBullet.java:943-971` 反辐射状态机、`:1508/1524/1628/1834` 活跃雷达目标过滤、
  ARM 近炸引信）。MissileEntityMixin 只是把同样逻辑挂到**本体导弹**（VehicleMissile 发射的
  `MissileEntity`）上。
- 结论：**RVP 武器发射的反辐射导弹完全不受影响**。丢失的只是"本体导弹带 RVP ARM 行为"
  这一附加能力 = 次要降级，建议永久放弃（恢复成本高、收益低，且需 RVP 自建弹体映射）。

### 4.7 作者答复后的机制再确认（2026-08-06 补充，修复方向不变）

**4.7.1 作者答复要点（原话）**
1. 本体标 `@OnlyIn` 就是警告不允许跨端用。
2. 哪里写了服务端会加载到 `LocalVehiclePlayer` 的代码，哪里自己继续标 `@OnlyIn`。
3. 例：`AmmoEntity.readSpawnData` 是"服务端→客户端同步实体初始化数据"的方法，只在
   客户端调用，用 `LocalVehiclePlayer.instance.getPlayer()` 是正常的。

**4.7.2 机制再确认（与作者答复完全自洽，方向不需要推翻）**

- 作者说得对：**正常加载时这些类不会崩**。JVM 惰性解析，服务端不执行 `readSpawnData`
  等客户端专用方法，也不会去解析方法字节码里的 LVP 引用。
- 崩溃的真正触发：**mixin 改脏类 → COMPUTE_FRAMES 全类重算所有方法栈帧 → ASM 强制解析
  方法字节码里的每一个类型引用（含死代码分支里的 LVP）→ `RuntimeDistCleaner` 拒载**。
- 精确的"危险类"判定（比 46 个带毒类更准）：**类中存在"非 `@OnlyIn(CLIENT)` 方法"里的
  客户端类型引用**。这类方法不被 dist cleaner 剥离，LVP 引用留在服务端字节码中，帧重算
  必崩。→ 即 8 个危险类的 16 个方法（`poisoned_methods.txt`）。
- 反例：`AmmoEntity` 等"带毒但安全"的类，LVP 引用全部在 `@OnlyIn(CLIENT)` 方法里，服务端
  加载时方法被 dist cleaner 剥离 → 帧重算不碰 LVP → `BaseBulletAccessor` 打它没事（已验证）。
- **结论：阶段 1 移除 mixin 是正确且必要的，作者答复不构成推翻。责任确认仍在 RVP 侧
  （mixin 帧重算 + RVP 自身 @OnlyIn 标注缺失）。**

## 8. 经验教训（本次会话总结）

1. **崩溃根因是"帧重算时解析 @OnlyIn(CLIENT) 类型"**，不是本体 bug。排查时先看
   `RuntimeDistCleaner` 拒绝的类，再反查谁改脏了它——**不要一上来就怀疑本体逻辑**。
2. **公共数组 mixin = 服务端毒药**：任何针对"公共类含 @OnlyIn(CLIENT) 引用"的 mixin 都会在
   服务端炸，即使目标方法是惰性死代码。新写 mixin 前先扫目标类常量池（`javap` 或解包 grep）。
3. **`@Accessor` 同样改脏目标类**——想"只加接口不改方法"也不行，照样全类重算帧。
4. **责任归因原则**：本体单独跑正常 → 一定是 RVP 引入的触发条件；RVP 的 mixin 改脏是唯一变量。
5. **修复要分层**：先"让系统跑起来"（改配置/可逆），再"恢复功能"（逐项、记录），避免一次大改。
6. **交接文档 > 聊天记录**：关键中间产物（中毒方法清单、对照表、命令）必须落盘，
   否则长会话上下文丢失就前功尽弃。
7. **`instanceof` 降级 vs 强转**：RVP 对扩展接口的引用应一律用 `instanceof`，禁止直接强转
   （强转在 mixin 缺失时抛 ClassCastException，instanceof 只静默失效）。
