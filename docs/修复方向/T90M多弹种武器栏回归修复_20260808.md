# T90M 多弹种武器栏回归修复（恢复 combineAndInit 装配）

日期：2026-08-08

## 意图

用户报告 T90M 四个武器栏问题 + 一个过热问题，明确要求对照旧代码副本
`D:\ywzj\ywzj\ywzj_rvp - 副本` 排查。本文记录武器栏问题的根因与修复。

## 问题清单（用户原话摘要）

1. 多弹种样式不对：主炮变成两个武器栏（应为 AP+HE 合并为一个多弹种槽）
2. 滚轮不能切换到第二个武器栏
3. 主炮换弹动画 UI 消失
4. 按键 1 使用同轴机枪变成烟雾弹
5. 过热系统：开一炮直接过热，疑似无 tick 防护（见文末单独分析）

## 根因

### 新旧机制差异

| 维度 | 副本（旧代码，正常） | 当前（回归） |
| --- | --- | --- |
| 装配触发 | `WeaponUnitGroupedSlotMixin` 在 `WeaponUnit.combineAndInit` HEAD 拦截装配并 `ci.cancel()` | 删除该 mixin，改用 `RVP_GroupedSlotSpawnHandler` 每 tick 延迟装配 |
| 装配时机 | 实体初始化阶段（服务端构造 / 客户端 `readSpawnData`），早于 `EntityJoinLevelEvent` | 实体加入世界后的服务端/客户端 tick 遍历 |
| 客户端覆盖 | `combineAndInit` 双端必然执行（客户端 `readSpawnData` 第 272 行也调 `initData()`） | 客户端 tick 遍历依赖 `level.entitiesForRendering()`，仅渲染范围内实体，范围外/延迟装配不可靠 |
| 装配后一致性 | 武器对象自创建即为 3 槽结构，同步数据 / HUD / 索引一致 | 加入世界后才替换武器对象，破坏双端同步、HUD 绑定、切换索引 |

配置加载路径（单机）确认：`RVP_VehicleExtendedConfigManager.INSTANCE` 为 static 单例，
服务端数据仓库 `AddReloadListenerEvent` reload 后填充；客户端实体复用同一 static 实例，
故 `combineAndInit` 时双端配置一致、装配必然成功（副本机制）。

### 症状与机制对应

- **主炮两个武器栏 / 换弹 UI 消失 / 滚轮与按键错乱**：客户端装配未执行或执行时机错乱，
  T90M 保持本体默认 4 槽 `[AP组, HE, 机枪代理, 烟雾弹]`；机枪代理在本体
  `combineAndInit` 的 `id == null` 分支无条件进 `weapons`（不看 `secondary`），
  而装配器把它放 `secondaryWeapons`，导致主/副武器槽位、HUD 圆点、换弹动画全部错位。
- **按键 1（SECONDARY_WEAPON_SHOOT）** 发射 `secondaryWeapons` 当前槽：装配正确时即同轴机枪。

## 改动点

1. 新增 `src/main/java/org/ywzj/rvp/mixin/WeaponUnitGroupedSlotMixin.java`
   - `@Inject(method = "combineAndInit", at = @At("HEAD"), cancellable = true)`
   - `shouldHandle` 命中（`hasGroupedWeaponSlots`）时调 `RVP_GroupedWeaponSlotAssembler.assemble` 并 `ci.cancel()`。
2. `src/main/resources/ywzj_rvp.mixins.json`：公共数组第 29 行注册 `WeaponUnitGroupedSlotMixin`。
3. 删除 `src/main/java/org/ywzj/rvp/event/RVP_GroupedSlotSpawnHandler.java`（tick 延迟装配，
   与 combineAndInit 装配双机制冲突）。
4. `RVP_VehicleSpawnHandler`：修正指向已删类的 javadoc；`refillAllWeapons` 恢复为 private
   （仅事件内调用；装配已在 combineAndInit 完成，早于 `EntityJoinLevelEvent`，补弹覆盖新武器实例）。

## 预期影响

- T90M / M1A2SEP 装配回落到副本一致行为：主炮 AP+HE 合并为外层 `VehicleMultiWeapons`（3 槽）。
- 滚轮 PRIMARY 循环、F 键大组切换（`WeaponUnitMultiWeaponSwitchBlockMixin` 放行 grouped carrier）、
  按键 1 同轴机枪、HUD 圆点与换弹动画恢复。
- 未触碰：过热系统、`RVP_VehicleExtendedConfigManager` S2C 同步、`WeaponUnitMultiWeaponSwitchBlockMixin`。

## 验证方式

- 手动 build（`gradlew compileJava` / `build`），dev 环境放 T90M：
  - 主炮一个武器栏，圆点 2 个（AP 组 / HE），滚轮不再切出独立主武器槽；
  - 按 1 发射同轴机枪，H 键烟雾弹；
  - 主炮射击后有换弹动画 UI。

## 过热问题（M1A2SEP）修复

### 意图

用户确认过热在 **M1A2SEP** 复现，期望修复"一炮直接过热"问题。**不调整热参数数据**
（用户明确要求只修 bug，不改 m1a2 的 `vehicle_heat_count`，仍为 500）。

### 根因

数据核对：仅 m1a2sep.json 有热配置（`vehicle_heat_count: 500`、`vehicle_max_heat_count: 1750`、
`vehicle_overheat_extra_heat: 30`）；T90M 载具/武器 JSON 均无 heat 字段 → T90M 热系统默认关闭
（`HeatSpec.enabled() = maxHeatCount > 0`）。

M1A2SEP 主炮为分组多弹种槽（`VehicleMultiWeapons`），客户端单发存在 **双计热**：

| 时机 | 调用链 | 加热 |
| --- | --- | --- |
| 发包即时 | `VehicleMultiWeapons.doClientShoot` RETURN → `VehicleMultiWeaponsChargeGateMixin.ywzj_rvp$afterShot` → `fireController.onShotFired()` | +500 |
| 服务器回包 | `ServerVehicleFire`（TRACKING_ENTITY）→ `VehicleFireEvent.Post` → `AllEvents.onVehicleFire` → `weapon.onClientFire()` → `RVP_WeaponBase.onClientFire` → `fireController.onShotFired()` | +500 |

即客户端每发实际 +1000（预期 2 倍），配合 FULL_AUTO + `shoot_interval: 20`（1 发/秒）按住连发，
第 3 发即触顶 1750 过热 —— 表现为"开一炮直接过热 / 按住鼠标持续计算过热"。
（服务端 `RVP_ProjectileWeapon.shoot` 的 `onShotFired()` 为服务端实体独立 HeatState，仅作服务端门控，不影响 HUD。）

### 改动点

1. `RVP_WeaponFireController`：从 `onShotFired()` 拆出 `resetStateAfterShot()`
   （仅重置 CHARGE/RAILGUN/BURST 模式状态，不加热）。
2. `VehicleMultiWeaponsChargeGateMixin.ywzj_rvp$afterShot`：改调 `resetStateAfterShot()`，
   发包后不再即时计热；热量统一由服务器回包（Post → `onClientFire`）记录一次。
   - 修复后客户端每发实际 +500（原 +1000 的一半），配合 4.5s 装填冷却，按住连发约 4-5 发才过热。
   - m1a2sep.json 数据未改动（`vehicle_heat_count` 保持 500）。

### 预期影响

- 每发实际计热从 1000 恢复为 500（去重，数据不变）。
- 单弹种 RVP 武器（非 multi）不受影响：其客户端计热本就只走 Post → `onClientFire` 一次。
- CHARGE/RAILGUN/BURST 多弹种武器的蓄力/点射状态重置逻辑保持不变（`resetStateAfterShot`）。

### 验证方式

- M1A2SEP 主炮连续开火，观察 HEAT 百分比：每发约 +29%（500/1750，修复前双计热等效 +57%），
  不再是单发近半/直接触顶；停止射击后百分比按冷却速率回落。

### 遗留说明

- `WeaponUnitMultiWeaponSwitchBlockMixin`（target=WeaponUnit、公共数组注册）为 B 系列规范隐患，
  当前实测可用，建议后续评估。
