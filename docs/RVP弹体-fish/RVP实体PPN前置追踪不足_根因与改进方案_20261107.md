# RVP 实体 PPN 前置追踪不足：根因定位与改动方案

日期：2026-11-07
状态：**已实施（2026-11-07）**。新增 `RVP_GuidanceData.ppn_lead_feedforward_ticks` 与实体 PPN 前置前馈，默认 10 Tick；含 HQ-10/HQ-9B 的纯 PPN / 纯 PIP / 方案 B 三模式仿真对照；完整构建 **1799 项测试，失败 0、错误 0、跳过 1**。

结论先说：这不是 PPN 公式写错，而是 PPN 只有**反馈项**、没有**前馈项**。航向误差按 `(R/R0)^N` 收敛，N=3 时到剩余距离 75% 处才建立约 43% 的前置角，剩下的前置角被压到末段集中修正；旧 PIP 的“指向预测相遇点”恰好提供了这个前馈。实施采用“远距前置前馈 + 末段退坡到纯 PPN”；按 HQ-10/HQ-9B 实测，前馈窗从草稿的 45 Tick 收紧到 **10 Tick**，避免 PPN 在末段过早接管、把恒定横穿的脱靶又拉回去。

### 1.3 现象结论

- PIP 在 **75% 距离、约 1/4~2/5 飞行时间** 就把前置角建立到 95% 以上，之后基本沿碰撞航向直飞。
- PPN 在 75% 距离只有 **43%~47%** 的前置角，60% 距离约 67%，要到 **30% 距离** 才接近 95%。
- 缺口不是均匀补的：PPN 的剩余量在末段以更大的航向变化率集中修正。高速横穿中，75% 距离处还差约 21° 前置角；其中约 19° 是在 75%→30% 这一段（约 77 Tick / 3.9 秒）补掉的，剩下约 2° 在最后 30% 距离内完成。这就是玩家看到的“前面不怎么前置，靠近了才甩一大下”。
- 同一场景首次接近最小距离：PIP 1.82 格，PPN 2.94 格（压力场景，仅说明几何趋势，不作为 2 格验收门槛）。

## 2. 根因

### 2.1 主因：PPN 只有反馈，没有前馈；航向误差按 `(R/R0)^N` 收敛

当前实现（`RVP_ProportionalNavigationMath.solve`，第 53–96 行）：

```text
r = 目标位置 - 弹位置
v_rel = 目标速度 - 弹速度
ω = (r × v_rel) / |r|²
a = N · (ω × 弹速度)          // 第 74 行
转角/刻 = |a| / 弹速 = N·|ω|  // 第 92 行；ω 与弹速近似垂直时成立，未计入执行器限幅
```

其中 N 来自 `guidance_data.predict_target_pos_gain`，默认 3.0（`RVP_GuidanceData` 第 79–85 行），当前所有武器都没有覆盖。

把碰撞航向记为参考方向，令航向误差为 ε、目标相对视线的横向速度为 `Vt⊥ ≈ Vm·εc`（εc 为所需前置角），视线角速度为 `λdot`。小角度下：

```text
视线横向相对速度  u = Vt⊥ - Vm·sin ε ≈ Vt⊥ - Vm·ε
λdot = u / R
PPN 把 λdot 压向 0： dε/dt = -N·λdot = -N·u/R
                  du/dt = -N·Vm·u/R
又 dR/dt = -Vc：    du/u  = N·dR/R
                  => u ∝ R^N
                  => ε = εc · [1 - (R/R0)^N]
```

即**剩余前置角比例 = `(R/R0)^N`**。N=3 时：

| R/R0 | 剩余前置角比例 | 已建立比例 |
| ---: | ---: | ---: |
| 0.75 | 42% | 58% |
| 0.60 | 22% | 78% |
| 0.50 | 12.5% | 87.5% |
| 0.30 | 2.7% | 97.3% |

需要补的剩余误差在末段所需的法向加速度约为 `ε_remain·Vm/R ∝ R^(N-1)`；N=3 时它随距离缩小按 **R²** 增长，所以修正天然堆在末段。这与 1.2 的实测吻合（实测比理想再低约 10~15 个百分点，来自启动 Tick 与机头响应滞后，见 2.3）。

关键点：**这是 PPN 的结构性质，不是数值 bug**。PPN 的指令与视线角速度成正比，而远距时视线角速度本身很小（`ω ≈ Vt⊥/R`），所以远距指令天然小；它靠“距离越近、同样的航向误差产生越大的 ω”来收尾。旧 PIP 把期望方向指到预测相遇点；对没有 `rvp_maxg` 的现役弹，这个方向还会经过 `turning_factor`（0.06~0.14）的单 Tick 比例插值再提交——6%×38°≈2.3°/Tick，仍明显大于 PPN 的 `N·ω`（约 0.5~1°/Tick），所以前 1/4~2/5 飞行时间就把前置角建完。差别在**前馈方向 + 大误差比例响应** vs **PPN 的小误差反馈**，不在“阶跃”或“预测点算得准不准”。

### 2.3 二级放大因素（不是主因，但会让“晚”更明显）

1. **N 固定 3.0，且当前所有武器都没覆盖。** 把 N 提到 5，75% 距离处的已建立比例从 58% 提到 76%，60% 处从 78% 提到 92%；但末段法向过载需求约按 N 增大，且 PPN 文档已明确“增益不提高 G/攻角/机头转速预算”，N 过大时执行器饱和会把“晚修正”变成“过冲/脱靶”，还会放大目标速度抖动的视线角速度噪声。**调 N 是缓解，不是结构修复。**

2. **机头/攻角响应滞后约 7~12 Tick。** 现役 PPN 弹的 `turning_factor` 为 0.06~0.14（HQ-10/ESSM 0.06、9M317M 0.08、IRIS-T/AIM-260 0.09、AIM-120D/PL-15 0.10、FIM-92 0.12、MICA 0.14），在 `RVP_AttackAngleInertiaModel.response` 中作为每 Tick 姿态响应比例，再乘 `sqrt(动压因子)`；`maxTurnDeg = 90·response·动压因子`。PPN 的远距指令本来就只有零点几度/Tick，再经过这个一阶滞后，前 10~20 Tick 的实际转角会被进一步压小。回放里 90% 距离处 PPN 前置 1.2°、理论约 3°，差的就是这一段。

3. **高抛弹的 PPN 被路线权重推迟。** 只要 `loft_height_above_target > 0` 且未自主截获，`loftWeight = smoothstep((水平距离 - loft_end)/loft_blend)`：AIM-120D 是 700/700（水平 1400 格内才开始有 PPN 权重），PL-15 是 200/700（900 格内）。更远处导弹飞的是“到高抛辅助点的 PIP 路线”，PPN 只塑形末段。回放显示 AIM-120D/PL-15 的 PIP 与 PPN 前置曲线几乎重合，说明**高抛工况下当前瓶颈不是 PPN 本身，而是路线权重**；本方案不改变高抛路线，前馈只作用于 PPN 分量，`loftWeight=1` 时被路线完全覆盖，权重降低后逐步参与，对高抛是中性到略改善。

4. **导引头截获前的中段没有实体 PPN。** ARH 在自主截获前，`RVP_RuntimeActiveSeekerGuidance` 可能返回固定记忆点 `RVP_GuidanceIntent.point(...)`（第 43–48 行），走纯追踪/无制导；AIM-120D 的 `active_radar_activation_range=384`、`guidance_target_distance_range=[[0,1500]]`。如果玩家观察到的“晚修正”发生在导引头截获之前，那是**中段点制导**的问题，不在本次 PPN 改动范围内；本方案只改善“已经进入实体 PPN 之后”的前置建立速度。

## 3. 方案对比

| 方案 | 改动量 | 前置改善 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 只把 `predict_target_pos_gain` 从 3 调到 4.5~5 | 纯 JSON，零代码 | 75% 距离处 43%→约 70~76% | 末段过载/诱导阻力增大；执行器饱和可能过冲；仍不是“早前置” | 可作 A/B 对照或临时缓解，不作最终方案 |
| B. 远距前置前馈 + 末段退坡到纯 PPN | 1 个数学入口 + 1 个分支 + 1 个可选字段 | 75% 距离处可到约 95%+ | 需要标定退坡窗口；机动目标可能过前置 | **推荐** |
| C. 实体寻的回退到 PIP | 删 PPN 分支 | 前置恢复 | 放弃 PPN 对变向/加速目标的改善（既有 1728 组对照已量化） | 不推荐 |

方案 B 的本质：**远距让“指向预测相遇点”的方向指令做前馈，末段把控制权平滑交回 PPN**。它不等于回退 PIP——PIP 方向只在退坡窗口之外参与，末段仍是纯 PPN；也不新增第二套制导状态机。

## 4. 推荐方案 B：前置前馈 + 末段退坡

### 4.1 控制结构

在 `RVP_GuidanceRuntimeMath` 的 PPN 分支内，保持现有 PPN 计算不动，新增一条“前置方向”请求，并按剩余相遇时间平滑混合：

```text
u_ppn  = PPN 本刻一步航迹请求（现有 RVP_ProportionalNavigationMath.solve）
u_pip  = 旧 PIP 分支本 Tick 会提交的单 Tick 请求（含 steeringFactor / solvePIPControl，
         不是把绝对 lead 方向直接当请求）
w      = smoothstep((t_go - T_near) / (T_far - T_near))  // 远距 1，末段 0（t_go 见 §4.2）
u_cmd  = slerp(u_ppn, u_pip, w)                          // 现有球面插值，保持速率
```

- `w = 1`：请求量级与旧 PIP 相同（含 `turning_factor` 的比例插值），远距立即建立前置；执行器仍走 PPN 分支的单次提交，不是满 G 阶跃。
- `w = 0`：完全等价当前 PPN，末段保持 PPN 的抗机动与收敛性。
- 中间：两个**同量纲的单 Tick 请求**连续插值，不引入模式切换状态；`RVP_ProportionalNavigationMath.blendRouteRequest` 已经实现同速率的球面插值，可直接复用（建议改名为通用的 `blendDirectionRequest`，高抛调用点同步改名，行为不变）。

**为什么混合“请求”而不是“绝对方向”**：旧 PIP 的请求不是把绝对航向一步打满，而是 `turning_factor`（现役弹 0.06~0.14）比例插值后的单 Tick 转角；PPN 请求也是单 Tick 转角。两者同量纲，插值才有物理意义；若把“一步 PPN 转角”和“绝对 lead 方向”直接插值，`w=1` 会变成满 G 阶跃，量级比旧 PIP 大得多，且带来末段过冲风险。

**为什么不在近距也用前馈**：PIP 的请求按“当前目标速度的预测相遇点”产生，末段目标机动/预测误差会让这个方向反复修正；PPN 按真实视线角速度反馈，末段更稳。退坡到纯 PPN 可以保留 PPN 的末段阻尼（既有对照里 PIP 的静止大离轴误差 0.0229 格 vs PPN 0.00056 格，也说明 PIP 的末段并不总是更好）。

### 4.2 退坡窗口：用剩余相遇时间，不写死距离

```text
t_go  = 相遇解 RVP_PredictiveInterceptMath.Solution.timeTicks   // 格 / 格每 Tick，已含闭速
w     = smoothstep((t_go - T_near) / (T_far - T_near))          // 远距 1，末段 0
T_far = 10 Tick（约 0.5 秒）   // 前馈保持全额的剩余时间（默认值）
T_near= T_far / 3（约 3.3 Tick） // 之后纯 PPN
```

- 用 `t_go` 而不是固定格数：同样 10 Tick，5 格/Tick 的弹对应 50 格，3 格/Tick 的弹对应 30 格；远近、快慢自动适配，不需要按武器 ID 或载具特判，也不需要读动压/转弯半径。
- **为什么不用“已飞行距离百分比”**：终端控制器的时间尺度是 Tick（每 Tick 可用转角、机头响应、G 预算），不是格；`t_go` 直接给出“还剩多少时间修正”，并且已经含闭合速度（迎头/尾追自动不同）。距离百分比只归一化了空间，没有归一化时间：同样 10 Tick、5.5 格/Tick 的弹约 55 格，350/600/1400 格射程都在剩 55 格时交接（都是 0.5 秒）；若按“剩余 10% 初始距离”交接，则分别剩 35/60/140 格，对应约 0.34/0.58/1.35 秒，长射程会提前 1 秒多交给 PPN，把 PIP 前置拉回去——与 45 Tick 实验同一种失效模式。已飞行距离还受路径弯曲、爬升和目标运动影响；`t_go` 是每 Tick 由相遇解重算的闭环量，不依赖初始距离或路径。
- **注意这里的“固定时间”是剩余相遇时间窗口，不是发射后的绝对时刻**：不同射程的交接发生在不同绝对飞行时间，但都对应“还剩约 0.5 秒”这一相同终端条件。
- 低速/高空时 `t_go` 本身变大，前馈自动保持更久；爬升/加速段 `t_go` 变化也连续。
- `t_go` 只在 `intercept.usable()` 时可用；`CLOSING_APPROXIMATION` 的有限近似同样可用，`UNREACHABLE`/`INVALID` 时 `w=0`，退回纯 PPN。
- 默认 10 Tick 是 **HQ-10/HQ-9B 实测后从 45 Tick 收紧**的结果：45 Tick 会在剩余约 2.25 秒时就开始交给 PPN，PPN 的末段指令会把已经建立的 PIP 前置拉回去，`hq10_fast` 脱靶 2.913→3.184 格；10 Tick 保留远距前置，只用最后约 0.5 秒给 PPN，`hq10_fast` 回到 2.913 格，同时 HQ-9B 的变向工况仍由 PPN 收住（2.33/2.34 格）。
- 若个别弹需要更早交权，调大 `T_far`（数据字段），不改公式；调小则更接近旧 PIP。

| `docs/plan/RVP武器数据模型/...`、`RVP包新增参数字段说明.md` | 补字段说明（单位、默认、生效条件） |

伪代码（只表达顺序，不是最终代码）：

```java
// PPN 分支内，limits 已解析
ppn = RVP_ProportionalNavigationMath.solve(pos, current,
        targetMotion.position(), targetMotion.velocity(), gain);
next = ppn.requestedVelocity();

// 高抛路线已求解时复用同一次相遇解；否则对 steeringTarget 求一次
RVP_PredictiveInterceptMath.Solution lead = intercept != null ? intercept
        : RVP_PredictiveInterceptMath.solve(pos, current,
              steeringTarget, targetMotion.velocity(), targetMotion.effectiveAcceleration());
double w = lead.usable() && ppn.status() == ACTIVE
        ? resolveLeadWeight(lead.timeTicks(),
              context.data().getGuidanceData().getPpnLeadFeedforwardTicks())
        : 0.0;
if (w > 0.0) {
    // 复用旧 PIP 分支的单 Tick 请求（含 steeringFactor），不是把绝对方向直接当请求
    PIPControl pip = solvePIPControl(context, current,
            lead.point().subtract(pos), routeMotion, lead, limits);
    next = RVP_ProportionalNavigationMath.blendDirectionRequest(
            current, next, pip.control().requestedVelocity(), w);
}
// 之后保持现有：factor 兜底、高抛权重混合、攻角单次提交
```

注意：
- `ppn.status()` 只让 `ACTIVE` 参与前馈；`CAPTURE`/`PASSED_TARGET`/`COINCIDENT` 等退化分支保持现状，避免在目标已在后方时叠加一个相反方向的前馈。
- 前馈方向取 `steeringTarget`（已含 loft/top-attack 逻辑），保证高抛权重降到 0 的边界处两条方向的基准点一致，不产生方向跳变。
- 攻角路径与无攻角路径都不改：混合后的 `next` 仍只提交一次，`turning_factor`/G/攻角预算不变。

### 4.4 预期效果（按 1.2 的回放口径）

- 慢横穿：75% 距离处前置比例 0.44 → 约 0.95（PIP 为 0.96）。
- 高速横穿：75% 距离处 0.43 → 约 0.95，末段那 21° 的集中修正被提前摊掉。
- 静止/迎头目标：`u_lead` 与目标方向几乎一致，前馈退化为“更早指向目标”，末段仍由 PPN 收敛；不会改变 PPN 的末段阻尼。
- 高抛弹：`loftWeight` 越高，前馈被路线权重压制得越多；`loftWeight=1` 时完全走原 PIP 路线，权重降到 0 后由“前馈 + PPN”接管，AIM-120D/PL-15 的回放应基本不变。

### 4.5 弹道平滑性：航迹连续，指令在少数边界上非 C1

先区分“弹道/航迹”和“制导指令”：

**航迹本身（位置、速度方向）是连续的，不会出现折角或瞬移。** 方案 B 的最终输出仍是一个单 Tick 请求，照旧交给 `RVP_ProjectileMotion.applyAttackAngleSolution` / `applyResolvedAeroSteering`，每 Tick 转角受 `availableGs`、`maxTurnDeg`、`turning_factor` 和攻角锥限制；即使请求一步跳几度，执行器也只能按本 Tick 可用转角去追，位置与速度方向不会跳变。所以轨迹是 C1（速度连续、方向连续），只是曲率/法向过载可能不连续。

**常规交会段的指令也是平滑的（C1）。** `w` 用 smoothstep，且两端导数为 0，退坡窗口 30 Tick；`u_ppn` 与 `u_pip` 都是单 Tick 请求（典型 0.2~2.5°/Tick），两者在相遇解连续时也连续，球面插值仍连续。即使退坡开始时两请求差 1°，摊到 30 Tick 也只有约 0.03°/Tick 的额外变化，远低于执行器单 Tick 可用转角，航迹上看不到“扳道岔”。

**真正可能出现一次小阶跃（C0）的边界只有三处：**

1. `RVP_PredictiveInterceptMath.Solution.usable()` 由 false 变 true（导弹加速到能追上目标、或相遇解从无正根转为有正根）：`w` 可能从 0 直接跳到 1，单 Tick 请求一次跳变（量级约为 lead 角乘 `turning_factor`，几度/Tick）。
2. `ppn.status()` 在 `ACTIVE` 与 `CAPTURE`/`PASSED_TARGET` 等之间翻转：前馈被整体门控，`w` 跳 0/1。
3. `t_go` 在 `QUADRATIC` 与 `CLOSING_APPROXIMATION` 两个分支之间切换：相遇点与剩余时间都可能跳一次，`w` 随之跳一次。

这三处的表现都是**法向过载/曲率的一次小突变**（“突然开始转”），不是航迹折角；而且旧 PIP 在 `usable()` 边界上本来就有同样的跳变（旧代码在不可解时回退纯追踪、可解时指向相遇点，再经 `turning_factor` 比例插值），方案 B 在 `w=1` 阶段的平滑性不差于旧 PIP。

**和当前 PPN 的对比：** 当前 PPN 的曲率需求约按 `R^(N-1)` 随距离缩小而增长，末段最陡；方案 B 把同样的总转弯量前移到远距完成，之后接近直线飞行，**整体曲率分布反而更平缓**，不是“在末段加一个急转”。

如果验收时这三处边界在实机上可见，再按代价从低到高加保护：

- 只对 `w` 做斜率限幅（每 Tick 最多变化 `1/(2·T_far)`），需要保存上一 Tick 的 `w`（1 个 float 的跨 Tick 状态）；
- `usable()` 连续 N Tick 才启用前馈（去抖），同样需要少量状态；
- 或在 `w=1` 的远距阶段直接复用旧 PIP 分支的请求（零新增状态，但代码分叉更多）。

默认先不加这三层保护：正常交会不触发边界，先靠 1728 组矩阵和实机观察确认是否真的出现可见抖动。

### 4.6 变向目标的前段增量（实测）

场景：HQ-10，R0=600，目标 65 格/秒沿 +X，分别在 30/72/102 刻后 60 刻内转 ±60°；用旧 PIP 代表方案 B 的 `w=1` 前段（`t_go` 仍大于默认 10 Tick），与当前 PPN 逐帧对照。前段取 10~40 刻（0.5~2 秒），即变向开始前/刚开始的窗口。

| 前段指标 | PIP（方案 B 前段） | 当前 PPN | 增量 |
| --- | ---: | ---: | ---: |
| 75% 距离前置/所需 | 0.97 | 0.43 | **+54 个百分点** |
| t=30 航向变化（相对初始 +Z） | 34.1° | 16.8° | +17.3°（约 2.0 倍） |
| 平均载荷因子（10~40 刻） | 0.194 | 0.111 | **+8.3 个百分点** |
| 峰值载荷因子（10~40 刻） | 0.401 | 0.159 | +24.2 个百分点 |
| 平均每 Tick 转角 | 1.07° | 0.62° | +0.45°（约 1.7 倍） |

载荷因子是相对本弹当前可用过载的归一化值（1.0 = 用满 G 预算），所以“+8.3 个百分点”表示前段平均多用了约 8% 的可用过载，不是绝对 G 值。表中 75% 距离与 t=30 两行都是**变向开始前**的口径；25% 变向的 75% 距离点已经在变向之后，前置比例不再沿用这一行。方案 B 在 `w=1` 阶段按旧 PIP 的单 Tick 请求路径实现（含 `turning_factor`），所以上表就是方案 B 的前段；若实现成“绝对 lead 方向直接与 PPN 请求混合”，会变成满 G 阶跃，前段比上表更大且有过冲风险，不在本方案内。

变向时机的影响：

- **25% 变向**（30 刻）：变向开始前（t<30）与上表一致；变向后 PIP 按目标当前速度重算相遇点，前段仍更早转（t=40：44.6° vs 24.9°，多 19.7°），PPN 靠视线角速度晚一拍。
- **60% 变向**（72 刻）：到 t=72 只多 4.6°（47.7° vs 43.1°）；且方案 B 此时已进入退坡，实际增量比 PIP 更小。
- **85% 变向**（102 刻）：PPN 在 t=90 已反超（49.9° vs 48.0°），前段不再“更猛”。

注意：+60° 向外转的两种时机双方都会大脱靶（目标在远离），上表只用来看前段转角与载荷，不用来看命中；反方向（-60°，朝导弹）时 PIP 首次接近 0.86 格、PPN 2.50 格，样本单一，只说明该几何下前馈更早建立前置，不作为统计结论。

**结论**：

- 方案 B 的 **75% 前置比例在 8 个工况中都等于纯 PIP**（0.96/0.97/0.95/0.97/0.37/0.71/0.71/0.71），说明“远距前置前馈”的目标达成；它不再像纯 PPN 那样到 75% 距离只有 43%/29% 的前置角。
- 方案 B 的脱靶在 8 个工况中都与纯 PPN 接近（最差 +0.17 格：HQ-9B 快速横穿 3.123 vs 2.955），并在两个 HQ-9B 变向工况明显优于纯 PPN（2.332/2.341 vs 2.600/2.971）和纯 PIP（7.832/11.027）。
- 纯 PIP 在 HQ-10 的慢速/快速/30 刻变向和 HQ-9B 慢速横穿上仍是脱靶最小；但它在 HQ-9B 的两个变向工况出现 7.8/11.0 格的大脱靶，不能作为统一替换方案。
- 因此当前实现是“**PIP 的前段前置 + PPN 的末段精度**”的折中：前置形状修正到位，脱靶保持 PPN 水平，变向工况还有改善；代价是恒定横穿没有拿到 PIP 的末段优势。

**退坡窗口实测（脱靶，格）**：`B1/B5/B10/B45` 分别表示 `ppn_lead_feedforward_ticks=1/5/10/45`；`B1` 基本等于纯 PIP，`B45` 是草稿默认值。

## 6. 风险、边界与回退

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 机动目标过前置 | 远距按“当前目标速度”预测相遇点，目标随后变向时前馈会先转多 | 末段退坡到 PPN；`w` 上限可设 0.8~0.9；矩阵验证变向三类 |
| 末段过冲/振荡 | 前馈是阶跃方向，若一直用到近距会与机头滞后叠加 | 用剩余相遇时间退坡，末段 `w=0`；保持 PPN 的阻尼 |
| 能量/诱导阻力 | 更早转向会增加载荷因子平方的诱导阻力 | 提前转到碰撞航向的总转角不变，通常比“先直飞再猛转”更省；用矩阵的命中/误差与实机能量观察确认 |
| 高抛方向跳变 | 高抛路线用辅助点，前馈用真实目标 | 前馈只作用于 PPN 分量，且方向同样取 `steeringTarget`；`loftWeight=1` 时被路线完全覆盖，权重下降时两者基准点相同，不会跳变 |
| 日志解析 | 既有诊断脚本按 `branch=PPN` 解析 | 不改分支名，只在行尾追加字段 |
| 现有测试期望值 | 若干用例断言精确 PPN 角 | 实施时按 §5.1 调整为“近距纯 PPN / 远距混合”两类断言 |

**明确不做**：

- 不新增 Mixin，不改 `ywzj_vehicle` 本体。
- 不按武器 ID 分支；退坡窗口由相遇时间自整定，只有可选的 `ppn_lead_feedforward_ticks` 数据字段。
- 不修改高抛 `loft_*` 参数、载具包、结构模型、客户端/网络协议。
- 不在本次一并处理“导引头截获前的中段点制导/无制导”问题；那是另一条链，需单独定位。
- 不把 `predict_target_pos_gain` 默认值改大；N 仍保持 3.0，留给 A/B 对照。

**回退**：把 `ppn_lead_feedforward_ticks` 设为 0（或删除字段走默认关闭分支）即可退回当前纯 PPN；代码回退点只有 `RVP_GuidanceRuntimeMath` 的 PPN 分支和 `blendDirectionRequest` 一处。
