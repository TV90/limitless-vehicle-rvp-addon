# RVP 虚拟弹网络优化开发文档（仅 S2C）

日期：2026-11-04。**状态：S2C 合并优化仍为开发前方案，尚未实现；配套显示接入已单独实现独立视觉消息，网络协议现为 43。本文的合并方案不代表已上线。**

适用环境：`limitless-vehicle-rvp-addon`，Minecraft 1.20.1 / Forge。配套文档：[虚拟弹只供显示弹体对象接入方案](RVP虚拟弹只供显示弹体对象接入开发方案_20261104.md)。显示对象、模型、喷焰、尾烟和画面平滑仍以该文档为准；本文集中规定虚拟弹相关 S2C 的合并、发送和验证。

## 1. 优化边界

**只优化虚拟弹相关 S2C。**S2C 是 Server to Client，即服务器向客户端发送消息。优化对象限定如下：

| 对象 | 当前状态 | 本文负责的工作 |
| --- | --- | --- |
| `S2CVirtualMissileTargets` | 已实现的虚拟目标完整集合 | 精简重复的身份与运动字段，保留原目标资格、锁定引用及恢复交接语义 |
| `S2CVirtualMissileVisualSnapshot` | 显示接入首版已独立实现 | 发送只供画面使用的位置、姿态、阶段和发动机状态，保留独立视觉资格；本文后续负责合并 |
| `S2CVirtualMissileSnapshot` | 本文拟定的合并消息，尚未实现 | 替代上面两条消息对同一枚虚拟弹重复发送的基础数据 |

本文不新增、不合并也不调整 C2S（客户端向服务器发送的消息）。真实弹视觉与克隆、战术地图、外置雷达整包、本体实体广播及其他特效消息，也均不列为合并或重构目标；它们的字段格式、发送频率和接收范围保持原规则。

真实→虚拟→真实是本方案必须处理的交接边界，但本文只规定虚拟弹 S2C 的登记、最终样本和撤销，不改真实实体生成 / 移除包，也不改弹道、伤害、雷达发现规则、区块票据或存档格式。

术语：Tick 是游戏刻，正常速度下每秒 20 刻；UUID 是一枚弹的长期身份编号；快照是某一时刻的状态副本；权威状态指服务器实际决定的飞行结果。网络优化只能改变状态怎么发送，不能改变导弹实际怎么飞。

## 2. 现有链路与重叠

已核对的当前实现：

- [RVP_VirtualMissileTargetSync](../../src/main/java/org/ywzj/rvp/virtualflight/server/RVP_VirtualMissileTargetSync.java) 在服务端刻末每 2 刻同步一次，状态转换时也可立即同步；候选来自现有权威虚拟目标，不依赖世界实体追踪。
- 它按本车 / 中继雷达包络及保留接触筛选目标，对每个条目调用 `saveWithoutId()` 和 `writeData()`，发送身份、位置、速度、姿态、武器与目标代理需要的数据。
- [S2CVirtualMissileTargets](../../src/main/java/org/ywzj/rvp/network/S2CVirtualMissileTargets.java) 当前携带维度、条目列表和已恢复实体 ID；每条目含实体 ID、NBT 和地面高度。NBT 是 Minecraft 的存档数据格式，当前目标链复用它建立客户端代理。
- [RVP_ClientVirtualMissileState](../../src/main/java/org/ywzj/rvp/client/state/RVP_ClientVirtualMissileState.java) 消费完整集合，维护目标代理与已有锁定引用；停止同步超过 20 刻或更换世界时清理缓存。
- 显示接入首版已另行每 2 刻发送轻量视觉快照。若同一玩家同时需要某枚虚拟弹的目标和模型，两条消息仍会重复携带该弹的身份、武器、位置、速度和姿态，待本文的合并方案消除。

虚拟弹不加入世界实体列表，原版实体追踪不会自动替它发送这些状态，因此由服务器主动推送 S2C。注册方向固定为 `PLAY_TO_CLIENT`，客户端在处理世界逻辑的主线程中应用，公共消息通过客户端端口分发；参见 [Forge 1.20.1 SimpleImpl 处理说明](https://docs.minecraftforge.net/en/1.20.1/networking/simpleimpl/#handling-packets)。

普通远程联机连接的 TCP（负责可靠传送字节的网络协议）已经提供可靠、有序的传输。应用层序号、完整集合和超时用于会话识别、交接与断流清理，不是重新实现传输重试；本方案不增加逐包收到确认。依据见 [RFC 9293 §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2)。

**目标集合与视觉集合不相同，也不保证谁包含谁。**步行近距玩家可以有视觉资格而无目标代理；雷达目标也可能位于视觉边界之外。当前目标包包含“可供扫描的候选”，不能把收到条目理解成已经发现或已经锁定。

## 3. 合并能节省什么

**主要收益来自少发重复数据、少做重复处理。只减少消息类数量，通常不能据此断言带宽明显下降。**本项目的 `SimpleChannel` 使用当前玩家连接发送自定义消息；Forge 的不同逻辑通道不各自建立一条 TCP 连接。已核对本地 Forge 47.4.13 的 `SimpleChannel.sendTo()` / `toVanillaPacket()`，它们将编码结果交给传入的现有 `Connection`。

这里要分清四件事：

| 优化动作 | 可能节省什么 | 没有自动节省什么 |
| --- | --- | --- |
| 同刻两条小消息装进一个外层包 | 公共头、部分编码与分派、主线程任务安排 | 两个子块仍各自带同一位置时，位置字节照发；业务处理内容也仍存在 |
| 同一枚弹的运动字段只编码一次 | 两条消费链交集中的重复字节，以及重复构造状态 / NBT 的开销 | 不同观察者、不同授权和不同采样刻的数据不能直接去重 |
| 服务器共用一次候选提取，消息暂时独立 | CPU（处理器）时间、临时对象和重复遍历 | 没改变线上编码时，带宽基本不变 |
| 降低不必要的频率、只发变化的元信息 | 重复状态、文字和资源名的发送量 | 正在飞行的弹几乎一直改变位置，不能因此完全停发运动样本 |

一条应用消息不等于一个 TCP 分段，合成一条大消息也不保证只占一个底层数据包；TCP 处理的是有序字节流。参见 [RFC 9293 §3.7](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.7)。Netty（游戏使用的网络收发库）也区分写入和提交待写数据，`writeAndFlush` 是两者组合，因此不能把“少一次消息调用”直接换算成固定数量的网络分段或系统调用，参见 [Netty Channel API](https://netty.io/4.1/api/io/netty/channel/Channel.html)。实际还要测压缩后的字节数、处理时间和延迟。

对同一观察者、相同采样频率，令 `V` 为视觉集合、`T` 为目标集合，`C` 为一枚弹两边重复的基础字段大小，`Ev` / `Et` 为各自特有字段，`H` 为消息公共头，`M` 为合并后新增的资格与索引开销：

```text
分开发送 = Hv + Ht + |V| × (C + Ev) + |T| × (C + Et)
合并发送 = Hj + |V∪T| × C + |V| × Ev + |T| × Et + M
大致节省 = (Hv + Ht - Hj) + |V∩T| × C - M
```

`V∪T` 是两边所有不同的弹；`V∩T` 是两边都要的弹；竖线表示数量。例：假设有 80 枚弹同时属于两边，每份共同字段按 96 字节估计，每秒更新 10 次，仅重复共同字段就约 `80 × 96 × 10 = 76800` 字节，即 **75 KiB/s**。这只是说明收益来源的算例，不是当前 NBT 大小、实际编码结果或实测提升。

如果玩家只有视觉没有雷达，交集接近 0，主要只能省公共头；两边都需要同一枚虚拟弹的观察者，才会明显受益于运动数据去重。不能为等另一条虚拟弹消息而跨刻延迟转换、终止或恢复；也不能因包数减少就放宽筛选，向更多玩家发送原本无权接收的数据。

独立视觉基线中，按每条约 200 字节、128 条、每秒 10 次估算，单观察者约为 **250 KiB/s**（每秒 250 个 1024 字节）。这也不是实测；数量上限只是防异常的兜底，最终还要根据实际字节数收紧预算。

## 4. 合并方案：一份虚拟弹基础表，两种资格

在独立显示链验证通过后，建议将 `S2CVirtualMissileTargets` 和独立视觉消息替换为一条 **`S2CVirtualMissileSnapshot`**。这是拟定名称，尚无代码。它只统一虚拟弹的线上数据；不把本体所有实体广播、战术地图或其他特效一并塞进来。

```text
S2CVirtualMissileSnapshot
  公共头：dimension、sessionId、sequence、serverGameTime
  entries：该观察者本次 V∪T 的完整集合
    identity：flightUuid、entityId、weaponId
    motion：position、velocity、yaw、pitch、flightTick、phase
    visualAllowed：是否属于视觉集合 V
    targetAllowed：是否属于现有目标同步集合 T
    visualData：仅 V 需要的发动机阶段、燃烧倒计时、尾烟保持期
    targetData：仅 T 需要的来源、目标代理及高度等补充数据
  departures：按身份记录视觉 / 目标各自退出原因，恢复时带最终样本
```

落实规则如下：

1. **同一身份、同一服务端采样刻，基础运动只写一次。**先提取权威状态，再分别计算 `V` 和 `T`，最后编码并集；不重复推进弹道、不让两条筛选链各自保存整份实体 NBT。
2. **两个资格由各自的原规则计算。**`visualAllowed` 不导出 `targetAllowed`，`targetAllowed` 也不自动允许绘制。后者只表示可建立原目标代理，扫描线、接触保持和锁定继续由原业务决定。
3. **共用不可变数据，分建客户端实例。**一份基础样本可以被显示和雷达缓存读取；只有 `visualAllowed` 才创建显示对象，只有 `targetAllowed` 才更新现有目标代理和远程目标表，不将一个会被渲染临时改坐标的对象用于两种职责。
4. **退出也按用途判断。**条目还在但 `visualAllowed` 变为 false，只停模型与新持续效果；`targetAllowed` 变为 false，只按现有语义撤销或交还目标表示。两项资格同时离开时撤销两个本地表示，但不宣告弹被击毁；权威弹终止时则明确同时清理两边。恢复原因与最终真实位置仍须保留。
5. **目标补充数据先审计后裁剪。**当前目标接收器走 `load()` / `readData()`，不能只删 NBT 就假定来源、武器类型、信号、碰撞箱和已有锁定引用都能继续工作。建议把真正需要的字段改为明确的网络字段，客户端经 RVP 适配入口填入代理；若临时保留一小块目标 NBT，它不得再重复携带基础表已有的位置、速度和身份。纯视觉条目不附带目标坐标和制导历史。
6. **先校验整批，再在同一次主线程处理里更新两个缓存。**不能一个子集合提前撤销、另一个子集合下刻才到，造成临时断锁或重复模型。各缓存仍按自己的资格和生命周期清理。
7. **视觉预算不能裁掉目标业务。**[显示接入方案](RVP虚拟弹只供显示弹体对象接入开发方案_20261104.md)第 6.3 节中，128 条是独立视觉消息的基线预算，合并后不能拿它裁剪现有目标集合。若 `V∪T` 超过总包预算，要有明确的分片批次、分片索引 / 总数、累计大小上限，全部收到并校验后才替换完整集合；若首版不做这套有界分片，则阶段 B 暂不切换，继续保留独立目标消息与独立视觉消息；不能按单包是否放得下临时混用两套完整集合，更不能把半份目标集合冒充完整集合。
8. **完成切换后停止旧的重复发送。**统一修改 RVP 发送器、注册与消费者，按最新协议号升级两端；同一枚虚拟弹不再同时走旧目标包和统一包。没有必要维护旧网络格式的长期兼容分支，也不改虚拟弹存档格式。

例如：A 弹只允许看见，条目带 `visualAllowed=true`、`targetAllowed=false`；B 弹只供远程雷达使用，两个值反过来；C 弹两边都需要，带两个 true，坐标仍只编码一次。这样合并的是网络数据，保留的是业务边界。

## 5. 发送时序、集合与预算

- 常规更新保持每 **2 刻**一次，读取权威管理器、改靶和雷达已经提交的结果。每维度每次提取一次不可变基础状态，再按观察者分别计算视觉与目标集合；不重复推进弹道，也不为发包重新初始化弹体。
- 同刻多枚转虚拟、终止或恢复，可合并到本刻末发送一份最终状态，不为凑包跨刻等待。已有交接确需在实体移除前预告时，保留这次及时推送；之后仍按统一序号处理，不能吞掉同刻较新的状态。
- `dimension`、`sessionId`、`sequence`、`serverGameTime` 由同一批次共用。相同服务端刻的较新序号替换该刻样本；重复或倒退序号不能覆盖较新数据。会话与世界实例的清理由显示接入方案和现有目标链共同保持。
- 完整集合缺席表示撤销对应资格；空完整集合仍必须应用，不能为了省空包漏掉最后一次清理。若观察者从来没有对应资格且旧集合也为空，可以不发送这份空集合。
- 合并后的资格应分别计数。视觉预算不能裁剪目标资格，地面高度查询的现有关闭状态不能因编码优化重新打开，也不能为筛选虚拟弹申请沿途区块。
- 数量、字符串长度、枚举、有限坐标、每包字节和整批累计字节均应有界。分片是把一批完整集合拆成若干网络消息；必须按批次收齐并校验后一次提交，超时丢弃未完成批次，不能把每片当作完整集合。

虚拟弹终止时撤销两个资格；仅离开视觉范围时只撤销显示；恢复成功时发送实际入世位置的最终样本与恢复原因，再按原有目标引用交接规则清理虚拟表示。客户端显示对象与雷达代理仍是两个实例，共享不可变基础样本即可。

## 6. 分步实施

| 阶段 | 具体工作 | 完成标准 |
| --- | --- | --- |
| A：共享提取与同刻刷新 | 两条虚拟弹消息先共用一次基础状态提取；分别筛选用途，合并同刻不必重复发送的完整集合 | 生命周期和资格保持一致；主要减少 CPU 时间与整表突发，不宣称已经消除了两条消息中的重复字节 |
| B：合并两条虚拟弹 S2C | 使用第 4 节的并集基础表与两个资格；一次主线程处理分发到两份客户端缓存；停用旧目标消息和独立视觉消息的重复发送 | 原目标引用与显示连续；仅视觉 / 仅目标 / 双资格及超预算都通过验证，编码字节数下降 |
| C：优化虚拟弹字段与静止状态 | 身份、武器资源名等不变字段在首次建立或变化时发；常规运动引用本会话的短 ID；暂停时少发未改变的姿态，但保留明确的集合资格与保活刷新 | 重连、ID 复用、配置重载和状态重建可靠，继续只使用虚拟弹 S2C，不扩展其他消息 |

阶段 C 的不变字段属于元信息，即“这枚弹是谁、使用哪份武器配置”。基线是客户端已保存的一份完整状态，差量是只发之后发生的变化；两种更新必须明确区分。不能让原来的完整集合消费者把“本次没变化，所以省略条目”理解为删除。

先缓存元信息、按字段变化发送，位置仍使用当前绝对值。运动中的弹仍需更新位置；暂停记录可省略不变运动字段，但必须显式维持其暂停状态和用途资格，不能因此超时。缺少短 ID 对应元信息时暂不应用条目，由周期性完整 S2C 快照补齐；初始化、重连和配置变更后及时重建基础状态。

首版保留 double 坐标。若以后在本范围内量化速度、角度或相对坐标，即用更少位数表示数值，必须先规定允许的显示误差和越界回退，再做轨迹框与模型对齐验证，不预设未经测试的压缩率。

如果首次显示功能交付已经完成阶段 B，可直接注册统一消息，不必先发布独立消息再马上替换。阶段 B 未通过时，先保留独立目标与视觉消息；不能为少一个包牺牲资格隔离和锁定连续性。本开发范围到阶段 C 为止，不安排跨真实弹、地图或外置雷达整包的后续合并阶段。

## 7. 预期代码改动点

| 位置 | 网络优化责任 |
| --- | --- |
| `RVP_VirtualMissileTargetSync` 与已实现的独立视觉同步服务 | 后续共用只读基础状态、用途筛选、观察者上次集合、同刻刷新与字节预算 |
| `S2CVirtualMissileTargets`、已实现的独立视觉消息 | 在阶段 A 作为对照基线；阶段 B 切换后停止注册和重复发送 |
| 拟新增 `S2CVirtualMissileSnapshot` | 有界编码、两个资格、用途补充数据、离开原因；需要分片时负责完整批次的收集约定 |
| `RVP_Network` 与公共客户端端口 | 注册统一的 `PLAY_TO_CLIENT` 消息，按届时最新协议号升级；端口分发到目标与显示消费者 |
| `RVP_ClientVirtualMissileState` 与已实现的独立显示缓存 | 后续应用同一批基础样本，分别更新代理；按各自资格和退出原因清理，保留锁定引用 |
| `RVP_VirtualMissileManager` 的状态出口 | 只通知已经提交的虚拟状态变化，保持原有登记、恢复、终止和拦截顺序 |

所有改动均在 RVP 子模组内，不修改 `ywzj_vehicle` 本体，不新增 Mixin 或访问器。公共消息和服务端类不直接引用客户端专用类型；渲染资源、模型与弹道计算不属于网络优化改动点。

当前 RVP 网络协议为 **43**（独立显示消息首版已递增）。真正实现统一消息时按届时仓库最新值递增，更新两端并切断旧的重复状态流；虚拟记录格式 2、轨迹实现 `rvp_entity/1` 不因发包优化升级。

## 8. 验收与性能对比

采用相同场景、玩家、配置和服务端采样频率，对比“独立消息基线”和“优化方案”，至少覆盖：无雷达步行玩家、视觉与目标大量重叠、只有雷达目标、多人各自观察、同刻批量转虚拟 / 终止，以及多数弹暂停等待恢复。

必须分别记录：虚拟弹相关 S2C 的每秒消息数、编码前后字节数、实际连接发送量、服务器提取 / 筛选 / 编码耗时、客户端解码 / 主线程处理耗时、临时对象数量，以及状态变化到画面应用的延迟。延迟同时看一般情况和较慢的 5% 情况，不能只报平均值。

验收以**少发重复字节且处理时间或延迟没有明显退步**为依据，不预填“提升百分之几”。包数变少而总字节数增加、雷达候选被视觉预算裁掉、虚拟目标交接被凑包延迟、空子块误清缓存，都不算优化成功。本轮只有源码核对和设计推算，没有实现合并、抓包或运行网络性能基准。

专项验收至少覆盖：

| 场景 | 必须证明的结果 |
| --- | --- |
| 仅视觉、仅目标、双资格 | 只更新对应缓存；双资格运动字段只编码一次，纯视觉不进入目标表 |
| 一项资格撤销，另一项保留 | 只撤销对应表示；不误判成弹已击毁，不中断另一条消费链 |
| 相同整数 ID 对应不同 UUID | 不接上旧目标、旧模型或旧尾烟；元信息与短 ID 重新核对 |
| 转虚拟、等待恢复、恢复成功、拦截终止 | 使用真实完成态；等待时不外推，恢复最终样本取真实入世位置，终止不复活 |
| 同刻批量转换与同刻多个序号 | 只发必要的最终集合 / 预告；较新状态不会被“本刻已发过”过滤掉 |
| 目标数超过视觉预算 | 不裁掉目标业务；未具备完整有界分片时不进入统一协议切换 |
| 分片缺失、重复、超限或超时 | 整批校验成功才提交；不发布半份完整集合，不无限占用缓存 |
| 空完整集合与变化集合 | 空完整集合清理对应用途；差量未携带的条目不被误删 |
| 暂停且没有变化的运动字段 | 用途资格与暂停保活仍有效；不误触发模型或目标缓存超时 |
| 切换统一协议后观察消息计数 | 相同虚拟弹不再同时从旧目标包与统一包收到重复运动状态 |
| 重新连接、重开世界、资源配置变化 | 旧会话数据清理，完整 S2C 可重新建立元信息和状态 |
| 与优化无关的网络消息 | 编码、发送频率、接收范围及操作时机无变更，不能把范围外的改动算作收益 |

保留 `RVP_VirtualEntityTrajectoryParityTest`、`RVP_VirtualMissileTargetsTest` 等轨迹与目标回归；阶段 B 将 `S2CVirtualMissileTargetsTest` 的编解码和恢复交接断言接到统一消息，不保留旧线上格式。网络测试通过后，仍需用真实客户端与专用服务器检查交接、画面和处理延迟。测量只统计本范围内虚拟弹 S2C 的改动，连接总流量作为旁证；其他消息保持一致。
