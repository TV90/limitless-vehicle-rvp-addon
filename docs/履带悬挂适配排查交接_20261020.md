## 五、已知正常参照（ZTZ99B 为什么能工作）

ZTZ99B 的履带是**本体作者自己配的**（ztz99a/ztz99b.structure.json 是本体自带），其特征：

- 渲染模型：FZL_R/L 树下 xuangua 臂骨 → FZL 轮骨（poly_mesh），骨名无 $ 前缀
- 结构模型：track_roller1-12 根级骨（各 1 碰撞盒）+ track_link→track_link_r/l 路径骨（8 点，首尾重合闭环）
- 载具数据：track 部件 structure_bone="track_link"，suspensions 键 = 路径子骨名
- 控制器：bone_binding 的 special_bindings 绑 hull_big_1-12 → left/right_wheel_rotation

**用户照着这个模式改了 T-90M 等五台车的结构模型和数据**，但改完后链板不渲染。

## 六、当前最可疑的未排查方向

1. **本体 TrackUnit.renderTrack 的链板渲染是否被触发**——需要确认 TrackUnit 是否对非本体包（rvp 命名空间）的载具执行渲染。可能的门槛：载具的注册命名空间、或 TrackUnit 遍历 partUnits 时的过滤条件。
2. **渲染模型骨名的 $ 前缀**——ztz100 的渲染轮骨带 $ 前缀。SBM 解析时 $ 前缀骨可能被特殊处理（如标记为虚拟骨不被渲染）。需查 SBM 对 $ 前缀骨的处理逻辑。
3. **本体 StructureModelManager 对新增结构骨的解析**——用户改结构模型时新增了 track_link/track_roller 骨，本体解析后这些骨是否正确进入 RuntimeIndex 并生成碰撞/渲染数据。可在 /rvpdebug 里加 StructureModelManager 的缓存 dump 来确认。
4. **本体侧 TrackUnit.combineAndInit 的调用时机**——只在 `BaseVehicleData` 初始化时调用一次，如果此时结构模型尚未加载完成，suspensions 匹配会失败。
5. **VRP 数据包 vs 本体数据包的命名空间隔离**——rvp 包的结构模型（rvp:vehicle/t90m）和本体包的（ywzj_vehicle:vehicle/ztz99a）是否走同一个 StructureModelManager 缓存。如果分开缓存，rvp 包的结构模型可能没被正确解析。

## 七、建议下一个 AI 的排查顺序

1. **先在游戏里按 F3+B 看 T-90M 的碰撞盒**——确认哪些有、哪些没有。这是最快的二分法。
2. **查看客户端 logs/latest.log** 搜索 `t90m` 或 `track` 或 `TrackUnit` 或 `StructureModel` 相关的 ERROR/WARN。
3. **在本体代码里搜 `TrackUnit.render` 的调用条件**——确认 render 方法是否被调用（可在方法入口加断点或日志）。
4. **确认 TrackUnitData.initStructureModel 是否被调用**——这是把结构骨 cube 转成碰撞盒+路径的关键方法，如果没被调用，一切都不会工作。
5. **检查 rvp 命名空间的载具是否走了和本体命名空间相同的 TrackUnit 创建逻辑**——可能的命名空间隔离导致 TrackUnit 没被创建。
6. 如果以上都正常但仍不渲染 → 在 TrackUnit.render 加临时日志（本体是只读，需要用 Mixin 注入）输出 tracks 列表大小、每个 TrackPath 的 linkCount 和当前 phase。
