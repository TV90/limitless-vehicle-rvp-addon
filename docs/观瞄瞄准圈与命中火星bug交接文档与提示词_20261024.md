## 2. BUG-1：命中火星不生效

### 2.1 需求原文

> machinegun 命中载具和墙体后，会在命中点生成一些扩散的火星粒子，火星粒子的数量和扩散范围取决于主炮的口径，扩散方向为命中方向的反方向，速度取决于命中弹药的速度（但不能是原速），然后要有较大的阻力衰减趋势。

### 2.2 当前实现（已按需求写完，只是不出效果）

**服务端生成**（`RVP_BaseBullet.java:5523`）：

```java
protected void spawnImpactSparks(ServerLevel serverLevel, Vec3 hitPos, Vec3 reflect) {
    if (weaponKind != RVP_EnumWeaponKind.MACHINEGUN || rvpData == null) return;
    if (serverLevel.getGameTime() % 2L != 0L && getFlightTickCount() > 4) return;  // 远距节流
    float caliber = rvpData.getEffectsData().getCaliber();
    int count = Mth.clamp(Math.round(caliber / 8.0F), 3, 18);
    double impactSpeed = getDeltaMovement().length();
    double speed = Math.min(impactSpeed * IMPACT_SPARK_SPEED_SCALE, IMPACT_SPARK_SPEED_MAX);  // 0.22 / 1.2
    if (speed <= 0.01D) return;
    float size = Mth.clamp(0.035F + caliber / 1100.0F, 0.04F, 0.32F);
    float spread = Mth.clamp(0.25F + caliber / 320.0F, 0.25F, 1.0F);
    int lifetime = 8 + serverLevel.random.nextInt(9);
    var options = new RVP_ImpactSparkOptions(1.0F, 0.78F, 0.35F, size,
            reflect.x, reflect.y, reflect.z, speed, spread, lifetime);
    serverLevel.sendParticles(options, hitPos.x, hitPos.y, hitPos.z,
            count, 0.0D, 0.0D, 0.0D, 0.0D);
}
```

参数表（需求 → 实现对应关系，**不要改这些公式，除非用户明确要求**）：

| 需求 | 实现 | 7.62mm | 125mm |
|---|---|---|---|
| 数量随口径 | `clamp(round(caliber/8),3,18)` | 3 | 16 |
| 扩散范围随口径 | `clamp(0.25+caliber/320,0.25,1.0)` | 0.27 | 0.64 |
| 尺寸随口径 | `clamp(0.035+caliber/1100,0.04,0.32)` | 0.042 | 0.149 |
| 方向=命中反方向 | 调用方传 `-deltaMovement` | — | — |
| 速度非原速 | `min(impactSpeed*0.22, 1.2)` | — | — |
| 大阻力衰减 | 粒子端 `DRAG=0.78` 全轴 + 微重力 0.02 | — | — |

**粒子端**（`RVP_ImpactSparkParticle.java`）：锥形散布（半角 `55°*spread`）、`hasPhysics=false`、寿命 8~16 tick、加法混合、不弹跳（与殉燃火星区分开）。

### 2.3 现象

用户实测（99B、DTC-10-125，`rvp:machinegun`）：**命中载具和墙体后，没有任何火星**。

### 2.4 已排除 / 已知情

以下都已核实，**不要重新排查**：

1. **不是「曳光影补渲」**。`compensateTracerLine()` 是死代码（无任何调用点），`TRACER_COMPENSATE_MAX_FLIGHT_TICK` 只在定义处出现。它从来没在画面里出现过，与本次新粒子无关。
2. **不是数据问题**。`limitless_vehicle/.../vt4_dtc10.json` 等配置无需为粒子新增字段；口径取 `effects_data.caliber`，未配置回退 7.62。
3. **不是节流误伤**。`getFlightTickCount() > 4` 时节流，但近距离首发时 `flightTick` 很小，不会命中节流。用户是近距测试。
4. **不是埋点位置问题**。方块命中在 `spawnAmmoBlockImpactEffects` 开头、实体命中在弹间拦截分支之后（弹打弹不产火花），两处都已验证过逻辑顺序。
5. **本文件之前没有可工作的自定义粒子 sendParticles 先例**。RVP 内 `RVP_TracerGhostOptions` 走同样的 `sendParticles` 模式，但它是死代码，从未真正运行过。**`RVP_ImpactSparkOptions` 是 RVP 第一个被真正调用的自定义 ParticleOptions + sendParticles 组合。**

### 2.5 排查顺序（建议按此顺序，每步都能单独证伪）

**第一步：粒子是否注册成功**

启动游戏，看日志有无注册相关报错；或直接执行命令（**最快的隔离测试**）：

```
/particle rvp:impact_spark 1.0 0.78 0.35 0.1 0.0 0.0 1.0 0.5 0.5 20
```

参数顺序见 `RVP_ImpactSparkOptions` 的 `fromCommand`：`r g b size dirX dirY dirZ speed spread lifetime`。

- 命令报「未知粒子类型」→ **ParticleType 没注册进 `ForgeRegistries.PARTICLE_TYPES`**。重点查 `RVP_Particles` 这个 DeferredRegister 类是否在注册表事件发生前被加载（类加载时机问题，参考 `RVP_ParticleIds` 的引用链）。
- 命令成功但看不到粒子 → **provider 没注册或 provider 内部抛异常**。查 `RVP_ClientBootstrap:101` 的 `registerSpecial` 是否真的被调用（在 `RegisterParticleProvidersEvent` 的监听里？），以及 `RVP_ImpactSparkParticle.Provider.createParticle` 的签名是否匹配 1.20.1 的 `ParticleProvider<T>` 接口。
- 命令成功且能看到粒子 → **粒子本身没问题，问题在服务端 sendParticles 链路或埋点分支**，跳到第二步。

**第二步：埋点分支是否走到**

在 `spawnImpactSparks` 入口加一行日志（临时，验证后删）：

```java
org.slf4j.Logger L = org.slf4j.LoggerFactory.getLogger("RVP_SPARK_DIAG");
L.info("[spark] hit weaponKind={} rvpData={} flight={} caliber={}",
        weaponKind, rvpData != null, getFlightTickCount(),
        rvpData == null ? -1 : rvpData.getEffectsData().getCaliber());
```

- 完全没输出 → 埋点没走到。查 `weaponKind` 实际值（**注意**：`weaponKind` 来自 `RVP_WeaponData.weaponKind`，其赋值链在 `RVP_WeaponTypes`；99B 的 DTC-10-125 是否真的是 `MACHINEGUN` 需实测确认，不要假设）。
- 有输出但 `weaponKind != MACHINEGUN` → 就是这个原因，按实际 kind 放宽条件（**先问用户是否接受扩大到其他 kind**）。
- 有输出且条件全过 → 跳到第三步。

**第三步：sendParticles 是否真的发包**

在 `sendParticles` 前后各加一行日志，确认执行到。若执行到但客户端无反应：

- 查 `RVP_ImpactSparkOptions` 是否完整实现 `ParticleOptions` 接口的三个方法：`getType()`、`writeToNetwork(FriendlyByteBuf)`、`getDeserializer()`。**1.20.1 的 `ParticleOptions` 要求 `writeToNetwork`，漏实现会在发包时静默失败或抛异常。**
- 查 `AllParticleTypes.createOptions(CODEC, DESERIALIZER)` 返回的 `ParticleType` 是否实现了 `ParticleType.writeToNetwork` / `fromNetwork`（`ParticleType` 接口有默认实现还是必须显式）。
- 对照 `RVP_TracerGhostOptions`（同模式，130 行左右）逐行 diff，看是否有遗漏的方法或字段。

**第四步（备选）：绕开网络包**

如果确认是自定义 ParticleOptions 网络序列化的问题，而用户不想深挖 MC 粒子网络协议，可以直接改成**客户端本地生成**：服务端只发一个自定义网络包（或复用现有 RVP 频道）带 `hitPos + reflect + caliber + speed`，客户端收到后 `level.addParticle(...)`。RVP 内已有客户端本地粒子的先例（殉燃火星 `RVP_WreckSparkParticle` 就是纯客户端 `addParticle`，不走 sendParticles，一直正常工作）。**这是保底方案，改动可控。**

## 3. BUG-2：意图圈横向乱跳

### 3.1 期望行为（用户原话归纳）

> 本体那个圈（意图）先动，炮塔准星（执行）追着圈转；**静止时圈和准星重合**；车体左右转时圈必须平滑，不能左右跳。

对应本体的层次：

| 层 | 取点 | 速度 |
|---|---|---|
| 意图（圈） | 炮塔**目标角** `yAimRot/xAimRot` | 鼠标指令，立即到位 |
| 执行（准星） | 炮塔**实际角** `yRot/xRot`（`Mth.approach(..., y_rot_speed)` 限速） | 40°/s（坦克已统一） |

### 3.2 背景：这个功能为什么存在

本体 0.6.2 的瞄准圈取 `toAimPosition()`（炮口 + 目标角）。而 RVP 的 `rvp_sight_fire_disguise`（视线发射伪装）让弹药**实际从观瞄相机出**（消除炮闩枢轴视差，近距离指哪打哪）。两者不同源 ⇒ 近距离分离。

**修正方向（用户强调两次，不要再搞反）**：

> 让【本体的圈】适配 disguise（改成相机口径），**不是**让 disguise 适配圈。
> 曾经改错一次：把 RVP 准星退回炮口，等于废掉了 disguise 的近距离指哪打哪语义。

### 3.3 当前实现

**mixin 侧**（`VehicleAimAtOverlaySeekerColorMixin.java:189`）：

```java
@Redirect(method = "render", remap = false, at = @At(value = "INVOKE", remap = false,
        target = "Lorg/ywzj/vehicle/client/gui/VehicleAimAtOverlay;"
                + "aimScreenPosition(Lorg/ywzj/vehicle/vehicle/part/WeaponUnit;)"
                + "Lnet/minecraft/world/phys/Vec3;"))
private Vec3 rvp$disguiseAimPosition(
        WeaponUnit weaponUnit,
        @com.llamalad7.mixinextras.sugar.Local(argsOnly = true) float partialTick) {
    if (RVP_ScopeViewSyncClient.disguiseAimActive(weaponUnit)) {
        Vec3 cameraAim = RVP_ScopeViewSyncClient.disguiseAimWorldPos(weaponUnit, partialTick);
        if (cameraAim != null) {
            return VectorUtil.worldToScreen(cameraAim);
        }
    }
    return aimScreenPosition(weaponUnit);   // @Shadow 回退原实现
}
```

**取点侧**（`RVP_ScopeViewSyncClient.java:243`，`disguiseAimWorldPos`）：

```
意图圈 = 相机位置
      + worldVec(xAimRot + xBarrelSelfRot, yAimRot + yBarrelSelfRot)   ← 目标角方向
      + computeBulletImpact(...)                                        ← 与准星同一套弹道积分
```

三级处理，缺一不可：
1. **叠加 `xBarrelSelfRot / yBarrelSelfRot`** —— 99B 的 `turret_barrel` 带 2.4° 上仰抵消炮塔前倾，不叠加圈会比真实炮口指向低一截。
2. **目标角帧间插值** `Mth.rotLerp(partialTick, prevTick, curTick)`。
3. **车体姿态帧间补偿** `(rotYXZ(pt) × rotYXZ()⁻¹) × dirTick`。

### 3.4 现象演变史（**这是最重要的部分**）

| 轮次 | 改动 | 结果 |
|---|---|---|
| v1 | 意图圈 = `weaponHitPos`（相机起点 + 炮口方向） | 圈和准星同一个点，完全重合，**没有层次** |
| v2 | 意图圈 = `cameraAimHit(partialTick)`（相机视线） | scope 下相机绑炮塔，视线≈炮口方向，**还是一起转**；且 `cameraDirection` 把 partialTick 当度数用，每帧飘 1°，静止也抖 |
| v3 | 意图圈 = `worldVec(xAimRot, yAimRot)`（目标角） | 层次出现；但**车体转动时左右剧烈晃动** |
| v4 | 加 `rotYXZ(partialTick)` 车体姿态补偿 | 大幅度跳动没了，**变成高频小幅度横跳** |
| v5 | 修插值缓存滚动条件（IdentityHashMap + 值变化检测） | **仍然跳**（当前状态） |

### 3.5 已排除路径（**逐条都有依据，不要重新试**）

1. **不是「相机链 vs 炮口链」的选择问题**。scope 视角下相机被 `cameraAimWith(weaponUnit)` 绑在炮塔上，`cameraAimRot` 与炮口方向近似同一个量，取视线永远和取炮口一起转。层次只能来自「目标角 vs 实际角」。
2. **不是本体的锅**。本体 `toAimPosition()` → `aimGlobalTransform()`（tick 级 `yAimRot`）+ `vehicle.rotYXZ()`（tick 级 `yRot/xRot/zRot`），**本体完全不做 partialTick 插值**，一 tick 内值恒定。所以本体"平滑"不是因为它在插值，而是因为它没有第二套时间基准。我早期"本体平滑是因为它插值了"的判断是错的。
3. **不是调用次数污染**。`aimScreenPosition` 在 `VehicleAimAtOverlay.render` 里每帧只调 1 次（`VehicleAimAtOverlay.java:66`，只针对 operator 的 weaponUnit）。
4. **不是缓存未按站分键**（这个确实修了但没用）。原来是全局 `lastIntentAimRotX/Y` + `vehicleId` 判断，已改成 `IdentityHashMap<WeaponUnit, float[4]>`，滚动判据为「当前值是否真的变了」。修完仍跳。
5. **不是死区/EMA 参数问题**。曾加过 0.03 格 / 0.5 格死区和 EMA 平滑，全部删除（治标不治本，且用户不接受"粘滞"手感）。
6. **不是下坠计算缺失**。意图圈已改用 `computeBulletImpact`（与准星同一套弹道积分），含下坠/阻力。
7. **不是 `xBarrelSelfRot` 符号问题**。直接叠加本体 public 字段，与 `xAimRot` 同单位同向（`aim()` 里是 `- yBarrelSelfRot`，`aimGlobalTransform` 里是 `+`，方向已核实）。

### 3.6 剩余嫌疑（按优先级）

**嫌疑 A：`yAimRot` 本身在车体转动时不是每 tick 平滑补偿**

scope 视角下车体自转时，炮塔要保持世界指向，`yAimRot` 必须每 tick 反向补偿。如果：
- 客户端本地预测写的 `yAimRot` 用旧 tick 车体角算；
- 服务端校正包的 `yAimRot` 晚 1 tick 到；

就会看到 `yAimRot` 每 tick 跳一次补偿量，`rotLerp` 把这个跳变插值成抖动。

**排查方法**：读本体 `LocalVehiclePlayer` 中 `weaponUnit.aim(...)` 的调用侧（在 `ywzj_vehicle/src/main/java/org/ywzj/vehicle/vehicle/LocalVehiclePlayer.java`，搜 `.aim(`），确认：
- `aim(vec)` 的 `vec` 是什么坐标系、什么时刻采样；
- 是否每 tick 都调用，还是只在鼠标变化时调用；
- 客户端是否有本地预测 + 服务端校正的双写。

**排查方法 2（更直接）**：在 `disguiseAimWorldPos` 里把 `curX/curY` 每秒打一次日志，观察车体匀速转动时 `yAimRot` 的变化是否线性。如果是台阶状（每 tick 一个常数步进），说明 `yAimRot` 本身平滑，问题在别处；如果步进不均匀（时大时小），说明 `yAimRot` 源头在抖。

**嫌疑 B：远距弹道 march 过度放大方向抖动**

`computeBulletImpact` 的落点可能在数百格外，方向上 0.01° 的抖动会被放大成数格的落点跳动，再投影成屏幕像素跳动。本体的 `toAimPosition()` 用 `hitPosition(vehicle, start, end)`（1024 射线），命中实际地形，距离通常远小于 march 距离。

**排查方法**：把 `computeBulletImpact` 临时换成 `VectorUtil.hitPosition(player, origin, origin.add(dir.scale(1024)))`（与本体同款直线射线），看抖动是否消失。
- 消失 → 确认是 march 放大，解决方向是缩短落点距离（如 clamp 到 256 格）或对最终落点做帧间平滑（注意：只平滑结果不动方向）。
- 不消失 → 是方向本身在抖，回到嫌疑 A。

### 3.7 保底方案（用户可接受的最小改动）

如果两个嫌疑都排查困难，有一个**用户明确认可方向**的退路：

**关掉对本体圈的接管**（删掉 `rvp$disguiseAimPosition` 这个 `@Redirect`，让本体圈回到 `toAimPosition()`）。代价是圈回到炮口口径，与 RVP 准星（相机口径）在近距离有小幅视差；好处是圈立刻恢复本体原生的平滑，层次也保留（本体圈本身就是目标角）。

这不是首选（用户要的就是让圈适配 disguise），但是一个明确的、可回退的落点。

## 5. 工程约束（接手方必须遵守，违反会被打回）

1. **Mixin 默认拒绝**。优先顺序：JSON 配置 → 继承/接口 → Forge 事件 → 网络包 → Accessor。禁 `@Overwrite`、禁整段 `@Redirect`（只允许拦单个调用点）。
2. **`@Redirect` handler 的 `static` 修饰符必须与【宿主方法】一致**，不是与被调用方法一致。`render` 是实例方法 ⇒ handler 必须非 static。写 static 会报 `'static' modifier of handler method does not match target`（本项目已踩过两次）。
3. **CRLF 文件必须用 python 按字节替换**。`Edit` 工具会把 CRLF 转 LF。已知 CRLF 文件：包内 `lang/*.json`、本体 `.java`、`config/*.toml`、`fire_support_profiles/*.json`，以及 RVP 的 `RVP_ScopeViewSyncClient.java`、`RVP_BaseBullet.java` 等。改前先 `b.count(b'\r\n')` 确认。
4. **禁一切真删除**（含临时文件）。只能逻辑删除：移到 `ywzj_rvp/_recycle_bin/<时间戳>/<原相对路径>` 并登记 `MOVE_LOG.md`。
5. **`limitless_vehicle/` 不提 gitee**，只提 `src/`。禁 `git add .`（工作区有大量未跟踪的 `_tmp_*`、`_backup*`）。
6. **构建必须全量**：`./gradlew build --offline --no-daemon -x test`。只跑 `compileJava` 会产生 refmap 中间态导致启动崩溃。
7. **`*.structure.json` 改前先请示 + 备份**。
8. **注释用中文**，禁硬编码武器 ID（走 `fire_data`），禁生成占位美术。
9. 提交前 `git status` / `git show --stat` 自查；双远端（gitee `origin` + github `github`）都要推。
10. **不要反汇编 jar**。本体源码就在 `D:\ywzj\ywzj\ywzj_vehicle\src\main\java\`，直接读。
